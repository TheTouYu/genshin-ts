# 16 效率（为什么 4 小时，以及怎么省 30%）

> **这是本次会话里用户第一次表达不满的原因**：
> 原话（T1 18:48）：「这个任务执行速度真的好慢，**快四个小时了**。」
> 后来我们派了一个专门的分析代理去算时间账，结论**出人意料**——瓶颈不是模型，是**编排**和**工具用法**。
>
> 出处：`18-evidence.md` H3/H4、§0 代价总账；分析报告：`workspace/tetris/docs/v2-perf-analysis.md`（含可复算脚本）。

## 1. 时间账（217 分钟挂钟的去向）

| 归因 | 占比 | 时间 | 事实 |
|---|---|---|---|
| **① 波次编排缺陷** | **56%** | 122 min | `modes-arch` 有 **92 分钟空窗白等**（T0 其实不依赖 T1-T3，被误排到波 2）；后期 86 分钟只剩它一人跑，`core-mechanics` **闲置 85 分钟陪跑** |
| **② runner 全量跑法** | 41% | ~35 min（尾部） | `modes-arch` 每步跑全量（9 次 × ~280s）；`core-mechanics` 用选择性跑（30 次平均 **5s**）——**同一个工具 52 倍差距** |
| **③ 模型生成** | 人时 27% | 207 min 人时 | 四代理合计的最大人时项——但这是"必须花"的部分 |
| ④ build + 语法门 | **5.2 min / 22 次**（avg 7s） | 不是瓶颈 | 任务书高估了它 |

**最反直觉的一条**：我们以为"编译/构建慢"，实测只占 **2.4%**。真正吃掉一半时间的是**等**。

## 2. 三个可复制的提速动作（不换模型，-30% 挂钟）

### 动作 1：无依赖任务**提前开工**
**问题**：建任务板时把 `T0（实例化重构）` 排在波 2，理由是"依赖 T1-T3"——**其实不依赖**。
**结果**：负责它的代理空窗 92 分钟；后期只剩它一人跑，另一个代理闲置 85 分钟陪跑。

**做法**：
- 建板后**逐个复核依赖**：这个任务的输入真的来自那个任务吗？还是"感觉应该在后面"？
- 每波结束做一次"关键路径检查"：**现在在跑的人数 ≤1 而待命 ≥2** → 立刻重排。
- 无依赖的重构/基础设施任务**先开**（它们通常是后续所有任务的地基）。

### 动作 2：runner 选择性跑 + commit 前一次全量
```bash
# ❌ 每步都跑全量（~280s）
node qxqy/runner.mjs

# ✅ 平时只跑受影响用例（~5s，参数是文件名子串，OR 语义）
node qxqy/runner.mjs 18 30 das keymap
# 匹配多个：tests/ 里有同号不同名文件（如 23-casual-takeover / 23-tspin-positive），
#           写全前缀更稳
node qxqy/runner.mjs 23-casual

# ✅ commit 前跑一次全量（本项目实测 45/45, 88.6s）
node qxqy/runner.mjs
```
**判据**：一个 45 用例的项目，日常改动只需跑 2~5 条（5 秒级），全量只在提交前/交付前跑。

### 动作 3：双代理**函数区隔离**并行
**已验证的零冲突模式**：两个代理改**不相交的函数**（本次：一个改 AI 评估 `evalBoard`，一个改输入/锁定延迟 `stepDown`/`mkDas`），互不覆盖。
**反面**：两个代理都改 `layoutDual`/`renderHud` 这类"共用出口" → 必然冲突（本次 3 次覆盖事故都发生在这类文件上）。

**判据**：派活前在任务书里写清"你只改这几个函数/这几行区间"。

## 3. 时间预算表（做同类任务时的参照）

| 阶段 | 合理耗时 | 本次实测 |
|---|---|---|
| 任务拆分 + 落盘 | 10~20 min | ~5 min |
| 单任务（中等复杂度） | 10~20 min | 10~60 min |
| 一次全量 runner | 60~310 s（随用例数增长） | 45 用例：68~101 s |
| 一次出图（6 界面） | <10 s | 数秒 |
| 一次 build | <2 s | 1.4 s |
| 一次视觉重做（含 2 轮迭代） | 20~40 min | ~30 min |
| 一次真机部署（5 脚本） | 1~2 min | ~1 min |

**用法**：如果你的"单任务"超过 20 分钟还没产出可验证的东西，说明任务粒度太大 → 拆。

## 4. 什么值得花时间（不要省错地方）

| 值得 | 不值得 |
|---|---|
| 出图逐字核对（每次 <2 分钟，能省一轮打回） | 每一步都跑全量 runner |
| 空白纸上的设计表（避免返工） | 手写重复的样板代码 |
| 真机首试（10 分钟，能抓 200-local 这类致命问题） | 反复"再试一次"式的盲改 |
| 空上下文视觉模型（20 分钟出一版结构方案） | 让带历史的代理反复微调外观 |

## 5. 用户视角的"慢"是什么

用户感受到的"慢"通常不是"你的命令慢"，而是：
1. **他要等**——每轮"我改好了，你试试"之间是好几个小时；
2. **他在重复**——同一问题报 4 次（DAS）、帮助页报 6 次；
3. **他在替你测试**——真机试玩本可以我们自己先用模拟器过（`00-gates.md` P6）。

**所以真正的提速不在工具，在"减少返工"**：
> 一次出图核对 = 省一轮打回 = 省 30~60 分钟（含用户等待）。
> 一条正确的判据 = 省一次"和没修一样"。

## 6. 反模式

1. **每一步都跑全量**（52 倍浪费）。
2. **把无依赖任务排到后面**（空窗 92 分钟）。
3. **一个代理只改共用出口文件**（必然冲突）。
4. **等子代理时轮询**（它完成会回报；等待期做独立任务）。
5. **反复"再试一次"而不设计一次能判真假的实验**（DAS 错判两轮的代价）。
6. **省掉出图核对**（省 2 分钟，赔一轮打回）。
