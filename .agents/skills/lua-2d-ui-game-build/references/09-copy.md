# 09 文案系统（40 条世界观文案怎么排）

> 用户把这个当作一个**复杂设计任务**提出来，而且给了六个维度：
> 「先做40条文案，**摆放在哪里？什么时候触发，哪些需要条件，静态还是动态**。文档的动画效果和颜色等等」
> 我们的第一次交付只把 6 条挂在标题页，用户在真机上直接发现（T44）：「最后，我要求的40条文案，**我就只在游戏开始有看到**」。
>
> 出处：`18-evidence.md` K 组 3 条；落地文档：`workspace/tetris/docs/genshin-copy-design.md`。

## 1. 六维设计表（每条文案必须填满）

| 维度 | 要写什么 | 例 |
|---|---|---|
| **位置** | 屏幕哪个区域（标题底栏/棋盘上方/结算面板/……） | 标题页底部手记条 |
| **触发时机** | 什么事件让它出现（进标题/消行/连击/升级/结算/接管） | 消 2 行时 |
| **触发条件** | 需要满足什么（等级/连击数/模式/首次） | 连击 ≥3 |
| **静态/动态** | 常驻 / 一次性 / 轮播 | 轮播（4s 换一条） |
| **动画** | 出现/消失动画（淡入/上滑/缩放） | 上滑 12px + 淡入 0.3s |
| **颜色** | 用哪套色（主题色/角色色/正文色） | 纳西妲草绿 `#7BC96F` |

**判据**：40 条每条都能填满六列——填不满的说明还没设计完。

## 1b. 数据驱动：COPY 表（别把文案写死在逻辑里）

`config.lua` 的 `COPY` 表字段（照抄这个结构就能扩到 40 条）：
```
编号 | 原文 | 类型 | 触发点 | 条件 | 动静 | 位置 | 颜色 | 优先级 | live(是否已接线)
```
main 只挂槽：标题 → 实例文字；局内 → `botBanner`；结算 → `settleExtra`。
**接线新条目不碰渲染代码**——这是能扩到 40 条的前提。

## 1c. 用例锁的是什么（最容易踩）

- `tests/29` 断言 **`botBanner == PERSIST_TIP` 整串**（at=1.4s）：
  → **改常驻文案（PERSIST_TIP）必须同步改该断言**；事件文案/标题手记/结算旁白可自由改。
- **print 日志锚一字不能动**（`clear n=` / `takeover hint|ai|back` / `guide stage=` / `bag=` / `hold swap`）——
  它们是**用例断言的对象**，改一个字就红。
- **优先级**（靠 `bannerTimer` 让位）：升级 > 四消 > 连击 > 普通消行；接管文案在 3s 无操作后出现。

## 2. 世界观锚点（用户给定的设定，必须查证再用）

- **玩家身份 = 周游世界的旅行者**（用户原话）。
- **小草神 = 纳西妲**，**智慧之神**——用户特意点出这个理由：「小草神是智慧之神，所以她来很合适，玩家则是旅行者」。
- 七国/角色/地理设定 → **联网查证**后再用（不许凭印象编）。
- 文案要**贴游戏、贴原神、贴主题配色**三者同时成立。

## 3. 落点通道（至少三条，只做一条等于没做）

| 通道 | 载体 | 本次实测条数 |
|---|---|---|
| **标题页** | 底部手记轮播（「旅行者，提瓦特的风一直在等你。」），**6.1s/条**、单条 ≤16 字 | 6 条 |
| **局内** | 消行 / 连击 / 升级 时的短句 | 4 + 3 + 2 = 9 条 |
| **结算** | 结算面板的评语 | 3 条 |
| **接管/交还** | 小草神接管时的对话 | 3 条 |
| 合计 | | **21 条已接线**（剩 19 条留表待接） |

**判据**：每条文案在代码里能 grep 到唯一落点；出图时在对应场景能看到。

**教训**：第一版只做了标题屏 6 条 → 用户真机发现"只在开始页看到"。**"我做了 40 条"和"玩家看到 40 条"是两件事。**

## 4. 接管/交还的文案（本次定稿，用户认可语气）

| 场景 | 文案 | 颜色 |
|---|---|---|
| 3 秒无操作 | 「纳西妲正看着你的盘面…」 | 草绿 |
| AI 接管 | 「纳西妲：交给我吧，旅行者！」 | 草绿 |
| 交还玩家 | 「旅行者归位！」 | 主题色 |
| 准备提示 | 「按 XX 键准备」 | 正文色 |

**节奏**（用户定版）：**3s 无操作 → 提示 3s → 接管**（不是 5s 直接接管）。
> 用户原话（T37）：「这个时间可以修改为没有操作 3s 后提示 3s，还没有操作就接管。提示的文案换成小草神来帮你之类，这个文案你自己想。」

## 5. 文案与用例的绑定（防"被演出顶掉"）

常驻文案容易被一次性演出文案覆盖掉（本次真实发生过：底栏常驻键位提示被顶掉）。

**做法**：
- 定义 `PERSIST_TIP`（常驻提示集），**用用例锁住**：断言"演出结束后，常驻提示回来了"。
- 控制断言读 textbox 的 `text` 字段（不受 `visible` 影响，见 `05-layer.md`）。
- 涉及双写时，`setText` 收口会同步写实例份与 textbox 份，断言读 textbox 份即可。

**判据**：有一条用例专门验"常驻提示在演出后仍在"。

## 6. 文案落地的顺序（避免半成品）

1. **先出设计表**（40 行 × 6 列），给用户过目（他要的是"设计完再落地"）。
2. 按通道分批接线（标题 → 局内 → 结算 → 接管）。
3. **每批接线后出图**核对（字号/框宽/位置/颜色）。
4. 剩下的留表 + 在交付报告里明说（"21/40 已接，剩 19 条待排优先级"）。

## 7. 常见错误

| 错误 | 后果 |
|---|---|
| 只做标题页 | 用户："只在开始页看到" |
| 文案太长 | 框宽不够 → 裁字（"空格"变"各"） |
| 用了不存在的设定 | 世界观出戏（必须先查资料） |
| 纯文本无常驻 | 玩家记不住操作（用户三次强调） |
| 颜色与主题不搭 | 破坏整体风格（用主题色/角色色） |
| 演出覆盖常驻 | 信息丢失（要 PERSIST_TIP + 用例锁） |

## 8. 交付前自检

```
□ 40 条 × 6 维的设计表存在吗？
□ 落地通道 ≥3 条吗（不是只有标题页）？
□ 每条都能 grep 到唯一落点吗？
□ 常驻提示有用例锁住吗（演出后仍在）？
□ 世界观设定查证过吗（不凭印象）？
□ 每条文案在出图里能看到、不裁字吗？
□ 交付报告里如实写了"接线 X 条 / 待接 Y 条"吗？
```
