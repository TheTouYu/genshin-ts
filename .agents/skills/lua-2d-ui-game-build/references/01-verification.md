# 01 验证与证据（怎么证明它真的好了）

> **这份文件的唯一目的**：让"修好了"这句话有可审计的分量。
> 25 小时里用户打回 12 次，其中 **6 次的原话是"和没修一样"「还照样有」「三个问题也都还在」**——
> 而这些时刻，我们的代码确实改了、用例确实绿了、探针确实读到"已接线"。
> 所以问题不在改没改，在**证据不对**。
>
> **出处**：`18-evidence.md` G 组全部 7 条 + C 组 C1/C2/C3/C6/C8。

## 1. 五种证据，各证什么，各不能证什么

| 证据 | 层级 | 能证明 | **不能证明**（跨层推断=翻车） |
|---|---|---|---|
| 语法门 / build 成功 | L0 | 代码能编译 | 运行时不报错、行为对 |
| `runner.mjs` 用例全绿 | L1 | 逻辑/状态机按断言走 | 画面上看得见、真机能编译 |
| 探针读控件树（存在/属性/位置） | L1.5 | 控件**存在**、属性**被设置** | 玩家**看得见**（层序可能被盖） |
| 模拟器出图 + `read_image` | **L2** | 画面上真的长这样 | 真机长这样（字体/API/模板可能不同） |
| 真机日志 + 弹窗 | L3 | 宿主层真的加载/编译/运行 | 画面对不对（日志不含像素） |

**唯一规则**：**界面/视觉结论只能由 L2 给**；**真机是否加载只能由 L3 给**；两者不可互相替代。
**最硬的教训**（用户 T41 原话）：「**不要太自信，要去看实际渲染出来的画面。**」

## 2. 六个证据陷阱（每个都有真实翻车）

### 陷阱 1：状态位 ≠ 渲染
`visible = true`、坐标正确、文字内容正确 —— 但它被上层实例盖住了，屏幕上什么都没有。
- 真实案例：v2.7 的全屏背景 wash（运行时实例）盖住 HUD（服务端 textbox），用户报"全部的积分没有了"。
- 判据：**只要涉及"看不看得见"，唯一证据是出图**。控件状态只能用来**证伪**（"这个控件根本不存在"）。

### 陷阱 2：日志缺失 ≠ 行为不存在
日志窗口异常关闭 / 采集未启动 / 日志文件被覆盖时，日志里没有记录，**不代表现象没发生**。
- 真实案例：DAS 第一次错判「用户跑的是旧构建，v2.7 起已修」——依据是那次日志里没有 `das` 记录，而真相是**日志窗口被关了**。
- 判据：下"日志里没有 X ⇒ X 没发生"之前，先确认三件事：
  1. 这份日志包含**本次**会话的启动行（`canvas` / `tpl guid=` / `listen ok`）；
  2. 日志文件 mtime 在试玩时间段内；
  3. 日志里能看到**预期会有的其他锚点**（如果连启动行都没有，说明采集根本没工作）。

### 陷阱 3：实验方法本身可能是 artifact
headless / 脚本化实验得出负结论时，先检查"被测链路的生效条件我满足了吗"。
- 真实案例：headless 实验得出"模拟器网页按键转发 POST 零条 = 上游有缺陷"，实际是实验没满足 play 页**五重门**（canvas 焦点 / 首个带 view 的快照 / epoch / 合成键过滤 / 键在映射表内，见 `03-input.md` §6）。
- 判据：**任何"是它的 bug"结论，先自证"我的实验是有效的"**——用一个已知会成功的最小动作做阳性对照。

### 陷阱 4：Lua 运行时错误默认静默
`runner` 只报断言红；`pcall` 吞掉 API 报错；每帧函数抛错只让函数**中途返回**。
- 真实案例 1：`layoutDual()` 引用 `nil` 全局 `halfH` → 每帧抛 `attempt to perform arithmetic on a nil value (global 'halfH')` → 函数后半段全不执行 → 外观是"文字挤压/双影/标签贴顶"。
- 真实案例 2：真机 `SetVisible` 严格计参、对齐字段只收枚举 → 三条 `ui fail` 被 `pcall` 吞掉 → 所有对齐设置真机全 fail → 文字乱位/裁切/大问号。
- 判据：
  - 出图流程里**同时**读日志，搜 `lua-error`；
  - 关键函数的**结尾锚点日志**（如 `print('layout dual')`）缺失 = 这个函数没跑到底；
  - **失败必须打出来**：包装 `pcall` 时把错误信息写进日志（`ui fail: <field> <err>`），只吞不打等于埋雷。

### 陷阱 5：改完就测 = 测的是旧代码
- 真实案例：改了 `lua/main.lua` 但没 build，`runner` 读的是存档里的旧 source → 用例全绿，但那不是你的代码。
- 判据：每次跑用例前确认 build 产物 mtime 晚于源文件 mtime；或把 build 挂进 runner 入口（本项目 `runner.mjs` 已内置）。

### 陷阱 6：工具静默失效（"我没看到" 也可能是观测坏了）
搜索/统计/解析类工具读错字段、路径、编码时，常常**不报错、只返回空**——很容易被当成"素材里没有"。
- 真实案例（本次复盘时发生）：写脚本提取会话事件流的工具输出时字段名写错（`content` vs `text`），
  每条解析成 `null` → **任何 `--grep` 都 0 命中且脚本退出码 0**，差点得出"会话里没有这条日志"的结论。
- 判据：任何搜索类脚本先跑**阳性对照**（搜一个确定存在的词）。0 命中时先怀疑工具，再怀疑素材。
- 这和技术陷阱 2（日志缺失≠行为不存在）同源：**"看不见"先归类为"我的观测方式可能坏了"**。

## 3. 假绿清单（用例绿了但功能是坏的）

| 假绿形态 | 为什么绿 | 怎么破 |
|---|---|---|
| 断言期望值本身写错（12 窗口、ρ≥0.5） | 断言与代码一起错 | 构造反例；物理上界先算 |
| 断言只测"函数返回了"，没测"画面/副作用" | 逻辑层测不到渲染层 | 加 L2 出图核对 |
| 用例用了硬编码坐标/尺寸（跟随画布变化就失效） | 只在一个画布下成立 | 用例跑两个画布（1280/1600） |
| 时序断言依赖固定 `sleep` | 负载高时假红，负载低时假绿 | 用锚点日志推进，不用 sleep |
| 反向断言缺失（"不该出现"没测） | 多余的东西没人管 | T-spin 类功能必须同时有正向 + 负向用例 |
| 用例只覆盖主路径（casual 单屏） | 双屏/对抗路径没测 | 每模式一条端到端 |

## 4. 出图核对：具体怎么做（这是 P3 的唯一过关方式）

**流程**：
1. 出全部页面：`node qxqy/shot-style.mjs all d` → `docs/d-*.png`（六界面：标题/游戏/双屏/结算/帮助/移动版）。
2. **逐张 `read_image`**——不是看一眼，是按下面的清单**逐项过**：

| 检查项 | 具体怎么看 | 对应根因 |
|---|---|---|
| 裁字 | 每个文字块**读到最后一个字**并念出来（「空格」不是「各」、「↑」不是「T」、「软降」不是「卜降」、「得分」首字在不在） | 框宽 < 文案宽；框高 < 1.45×size+4 |
| 遮挡 | 有没有文字压在文字上、压在棋盘上、被背景吞掉的区域 | 层序 / 双写漏位 |
| 双份 | 同一信息出现两次（一眼多的那份小字） | 双写没隐藏 textbox 份 |
| 越界 | 元素是否超出画布/被画布边缘切掉 | 坐标系/画布尺寸写死 |
| 对齐 | 字是否贴顶/贴左、垂直居中了吗 | `valign` 缺失（默认 Top） |
| 主次 | 同级元素有区分度吗（三个按钮长一样 = 不合格） | 没有层级设计 |
| 语义 | 出现的每个图形/文字都有意义吗（"这个方块意义不明"就是缺陷） | 装饰无标签 |
| 模式正确性 | 这个页面上出现的玩家编号/键位/文案**该出现吗** | 模式×文字矩阵没核 |

3. **同时**读日志搜 `lua-error`（陷阱 4）。
4. 有问题的：修 → 重新出图 → **重新逐字核对**（不要"我改了那行所以应该好了"）。

**为什么必须"全部页面"而不是"改动的那一页"**：
真实案例——修双屏布局（`layoutDual`）把单屏的 `hudNext` 位置弄丢了；修 HUD 双写把 `botBanner` 弄成了永久隐藏。**布局/层序函数的改动是全局的**。

## 5. 探针的正确用法（能证伪，不能证明）

**可以用的场景**：
- 「这个控件到底存不存在」→ 探针能答。
- 「这个字段有没有被设置上」→ 探针能答（但设上了不等于看得见）。
- 「布局函数有没有跑完」→ 用**结尾锚点日志**比探针更可靠。

**不许用的场景**：
- 「玩家看得见吗」→ 只能出图。
- 「修好了吗」→ 只能出图 + 逐字核对。
- 「真机能编译吗」→ 只能真机日志/弹窗。

**探针写法要点**（本项目 `qxqy/runner.mjs` 的 `playGet()`）：
```js
// 一次读全：scene（控件树）+ logs（脚本日志）
const st = playGet();
// 1) 控件是否存在/属性
// 2) 日志里有没有 lua-error / 锚点行
// 3) 断言都写进用例，别只在 REPL 里看一眼
```

## 6. 三栏交付报告（每次说"完成"必须用这个格式）

```markdown
## 已验证（分层写，不许合并成一个 ✅）
- L0/L1：`node qxqy/runner.mjs` → 45/45 绿，exit 0，关键行「…」
- L2：出图 d-title/d-game/d-dual/d-settle/d-help → 逐字核对：无裁字/无遮挡/无双份
- L3：真机日志 → module ok ×3 / tpl guid=… / hud inst n=9 / lua-error 0 条

## 尚未验证（如实说）
- 真机 imageColor 的透明度通道是否生效（若被忽略，遮罩会变纯色）
- 真机 SetVisible 对运行时实例是否可靠（已加"挪出画布"兜底）

## 需要你确认
- 真机 hl 图切出再切回 → 试玩 → 是否看到 X（这是 v3.x 独有的指纹）
```

**为什么要这栏**：用户能一眼看出"哪些是我该验的"，而不是被一句"全部修好了"骗过去。真实案例：报告里写"② 的冻结行为在模拟器里无法快速造出（需真死一局），是靠逻辑+回归担保、真机一局即验的"——这种**主动交代**是正确的做法。

## 7. 命令汇报四元组（每次执行命令后）

```
跑了什么：node qxqy/runner.mjs
工作目录：/home/h/genshin-ts/workspace/tetris
退出码：0
关键日志行：45/45 PASS 71.6s / lua-error 0
```
成功判据 = **退出码 0 且日志无明显错误**——两者缺一都不算成功。

## 8. 一句话

> 证据的层级不能糊：**编译 ≠ 注入 ≠ 结构 ≠ 渲染 ≠ 行为 ≠ 用户确认**。
> 每次说"完成"，先问：我拿到的这个证据，能证明用户报的那个现象已经消失吗？
