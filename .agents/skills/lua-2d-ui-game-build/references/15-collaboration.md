# 15 多代理协作（怎么让 3~5 个代理不互相毁掉对方的工作）

> **为什么需要这一章**：25 小时里我们用了 **8 个代理**（3 个主力 + 1 个性能分析 + 1 个视觉 + 2 个 DS 替换 + lead），
> 换来 80 个 commit 的产出，也换来 **3 次同文件覆盖事故 + 2 次队友进程崩溃**。
> 这一章记录的是"付出过代价才定下来"的纪律，不是最佳实践清单。
>
> **出处**：`18-evidence.md` H 组。

## 1. 队伍编制（先定角色，再开活）

| 角色 | 适合什么 | 不适合什么 |
|---|---|---|
| **Lead（你）** | 排程、裁决、验收、部署、对外汇报 | 大块编码（会被打断） |
| **机制组** | 玩法规则、状态机、输入、数值 | 审美、视觉重做 |
| **模式/布局组** | 多模式、双屏、浮层、布局 | 性能剖析 |
| **AI 组** | 评估函数、搜索、难度、性能热路径 | 界面细节 |
| **视觉专员**（需视觉模型 + **空上下文**） | 审美重做、界面设计、出图自评 | 玩法逻辑 |
| **分析组**（临时，任务专一） | 性能归因、trace 分析、时间账 | 长期在编 |

**三个硬规则**：
1. **一个代理只在一个关键路径上**（否则会出现"后期只剩一人跑、另一人闲置 85 分钟陪跑"）。
2. **写作用域不重叠**：两个代理不写同一个函数区。函数区隔离的并行已验证零冲突（T5/T8 并行，一个改 AI 评估、一个改输入/锁定延迟）。
3. **视觉/审美类必须给空上下文代理**：带历史的代理会沿用旧思路（帮助页被打回 3 次，最后靠空上下文 DS 重做才过）。

## 2. 三次覆盖事故与定稿纪律

**发生了什么**（同一天 3 次）：
- 队友 A 未提交的改动被队友 B 的写盘冲掉；
- 一次"空壳 commit"（commit 进了但内容不在）；
- 最惨一次：`modes-arch` 的「双 ready + 回主页 + 常驻提示」**全部丢失** → 需要**冻结其他写者 + 给它独占窗口重放**。

**定稿四条纪律**（写进计划书，之后没再复发）：
1. **写盘前核对全量 diff**（`git status --short` + `git diff --stat HEAD`，确认没卷进别人的改动）。
2. **落树即广播**（改到工作树就告诉其他人"我在改 X 文件"，不要等 commit）。
3. **单元即 commit，commit 后哨兵 grep 复验内容真的在**。
4. **禁止整文件重放**（不许 `git checkout` 整个文件覆盖别人）。

**独占窗口协议**（事故后的恢复手段，可复用）：
```
① 通知其他所有写者：进入冻结（只读，不许写盘）
② 确认冻结：逐个代理回执"已停"
③ 给受损代理独占窗口：重放 → 提交 → 8 项哨兵 grep 全过
④ 释放窗口：解除冻结，其他代理从新 HEAD 继续
```
**判据**：独占窗口结束前必须跑一遍**哨兵 grep 清单**（把这次重放的每条改动各写一个 grep 表达式，逐条确认在 HEAD 里）。

## 3. 哨兵 grep（防"空壳 commit"的唯一手段）

commit 之后，对每条改动写一行可 grep 的特征串，逐条验证：
```bash
git show --stat HEAD                          # 改了哪些文件
grep -n 'MODE_OVER' lua/main.lua              # 特征 1 在不在
grep -n 'das stop reason=timeout' lua/main.lua # 特征 2
grep -n 'menu cards n=' lua/main.lua          # 特征 3
```
**为什么**：`git commit` 成功 ≠ 内容进了 commit（曾出现过 commit 里只有空 diff 或只含别人的改动）。
**判据**：每条特征串都要能 grep 到；缺一条就是空壳，重做。

## 4. 队友崩溃 / failed 的处理

**真实案例**：12:08 `modes-arch` failed；12:11 `core-mechanics` failed，留下 **494 行混合态 diff**。

**处置顺序**（别急着重派）：
1. **先查它留下了什么**：`git status` + `git diff --stat` + 关键函数 grep。
   - 半成品常常已经改了 80%（那次它的 8 个文字位双写已覆盖，只差验证）。
2. **判断是"能接手"还是"要重做"**：
   - 改动是局部的、语义清楚的 → Lead 自己接手收尾（本次就是这样做的，比重新解释任务给新代理快）。
   - 改动是架构性的、混合了其他人的编辑、语义不清 → 丢弃 + 重派。
3. **重派时给的是"现象 + 判据"，不是"上次你做到哪"**——新代理是空上下文，不要假定它记得任何东西。

**模型选择**（用户原话 T46）：「你那两个队友是glm吧，不可靠。创建新的队友，用ds，继续完成修复。」
- 视觉/审美/精细调试 → 视觉模型或最强模型；
- 机械重命名/批量替换 → 便宜模型；
- **不要**在同一个失败任务上反复换便宜模型试。

## 5. 任务板与依赖（避免空窗）

**做**：
- 建任务板时把**依赖关系**写清（`blocked_by`），并**检查依赖是否真的存在**。
  > 真实失误：T0（实例化重构）被排到"波 2"，理由是"依赖 T1-T3"——其实**不依赖**。结果 `modes-arch` 空窗白等 **92 分钟**。
- 无依赖的任务**提前开工**。
- 每波结束做一次"关键路径检查"：现在谁是唯一在跑的人？其他人为什么在等？

**判据**：任一时刻，若"在跑的人数 ≤1"而"待命的人数 ≥2"，立刻重排——要么给待命的派独立小活，要么把关键路径上的任务拆分。

## 6. 与 Lead 的汇报契约

子代理交活时必须带：
1. **跑了什么命令 + 退出码 + 关键日志行**（不许只说"通过了"）；
2. **改了哪些文件 + 关键特征串**（供哨兵 grep）；
3. **未验证项**（如实说，别等 Lead 问）；
4. **离"完成"还差什么**。

Lead 收到后做三件事：哨兵 grep → 自己复核关键读数 → 决定是否进下一个门。

## 7. 反模式

1. **让子代理"顺手把技能也更新"**——子代理的上下文不足以判断技能该写什么；技能回灌是 Lead 的活。
2. **同时开 3 个同文件写者**——覆盖事故的充分条件。
3. **等子代理时空转轮询**——它完成会主动回报；等待期做独立任务（查 git、写文档、跑基线）。
4. **把用户的裁决转述给子代理时加自己的理解**——转述要**逐字 + 标注来源**，歧义要回去问用户（真实案例：coop 分工，我们提了方案 A，用户给的是完全不同的"一人旋转、一人管移动和下落"）。
5. **失败任务不换模型只换提示词**——同一个模型在同一类任务上失败两次，就换模型或换人。
