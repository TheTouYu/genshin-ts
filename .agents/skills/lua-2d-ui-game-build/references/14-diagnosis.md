# 14 排查方法论（怎么从症状走到真因）

> **这份文件的独特价值**：25 小时里，**同一个 bug 我们错判了两次**，直到用户给出一条定位线索才收敛。
> 所以这里记的不是"排查步骤清单"，而是**错判的类型学**——让你在犯同样错误之前认出来它。
>
> **出处**：`18-evidence.md` B1（DAS 三次定案）、C6（`layoutDual` nil）、C1/C2/C3（层序链）、
> F2（注入版）、F3（多模块）、F4（200-local）、G3/G4（证据陷阱）。

## 1. 三条排查原则

### 原则 1：先划现象边界，再谈根因
用户给的现象描述里藏着**最重要的定位信息**，比我们的任何猜测都值钱。

> 用户（T44）：「按下左它所有的方块都在快速朝左边移动了。**而且这个在休闲模式下移动又是正常的。**」

这一句"休闲正常"直接把范围从"整个输入系统"缩到"多盘模式的实例路由"——**这是最终真因的入口**。
而我们前两轮都在猜公共层（网页 keyup 转发、旧构建），全错。

**动作**：
- 现象在**哪些模式/哪些画布/哪些机器**出现？（先做差异表）
- 出现 / 不出现的**唯一变量**是什么？
- 时间上：什么时候开始的？（对应哪个 commit / 哪次部署）

### 原则 2：找"能判真假的最小读数"，不要找"能解释一切的理论"
好的读数：一条日志行、一个实测数字、一张图。
坏的理论：听起来合理但无法证伪的机制（"可能是浏览器把事件吞了"）。

**动作**：把假设写成**可判真假的句子** + **读数**。
- ❌「可能是事件丢失」→ 无法判真假。
- ✅「如果是事件丢失，那么日志里 `das stop reason=timeout` 会出现」（这条日志是实现里真实存在的兜底路径）。

### 原则 3：证伪优先，先做"能推翻自己"的实验
每次得出一个结论，先问：**什么读数会证明我错了？** 如果答不出，这个结论还不能用。

**案例**：DAS 的结论"网页按键转发链整链失效"之所以错了，是因为从没设计过"我的实验本身是否有效"的阳性对照（见 `01-verification.md` §2 陷阱 3）。

## 2. 六种通用手段（每个都有真实战果）

### 手段 1：模式差异定位法（最强，先做这个）
同一个功能在 A 模式正常、B 模式不正常 → **diff 两个模式的数据流**，不要先怀疑公共层。

| 案例 | 差异 | 真因 |
|---|---|---|
| DAS 连移 | casual 正常 / ai-battle 疯走 | `ACTIVE` 实例数不同：单实例时"全局 g"恰好就是玩家盘；双实例时 `OnUpdate` 每帧把 `g` 留在最后一个实例 → Up 回调清错盘 |
| AI 盘 0 消行 | 单盘正常 / 镜像盘 0 | 镜像喂块路径没同步 `nextName` |
| 双屏布局 | 单屏正常 / 双屏文字挤 | 双屏走 `layoutDual()` 而非 `layout()`，前者有 nil 全局 |

**判据**：拿到"只在 X 出现"的描述，第一件事是列出 X 与基线的**所有**差异（实例数/走哪个函数/吃哪个配置），逐个排除。

### 手段 2：锚点日志法（判断"函数跑到哪了"）
每帧/每关键路径留一行稳定锚点日志；**锚点缺失 = 那段没执行**。

- 案例：`layoutDual()` 引用 nil 全局 → 每帧抛错 → 函数从断点返回 → 结尾 `print('layout dual')` 从未打印 → 判据明确。
- 本案锚点清单：`canvas WxH` / `tpl guid=` / `cellCount=` / `listen ok` / `module ok` / `hud inst n=` / `menu stage n=` / `das stop reason=timeout` / `hold swap in=…` / `layout dual` / `das cap` / `garbage n=` / `ui fail: <field>`。

**动作**：怀疑某函数没跑完 → 先在它**末尾**加一行 print，重跑，看有没有。

### 手段 3：错误静默排查（Lua 特有）
**Lua 的运行时错误默认不进 runner 断言**；`pcall` 会把它吞掉；每帧函数抛错只影响那一帧后半段。

**动作**：
1. 出图流程里同时抓日志，搜 `lua-error`；
2. 所有 `pcall` 包装都要把错误写进日志（`ui fail: SetVisible expected 1 arg got 3`）；
3. 逐帧函数（`OnUpdate`/`tickInstance`/`layout*`）里任何 nil 访问都可能是"看起来是布局问题、实际是崩溃"。

**判据**：症状是"某一块内容不对/缺失"，而日志干净 → **先怀疑有错误的静默路径**，不要相信"没报错"。

### 手段 4：层序反查法（"看不见"类问题）
症状：控件存在、属性对、位置对，但看不见。

**动作**：把可疑元素**临时移到最高层**（或换一个显眼颜色/字号），重出图。
- 移动后看得见 → 就是层序问题。
- 移动后仍看不见 → 才是"没创建/被隐藏/坐标出界"。

**案例**：HUD 被背景 wash 盖住；结算页文字被半透明面板压成灰雾；双写只覆盖 5 个键漏了 `botBanner/topBanner`。

### 手段 5：版本指纹法（"用户说没变"类问题）
症状：用户说"还是旧的""问题全在"。

**动作**：先取真机日志的指纹行，证明跑的是哪版——**再决定改代码**。
- 指纹：`menu stage n=` / `menu cards n= style=` / `hud inst n=` / `module ok` / `tpl guid=`。
- 如果指纹是旧的 → 问题在部署，不在代码（`12-deploy`）。
- 如果指纹是新的 → 问题在代码/渲染，进 `17-symptoms`。

**教训**：我们至少有 3 次在没确认版本的情况下改代码，其中 1 次（DAS）据此得出"已修好"的错误结论。

### 手段 6：物理上界法（数值/性能类）
症状：某个指标怎么调都达不到目标。

**动作**：先算**物理/理论上下界**，再看当前读数。
- ρ ≤ 0.40（每块 4 格 / 每行 10 格）——所以"ρ≥0.5"是错的验收线。
- 帧耗时：+35 倍这种量级不可能来自"代码写得不够优化"，一定来自"每帧都在做无用功"（权重为 0 的特征还在全盘扫）。

## 3. 错判的类型学（认出来，才能停）

| 类型 | 长什么样 | 为什么错 | 怎么防 |
|---|---|---|---|
| **A 采集缺失当反证** | "日志里没有 X 记录，所以 X 没发生" | 采集本身可能不在（日志窗口关了/文件被覆盖） | 先验证采集存活：日志里有本次启动行吗？ |
| **B 实验 artifact** | "我用脚本实验复现了缺陷" | 脚本没满足被测链路的生效条件（五重门） | 加阳性对照：已知会成功的动作在同样实验里成功吗 |
| **C 旧代码当代码** | "代码里已经修了/用例绿了" | build 没跑 / 部署没做 / 跑的是旧构建 | 版本指纹 + build mtime |
| **D 状态位当画面** | "控件 visible=true / 属性都设了" | 层序遮挡 / 隐藏的 textbox / 坐标出界 | 出图 |
| **E 表面症状当根因** | "文字挤 → 调间距" | 真因是函数中途抛错，后半段没执行 | 锚点日志 + `lua-error` |
| **F 数学命题未验证** | "任意 12 块含全 7 种" | 命题本身是假的 | 构造反例；物理上界 |

**停手信号**：如果你已经连续两个结论被推翻，**不要急着给第三个**——先问用户要一个**现场读数**（截图/日志序列），或者自己构造一个能判真假的实验。DAS 的收敛点就是用户给了一句"休闲模式正常"。

## 4. 三个完整案例（当模板用）

### 案例 1：DAS 连移——三次定案、两次翻案
```
用户报（T6/T19/T26/T44）：按下左会一直左；休闲模式正常。
错判 1：网页 keyup 转发丢失 → 加"连走 12 格强制停"防御
   → 推翻：只是把无限变有限，根因没动；用户 T26「这个bug还在，你没修好」
错判 2：用户跑的是旧构建（v2.7 已修）→ 依据"日志里没有 das 记录"
   → 推翻：那次日志窗口异常关闭，日志缺失≠行为不存在
错判 3：模拟器网页按键转发链整链静默（上游缺陷）
   → 推翻：headless 实验没满足 play 页五重门（canvas 焦点/首快照/epoch/…）
真因（一行）：Up 回调清的是全局 g；OnUpdate 每帧把 g 留在最后一个实例 → 清错盘
修法：① Up 回调先 g = routePlayer(key) ② DAS_HOLD 时间上限兜底 ③ 只清自己按住的方向
判据：日志出现 das stop reason=timeout，或 move 序列逐条与按键次数一致
```
**可复用**：①"只在某模式出现"= 先 diff 实例路由；②防御代码不能替代根因；③日志缺失先验采集。

### 案例 2：层序链（"积分/底栏/提示"成片消失）
```
用户报：积分全没 / 底栏操作指南没有 / H 帮助没有 / 接管提示没看到 / 底栏空
第一次修：HUD 双写（实例可见 + textbox 隐藏）→ 只覆盖 5 个键
   → 用户 T37 仍报"底栏没有/H 没有/接管提示没有"
第二次修：把 botBanner/topBanner 也纳入双写
   → 但这俩被 SetVisible(false) 后，40+ 处 setText 变成"写了但看不见"
第三次修：setText 单点收口（同步写同名实例份）
判据：出图逐字核对每个常驻文字位；日志 hud inst n=9 (textbox hidden)
```
**可复用**：层序问题会**成片**出现；修一处必须扫"同层所有位"；隐藏旧通道前先找齐所有写入点。

### 案例 3：`layoutDual()` 的 nil 全局（"文字挤/双影/贴顶"）
```
用户报：三个问题还在，和没修一样（截图箭头标了"得分被裁""AI 已""空格→各"）
错判：文案太长 / 间距不够 / 需要重排
真因：layoutDual 里 -(halfH - 96)，halfH 是 layout() 的 local → nil → 每帧抛错
   → 函数从断点返回 → HUD 复位/隐藏收口/hudNext 归位/结尾 print 全没执行
判据：日志搜 lua-error；或结尾锚点 print('layout dual') 缺失
修法：画布尺寸函数内现算（CANVAS_W/H）+ HUD 摆位单源收口
```
**可复用**：**症状是"布局乱"，根因可能是"函数没跑完"**。任何"某段代码的效果完全没出现"都要怀疑抛错。

## 5. 排查时的记录纪律

每轮排查写三行（进当天文档或 commit message）：
```
假设：<可判真假的一句话>
读数：<实际看到的日志/数字/图>
结论：<支持/推翻>，下一步 <动作>
```
**为什么**：DAS 那两轮错判之所以代价高，是因为每次结论都没写"如果错了会怎样"，于是下一轮又从零猜。

## 6. 什么时候停手去问（别硬猜）

满足任一条件就停：
1. 连续两个结论被推翻（如 DAS）；
2. 需要的读数只能由用户现场产生（真实浏览器行为、真机弹窗）；
3. 修复方向有多个且代价都很大（需要用户裁决设计取舍，如 coop 分工方式）；
4. 涉及破坏性操作（覆盖地图/删除脚本/改玩家状态）。

**问的时候给三样**：①我已经排除了什么（附读数）②现在只剩哪几种可能 ③请你做哪个最小动作能给到判据。
> 好的例子（T31）：「在网页试玩时开着日志窗口，按几下左/右，把带 `move`/`das` 的行发我——一条序列就能定案。」
> 坏的例子：「你能不能再试一次，我改了。」
