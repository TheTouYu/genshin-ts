# 11 性能（"卡" 与 "AI 停住"）

> **本章最重要的认知**：用户报的"卡"和"方块停止不动"**是同一个根因**——
> 一段"权重已经是 0 但还在算"的特征计算，每帧吃掉 9.5ms → 帧率暴跌 → **AI 的分帧推进被饿死** → 方块悬停不动。
> 所以性能问题不要分开治两个症状，先出**帧探针**。
>
> 出处：`18-evidence.md` I 组 4 条、J4；代码：`lua/main.lua:1899-1923`（权重短路）、`4785-4796`（每帧步进上限）。

## 1. 先测量，再动手（帧探针）

**必须的读数**（不要凭感觉）：
| 指标 | 怎么取 | 判据 |
|---|---|---|
| 帧耗时 p50 / p99 | 每帧记 `os.clock()` 差值，跑 N 秒取分位 | p99 < 2×p50 |
| 掉帧次数 | p99 超过 16.7ms（60fps）的帧数 | 长局应接近 0 |
| 单函数耗时 | 在嫌疑函数前后各记一次时间戳 | 定位到具体函数 |
| GC/分配 | 观察帧耗时是否周期性抖动 | 抖动 = 帧内分配 |

**实测对照**（本次）：
| 状态 | 帧耗时 | p99 | 掉帧 |
|---|---|---|---|
| 修前 | 9.55ms | 105ms | 每秒 ~6 次 |
| 修后 | **1.24ms** | **11.9ms** | **清零** |
| 副作用 | AI 变强（ρ 0.30 → 0.34）、runner 308s → 63.6s | | |

**方法学提醒（必须）**：共享宿主负载会漂移——同一版本两次测量可以是 **0.34ms vs 9.8ms**（20 倍差）。
所以性能结论**不能**用单次绝对值，必须用**交替对照法**：版本序列 **A/B/B/A** 交替跑多轮，取中位。
- 目标线：**p99 < 16.7ms**（60fps 帧预算）；>50ms 的帧 ≈ 秒级掉帧。
- 探针写法：`playStart` → 循环 `playStep` 并读帧耗时 → 报 mean/p90/p99。

## 2. 头号杀手：权重为 0 但还在算

**真实案例**（本次 +35 倍帧耗时的来源）：
```lua
-- Dellacherie 补充特征在校准实验里被判定为负贡献 → 权重设为 0
-- 但计算代码还在：每个候选方块都把整盘扫一遍
for _, cand in ipairs(candidates) do          -- ~34 个候选
  local rowTrans = computeRowTransitions(board)   -- 全盘扫描
  local colTrans = computeColumnTransitions(board) -- 全盘扫描
  local wellSum  = computeWells(board)             -- 全盘扫描
  score = score + W.rowTrans * rowTrans + ...      -- W.rowTrans == 0，白算
end
```
**修法：权重为 0 时短路跳过计算**（不是删代码——保留以便将来重新启用）：
```lua
if W.rowTrans ~= 0 then score = score + W.rowTrans * computeRowTransitions(board) end
```

**通用规则**：**任何"乘 0 的项"都是纯浪费**。搜索类热路径上，先按权重筛一遍"这个特征要不要算"。

**判据**：帧耗时从 9.55ms → 1.24ms（约 8 倍）；连带 p99 与掉帧归零。

## 3. 分帧计算（AI 搜索的时间预算）

**机制**：AI 搜索不能在一帧内跑完（一帧余量只有几毫秒），要**分帧推进**：
- 每帧预算 **~8ms**；
- 用状态机保存"算到第几个候选"；
- 下一帧继续。

**副作用（关键）**：分帧 AI 的**推进速度与帧率成正比**。所以：
> 帧率暴跌 → AI 每帧只能算一点点 → 方块长时间悬停 → 用户报「AI 操作的时候，方块停止不动」。

**判据**：AI 盘的块间隔时间稳定（日志里每块的 `lock` 时间戳间隔方差小）。

## 4. 帧内零分配

**为什么**：模拟器是**解释器**，每次建表都会触发内存分配，攒到一定程度触发 GC → 帧耗时尖峰。

**规则**：
- 搜索用的"模拟盘"**复用**（不要每个候选都 `{...}` 新建）；
- 循环里不要 `table.insert` / 字符串拼接（`..` 也是分配）；
- 高频日志要条件化（`if DEBUG then print(...) end`），或只在状态变化时打。

**判据**：帧耗时曲线没有周期性尖峰。

## 5. 每帧工作量上限（防一帧雪崩）

```lua
-- 每帧步进上限（防止一帧内因为 lag 而补算一大堆）
local steps = math.min(elapsed / STEP, MAX_STEPS_PER_FRAME)
```
**为什么**：卡顿时 `elapsed` 变大，若无上限会在一帧内补算多次重力/移动 → 更卡（正反馈）。

## 5b. 降级顺序（真卡的时候牺牲什么）

**背景装饰 → 粒子 → 实例层文字**（保底：布局 textbox 仍然可见）。
> 理由：文字承载信息，装饰只承载氛围；而 textbox 层在最底下，永远还能被看到（层序铁律的反向利用）。

## 6. 元素数量上限（背景池 / 实例数）

**事实**：本项目背景池 **18 个实例**（`MODE_BG_POOL = 18`）、棋盘 **200 格**、标题页 **46 个实例**、HUD 双写 **9 个**。
**池溢出是静默的**：构图条数超过池容量时引擎**丢元素且不报错**——所以代码里必须有 `print('bg overflow !! specs=… pool=…')`
（实测 v2.7 因此静默丢了 2 个背景元素，靠这行日志才发现）。
**规则**：
- 全屏装饰用**少量大图元**（不是几百个小粒子）；
- 抖屏这类"对每个元素写坐标"的操作要**只在必要帧执行**（200 格 × 2~9 帧 = 1200~1800 次写）；
- 静态背景**建一次复用**，不要每帧重建。

**判据**：启动日志里的实例计数（`bg pool n=18` / `cellCount=200` / `menu stage n=46` / `hud inst n=9`）与实际设计一致。

## 7. "卡"的三种不同根因（别混）

| 症状 | 根因 | 判据 | 修法 |
|---|---|---|---|
| 整体掉帧、操作延迟 | 帧耗时爆表 | p99 高 | 消掉热路径无用计算（§2） |
| AI 思考时方块停住 | 分帧被低帧率饿死 | AI 盘块间隔不稳 | 先修帧率（同 §2） |
| 按键"自己一直走" | **不是性能问题**，是 DAS/事件路由（`03-input.md`） | 日志 move 序列 | 别往性能上查 |

**教训**：用户说"卡"时，先问"卡的时候 AI 在动吗/按键有反应吗"，能直接分流。
