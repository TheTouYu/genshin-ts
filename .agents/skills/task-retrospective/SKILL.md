# 任务复盘与自我进化（task-retrospective）

把"一波任务"（常含多次错误、多轮修复、压缩上下文）的完整历程变成可复查的复盘文档 + 系统性迭代，
让每次踩坑都转化为长期能力。以 2026-08-16 灯阵信号五连错复盘为参考案例
（`docs/game-engine-knowledge/retrospective-2026-08-16-signal-registration-series.md`）。

## 触发与前置

- 用户说"复盘/反思/沉淀/总结这波工作"，或一波任务刚闭环（游戏核验通过、修复交付、批量提交完成）后用户要求"进入自我进化环节"。
- 用户说"扩展检查/一次修一系列/别只修一个小问题/还有没有同类问题"时，本技能同样适用——复盘前的**同族扩展**（见第四节）。
- 开始前先回答：这波任务的**边界**是什么（从哪个时间点/提交开始）？涉及哪些领域（信号/实体/节点图/编译器/流程）？
- 若边界不清（如"这波"跨越多个会话），先问一个澄清问题或按时间线/提交范围推断，不猜测。
- **压缩恢复前置（2026-08-21 新增）**：模型触发上下文压缩后，下一次会重新加载项目根的初始文件 **`AGENTS.md` 与 `CLAUDE.md`**，它们就是压缩后模型的第一手初始上下文。复盘开始必须把这两个文件纳入核对对象（见流程 1 的"初始文件同步"），否则过期规则会随压缩扩散到后续所有任务。

## 任务迭代节奏（自主闭环，2026-08-22 用户要求固化）

本技能是「任务迭代节奏」的第 4 环。完整节奏已固化到 `AGENTS.md`「自进化与反思」节：

```text
① 探索 + 精准加载技能 → ② 执行中主动优化资源 → ③ 完成小点主动提交
→ ④ 完成小任务主动复盘沉淀（本技能） → ⑤ 迭代一轮写入知识树（PKC）
```

**手动触发本技能的两个场景**：
1. 常规：一波任务闭环（修复交付/批量提交），用户说"复盘/沉淀这波工作"。
2. **兜底触发（本节奏的保险）**：模型执行中**漏掉了自主节奏**——忘记主动提交、忘记小任务闭环就沉淀、
   忘记把可复用规则写入知识树——用户可以手动说"复盘/回顾节奏"，触发本技能让模型重新对齐完整节奏，
   补做漏掉的环节（对照 AGENTS.md 的五步逐项检查：哪些漏了、现在补哪步、怎么补）。

## 流程（五步闭环）

### 1. 收集素材（先全后精）

- **提交时间线**：`git log --oneline <起点>..HEAD | grep -iE "关键词"`——列出相关提交，作为历程骨架。
- **历史会话检索**（跨会话/压缩上下文时必做）：加载 `dsh-session-history` 技能，
  `scan` 看全景 → `search "<关键词>"` 定位关键决策 → `show` 深入单个会话 →
  `errors <会话>` 找模型错误（isError 是黄金标记）。
- **用户原话优先**：先提取 user/message 中的目标、约束、验收标准，不要用 assistant 复述替代。
- **用户纠正钩子（2026-09-01 协作复盘催生，必答一问）**：本轮用户**纠正过我的方法/理解/流程**吗
  （不只是指出 bug，而是"应该怎么查/怎么做"类纠偏）？
  - 有 → 先**逐字记录原话**（不用自己的话转译），归入第四节"流程与方法论教训"；
  - 属于可复用方法论（如排查流程、报告格式、沟通方式）→ 第五节系统性迭代时**回灌对应技能**，
    不要只在复盘文档里留档；
  - 为什么必答：2026-08-25~09-01 实证"分层排查"被用户教了 8 遍（5 遍在一天内）才固化——
    纠正到达时内嵌在任务现场，若复盘不主动回收，它就永远只是"当轮的纠偏"而不是知识。
- **验收口径审计（2026-09-09 笔记本 v1/v2 复盘催生，必答三问）**：本轮交付的**验收标准是谁写的**？
  ① 任务书/判据里有没有**被审方自己预写的「已知限制/豁免清单」**（把缺陷提前判定为"不算缺陷"）？
  ② 每个门禁的 `pass` 覆盖了哪些维度、**没覆盖**哪些维度（是否被当成了全维度通过）？
  ③ 评测/验证产物是否**留档可复现**（超时、0 字节 final、无 trace = 结论不可复现，不得写进交付文档）？
  ④ **过程可信度审计（2026-09-11 前唇白线战催生，必答）**：本轮有多少结论是建立在**没发生的实验**或
  **量错对象的刻度**上的？逐条标注作废范围——① 空实验（补丁锚点 0 替换、改 `src` 未 build 而工具读 `dist/`、
  缓存旧页/旧网格）：读数"不变"≠假设不成立；② 归属错位（指标采样对象与假设对象不是同一个面/件）：
  五组对照可全 null；③ 口径漂移（指标悄悄量到别的特征，如"全帧亮占比"量到屏幕图标）：跨轮数字不可比。
  复盘文档里把**作废的结论明确划掉**并写清"因为什么作废"，不要静默替换成新结论。
  - **污染半径 = 所有信任过这把坏尺子的轮次**（2026-09-11 实证）：发现「量错对象」后，必须逐轮清点下游结论
    并主动作废重测（那次作废了 r41–r43 全部，战役才变得可解）；只修尺子不作废上游 = 把旧结论带到新口径下继续用。
  - 为什么必答：同一次战役里，三条合计浪费 ≈1h40m（占该 bug 总耗时 3.6h 的一半），且其中有结论后来被自己反转。
  可迁移规律已固化到 `diagnosing-bugs` Phase 4（归属优先 / 空实验门 / 按不变量打补丁 / 对象存活 / 代理信号台阶）与 `model-build-test` §12.6。
  ⑤ **被测对象是不是新的**（2026-09-13 预设组合器 6 轮误诊催生，必答）：每轮读数前，是否证明了"我测的是新对象"？
     - ① 配置真的解析通过（平台的校验 / dry-run 命令退出 0）？② **服务进程换了**（pid 变化——不接受"日志里出现 token"，
       那行可能是**旧进程**写的）？③ 产物指纹（mtime / 字节 / hash）变了？
     - 反例：profile 的配置文件被改成非法 YAML → 新进程根本没起、旧进程继续占着端口 → **6 轮读数全打在旧进程上**，
       并据此冤枉了三个无辜插件（相关结论全部作废）。污染半径 = 所有打在旧对象上的轮次，按 ④ 的规则显式作废。
     - 另注意**校验通过 ≠ 实例可用**：同一份"解析干净"的配置可以每次请求都失败。
      - 变体（2026-10-16 skill-rec 组合器收编实证）：**时点污染**——验证时刻 ≠ 交付时刻。
        跨仓绝对路径引用（如能力目录的 localModule entry 指向兄弟仓版本化入口）在验证
        通过后被并行窗口 bump 并删旧文件，40 分钟后交付物里的路径已指向不存在的文件。
        对策：引用跨仓/版本化路径的交付，**收尾前重验一次目标仍存在**（ls 目标 + 读回），
        并在数据条目里写明同步义务（"main bump 时须同步改此 entry"）。
     - **自检会污染共享观测面**（2026-10-16 skill-rec 挂载诊断实证）：构建后跑 `import()` 冒烟会在诊断日志里写下
       与真会话同格式的 marker——后来靠「marker 时刻早于会话 20 分钟」才识破。凡自检会写痕迹到共享观测面
       （日志/dbg 文件/遥测），marker 必须带来源标识，或自检后清痕。
  ⑥ **样本量与窗口**（2026-10-15 dsh-memo-river 拆批上线实证，必答）：结论是不是建立在 **n<10 的样本**、
  或按「方便」而非**状态变更点**切的窗口上？
     - 反例：先拿**单个**样本（457ms）宣布「-55% 见效」，被质疑后又挑出旧分布的**低端三例**当基线宣称「没改善」；
       按服务端/代码状态切三段全量对账（n=48/44/12）才看得见真账：服务端去重 -67% 是主功、拆批再 -18%。
     - 判据：**n≥10 才报分布**、报分位数不报单点；对照窗按状态变更点切（不是按方便切）；
       采样器/监控一律**锚定「从此刻起」**（首版把日志尾部历史行全部回填 → 1193 条换端点前的旧样本混入，p50 假报 3115ms）。
     - 为什么必答：小样本 + 自选窗口能让**任何**改动看起来成功或失败，而这两种错都会**当场说给用户听**，
       再被自己反转一次——比不说更贵。
  - 为什么必答：2026-09-09 实证——v2 三轮机器门禁全绿（`gms.verify ok` / 独立 AABB 0 缝隙 / 视觉复核 pass 0 blocker），
    用户进游戏一眼判定"你做的不是 mac"；根因正是评测任务书由模型自写，且把"四角约 4 mm 直角外沿"写进豁免清单，
    评测器于是无权报出用户后来指出的缺陷。
  - 有 → 逐字摘录豁免清单/判据原文进复盘文档；并把"验收标准不许自写自判"回灌到对应技能。
- **当前状态核对**：`git log --oneline` + 相关测试 + 真实地图/产物状态——历史说法必须与当前交叉验证。
- **初始文件同步（压缩恢复后必做，2026-08-21 新增）**：对照本轮实际变化清单（`git status` 涉及文件、新增/改名工具、`.agents/skills/` 目录、CLI `--help` 输出），核对根目录 `AGENTS.md` 与 `CLAUDE.md` 是否过期或缺项：
  - `AGENTS.md`：技能路由表是否覆盖现有技能（新增技能要加行）、本轮新纪律/新路径/新红线是否已写入、旧说法是否与证据冲突；
  - `CLAUDE.md`：常用命令是否缺新 CLI 选项、架构/修改约束是否仍准确；
  - 发现不同步 → 按"适用范围最小"原则直接更新（它们是小文件，放得下的才放），并在复盘文档产出清单里记录同步内容。

- **记忆工程前置（2026-10-17 新增，本技能自身迭代）**：复盘前先答两问——
  ① **结论落在生效载体上了吗？**（技能 > AGENTS > 文档；只进复盘文档=下次不会自动加载）；
  ② **改过的全局技能有版本追溯吗？**（`~/.agents/skills/` 常不在项目仓内 ⇒ 改前留 `.bak`，
  并在复盘文档"产出清单"里写明改了什么——那是它唯一的 diff 记录）。
  实例：2026-10-17 压缩丢细节事故复盘（`retrospective-2026-10-17-compression-loss-and-recovery.md`）。

### 2. 梳理谱系（不止单次修复）

- **同类错误排成谱系**：同一症状（如"游戏拒载"）背后往往多个根因（版本一致性/版本下限/布局/默认值…），
  列成表格：`# | 日期 | 根因层 | 具体错误 | 修复 | 提交`。
- **找系统性根因**：问三个为什么——为什么反复踩？是样本字节未提炼语义？验证链有盲区？
  一次修复掩盖下一个？提炼 2-3 条**可复用的规律**，不是罗列事实。
- **方法论教训**：哪些流程/操作帮助了定位（如三版本差分）？哪些绕了路？
- **元层铁证（2026-08-29 元复盘实证）**：复盘/矩阵中关于知识库状态、工具返回码的断言
  （已入树/未入树/已应用/失败）同样是"结论"，必须先 query/validate/bundle-status 取证，
  否则标"待查证"——铁证原则不只适用于引擎行为（实例：矩阵把 R11 标红"未入树"未查证；
  bundle-apply exit 1 先按失败定性，实际事务已落盘）。

### 3. 写复盘文档

输出到 `docs/game-engine-knowledge/retrospective-YYYY-MM-DD-<主题>.md`（权威文档）或
`docs/maintenance/`（维护记录），包含：

```text
# 完整复盘：<主题>（日期）
> 范围 / 视角 / 证据（提交+会话+快照路径）/ 状态
## 一、错误谱系总览（表格）
## 二、最近一次错误的完整调查链（现象→差分→根因→修复→验证）
## 三、为什么反复出问题——系统性根因（2-3 条）
## 四、流程与方法论教训
## 五、风险探索与未闭合项
## 六、产出清单（修复/文档/技能/证据/提交）
```

- 文档开头保留状态、来源、证据路径；区分"当前实现/自动回归/真实 GIA/用户验证/历史/待验证"。
- 局部经验进案例文档，高频可复用经验才进 AGENTS.md。
- **DSH 环境（2026-08-29 实证）**：大段文档内容先 write 工具落文件再 edit 引用，
  不要在 run_code 模板字面量里内联——反引号截断模板、转义序列变字面量（与 08-28 正则版同族）。
- **全量回写大文件纪律（2026-09-03 open-items 事故实证）**：对账本/长文档做「read→write 全量复制回写」
  曾发生**尾部内容丢失**（9331378 提交静默删掉文件尾部 34 行，git diff --stat 才暴露）。写回前先记录
  基线（`wc -l` + `git diff --stat` 期望改动面 + `tail -3` 尾部锚点）；写回后**立即**用
  `git diff --stat` / `tail -3` / `git diff --check` 核对改动面与预期一致；不一致时不要增量修补——
  用 `git show <基线commit>:<file>` 导出基线 + python 精确 replace 重建再提交（3ec025f 修复路径）。
  本坑与 08-29 内联截断同族：DSH 写路径对大文本不可全信，凡 diff 面可疑先查 git。

### 4. 同族扩展（修复类任务的必做步骤，2026-08-14 魔方 P4 实证）

复盘前先问：**这个 bug 的"同类边界"是什么？** 单点修复不是终点——枚举同族风险点，一次修一组。

- **快速定位（图优先，rg 兜底）**：`trace_path {function_name, direction: inbound, depth: 2}`
  找出共享同一修复函数的**所有入口**；决策矩阵：结构/调用关系 → codebase-memory 图；
  字面量/错误串/单文件细节 → rg/read。图结果必须用 `read` 落回真实源码确认后才改代码。
- **按 bug 类型选检查清单**：
  - 参数边界类：同一 API 所有参数处理点是否都防御（裸值/句柄/null）？
  - 类型推断类：同一类型族的变体选择是否全链路（IR→GIA→pin 编码）？
  - 编码形态类：官方 golden 与生产输出逐字段对照，同一节点族全部覆盖？
  - exec 边完整性类：IR implEdges 源真实、合成调用 OutFlow 有 connects、链尾有物理 InFlow pin？
- **一次修一组 + 回归**：修改按"最小函数 + 同族覆盖"组织；可靠退出码
  `tsx test.ts && echo PASS || echo FAIL`（禁止 `grep | tail` 管道判断——退出码恒为最后命令）。
- **未覆盖项显式登记**：同族中不做/不能做的（无证据、超范围）显式列出，不静默跳过。

### 5. 系统性迭代（复盘的核心价值）

**落盘优先级铁律（2026-08-29 用户明确，元复盘实证）**：可行动经验的第一落点是**技能**——
下次同类任务只会自动加载技能，不会自动翻文档。复盘结束必须逐条问：
"这条经验下次会通过哪条路径生效？" 答案是"去翻复盘文档/open-items/common-errors"的，
说明还没落到位。文档/PKC/账本是索引与长期记忆，**不是生效载体**。

按"适用范围最小"原则逐层落盘，**每层都要真的改**。

> **落地自检（可执行，2026-10-17 新增）**：`python3 scripts/skill-salvage.py` —— 扫最近 N 篇日记里的工具/命令 token，与技能 + AGENTS/CLAUDE 载体语料比对，分两类报出：① **真孤儿**（磁盘上存在但载体里搜不到 ⇒ 该打捞，退出码 1）② 非现存名字（计划项/已废弃，别当知识）。零孤儿 = 本波知识确实落到了生效载体。

1. **权威技术文档**（如 `signals.md`）：把谱系中最新的**通用规则**追加为章节（含证据链+工程结论+commit）。
2. **open-items.md**：登记"已修复待知识库录入"（O-YYYY-MM-DD-NN 格式）+ 未闭合风险项。
3. **技能（按"本轮实际加载的技能清单"逐个检查，2026-08-21 补充机制）**：
   不是只更新"印象中涉及的技能"，而是先列出**本轮实际用过的技能**（本会话的 skill 调用记录；跨会话用
   `dsh-session-history` 检索 `skill_content` 事件），逐个过一遍可迭代点，**每个技能要么改、要么显式说明"已检查无需迭代"**：
   - 工具/脚本行为变化（新 CLI 选项、误报、缺参数）→ 更新该技能的工具速查与判读说明；
   - 本轮新规则/新纪律 → 落到对应领域技能（如 exec 链铁律进 dsl-nodegraph-development）；
   - 流程缺口（某步跳过导致返工）→ 在技能流程里补强制步骤；

   典型高频技能池：`gil-node-graph-reading` / `dsl-nodegraph-development` / `debug-log-investigator` /

4. **AGENTS.md**：只有高频、可复用、可行动且已证实的经验才进；局部案例不推广。

- 运行受影响测试（`npx tsx tests/<file>.ts`）+ `git diff --check`；改动生产 TypeScript 先 `npm run build`。
- **先认目标仓的提交门禁（2026-10-16 实证，genshin-ts）**：不少仓有 pre-commit 文档治理钩子
  （该仓 `doc_health`：根 `AGENTS.md` 有 **16384B 硬阈值**、**禁 `--no-verify`**）。本轮把一行路由写进根 AGENTS.md
  直接把它推到 16595B → 提交被拒。对策：**落点选适用范围最小的文件**（子目录 `AGENTS.md`、该目录 `README.md`、
  或写成最小指针行并先算余量 `stat -c%s`），被拒时读完钩子输出再改，**不要绕过门禁**。

  （钩子失败时 `git commit` 的退出码与"看起来成功了"的观感会分叉）。

## 原则

- **复盘本身也要可复用**：把"这次怎么定位到根因的"写清楚（方法 > 结论），下次同类问题能照做。
- **不重复考古**：已沉淀的结论不重查；检索到历史说法后与当前源码/测试交叉验证，避免旧结论冒充新证据。
- **克制**：不要为凑篇幅写无人再看的文档；每份产出都要有"未来某次任务会来查"的理由。
- **每轮结束做规则反馈检查**：本轮源码/测试/真实反馈是否与 AGENTS.md 冲突，冲突则更新最小规则文件。
