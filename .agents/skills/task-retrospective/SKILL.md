# 任务复盘与自我进化（task-retrospective）

把"一波任务"（常含多次错误、多轮修复、压缩上下文）的完整历程变成可复查的复盘文档 + 系统性迭代，
让每次踩坑都转化为长期能力。以 2026-08-16 灯阵信号五连错复盘为参考案例
（`docs/game-engine-knowledge/retrospective-2026-08-16-signal-registration-series.md`）。

## 触发与前置

- 用户说"复盘/反思/沉淀/总结这波工作"，或一波任务刚闭环（游戏核验通过、修复交付、批量提交完成）后用户要求"进入自我进化环节"。
- 用户说"扩展检查/一次修一系列/别只修一个小问题/还有没有同类问题"时，本技能同样适用——复盘前的**同族扩展**（见第四节）。
- 开始前先回答：这波任务的**边界**是什么（从哪个时间点/提交开始）？涉及哪些领域（信号/实体/节点图/编译器/流程）？
- 若边界不清（如"这波"跨越多个会话），先问一个澄清问题或按时间线/提交范围推断，不猜测。
- **压缩恢复前置（2026-08-21 新增）**：模型触发上下文压缩后，下一次会重新加载项目根的初始文件 **`AGENTS.md` 与 `CLAUDE.md`**，它们就是压缩后模型的第一手初始上下文。复盘开始必须把这两个文件纳入核对对象（见流程 1 的"初始文件同步"），否则过期规则会随压缩扩散到后续所有任务。

## 任务迭代节奏（自主闭环，2026-08-22 用户要求固化）

本技能是「任务迭代节奏」的第 4 环。完整节奏已固化到 `AGENTS.md`「自进化与反思」节：

```text
① 探索 + 精准加载技能 → ② 执行中主动优化资源 → ③ 完成小点主动提交
→ ④ 完成小任务主动复盘沉淀（本技能） → ⑤ 迭代一轮写入知识树（PKC）
```

**手动触发本技能的两个场景**：
1. 常规：一波任务闭环（修复交付/批量提交），用户说"复盘/沉淀这波工作"。
2. **兜底触发（本节奏的保险）**：模型执行中**漏掉了自主节奏**——忘记主动提交、忘记小任务闭环就沉淀、
   忘记把可复用规则写入知识树——用户可以手动说"复盘/回顾节奏"，触发本技能让模型重新对齐完整节奏，
   补做漏掉的环节（对照 AGENTS.md 的五步逐项检查：哪些漏了、现在补哪步、怎么补）。

## 流程（五步闭环）

### 1. 收集素材（先全后精）

- **提交时间线**：`git log --oneline <起点>..HEAD | grep -iE "关键词"`——列出相关提交，作为历程骨架。
- **历史会话检索**（跨会话/压缩上下文时必做）：加载 `dsh-session-history` 技能，
  `scan` 看全景 → `search "<关键词>"` 定位关键决策 → `show` 深入单个会话 →
  `errors <会话>` 找模型错误（isError 是黄金标记）。
- **用户原话优先**：先提取 user/message 中的目标、约束、验收标准，不要用 assistant 复述替代。
- **当前状态核对**：`git log --oneline` + 相关测试 + 真实地图/产物状态——历史说法必须与当前交叉验证。
- **初始文件同步（压缩恢复后必做，2026-08-21 新增）**：对照本轮实际变化清单（`git status` 涉及文件、新增/改名工具、`.agents/skills/` 目录、CLI `--help` 输出），核对根目录 `AGENTS.md` 与 `CLAUDE.md` 是否过期或缺项：
  - `AGENTS.md`：技能路由表是否覆盖现有技能（新增技能要加行）、本轮新纪律/新路径/新红线是否已写入、旧说法是否与证据冲突；
  - `CLAUDE.md`：常用命令是否缺新 CLI 选项、架构/修改约束是否仍准确；
  - 发现不同步 → 按"适用范围最小"原则直接更新（它们是小文件，放得下的才放），并在复盘文档产出清单里记录同步内容。

### 2. 梳理谱系（不止单次修复）

- **同类错误排成谱系**：同一症状（如"游戏拒载"）背后往往多个根因（版本一致性/版本下限/布局/默认值…），
  列成表格：`# | 日期 | 根因层 | 具体错误 | 修复 | 提交`。
- **找系统性根因**：问三个为什么——为什么反复踩？是样本字节未提炼语义？验证链有盲区？
  一次修复掩盖下一个？提炼 2-3 条**可复用的规律**，不是罗列事实。
- **方法论教训**：哪些流程/操作帮助了定位（如三版本差分）？哪些绕了路？

### 3. 写复盘文档

输出到 `docs/game-engine-knowledge/retrospective-YYYY-MM-DD-<主题>.md`（权威文档）或
`docs/maintenance/`（维护记录），包含：

```text
# 完整复盘：<主题>（日期）
> 范围 / 视角 / 证据（提交+会话+快照路径）/ 状态
## 一、错误谱系总览（表格）
## 二、最近一次错误的完整调查链（现象→差分→根因→修复→验证）
## 三、为什么反复出问题——系统性根因（2-3 条）
## 四、流程与方法论教训
## 五、风险探索与未闭合项
## 六、产出清单（修复/文档/技能/证据/提交）
```

- 文档开头保留状态、来源、证据路径；区分"当前实现/自动回归/真实 GIA/用户验证/历史/待验证"。
- 局部经验进案例文档，高频可复用经验才进 AGENTS.md。

### 4. 同族扩展（修复类任务的必做步骤，2026-08-14 魔方 P4 实证）

复盘前先问：**这个 bug 的"同类边界"是什么？** 单点修复不是终点——枚举同族风险点，一次修一组。

- **快速定位（图优先，rg 兜底）**：`trace_path {function_name, direction: inbound, depth: 2}`
  找出共享同一修复函数的**所有入口**；决策矩阵：结构/调用关系 → codebase-memory 图；
  字面量/错误串/单文件细节 → rg/read。图结果必须用 `read` 落回真实源码确认后才改代码。
- **按 bug 类型选检查清单**：
  - 参数边界类：同一 API 所有参数处理点是否都防御（裸值/句柄/null）？
  - 类型推断类：同一类型族的变体选择是否全链路（IR→GIA→pin 编码）？
  - 编码形态类：官方 golden 与生产输出逐字段对照，同一节点族全部覆盖？
  - exec 边完整性类：IR implEdges 源真实、合成调用 OutFlow 有 connects、链尾有物理 InFlow pin？
- **一次修一组 + 回归**：修改按"最小函数 + 同族覆盖"组织；可靠退出码
  `tsx test.ts && echo PASS || echo FAIL`（禁止 `grep | tail` 管道判断——退出码恒为最后命令）。
- **未覆盖项显式登记**：同族中不做/不能做的（无证据、超范围）显式列出，不静默跳过。

### 5. 系统性迭代（复盘的核心价值）

按"适用范围最小"原则逐层落盘，**每层都要真的改**：

1. **权威技术文档**（如 `signals.md`）：把谱系中最新的**通用规则**追加为章节（含证据链+工程结论+commit）。
2. **open-items.md**：登记"已修复待知识库录入"（O-YYYY-MM-DD-NN 格式）+ 未闭合风险项。
3. **技能（按"本轮实际加载的技能清单"逐个检查，2026-08-21 补充机制）**：
   不是只更新"印象中涉及的技能"，而是先列出**本轮实际用过的技能**（本会话的 skill 调用记录；跨会话用
   `dsh-session-history` 检索 `skill_content` 事件），逐个过一遍可迭代点，**每个技能要么改、要么显式说明"已检查无需迭代"**：
   - 工具/脚本行为变化（新 CLI 选项、误报、缺参数）→ 更新该技能的工具速查与判读说明；
   - 本轮新规则/新纪律 → 落到对应领域技能（如 exec 链铁律进 dsl-nodegraph-development）；
   - 流程缺口（某步跳过导致返工）→ 在技能流程里补强制步骤；
   - 写回前先 read 该技能文件；改动注明证据（日期+实证场景）。
   典型高频技能池：`gil-node-graph-reading` / `dsl-nodegraph-development` / `debug-log-investigator` /
   `verify-injection` / `genshin-ts-asset-operations` / `gil-node-graph-editing` / `task-retrospective` 自身。
4. **AGENTS.md**：只有高频、可复用、可行动且已证实的经验才进；局部案例不推广。

### 6. 验证与提交

- 运行受影响测试（`npx tsx tests/<file>.ts`）+ `git diff --check`；改动生产 TypeScript 先 `npm run build`。
- 按主题分批提交（修复 / 技能 / 文档），提交信息注明意图。
- **知识库转交**：把待录入项（O-xx）发给知识库维护者代理；代理离线时保留 open-items 条目即可。

## 原则

- **复盘本身也要可复用**：把"这次怎么定位到根因的"写清楚（方法 > 结论），下次同类问题能照做。
- **不重复考古**：已沉淀的结论不重查；检索到历史说法后与当前源码/测试交叉验证，避免旧结论冒充新证据。
- **克制**：不要为凑篇幅写无人再看的文档；每份产出都要有"未来某次任务会来查"的理由。
- **每轮结束做规则反馈检查**：本轮源码/测试/真实反馈是否与 AGENTS.md 冲突，冲突则更新最小规则文件。
