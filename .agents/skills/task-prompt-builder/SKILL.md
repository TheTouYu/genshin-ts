# 任务提示词构建（task-prompt-builder）

## 定位

把"开启一个任务"做成有章法：先收集信息（用户 + 当前任务状态），再按固定骨架产出高效提示词。
高效的标准：目标清晰、核验可执行、长期任务能跨会话续接、复用已有资产、给元知识不代劳。
参考实例：魔方 3x3 客户端改造任务的启动提示词（本技能的第一个生产用例）。

## 七角度骨架（产出模板，顺序固定）

```markdown
# 任务：<一句话主题>

## 一、任务目标
- 要做什么、成功长什么样；多层目标（如玩法层+工程层）分开写

## 二、铁律（用户明确要求且不可妥协的约束）
- 破坏性操作边界、质量红线、证据分层、遇阻时的行为（记录/沟通/不绕过）

## 三、核验标准
- 模型侧（提交前必须全过）：编译/测试/读图回读/日志自核验
- 用户侧（每轮验证）：用户做什么、提供什么（如日志/复测结论）
- 最终验收：可测量的终态（如日志铁证特征、量化对比）

## 四、多轮迭代与多会话拆分
- 轮次骨架（顺序可调整，注明"由你按探索结果调整"）
- 会话衔接机制：新会话先读什么（PROGRESS/PKC/历史会话）、每轮结束落什么

## 五、复用清单（先查再用，不要重新发明）
- 技能（按路由加载）、已逆向参考资产、工具、文档——只写"哪里有什么"

## 六、已知局限与风险
- 未验证点/未闭合项/已知坑——记录用，不是让执行者绕过

## 七、第 0 轮任务（现在开始）
- 3-5 个具体动作 + 交付物清单，交用户确认后继续
```

## 流程

### Step 1 对齐（最小提问，最多 3 个问题）
- 用户已描述任务 → 用一句话复述确认边界，不问废话
- 只问真正缺失且影响产出的：任务目标 / 验证方式（谁验证、什么证据）/ 迭代粒度与是否原地改 vs 新文件夹
- 用户原话中的红线、验收口径原样保留进提示词，不用自己的话稀释

### Step 2 收集任务状态（并行，用真实工具确认，不凭记忆）
- 技能清单：`ls .agents/skills/`（找相关技能，路由表里写全名）
- 知识树：`python tools/pkc.py tree` + `query "<关键词>" --level 2`（已沉淀的相关结论）
- 未闭合项：`docs/maintenance/open-items.md` 尾部（相关 O-xx 条目）
- 历史：`git log --oneline -15`（最近的复盘/修复提交 = 已覆盖知识）
- 相关资产：`examples/<主题>/PROGRESS.md`、`docs/game-engine-knowledge/` 目录、参考样本文件路径
- 跨会话任务另查：dsh-session-history（历史决策与未完成项）

### Step 3 生成
- 按七角度骨架输出完整提示词，放进 markdown 代码块（可直接复制给新会话/子代理/goal）
- 附 3-6 条"设计说明"：为什么这样写、哪里故意留给执行者自己探索
- 结尾写"使用者第 0 轮交付物清单"

### Step 4 交付与迭代
- 用户反馈 → 修订；提示词被使用后暴露的问题（信息缺失/过度限制/资源引用失效）→ 记下来回灌本技能

## 原则（为什么这样写）

- **引导而非代劳**：只给"哪里有什么"和元知识（入口函数名、文档位置、已知结论），不写"你应该这样做"。
  执行者自己探索出的方案往往更贴合实际——上次实例中"参考地图服务器每块重算位置是否照搬"就故意留给模型判断。
- **资源引用必须真实**：引用的技能/文档/工具/文件路径先用工具确认存在，虚构引用会毁掉执行者的第一轮。
- **证据分层要写进核验标准**：编译通过 ≠ 注入正确 ≠ 游戏行为正确；模型侧与用户侧分工明确，双方不互相等待。
- **长期任务必写会话衔接机制**：新会话先读 PROGRESS → 查 PKC → 查历史会话；每轮结束落 PROGRESS + 复盘 + PKC + 提交。
- **用户的红线原样固化**（如"不许绕过 bug，停下来沟通"）；局部偏好（提交粒度、新文件夹先行）也写进铁律。
- **克制提问**：信息够写就写；问题多说明你还没读懂用户，先重读对话而不是连环问。

## 陷阱

- 把"执行方案"写进提示词（替模型做完探索）——引导不是代劳
- 复用清单凭记忆写、未验证路径——执行者第一轮就踩空
- 核验标准只有"跑通"没有分层证据——长期任务必然返工
- 长期任务不写会话衔接——换会话就断线
- 用户红线被"软化"成建议——红线是提示词里最高优先级
