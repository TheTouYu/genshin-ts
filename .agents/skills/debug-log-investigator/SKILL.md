# 调试日志查询与破译（debug-log-investigator）

## 定位

目标：从游戏落盘的 `Beyond_Debug_Log/*.gia` 调试日志中，**完整还原节点图执行过程**——
普通打印、节点执行顺序、每个节点的输入/输出参数和值、变量读取/赋值/变化、if/循环等控制流、以及每节点"计算的负载"。
同时支持**受控实验驱动**：改实验节点图 → 编译注入 → 用户运行 → 退出落盘 → 相邻日志比对，逐步闭合未知编码规则。

权威知识文档：`docs/game-engine-knowledge/debug-log-format.md`（本技能的全部规则明细，改动必须同步）
证据快照：`~/genshin-ts-evidence/debug-log/format-investigation/raw/`
实验地图：LogFormatLab（1073741881），节点图 1073741825，实体 1077936181，实验源码 `lab/loglab.ts`

## 一句话流程

```
定位最新 .gia → 提取文本日志（验证打印）→ 帧表解码（执行过程）→ 类型码/操作码/节点定义对照 → 与用户面板逐节点核对 → 更新知识文档
```

### 多图协作问题查询 playbook（2026-09-02 3093 实证：求解器角块阶段打乱十字）

「规划图→执行图→转动图→状态回读」多图协作类问题（求解器/状态机/队列），五步走：

1. **定位与快照**：`ls -lt 日志目录 | head` 锁定最新 → 快照进**工作区** `.gsts/evidence/<主题>/` + sha256
   （home 目录可能只读；Debug_Log 滚动清理只留 ~28 个，快照要趁早）。
2. **概览**：`records --gil <地图> --summary` 看图分布/规模/秒范围——判断会话覆盖哪些图。
3. **按图 dump（工作区！）**：每图一份 `frames --graph <id> > 文件`（大日志 5 万+ 行必须落文件；
   /tmp 不跨命令持久）。**多图协作问题的 dump 至少含规划图+执行图+状态发布图三份**。
4. **合并对齐**：`gia_log_align.py` 合并成单表（上表）。回退/破坏轮次一眼锁定；注意
   「Integer 显示(空)」可能是有效值 0——定性前与源码表值离线对照。
5. **离线对照三件套**（区分「表错 / 编译错 / 图结构错」三层）：
   - **表数据对照**：日志读到的表值 vs 源码 `*Tables.ts`（python 解析 bigint[] 数组）；
   - **编译产物对照**：`tools/decode-gia.ts` 数 entries/节点/MB 数（新旧 gia 对比，结构变化
     与源码改动一一对应的最轻量核验）；
   - **根因逻辑离线复现**：把假设根因写成代码跑模拟，**逐位复现**日志错误序列 → 根因实锤；
     配套「新逻辑模拟 = 期望序列」双验证（见流程 2.7）。

**图结构核验工具速记**（3093 实证，JSON 层勿手搓）：
- `tools/explain-gil-node-graph.ts <map.gil> --graph <id> --depth 2`：MB 节点的 case 列表显示为
  `L ← 字面量 [0,1,2,…]`——**case 数直接数列表长度**（比任何自写解析都快）；default 出边直读。
- `tools/trace-gil-dataflow.ts <map.gil> --graph <id> --node <n> --all-inputs`：值来源链直读
  （用法：--node 指定节点号，必须带 --all-inputs 或 --input，无位置参数形式）。
- decode-gia 的 JSON 只适合数 entries/找声明；**重建控制流邻接别在 JSON 层手搓**（3093 绕路 4 轮），
  直接用上面两个官方工具。

**提取正则坑**：写 sed/awk/grep 提取前**先看 3 行原始输出**确认字段格式（`|` 是帧行分隔符，
正则里未转义会静默不匹配）；负整数解析一律 python BigInt（见「负整数双显示坑」定则）。

1. **活动分布定死活**：`gia_log_activity.py <日志> --graph <物理图id>`——重计算何时起止、

### 踢球链路事件时间轴判读 playbook（2026-09-03 足球 R3 收口实证：选项→任务→ack→镜像量化）

「按键/事件→任务→客户端应用→镜像」链路（踢球延迟、停距、侧旋横偏、冻结窗口）五步走：

1. **标记秒级时间轴（第一工具）**：`gia_log_markers.py <日志> --markers fb:tab,fb:ack,fb:auto1,fb:auto3,fb:auto5,fb:auto7,fb:wdgate,fb:tear,fb:repub --digits`——

2. **text 对照**：`gia_log.py text` 拿完整 f22 流（含 e5 对账 mm 值等未列串），rec 号与步骤 1 对齐。
3. **两图 frames dump 落文件**：服务端镜像应用复合（如 fb_mirror_apply）+ 客户端计算图各一份（大日志必须落文件再分析）。

   一行一拍轨迹；停距=同段末帧 px−踢出帧 px；横偏=x 目标处对相邻两帧插值 z。
5. **pivot 输出坑（本轮实证，必看）**：引擎**零值分量省略**（Vector=(0,1.85,0) 的 x/z OUT 显示空、px=0 的行整格空）——

### 服务端日志·定时器事件引脚与日志目录族（2026-09-01 引脚回归复盘实证）

- **When Timer Is Triggered（gid 83）OUT3/OUT4 填充按定时器种类分岔**：OUT3（序列序号）仅
  「延迟列表多槽」定时器触发时携带槽位号；OUT4（循环次数）仅「重复型」定时器携带计数
  （3067 dsp=1..19 实证），非重复定时器**双空**。日志里 `OUT3/4:Integer=` 空显示 ≠ 值 0
  （真 0 会显示 `Integer=0`）——排查「多槽动画全落槽 0」先查消费线接的是哪个引脚
  （详情见 game-engine-knowledge/node-graphs.md 定时器节；修复 c7c263a）。
- **日志目录族**：`Beyond_Performance_Report/*.gia` 与 `Beyond_Debug_Log/*.gia` 同会话号成对，
  但前者**无 f21 记录**（records/frames 解析为空报错属正常）；Debug_Log 会被游戏侧滚动清理
  （2026-09-01 实证只保留最近 ~28 个）——**关键现场日志要当场摘录帧值**，别指望文件还在。

### 服务端日志·「显式写布尔值却被回退」判读门（2026-09-01 bool false 实证）

- **症状**：某分支显式 set 变量=false（如 unlock 分支复位 lock），但运行日志帧显示
  Set Node Graph Variable | IN2:Boolean=1（写入 true）→ 后续逻辑被锁死（如交互无响应）。
- **根因方向（编译器 alreadySetVal 语义）**：编译器产物 value pin 内层 alreadySetVal:false
  会被引擎视为"值未设置"→ 回退该类型默认值（bool 默认 true！）。int/float/string 默认=0/空
  恰好与显式 0/空等价，只有 bool 会暴露差异。
- **判读顺序**：① 确认该分支定时器/信号确实触发（事件记录在）；② 看 Set 帧的 IN2 值是否与
  源码意图相反；③ 若相反 → 回读 .gil 该节点 value pin：enum:0 但内层 alreadySetVal 缺失/0
  = 编译器 bug（参照物：正常形态是 alreadySetVal:true，见 e7fe704 修复）。
- **铁证原则**：运行日志是唯一铁证——.gil 字节显示 0 但日志显示 1，就是"引擎不认该编码形态"，
  不要用"注入没替换/地图被改写"的静态推断替代（2026-09-01 3074 rec58 实证）。

### 日志显示层假象族 + 黄金对照判读门（2026-09-04 魔方 client 竞态复盘实证，3185 vs 3099）

- **显示假象三形态（单份日志误判之源，值本身没错）**：
  - int_list 负值显示为 `[值的uint8, 255×8]`（-1→`255×9`、-2→`254,255×8`、-6→`250,255×8`）——
    **不是 9 个物理元素/残留**，getCorrespondingValueFromList 按真实索引取值正常；
  - 部分 int_list 图变量 Get 帧读出显示 float 垃圾/nan（如 CF_CORNER_POLICY_c2
    `[0.0001508, 9.982e-18, nan…]`），同一帧 getCorrespondingValueFromList 的 IN0 又显示
    hex 字节串——**显示层按不同 wire 形态解码，表内容本身完好**；
  - Integer 空显示可能是有效 0（O-2026-09-04-02 口径）。
- **黄金对照判读门**：显示形态与预期内容矛盾时，**先找一份同链路已成功的日志同字段对照**
  （3099 主线正常还原 vs 3185 病灶），同形态 → 假象/正常（跳过破译），不同形态 → 真异常。
  2026-09-04 实证一次对照杀死 3 个错误假设（DIR 表 72 项/POLICY float 垃圾/solve_seq 255×8），
  比逐帧语义推理快一个数量级。
- **对照日志哪里找**：Debug_Log 滚动清理只留 ~28 个，正常会话日志要靠 evidence 归档——先查

### 竞态判定 playbook：定时器等待 vs 事件到达（2026-09-04 魔方 client 版角块振荡实证）

适用：「规划器按旧状态重算/重复发宏/状态回退振荡」类问题，链路含**固定定时器等待异步完成**
（doneTick 等宏尾步发布、emitTick 等动画完成）。四步走：

1. **构造时间轴**：dump 两侧 frames 落文件（触发侧=执行器/定时器图，被等侧=发布/动画图），
   提取关键事件 rec 号对齐成单表（发送 op 序列 / 定时器触发 / 状态发布）。
2. **竞态窗口判据**：**比对「触发重算的事件 rec 号」与「被等待的最后一条发布 rec 号」先后**——
   重算事件（如 op5）早于被等发布（如 solver_cp 更新）到达 = 竞态实锤（rec 序=真实时间序铁证；
   2026-09-04 实证：doneTick op5@rec2837 早于宏尾步发布@rec3107，规划器读十字尾旧状态重发宏）。
3. **离线重放终审**：表驱动模拟（同表同语义，负码=3 次正转）与日志逐位对照——逐位一致=执行层
   正确，偏差只能来自「状态快照时机」→ 调查重定向到时序；模拟结论也需两个独立脚本对拍
   （单脚本表解析 bug 曾误导一轮）。
4. **修复口径**：定时器容差必须 > 链路物理最坏耗时（跨端往返=任务发布→客户端 15Hz 拍→分片回传
   →收齐→动画→unlock→发布，实测 ~0.9-1.1s）；快模式系数会把容差打折到竞态区——受物理链路
   约束的等待定时器不参与折扣（solver.ts fixed 化，commit 92d1f69）。
   根治方向=事件驱动（被等事件发完成信号驱动推进），容差放大只是止血。
5. **可复用脚本（抄走即用）**：`examples/rubik-3x3-client/.gsts/evidence/3185-fullrun/` 下——

    命令前默念本条。


2. **text 打点对四层签名**：armed→seed→ack(e 值)→dup/tear/wdgate——异常标记
   （tear/repub/wdgate/stale）出现的位置=故障层；全部正常+行为异常=纯逻辑 bug。
3. **apply 帧值=状态机现况快照**：`frames --rec <n>` 里 grep **状态写入复合/节点名**
   （如 fb_mirror_apply），其 IN1/IN2 参数就是当拍写入的变量名+值——3096 会话一条
   命令拿到 `py=0.25 / vy=0.8086 / state=1(Bouncing) @tick161`，状态卡死实锤。
   **通用规律：想看任何变量"现在是什么"，找它的写入节点帧，别从源头追。**

**本次实证的根因类型（错误谱系新条目）**：离散反弹映射 v→e·(g·DT−v) 存在稳定不动点
e·g·DT/(1+e)，若"弹跳瞬态标记"优先级高于"低于阈值→落地分类"，球永卡微弹不动点
（视觉=原地振动≈冻结）。**教训：给状态机新增瞬态标记态时，必须重验每个旧逃逸路径
（尤其阈值逃逸）仍可达——新态的优先级插入点就是不变量破坏点。**

**配套打印纪律（用户 2026-09-03 定则）**：详情日志开启时逐节点数据分毫不差、比 print
更全——**print 节点只留关键状态入口（会话生命周期/任务唤醒/异常标记），高频路径
（每秒多次执行的 onSignal/timer 分支）零 print**；需要完整数据时请用户按图开详情日志，
不要往代码里加打印。

## 零记录图死链回溯 playbook（2026-10-12 足球 1825 复测实证：4 图活 6 图死）

**症状=部分图零日志记录（records --summary 图清单≠预期）或用户操作无反应**——不是
这些图有 bug，是它们的**触发链上游断了**。行为排查 playbook 管"活图卡哪态"，本
playbook 管"图为什么根本没跑"。按序四步，每步只回答一个问题：

1. **图覆盖对比定"死面"**：`records --summary` 列出实际在跑的图 → 与预期图清单对比，
   零记录图集合=死面。再看 perf 确认非超载（每秒负载远低于红线时整链死=链路问题非性能问题）。
2. **挂载表回读**：`gsts assets:mounts list --gil <地图>`——零记录图挂在哪、挂载点
   实体存不存在。**当前图 vs donor 基线挂载逐字对比**：两边都未挂载=终版停用态（设计
   如此，如 09-06/07 演出实测后有意 detach）；donor 挂了当前没挂=重建遗漏（必修）。
3. **触发源因果回溯**：从零记录图往上游找入口事件——`onSignal(x)` 谁发 x？
   `characterSkill start` 谁装配技能？装配器图（whenEntityIsCreated→addCharacterSkill+
   addUnitStatus 类）自己挂载了吗？**死链经常是"装配器未挂载→技能/状态不在→下游全静默"**
   （1836 案：演出装配器未挂载→6132 状态不在→439/437 零施放→phys2 不发信号→sink/render
   零输入，六图连坐）。源头图源码头注释的入口事件类型（timer/onSignal/技能施放）是回溯起点。
4. **用户操作零帧取证**：症状是"点了没反应"时，在操作时段的会话日志里找该事件帧——
   `frames` 按图 grep 事件名（如 whenTabIsSelected）。**零帧=事件根本没到图**（tabBar
   事件链断），有帧但无后续=图内逻辑问题。别先查物理/逻辑层——1835 案 265 次 timer 循环
   全正常但 whenTabIsSelected 零帧，直接排除图内逻辑嫌疑。

**donor 对照的注意**：donor 是"终版快照"不是"理想态"——终版可能本身停用了某链
（1836 在 donor 也未挂载）。**对照只回答"差异是不是重建造成的"，不回答"该不该挂"**——
挂回与否要回溯设计意图（票据/BOARD/源码注释）后由用户裁决。

**修复验证口径**：挂载/槽修复后用户复测，新会话日志里死面图应出现记录、操作事件应
出现帧——日志形态变化本身就是验收信号（仍需行为层确认最终效果）。

## 性能分析 playbook（2026-08-20 魔方性能优化实证，复用标准命令）

目标：量化"每次操作/每 tick 的真实执行性能 = **单次负载 × 执行次数**"，并定位**被踢关键指标 = 每秒负载**。
**首选 `perf` 子命令**（一步到位）：

1. **会话全景 + 每秒负载（首选，2026-08-21 升级）**：
   ```bash
   gia_log.py <日志.gia> perf --gil <地图.gil> --compare <优化前.gia> 2>/dev/null
   ```
   输出：
   - **每秒负载表**：按记录字段 f3（会话内已过秒数）分组，帧数/总负载/均负载按降序 TOP + 时间序峰值；
     **这是"1秒内平均负载过高被踢"的直接指标**。
   - `--sec <n>`：查看指定秒的节点链明细，定位该秒内是哪些节点把负载推高（如整体转 orbit2 8 次×35 负载）。
   - 每记录：秒 / 帧数 / 总负载 / 均负载（找大记录与重复模式：~380=点击、~963=面转、~2605=整体转）。
   - 节点链 TOP（次数 × 总负载，**一眼看出真实热点**）。
   - `--compare`：逐记录 + 逐秒 Δ 帧/Δ 负载。
2. **单记录帧明细（需要具体值/时序时）**：`frames --gil <地图> --rec <n>`——帧已标注**完整嵌套节点链**
   （`复合:A > 复合:B > 节点X`），配合 `--contains <节点名>` 定点过滤；load= 字段看单帧负载。
3. **一次完整操作帧预算**：perf 每记录帧数求和（如 28 点击 + 963 面转 + 477 视觉 + 7×174 块事件 ≈ 2800）；
   优化前后同操作对比（perf --compare 直接给 Δ）即量化收益。
4. **`--compare` 按 rec 对齐，只适用于相同操作序列**；两轮操作组合不同（如一轮整体转、一轮打乱+面转）时，
   自动 Δ 会误导——按操作类型手工抽同类记录（face/whole/afterTurn）再比（2026-08-20 魔方优化轮实证）。
5. **滚动窗口定位被踢（2026-08-21 3×3 魔方实证）**：1 秒峰值更高不一定被踢（旧日志 9,439 未踢），
   要看 **3s/5s/10s 连续负载窗口**——新日志 10 秒窗口 34,180 > 旧日志 28,938 才是被踢分水岭。
   分析时用 `perf` 每秒负载表手工累加滚动窗口，或写一次性 python 对 f3 秒桶做滑动和。

**典型热点形态**（优化目标模板）：
①复杂链输出被 ≥2 处消费 → **物化到变量**（set 后 get 读回）只付读变量负载（魔方 vel1 实证：块事件 -14 帧/事件）；
②事件回调里对每个候选实体做位置读取+层判断 → 改逻辑层表数据直接确定命中（turn_lookup 改造）；
③简单节点（GetVar load=2）被多处消费 → 共享引用只减节点**不减负载**（exec 链实测无效，纯数据复合有效）；
④跨图共享状态在**每个定时器事件**里重复 `syncShared`（GetCustomVariable+SetNodeGraphVariable 链每 tick 跑）
  → 面转 16 次/整体转 52 次重复同步，单次转动负载 ~5000-10000；改成**每次操作首个事件同步一次**
  （`base==0 && seq==0`），后续事件直接用图变量（2026-08-21 3×3 魔方实证）。

## 高频链路/同步率判读 playbook（2026-09-03 足球 E2 判负沉淀，3129/3130/3131 实证）

适用：跨端"每施放→计算→回传→服务端应用"链路的频率/负载/丢拍量化（20008 客户端图 + 服务端镜像回写）。

- **逐记录事件标记法（勿按行数计数）**：同图每次调用帧序相同（如 P 发送恒在 frame[475]），
  行数=记录数×重复。按帧流 `=== recN:` 头分组，每记录只记事件有无。事件签名：客户端入口记录=施放；
  P/T 发送=`IN0:String=P/T`；垃圾 P=同行含 `nan` 或 `None=?`；服务端 P 到达=`复合:监听信号 (1610612775)`；
  服务端应用=`复合:fb_mirror_apply`；echo=1610612772 监听。
- **records 秒映射坑**：`gia_log.py records` 输出是 Python repr 非 JSON；f3 是裸键 `3: N`（无引号），
  取秒用正则 `\b3:\s*(\d+)`，缺省=0。**f3 为整秒粒度，不支持亚秒送达直测**——0.08s 送达常数用
  "到达受限模型"间接自洽：apply 间隔 ≈ 有效到达 gap + 0.08。
- **会话分阶段判读**：先出每秒直方图再选稳定窗口（贴球 A / 密集带球 B / 停球空转），勿用整会话均值
  （3131 活动均值 6.1Hz 会掩盖 B 段 8.0Hz）。
- **垃圾 P 判读**：tick=None + Vector nan（如 (nan,0.0,nan)）= 镜像空读/撕裂快照；服务端帧层 0 nan=
  发送侧即被拒——用户侧"引擎节点异常（如向量归一化输入 0 向量）"即此形态的表现。
- **闭环锁步模型**：客户端须见服务端镜像 tick 回写才发新版本 → apply≈1/(2×送达+处理)；E2 实测 ~8Hz
  天花板。目标 >10Hz（如 20Hz 同步）必须打破锁步（原生写/直驱），在原链上提频无效。
- **详情日志体积预算**：20008 每施放全算 ~25KB/拍，80/s≈2MB/s 会触发引擎负载踢出；高频实验前先降
  详情配给或用 `gia_log_activity.py` 粗测体积桶，勿整轮全开。
- 现成脚本：`scripts/gia_log_event_mark.py`（客户端帧流逐记录事件标记，stdin=帧流）；服务端侧标记与
  汇总方法见复盘 `docs/game-engine-knowledge/retrospective-2026-09-03-e2-gate-open-negative.md`。
