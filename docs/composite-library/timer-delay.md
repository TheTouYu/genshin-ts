## 用途

时间驱动玩法的骨架：创建定时器、延时执行、全局计时器（Update）、间隔动作。

## 通用方法论（提炼）

1. **定时器封装 = Start Timer + When Timer Is Triggered + 名字匹配**：`Start Timer` 启动定时器，`When Timer Is Triggered` 监听触发，`Equal` 判断「触发的定时器名 == 我启动的定时器名」。**定时器名是唯一标识，必须不重复**（作者反复强调「确保定时器名称不会重复」）。
2. **延时执行 = 定时器 + 触发后继续**：`1073741849` 就是「等待一段时间后执行后续逻辑」，本质是定时器触发后把控制流交给后续节点。**这是 `setTimeout` 在节点图里的等价物**。
3. **全局计时器 Update 是「帧循环」的替代**：节点图没有 while 循环，作者用「关卡实体挂载全局正计时器 Update + 图变量 time」实现「每帧/每 N 秒执行一次」。**这是实现持续检测（如玩家退出检测、范围检测）的标准套路**。
4. **间隔动作 = 全局时间 + 减法算间隔**：`1073741851` 用「当前全局时间 - 上次记录时间」算出间隔，达到阈值就执行动作。**「记录上次时间 + 算差值」是通用的节流/间隔模板**。
5. **定时器名用 Data Type Conversion 生成唯一名**：多块并发注册定时器时，用 `dataTypeConversion(i, 'str')` 把块索引转成唯一定时器名（如 '0'..'7'），避免冲突（与 `composite-usage-guide.md` 模式 A 一致）。

## 复用提示

- 「定时器封装」和「延时执行」是最常用的两个，几乎每个玩法都要。
- 「全局计时器 Update」套路是**持续检测类玩法**（玩家退出、范围检测、状态轮询）的基础，但要注意**负载**：作者在 1610612739 注释里明确「更新间隔建议 1s，负载约 50ms；最快 0.06s 负载 800ms」——**间隔越短负载越高，要按需权衡**。
- 定时器名冲突是高频 bug，复用前先确认目标实体上没有同名定时器。
