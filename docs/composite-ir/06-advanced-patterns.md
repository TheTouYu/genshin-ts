# 高级复合模式

> 状态：已验证
> 来源：真实 GIA 验证（实用/log系统.gia + 复杂gia/物理运动.gia + 弹球.gia + 传球.gia）
> 最近校验：2026-07-06
> 适用范围：真实 GIA 逆向高级模式；与 gsts 当前实现差异需单独标注。

覆盖：`实用/log系统.gia`（90KB, 48 CompositeDefs）和 `复杂gia/物理运动.gia`（118KB, 50 CompositeDefs）中发现的新模式和复杂结构。

## 1. structureDef（which=29）— 结构体类型注册表

`log系统.gia` 中发现一种全新的 accessory 类型——**structureDef（which=29）**，用于定义 struct 数据类型的字段结构。

```json
{
  "which": 29,
  "structureDef": {
    "def": {
      "genericField": { "vars": [ /* 字段定义 */ ] },
      "connectField": { "vars": [ /* 字段定义 */ ] },
      "structName": "字符串超列表",
      "classBase": 1,
      "index": 10,
      "itemCount": 11
    }
  }
}
```

**关键字段**：

| 字段 | 含义 |
|------|------|
| `genericField.vars` | 字段定义列表 |
| `connectField.vars` | 连接器字段定义（与 genericField 一致） |
| `structName` | 结构体名称 |
| `index` | 结构体索引 |
| `itemCount` | 字段数 + 1（从 2 开始计数） |
| `classBase` | 基础类（1=IdBase） |

**字段定义（var 条目）**：

```json
{
  "name": "列表1",
  "name2": "列表1",
  "type": 11,        // StringList
  "index": 2         // 从 2 开始（0/1 为系统预留）
}
```

### structureDef 与 relatedIds

structureDef 通过 `relatedIds` 聚合所有操作该 struct 类型的 CompositeDef：

```
structureDef (id=1077936139)
  ├── relatedIds → 拼装结构体 ×4 (10输入→1输出)
  ├── relatedIds → 拆分结构体 ×4 (1输入→10输出)
  └── relatedIds → 修改结构体 ×1 (22输入→0输出)
```

这意味着一个 struct 类型在 GIA 中由三部分构成：
1. **structureDef** — 类型注册表（定义字段）
2. **拼装/拆分/修改 CompositeDef** — 操作定义
3. **调用处的数据连线** — 运行时数据流

**ID 特征**：`id.type = 15` — struct 类型使用独立的 ID 命名空间。

## 2. Struct 三操作复合

### 2.1 拼装结构体（Assemble）

将多个字段值合并为一个 struct 值：

```
拼装结构体 (graphId=0, 内置)
  inputs:  列表1~列表10  (10个 string list)
  outputs: 字符串超列表  (1个 struct)
  0 InFlow, 0 OutFlow（纯数据复合）
```

4 个实例（1073742328, 1610612832, 1610612843, 1610612845）共享完全相同的接口签名。

### 2.2 拆分结构体（Disassemble）

与拼装相反，将 struct 值拆分为多个字段：

```
拆分结构体 (graphId=0, 内置)
  inputs:  字符串超列表  (1个 struct)
  outputs: 列表1~列表10  (10个 string list)
  0 InFlow, 0 OutFlow（纯数据复合）
```

4 个实例（1073742327, 1610612839, 1610612844, 1610612846）。

### 2.3 修改结构体（Modify）

选择性地修改 struct 中的特定字段：

```
修改结构体 (graphId=0, 内置)
  inputs:  22 个！(超列表 + 修改对象 + 列表1~10 + 是否设置_列表1~10)
  outputs: 0
  1 InFlow, 1 OutFlow（有执行流）
```

每个字段都有一个对应的"是否设置_列表N"布尔值来控制是否修改该字段。

## 3. 多 OutFlow 复合

### 3.1 异步迭代（5 OutFlow）

`log系统.gia` 中最复杂的 exec 流复合：

```
异步迭代
  inflows[2]:  入口(pi=1024), 继续(pi=1026)
  outflows[5]: 继续(pi=1712), 1(pi=1048), 2(pi=1049), 3已迭代(pi=1033), 4(pi=1050)
  inputs[2]:   请使用唯一命名(pi=1027), 初始值(pi=1032)
  outputs[1]:  迭代值(pi=1025)
  impl nodes:  8 个（含 1 个嵌套 composite 调用）
  compositePins: 12 条
```

impl 节点构成：
- node[1] `kind=22001` — 嵌套调用"顺序执行"复合
- node[25,26,28,30] `kind=22000` — adition/比较/列表操作
- 同一 InParam 通过 compositePins 路由到 **3 个内部节点**

### 3.2 条件branch（5 OutFlow）

```
条件branch
  inflows[1]:  入口
  outflows[5]: 5 个命名出口
  inputs[4]:   4 个条件输入（来自切换开关和运算结果）
```

### 4.2 条件branch（多条件分支）

```
条件branch (1 InFlow, 4 InParam, 5 OutFlow)
  impl 节点: 4 个 Sequence/Branch (nodeId=2)
  compositePins: 10 条（4 个条件的路由）
  outflow[0..3] = "是"（分别对应 4 个条件）  
  outflow[4] = "否"（都不满足时）
```

每个 InParam 路由到不同的内部 Sequence 节点，每个 Sequence 对应一个独立的分支条件——实现了一个**多条件判断网关**。

## 5. 数据驱动架构

`log系统.gia` 的主图采用**数据驱动**架构，而非执行流驱动：

- event 执行流非常简单（只连到 1 个节点）
- 14 个复合调用之间通过 **23 条数据连线** 互联
- 复合调用节点通过数据连线触发，而非 exec 流串行

```
数据流拓扑核心：
  切换开关 ──→ 条件branch (4条输入)
  切换开关 ──→ [运算]多次或运算 (3条输入)
  切换开关 ──→ 翻页设置i (3条输入)
  日志储存器参数 ──→ (信号发送器)
  node#316 ──→ 多个目标 (数据转发枢纽)
```

## 7. 切换开关——六路分配器模式

> **P0** 来自 `实用/log系统.gia`。已通过真实文件验证（`log系统.gia`，2026-06-29）。

### 模式特征

| 属性 | 值 |
|:----|:---|
| InFlow | 0（纯数据复合） |
| OutFlow | 0 |
| InParam | 1（"输入1", pi=1195, type=int） |
| OutParam | 6（六路命名输出, pi=1197/1309/1200/1201/1348/669） |
| impl 节点数 | 8 |
| 嵌套调用 | 0（纯原生节点） |

### 真实 impl 节点构成

```
[1] kind=22000 nodeId=14  pins=2  — get_local_variable?
[2] kind=22000 nodeId=227 pins=2  — ★ 切换核心（switch/selector 节点）
[3] kind=22000 nodeId=14  pins=2  — 输出选择器
[4] kind=22000 nodeId=14  pins=2  — 输出选择器
[5] kind=22000 nodeId=14  pins=2  — 输出选择器
[6] kind=22000 nodeId=14  pins=2  — 输出选择器
[7] kind=22000 nodeId=14  pins=2  — 输出选择器
[9] kind=22000 nodeId=14  pins=2  — 输入接收
```

其中 `nodeId=227` 是切换核心节点，`nodeId=14` 出现了 7 次作为各输出路径的选择器/分配器。

### compositePins 路由（13 条映射）

```
InParam[0]（"输入1"）→ 节点[1,3,4,5,6,7,9]  ← 输入扇出到 7 个内部节点
OutParam[0]（"日志开关"）→ 节点[2] OutParam[0]  ← 切换核心输出
OutParam[1]（"刷新"）→ 节点[5] OutParam[0]
OutParam[2]（"上一页"）→ 节点[4] OutParam[0]
OutParam[3]（"下一页"）→ 节点[3] OutParam[0]
OutParam[4]（"最后一页"）→ 节点[6] OutParam[0]
OutParam[5]（"删除前面的日志"）→ 节点[7] OutParam[0]
```

实现机制：输入值先分发到所有输出选择器（`nodeId=14`），切换核心（`nodeId=227`）根据输入值决定哪个输出被激活。这是一种**数据选择器 （data selector/multiplexer）** 模式，而非简单的 1:6 分配器。

### 与已知模式对比

| 对比对象 | 相似点 | 不同点 |
|---------|-------|-------|
| 纯数据复合（加法） | 无 InFlow/OutFlow | 切换有 8 个 impl 节点 + 7 路扇出 |
| 多 OutFlow 复合（条件branch） | 多输出 | 条件branch 有 InFlow 执行流；切换纯数据 |
| struct 拆分（拆分结构体） | 1→N 的分发语义 | 拆分是确定性的（所有字段同时输出）；切换是选择性的（根据输入路由） |

### 使用上下文

在 `log系统.gia` 主图数据流拓扑中，"切换开关"是中心数据枢纽，同时驱动 `条件branch`、`[运算]多次或运算`、`翻页设置i` 等多个复合的输入（参见 §5 数据驱动架构）——23 条数据连线中，"切换开关"贡献了约 40% 的数据路由。

## 8. 纯原生复合（零嵌套调用的 impl 图）

> **P0** 来自 `实用/log系统.gia`。已通过真实文件验证（`log系统.gia`，2026-06-29）。

### 模式定义

**纯原生复合** 指 impl 图中**仅有原生节点（`kind=22000`）**，不含任何复合调用（`kind=22001`）的复合定义。所有逻辑通过原语节点组合实现。

### 真实接口数据

| 复合名 | impl 节点数 | InFlow | OutFlow | InParam | OutParam | 嵌套调用 |
|:------|:----------:|:------:|:-------:|:-------:|:--------:|:--------:|
| 控制_十次内While循环 | **14** | 1 | 2 | **2** | **0** | 0 |
| 静态循环0到9 | **13** | 1 | 2 | 0 | **1** | 0 |
| 循环单词执行 | **8** | 1 | 2 | 1 | 1 | 0 |

### 真实 impl 节点分析（以"控制_十次内While循环"为例）

14 个 impl 节点均为 `kind=22000`（原生节点），0 个嵌套调用：

```
[1]  nodeId=19 (set_local_variable)    pins=2  — 初始化计数器
[2]  nodeId=18 (get_local_variable)    pins=2  — 读取计数器
[3]  nodeId=3  (comparison/less_than)  pins=12 — 比较: 计数器 < 10?
[4]  nodeId=2  (Sequence/Branch)       pins=2  — 分支: 条件真假
[5]  nodeId=2  (Sequence/Branch)       pins=2  — 循环体
[6]  nodeId=2  (Sequence/Branch)       pins=2  — 循环体
[7]  nodeId=2  (Sequence/Branch)       pins=2  — 循环体
[8]  nodeId=2  (Sequence/Branch)       pins=2  — 循环体
[9]  nodeId=2  (Sequence/Branch)       pins=2  — 循环体
[10] nodeId=2  (Sequence/Branch)       pins=2  — 循环体
[11] nodeId=2  (Sequence/Branch)       pins=2  — 循环体
[12] nodeId=2  (Sequence/Branch)       pins=2  — 循环体
[13] nodeId=2  (Sequence/Branch)       pins=2  — 循环体
[14] nodeId=2  (Sequence/Branch)       pins=1  — 循环体（最后）
```

**实现机制**：`nodeId=3` 是比较节点（`<` 或 `≤`），比较计数器和循环上限（10）。11 个 `nodeId=2`（Sequence/Branch）节点构成循环体逻辑和分支跳转。这是典型的**原生节点组合实现 while 循环**——无内置 `finite_loop` 节点，完全通过原语组合实现循环语义。

### 与"有限循环"比较

| 维度 | 有限循环（内置节点） | 纯原生循环 |
|:----|:------------------:|:----------:|
| 实现方式 | 单个 `finite_loop` 节点 | 多个原语组合（比较/Sequence/Branch） |
| impl 节点数 | 1 | 8-14 |
| 效率 | 高（内置实现，单节点） | 低（11 个 Branch 节点串联） |
| 灵活性 | 固定循环语义 | 可自定义循环行为 |
| 嵌套调用 | 0 | 0（两者均无） |

## 9. 事件触发器复合

> **P0** 来自 `实用/log系统.gia`。已通过真实文件验证（`log系统.gia`，2026-06-29）。

### 模式定义

**事件触发器复合** 是没有 InFlow（由游戏事件触发，而非执行流驱动）但有 OutFlow 的复合定义。当前文档中涵盖的执行型复合（有 InFlow）和信号复合（which=14）均不覆盖这个模式。

### 已知实例：`[时间]自身定时器触发时`

| 属性 | 值 |
|:----|:---|
| InFlow | **0**（无执行流入——事件触发） |
| OutFlow | 1（触发后激活） |
| InParam | 1（定时器间隔或配置） |
| OutParam | 2（自身实体、定时器实体？） |
| impl 节点 | 待定 |

### 与相关模式对比

| 对比对象 | InFlow | OutFlow | 触发机制 |
|:--------|:-----:|:-------:|:--------:|
| 普通执行型复合 | ✅ ≥1 | ✅ ≥1 | 执行流驱动 |
| 纯数据复合 | ❌ 0 | ❌ 0 | 数据依赖驱动 |
| 信号复合（which=14） | ❌ 0 | ✅ ≥1 | 游戏引擎内置信号 |
| **事件触发器** | ❌ **0** | ✅ ≥1 | 游戏事件（定时器） |
| 有限循环 | ✅ 2 | ✅ 2 | 执行流 + InFlow[1] 继续 |

### 真实 impl 节点构成

`[时间]自身定时器触发时` 有 **3 个 impl 节点**，均为 `kind=22000`（原生节点），**无嵌套调用**：

```
[1]  nodeId=14 (get_local_variable)  pins=2  — 读取定时器名称
[2]  nodeId=2  (Sequence/Branch)     pins=1  — 执行流触发
[15] nodeId=83 (timer_trigger?)      pins=1  — ★ 定时器触发原语
```

### 与纯原生复合的关系

与 §8 的纯原生复合不同，事件触发器复合**没有 InFlow**（由游戏事件驱动，而非执行流驱动）。但其 impl 图同样**仅由原生节点构成**（无 `kind=22001` 嵌套调用）。`nodeId=83` 很可能是游戏引擎提供的定时器触发原语节点。

### 延伸：监听信号也属于事件触发器

`log系统.gia` 中有 **3 个事件触发器复合**：

| 复合名 | ID | InFlow | OutFlow | InParam | OutParam |
|:------|:--:|:-----:|:-------:|:-------:|:--------:|
| [时间]自身定时器触发时 | 1073742222 | 0 | 1 | 1 | 2 |

## 14. I=1/O=0 下沉式复合

> **P0** 来自 `复杂gia/物理运动.gia`。已通过真实文件验证（2026-06-30）。

### 14.1 模式定义

**下沉式复合（Sink Composite）** 是 InFlow≥1 且 OutFlow=0 的复合定义——吸收执行流进入内部，但不将执行流传出。

### 14.2 物理运动实例

| 复合名 | InFlow | OutFlow | InParam | OutParam | impl 节点 | 嵌套调用 |
|:------|:-----:|:-------:|:-------:|:--------:|:---------:|:--------:|
| 设置物理参数 | **1** | **0** | 1 | 0 | **30** | 1 |
| 更新w，v信号版本 | **1** | **0** | 0 | 0 | 5 | 1 |
| 设置额外碰撞重力 | **1** | **0** | 2 | 0 | 6 | 1 |

### 14.3 设置物理参数——最大下沉式复合

30 个 impl 节点 + 1 个嵌套调用，是物理运动引擎中第二大的复合：

**impl 节点构成**：
- 16× nodeId=323 (set_struct_field) — 大量 struct 字段设置
- 11× nodeId=50 (get_local_variable) — 读取变量
- 2× nodeId=75 (get_game_time?) — 时间相关
- 1× nodeId=73 (nothing) — 空节点（占位）
- 1× kind=22001 nodeId=1610612762 (mul3) — 嵌套调用

**compositePins 特征**：
- InFlow 扇出：**10 条映射**（同一 InFlow 路由到 10 个内部节点）
- InParam 扇出：**11 条映射**（同一输入路由到 11 个内部节点）

### 14.4 下沉式复合使用场景

| 场景 | 示例 | 原因 |
|:----|:----|:-----|
| 状态设置 | 设置物理参数 | 一次性初始化参数，执行后不需要下游 |
| 信号触发 | 更新w,v信号版本 | 触发信号发送复合，信号本身是异步的 |
| 定时器操作 | 设置额外碰撞重力 | 启动定时器后独立运行 |

### 14.5 与终端复合的区别

终端复合是**非终端复合**在调用侧的端子化（OutFlow 后续无连线），而下沉式复合是**复合定义本身**就没有 OutFlow：

| 维度 | 终端复合 | 下沉式复合 |
|:----|:-------:|:----------:|
| 定义 | CompositeDef 有 OutFlow | CompositeDef **无** OutFlow |
| 调用侧 | OutFlow 无 connects | 根本无 OutFlow pin |
| 示例 | 01.gia 中的"双分支-user" | 设置物理参数 |
| 灵活度 | 换个位置可变为非终端 | 永远是终端 |

## 15. 信号驱动架构——无 Event 的纯信号触发图

> **新增** 来自 `复杂gia/弹球.gia`（55KB, 33 CompositeDefs, gameVersion 6.6.0）。已通过真实文件验证（2026-06-30）。

### 15.1 架构概览

`弹球.gia`（主图名"丝滑弹球"）展示了一种全新的 GIA 执行模型——**信号驱动架构**。与之前分析的所有 GIA 文件不同，其主图**没有任何 event 节点**，全部执行流由 ClientExec 信号触发启动。

**规模对比**：

| 维度 | 弹球.gia | 物理运动.gia | 传球.gia |
|:----|:--------:|:-----------:|:--------:|
| CompositeDef | 33 | 50 | 14 |
| SignalDef | **8** | **12** | 2 |
| 数据连线 | **72** | 71 | 6 |
| event 节点 | ❌ **无** | ✅ 有 | ✅ 有 |
| ClientExec | **7** | ? | 1 |
| 主图 SysGraph | **36** | ? | 11 |
| 最大 impl 图 | 25（发生碰撞带球） | 54（物理运动控制器） | 9（蓄力时间） |

### 15.2 信号触发机制

弹球.gia 的主图有 **7 个 ClientExec（i1.kind=5）pin** 的节点。关键发现：**全部 7 个节点共享同一个 client signal 索引**（`clientExecNode: ClientSignal[1]`）—— 一个客户端信号扇出到 7 个并行触发点。

这 7 个节点分为两种角色：

| 角色 | 数量 | 类型 | 行为 |
|:----|:----:|:----|:-----|
| **信号发送器** 🚀 | **6** | 发送信号（which=14, kind=1001） | 含 InParam 输入参数（run, v, w, 额外受力），触发后发射信号，**无 OutFlow**——终端信号发射 |
| **信号接收器** 📡 | **1** | 监听信号（which=12, kind=1002） | 接收信号后通过 OutFlow[0] 启动主图执行流——唯一的执行入口 |

```
7 × ClientSignal[1]（同一信号源）
  │
  ├──× 6（发送信号）→ 无 OutFlow，发射信号后结束
  │
  └──× 1（监听信号, node[69]）
       └ OutFlow[0] → InFlow[0] ← 主图唯一的执行流入口
```

**注意**：6 个"发送信号"虽然不驱动本图执行流，但它们通过信号向其他图或系统发送数据（run, v, w, 额外受力 等物理量）。这意味着弹球.gia **既反应信号，也生成信号**。

### 15.3 四种信号生态

弹球.gia 有 4 套完整的信号体系（发送信号 + 监听信号 + 向服务器节点图发送信号）：

| 信号体系 | 参数 | 作用 |
|:---------|:----|:-----|
| `1610612927/2928/2929` | run(v3), v(vec), w(vec), 额外受力(float) | ⭐ **主图 6 个发送信号使用**——物理碰撞/缩放信号 |
| `1610612901/2902/2903` | r(vec), 位置(vec), 参数(string), 事件(string), d(float), 角色实体 | ⭐ **主图 1 个监听信号(node[69])使用**——足球传球信号 |
| `1610612746/2748/2749` | 运动实体, 挂载实体, 参数_1 | 定义但主图未直接使用的信号 |
| `1610612889/2890/2891` | 事件名称(string), msg(string[]), 日志操作(int), i(int) | 日志记录信号 |

### 15.4 0 入边入口——纯反应式图

弹球.gia 中**没有**无入边的可执行节点 —— 这意味着：

- 所有执行流并非独立启动，而是对信号的**反应**
- 74 个主图节点（36 SysGraph + 38 SysCall）构成一个完整的**信号反应网络**
- 数据连线 72 条（与物理运动.gia 71 条相近，但连线拓扑截然不同）

```
执行模型对比：

event驱动（传球.gia）:     信号驱动（弹球.gia）:
  event → branch             信号 → 监听信号 → 执行子图
    ├──→ 职业branch              ├──→ 条件branch → 缩放
    │     ├──→ 前锋              ├──→ 碰撞检测 → 标准碰撞
    │     ├──→ 中锋              ├──→ 定时器循环 → 传球处理
    │     └──→ 后卫              └──→ e技能处理
    └──→ 蓄力时间 → 职业branch
```

### 15.4 监听信号复合——CompositeDef 形态的信号接收器

弹球.gia 中的监听信号虽然不是 SignalDef（which=14），但通过 relatedIds 与 SignalDef 关联：

| 信号名称 | CompositeDef ID | graphId | OutParam 数量 |
|:---------|:--------------:|:-------:|:------------:|
| 监听信号（信号1） | 1610612748 | 0 | 6 |
| 监听信号（信号2） | 1610612928 | 0 | 7 |
| 监听信号（信号3） | 1610612902 | 0 | 9 |
| 监听信号（信号4） | 1610612890 | 0 | 7 |

全部 graphId=0（内置），无 impl 图，但 `relatedIds` 指向对应的 SignalDef（which=14），实现信号→监听复合→执行流的三段式连接。

### 15.5 信号驱动 vs event 驱动——选择准则

| 维度 | Event 驱动 | 信号驱动 |
|:----|:----------:|:--------:|
| 入口 | 单个 event 节点（kind=22000, nodeId=71） | 多个 ClientExec（i1.kind=5） |
| OutFlow fork | event OutFlow → 多个下游 | 每个监听信号独立触发子图 |
| 适用场景 | **线性逻辑**：条件分支、顺序执行 | **反应式**：物理碰撞、多输入事件 |
| 复杂度来源 | 分支深度和嵌套 | 信号数量和子图独立性 |
| 主图连接度 | 低（event → branch → 终端） | 高（多个信号同时驱动数据网络） |
| 示例文件 | 传球.gia、user_edit/所有40文件 | **弹球.gia** |

## 16. 共享复合库——跨文件接口一致的复合定义

> **新增** 来自 `复杂gia/传球.gia` + `复杂gia/弹球.gia` 的交叉对比。已通过真实文件验证（2026-06-30）。

### 16.1 发现

跨文件分析发现：**同一 CompositeDef ID 在不同 GIA 文件中可以有完全相同的结构**。在传球.gia 和弹球.gia 中，存在 11 个共享 CompositeDef，接口全部一致：

| ID | 名称 | I | O | In | Out | impl 节点 | 嵌套 |
|:--:|:----|:-:|:-:|:--:|:---:|:---------:|:----:|
| 1610612902 | 监听信号 | 0 | 1 | 0 | 9 | 0 | 0 |
| 1610612905 | 获取三实体 | 0 | 0 | 0 | 3 | 3 | 0 |
| 1610612956 | e技能特效 | 1 | 0 | 0 | 0 | 4 | 1 |
| 1073742225 | [时间]定时器设置与触发 | 1 | 2 | 4 | 0 | 5 | 0 |
| 1610612834 | 自身实体条件 | 1 | 1 | 1 | 0 | 3 | 0 |
| 1610612909 | 标记e技能释放 | 1 | 1 | 1 | 1 | 9 | 2 |
| 1073742219 | [时间]获取关卡计时器时间(1) | 0 | 0 | 0 | 1 | 2 | 1 |
| 1073742220 | [查询]获取关卡实体 | 0 | 0 | 0 | 1 | 1 | 0 |
| **1610612800** | **条件branch** | **1** | **5** | **4** | **0** | **4** | **0** |
| **1073741912** | **顺序执行** | **1** | **4** | **0** | **0** | **5** | **0** |
| **1610612908** | **职业branch** | **1** | **5** | **0** | **0** | **8** | **1** |

此外，2 个 SignalDef 也跨文件共享：

| ID | 名称 | 传球.gia | 弹球.gia |
|:--:|:----|:--------:|:--------:|
| 1610612901 | 发送信号 | ✅ | ✅ |
| 1610612903 | 向服务器节点图发送信号 | ✅ | ✅ |

### 16.2 与"不同定义"对比

这与之前发现的"同一 ID 在不同文件中可以有不同定义"并不矛盾：

| 模式 | ID 含义 | 条件 | 示例 |
|:----|:-------|:----|:-----|
| **共享库**（接口完全一致） | 编辑器**内建**的通用复合 | 跨文件、同一游戏 | 条件branch、顺序执行、监听信号 |
| **各自定义**（接口不同） | 用户**手动创建**的复合 | 跨文件、不同游戏 | user_edit/two_exec.gia vs two_exec2.gia |

**核心判断规则**：
- 如果同一个 ID 出现在多个 GIA 文件中且接口完全一致 → 这是**内建库**（编辑器预设）
- 如果同一个 ID 仅出现在一个文件中，或跨文件但接口不同 → 这是**用户自定义**

### 16.3 内建复合库的特征

从 11 个已确认的内建复合推导出以下特征：

1. **ID 范围**：`10737418xx` 和 `16106128xx` 两个命名空间——注意 `docs/architecture/composite/ir-representation.md` 中 gsts 编译器的 `CompositeRegistry` 使用 `1610700000+`，而我们 3 个真实文件（共 97 个复合）中**无一**在此空间。这确认了这些文件为**游戏编辑器导出**而非 gsts 生成。
2. **用途通用**：条件分支、顺序执行、定时器、实体查询——这些是"游戏编辑器 DSL"的基元
3. **零或极少嵌套**：4 个零嵌套、5 个 1-2 嵌套——内建复合的实现简单且稳定
4. **impl 图小**：平均 **3.8 个 impl 节点**（vs 用户复合的 8-54 节点）
5. **命名规范**：`[类别]名称` 格式（如 `[时间]定时器设置与触发`、`[查询]获取关卡实体`）
6. **graphId=0 的内置复合**：监听信号无 impl 图

### 16.4 三文件验证扩展

将物理运动.gia 加入对比后，共享复合库的结论更显著：

| 文件对 | 共享 CompositeDef 数 | 接口一致 | 共享 SignalDef 数 |
|:------|:-------------------:|:--------:|:----------------:|
| 传球.gia ↔ 弹球.gia | **11** | ✅ 100% | **2** |
| **全部三文件** | **17**（含系统级：顺序执行、条件branch、时间系列） | ✅ 100% | **0**（物理运动无共享 SignalDef） |

**关键观察**：`1073741912`（顺序执行）和 `1610612800`（条件branch）在所有三个 `复杂gia/` 文件中都存在，且接口完全一致。这两者是最基础的执行控制基元——类似编程语言中的 `if` 和 `;`。

### 16.5 对分析工作流的影响

共享复合库的发现改变了对 GIA 文件复杂度的衡量方式：

| 过去 | 现在 |
|:----|:----|
| 统计 CompositeDef 总数 | **区分"内建"和"用户自定义"** |
| 假设每个 GIA 文件独立 | 识别跨文件共享的内建基元 |
| 关注单个复合的复杂度 | **关注"独特复合"的架构贡献** |

应用示例：弹球.gia 的 33 个 CompositeDef 中，**13 个是内建共享的**（11 CompositeDef + 2 SignalDef），真正独特的用户定义复合仅 **20 个**。这比原始计数（33）更准确地反映了文件的实际复杂度。

## 17. 架构风格分类——GIA 的三种执行模型

> **新增** 基于 `复杂gia/` 全部三个文件的交叉对比。已通过真实文件验证（2026-06-30）。

### 17.1 三文件全维度对比

| 维度 | 传球.gia | 弹球.gia | 物理运动.gia |
|:----|:--------:|:--------:|:------------:|

| 主图名 | "传球" | "丝滑弹球" | "物理运动控制器" |
| CompositeDef | 14 | 33 | 50 |
| 独特 CompositeDef | ~3 | ~20 | ~50 |
| SignalDef | 2 | **8** | **12** |
| event 节点 | ✅ | ❌ | ✅ |
| ClientExec | 1 | **7** | ? |

| 主图节点 | 24 | **74** | ? |
| SysGraph（复合调用） | 11 | 36 | ? |

| 复杂度等级 | ⭐ 低 | ⭐⭐ 中 | ⭐⭐⭐ 高 |

### 17.2 三种架构风格

基于全维度对比，GIA 文件可以归入三种架构风格：

#### 类型 A：事件驱动逻辑

**代表**：传球.gia、user_edit/全部 40 个文件

```
event → OutFlow fork → 条件/顺序/分支 → 终端复合
                          ↓
                      纯数据复合 ← 数据连线
```

**特征**：
- 有 event 节点，执行流为主要控制结构
- 数据连线少（<10），逻辑集中在分支和条件中
- 复合调用以终端为主（OutFlow 不续接）
- 适用：简单游戏逻辑、条件判断、UI 操作

#### 类型 B：信号驱动反应式

**代表**：弹球.gia

```
多个信号 → ClientExec → 监听信号复合 → 并行子图
                ↓                          ↓
             (触发)                 纯数据计算（碰撞/缩放/足球属性）
```

**特征**：
- **无** event 节点
- 多个 ClientExec 信号触发点（≥5）
- 数据连线密集（50+），形成反应式数据网络
- 复合调用以非终端为主（执行链延续）
- 适用：实时物理模拟、多输入响应、游戏内物理系统

#### 类型 C：纯数据计算流水线

**代表**：物理运动.gia

```
event → 信号输入 → 物理运动控制器（54节点编排器）
                      ↓
                  aerodynamics → friction → 合力 → 分力 → 更新v,w
```

**特征**：
- 有 event 节点，但 event 仅起触发作用
- **纯数据复合占主导**（>50%），执行型复合较少
- 数据连线极密集（70+），形成计算流水线拓扑
- 复合组合体嵌套（向量运算族 4 层嵌套）
- 适用：科学计算、物理引擎、数据处理管道

### 17.3 风格间关系

三种风格不是互斥的——一个大 GIA 可以混合多种风格（物理运动.gia 同时有 event 触发 + 信号输入 + 纯数据流水线），但通常有一种主导风格：

```
事件驱动逻辑 ──→ [加入信号触发] ──→ 信号驱动反应式
       │                                  │
       └── [加入大量纯数据复合] ──────────┘
                          │
                          ▼
                   纯数据计算流水线
```

| 风格 | 复杂度增长路径 | 典型数据连线数 |
|:----|:--------------|:-------------:|
| 事件驱动 | event → branch → 更多 branch | < 20 |
| 信号驱动 | signal → 更多信号 + 并行子图 | 20-80 |
| 计算流水线 | 计算链加长 + 组合体嵌套加深 | 50-150 |
