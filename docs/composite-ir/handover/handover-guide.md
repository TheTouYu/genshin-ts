## 1. 为什么需要这个指南

在本项目的一次典型交接中，接手者遇到了以下问题，而这些都是文档本可以避免的：

| 问题 | 后果 | 根因 |
|------|------|------|
| 复合 capture 节点被 `implNodes` 排除，多 OutFlow 场景子节点孤立 | 花费 30+ 分钟定位、3 轮修复 | 文档未描述 `execNodes` vs `eventNode` 的区别 |
| BFS 放置的节点被 data 布局覆盖 | 又花 20 分钟排查坐标异常 | 文档只说了算法名称，未说明执行阶段（stages）和覆盖规则 |
| 不知道 `leaf()` 需要和 `fork()` 配合使用 | 写了错误的多 outflow 代码 | API 有 `fork` 示例但没有 `leaf` 示例 |
| 主图不生成多 outflow 终端节点 | 以为是自己代码写错了 | 文档没有**标记已知差距** |
| 调试时 dist 缓存了旧代码 | DEBUG 日志不生效，以为是代码没改对 | 文档未描述 require 缓存和 clean rebuild 的坑 |
| 运行 `npm test` 后被 stash 冲掉了修改 | 全部源代码修改丢失，重做 | 文档没有提测试套件会先 clean dist |

**教训：交接文档的目标不是「记录已完成的事」，而是「让下一个人能独立工作」。**

---

## 2. 交接文档的核心目标

```
接手者拿到文档后，应该能回答这三个问题：
1. 我要做什么？   →  任务范围、优先级、完成标准
2. 我该怎么做？   →  步骤、工具、API 用法
3. 哪些会坑我？   →  已知问题、隐藏约束、未完成的设计决策
```

如果接手者遇到一个意外行为，在文档中找不到解释，那就是文档缺失。

---

## 3. 必须包含的 7 个模块

一个交接文档必须包含以下模块，缺一不可：

```
┌─────────────────────────────────────────────────┐
│  1. 背景                    为什么做这个任务      │
│  2. 当前状态                已做了什么 / 参数      │
│  3. 工作方法论              步骤 / 工具 / 标准     │
│  4. 关键概念 / API          接手者必须知道的概念    │
│  5. 进度追踪                已完成的 / 排期         │
│  6. 已知问题                半成品 / 隐患 / 边界    │
│  7. 文件索引                去哪里找代码             │
└─────────────────────────────────────────────────┘
```

以下逐一说明每个模块的写作要点。

---

## 4. 每一模块的写作指南

### 模块 1：背景

**目的**：解释「为什么要做这件事」，让接手者理解优先级和取舍。

**写作要点**：
- 一句话说明业务目标
- 说明约束条件（编辑器如何工作、哪些场景需要关心、哪些不关心）
- 指向外部资料（链接到更详细的分析文档）

**检查清单**：
- [ ] 接手者读完能回答「这件事的输入和输出是什么」
- [ ] 接手者读完能判断「这个行为是不是预期的」

**反面案例**：
```
编辑器里每个窗口只显示当前复合的直接子节点。
布局无关紧要，几节点随手拖都能对齐。
```

接手者可能困惑：「那为什么还要做布局？」应该补充：自动布局是为了保证小图（≤8节点）紧凑整齐，在批量生成时不需要手动拖拽。

---

### 模块 2：当前状态

**目的**：让接手者立即知道「已经做到了什么程度」，避免重复劳动。

**写作要点**：
- 列出已完成修改的清单（文件 + 改动说明）
- 列出所有配置参数和常量（原文贴出）
- 明确标注「哪些是刚校准过的」

**检查清单**：
- [ ] 接手者读了参数表就能理解布局计算的基本单位
- [ ] 每个常量都有注释说明其含义

**这次踩的坑**：文档写了 `LAYOUT_EXEC_H_STEP = 350` 但没有说明 `branchGap = rowHeight * 0.6 = 168` 和 `LAYOUT_EXEC_V_STEP = 150` 是两套不同的 Y 步进，分别用于主图和 impl 图。接手者需要知道这两个常量的区别。

---

### 模块 3：工作方法论

**目的**：写出「一份接手者可以照着执行的 SOP」。

**写作要点**：
- 步骤要精确到命令行（复制粘贴就能跑）
- 说明判断标准（"间距合理" 的标准是什么）
- 常见失败的诊断方法

**检查清单**：
- [ ] 所有命令行都已经验证过能跑通
- [ ] 说明了「编译成功 ≠ 正确」，需要对比参考文件
- [ ] 包含了调试技巧（比如加 DEBUG 日志的步骤）

**这次踩的坑**：文档没有说明 `require.cache` 会导致 dist 文件缓存在 Node.js 进程中。用 `npx tsx` 而不是 `node` 运行可以避免这个问题，但接手者如果不知道这个区别，会浪费大量时间怀疑代码没有被编译。

修复方式：在调试步骤中加上一条：

```
注意：如果修改了 composite.ts 等文件后重新运行，要确保 build 成功。
可以用 grep DEBUG dist/xxx.js 验证新代码是否真的编译进了 dist。
```

---

### 模块 4：关键概念 / API

**目的**：解释接手者需要理解的核心抽象和 API 用法。

**写作要点**：
- 不要只列 API 签名——要给出**完整可运行的例子**
- 说明 API 之间的相互关系和调用顺序
- 对内部抽象（`execNodes`、`eventNode`、`captureNodeId`）给出清晰的对比表

**检查清单**：
- [ ] 每个 API 至少有一个最小化示例
- [ ] 示例应该包含**常见的错误用法**和正确的替代
- [ ] 内部数据结构的关键字段有解释（不仅是类型定义）

**这次踩的坑**：复合节点的 `implNodes` 只包含 `execNodes + dataNodes`，而 capture 入口节点是 `eventNode`。接手者不知道 `eventNode` 的存在，自然也不知道它被遗漏了。

应该用表格对比：
```
┌────────────────┬───────────────┬──────────────────────────┐
│ 字段           │ 来源          │ 是否在 implNodes 中       │
├────────────────┼───────────────┼──────────────────────────┤
│ eventNode      │ startCapture  │ ❌ 被排除                │
│ execNodes[0]   │ 第一个注册点  │ ✅ 是                    │
│ dataNodes      │ data 类型注册 │ ✅ 是                    │
└────────────────┴───────────────┴──────────────────────────┘
```

另一个例子：`fork` API 有示例但 `leaf` 没有。接手者需要知道 `fork` + `leaf` 的组合才能创建多 OutFlow 复合。

---

### 模块 5：进度追踪

**目的**：让接手者立刻知道「该从哪儿继续」。

**写作要点**：
- 用表格列出已完成和待做的对照
- 优先级推荐（哪个先做、哪个后做）
- 标注每个待做项的依赖和预估难度

**检查清单**：
- [ ] 已完成的用 ✅ 标记，对完成状态有客观标准
- [ ] 待做项有明确入口（参考文件名、gsts 测试文件名）
- [ ] 标注了关键缺口（如「当前不支持主图多 outflow 终端」）

**这次踩的坑**：只写了「继续对比 user_edit 文件」，但没有指出**对比完成的标准是什么**。"间距合理" 过于模糊。应该明确：无审计警告、拓扑一致、单维间距偏差在 50px 以内。

---

### 模块 6：已知问题

**目的**：坦诚说出「哪些地方还没做好」，让接手者遇到问题时知道这是预期的还是 Bug。

**写作要点**：
- 分两类：**已知半成品**（有计划做）和**已知 Bug**（需要修）
- 每项标注**影响范围**和**触发条件**
- 如果暂时不修，给出原因和 workaround

**检查清单**：
- [ ] 接手者遇到异常行为时能在这里找到解释
- [ ] 接手者不会把已知半成品当 Bug 去修

**典型遗漏**（本次踩坑）：
- 主图在复合调用有多 outflow 时不生成终端节点 → 这是已知缺口，但没有在文档里提，接手者以为是自己写错了
- `computeImplLayout` 的数据节点布局会覆盖 BFS 放置的坐标 → 这也是个潜在的 Bug 模式，应该预见到

---

### 模块 7：文件索引

**目的**：让接手者能快速跳转到需要修改的代码。

**写作要点**：
- 每个文件标注具体用途（不是文件名就够）
- 标注关键函数名和行号范围（行号在 diff 中易变，但至少给出函数名）
- 标注哪些文件是你这次新加的、哪些是改过的

**检查清单**：
- [ ] 接手者能根据报错的文件路径反查到这里找到上下文
- [ ] 新增文件的用途在索引中有说明

## 5. 容易遗漏的危险信号

以下信号说明文档有缺口，接手者会在这里卡住：

### 🔴 算法阶段不明确
```
computeImplLayout 只有简单 BFS + 终端节点处理
```
问题：BFS 之后还有数据节点布局，而这个布局**会覆盖 BFS 的位置**。文档没说明执行顺序和覆盖规则。
修复：用伪代码写出算法阶段：

```
function computeImplLayout(nodes, edges):
  Stage 1: BFS exec flow -> 放置 entry 和所有 exec 子节点
  Stage 2: 终端节点 -> 放置链末节点（已 BFS 放置的跳过）
  Stage 3: 数据节点 Kahn -> 按深度/行放置（⚠ 会覆盖 Stage 1 的坐标）
```

### 🟡 内部字段不说明
```
def.captured = { execNodes: flow.execNodes, ... }
```
问题：接手者不知道 `flow.eventNode` 的存在，不知道 `execNodes` 不包含入口节点。
修复：用表格对比所有字段，说明包含和不包含的内容。

### 🟡 API 只有签名没有组合用法
```
fork(...branches: Array<() => void>): void
```
问题：只有单 API 说明，没有 `fork` + `leaf` 组合示例。
修复：给出反面示例和正确示例。

### 🟡 已知差距未标记
```
参考文件有 2 个终端，但 gsts 输出只有事件和复合调用
```
问题：接手者会发现输出和参考不一致，花时间排查一个已知问题。
修复：在进度表里标注「⚠ 主图多 outflow 终端未实现」。

### 🟡 构建系统的隐藏行为
```
npm run build -> tsc -> postbuild
```
问题：`prebuild` 会先 clean dist，所以 `npm run build` 之后所有 GIA 文件都消失了。`npm test` 也是。接手者如果在 build 之后检查 GIA，会惊讶地发现文件不见了。
修复：在注意事项中明确说明 prebuild 的行为。

## 6. 反例与正例

### 反例：只说结果不说原因

```
布局常量校准至 columnWidth: 350, rowHeight: 280, maxColumns: 8
```
接手者会问：为什么是 350 不是 300？为什么 maxColumns 是 8？

### 正例

```
布局常量校准至 columnWidth: 350, rowHeight: 280, maxColumns: 8

- columnWidth 350：基于 3 个复杂 GIA 分析，编辑器手动间距典型值 335-414，350 取中
- maxColumns 8：主图最长链 ≤8 节点，超过时换行；小图不需要，大图兜底
- rowHeight 280：编辑器节点高度约 200px + 间距 ≈280
- branchGap = rowHeight * 0.6 = 168：多分支 Y 偏移（主图用）
- LAYOUT_EXEC_V_STEP = 150：impl 图分支 Y 偏移（比主图紧凑）
```

### 反例：只列成功步骤不列故障排查

```
4. 对比：npx tsx tests/composite/dump-nodes.ts dist/tests/layout-xxx.gia
```

### 正例

```
4. 对比：
   ```bash
   npx tsx tests/composite/dump-nodes.ts dist/tests/layout-xxx.gia
   ```
   如果 dump 显示的节点坐标都是 (0,0)：
     - 检查 compositePins 中的 innerNodeId 是否指向正确的节点
     - 检查 computeImplLayout 中 dataNodeIds 的过滤条件
     - 加 DEBUG 日志到 computeImplLayout 验证 BFS 是否执行
```

## 7. 维护节奏

交接文档不是一次写完就结束的。每次接手者遇到文档未提及的问题，就应该更新文档。

### 触发更新的时机

| 触发条件 | 操作 |
|---------|------|
| 接手者问了一个文档里没有的问题 | 把问题和答案补充到对应模块 |
| 发现了一个隐藏约束 | 加入「已知问题」或「注意事项」 |
| 修复了一个 Bug | 在「已完成的修改」表中加入，标注影响范围 |
| 新增了一个概念/API | 加入「关键概念 / API」模块 |
| 完成了某个待做项 | 更新「进度追踪」，标注 ✅ |

### 原则

1. **不要只写「已完成」**，还要写「做的时候踩了什么坑」
2. **不要只写 API 签名**，还要写 **「为什么这样设计」**和**「什么情况下会出错」**
3. **不要假设接手者有你的上下文**——把你知道的但你写代码时没有意识到的设计决策写下来

```

### 3. 标记已知缺口

- ❌ 主图多 outflow 复合调用不生成终端节点
