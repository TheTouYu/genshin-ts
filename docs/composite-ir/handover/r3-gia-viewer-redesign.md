## 一、为什么需要重塑

当前工具 (`ascii-layout.ts`) 的问题：

| 问题 | 影响 |
|------|------|
| 2D ASCII 渲染无法处理大 Y 范围 | 传球.gia (2345px) 输出数十页空白行 |
| 不区分事件/复合/数据节点 | 大图无法聚焦 |
| 数据节点产生大量孤立警告 | 干扰信号 |
| 没有复合展开 | 复合调用显示为 raw ID |
| 没有引脚级浏览 | 无法追溯数据链路 |

## 四、已知设计约束（从预览确认）

以下原则已在 `r3-ascii-view-preview.md` 中提出，待 step-1 验证后确认或修改：

### 4.1 节点统一模型（待确认）

```
节点 = { 名字, ID, 控制流入?, 控制流出?, 数据流入?, 数据流出? }
```

所有节点 4 个维度：控制流入、控制流出、数据流入、数据流出。空的维度不显示。

### 4.2 命名规则（待验证）

| 节点类型 | 显示名 | 来源 |
|---------|-------|------|
| **事件起点** | `When Entity Is Created` | NODE_ID/EVENT_IDS |
| **复合调用** | `复合:监听信号` | `accessories[i].compositeDef.def.name` |
| **标准节点** | `Multiple Branches` | NODE_PIN_RECORDS |
| **未知节点** | `sys({nodeId})` | 回退 |
| **孤立起点** | `[孤立起点] Get Self Entity` | 非事件但为 exec 根 |
| **复合引脚** | `前锋`/`中锋`/... / `出口N` | def.outflows[i].name / 自动 |
| **标准引脚** | `出口N` / `执行流入` | 自动编号 / 固定 |

### 4.3 exec 链分类（待确认）

```
if nodeId ∈ EVENT_IDS → "事件:..."
else if isExecRoot → "[孤立起点]..."
else → 普通节点
```

EVENT_IDS = {71, 72, 83, 91, 92, 253, 304, 385, ...}

### 4.4 视图体系（框架）

| 视图 | 含义 | 范围 |
|------|------|------|
| **summary** | 范围内元素概要 | 文件/事件/复合 |
| **tree** | exec 拓扑树 | 事件/复合.impl |
| **detail** | 单节点全部信息 | 单节点 |
| **full** | 2D ASCII 精确位置 | 小范围 |
| **trace** | 数据链路追溯 | 参数级别 |

### 4.5 scope 路径体系（框架）

```
gia 文件 .event[0] .chain[2] .composite .impl
gia 文件 .node[7]
gia 文件 .trace .node[7] .inparam[0]     ← 追踪数据来源
```

## 六、你的角色和贡献

这个工具的设计不是 LLM 闭门造车。以下是你独有的价值：

### 你提供的核心输入

| 输入 | 价值 | 时间点 |
|------|------|--------|
| 游戏编辑器实际画面 | 验证/纠正我的 protobuf 推导 | step-1 绘制中 |
| 游戏节点系统的领域知识 | 解释"为什么这么设计" | 全程 |
| 使用场景和操作习惯 | 工具的交互方式该做成什么样 | step-2 设计时 |
| 对输出的审美偏好 | 输出格式（tree vs 渲染 vs 表格） | step-2 |
| 类似工具的使用经验 | 该学什么、该避开什么 | step-2 |

### 协作流程

```
step-1 (绘制传球.gia)
  我: protobuf 解析的全部数据、推导的连线、命名映射
  你: 游戏内观察 → 纠正错误，补充缺失

step-2 (设计工具)
  我: 设计提案、预览输出、技术可行性
  你: 使用场景、交互偏好、验收审核

step-3 (实现)
  我: 代码实现、测试
  你: 功能验收、游戏内端到端验证
```
