# 单任务交接模板

> 状态：当前推荐
> 来源：当前协作实践
> 最近校验：YYYY-MM-DD
> 适用范围：一次会话完成一个明确任务的轮次交接

本文档是新 handover 的默认模板。历史 handover 保持原样，不按本模板回写。

交接文档的目标是让下一位助手以最少上下文立即开始工作。99% 的轮次应只有一个明确任务；如果一份交接需要承载多个无关目标，应拆成多个后续轮次，而不是扩写文档。

建议控制在 80-150 行。正文只保留以下两个主要部分。

---

## 一、下一轮目标

### 唯一目标

> 用一句话写明下一轮要完成的结果，不写本轮过程。

示例：

```text
按真实最小 GIA 修复 composite impl 的 vec3 Local Variable 编码，并生成一个可供游戏验证的文件。
```

### 范围

写清本轮会改什么、不会改什么。最多 3-5 条。

- 要修改的行为或结构。
- 要覆盖的具体文件、节点或场景。
- 明确不处理的相邻问题，防止任务扩散。

### 完成标准

必须是可检查的结果，不写“感觉正确”或“尽量一致”。

1. 自动验证：具体脚本、结构字段或测试结果。
2. 生成结果：目标 `.gia` 路径或其他交付物。
3. 游戏验证：由谁测试、重点检查什么。
4. 提交条件：只有用户确认通过后才提交，或本轮允许自动提交的明确边界。

---

## 二、可用资源与执行边界

### 已验证基线

只写下一轮可以直接信任的当前事实。每条标明证据等级：

- `游戏内通过`：用户已经实际确认。
- `真实 GIA 已验证`：有真实文件和解码证据。
- `自动验证通过`：只有测试或生成结果，尚未游戏确认。
- `待验证`：明确写成假设，不能作为实现依据。

不要复述完整历史。被后续结果替代的失败过程不放在这里，必要时只链接历史 handover。

### 文档资源索引

这里按优先级列出可用文档资源。**列出引用不等于预先加载全文**；下一位助手只在触发条件满足时读取对应小节。每个引用必须同时写明用途、读取条件和建议读取范围。

#### P0：工作细节准则

每轮 handover 默认首先引用：

- [`layout-working-rules.md`](layout-working-rules.md)
  - 用途：协作边界、游戏目录、生成/注入/归档命令、小步验证规则。
  - 何时读：任务涉及真实 GIA、游戏导入、注入、归档、布局调参或用户游戏反馈时。
  - 读取范围：优先读“核心协作规则”“明确最小样本任务的快速路径”“路径速查”，再按需读对应命令小节；不要默认加载全文。

如果任务不属于布局或游戏交互，也应在此位置引用对应领域的工作准则，而不是省略工作边界。

#### P1：当前任务权威资料

列出 1-3 个与唯一目标直接相关的当前文档：

```text
<文档链接>  用途：<解决什么问题>
             何时读：<出现什么问题时读取>
             范围：<具体章节或关键词>
```

常见例子：

- `physics-motion-recreate-guide.md`：查真实物理复合结构和已经确认的 API 写法。
- `raw-control-flow-dsl-quickstart.md`：需要手工控制 InFlow/OutFlow 拓扑时读取。
- `gia-tools-reference.md`：不确定该用哪个 decode/trace/diff 工具时读取；优先使用已配置 `NODE_OPTIONS='--no-deprecation'` 的 npm wrapper。

工具使用约定：

- 执行流优先使用 `npm run trace-exec -- <file.gia> ...`，数据流优先使用 `npm run trace-dataflow -- <file.gia> ...`。
- 解码和结构对比优先使用 `npm run gia:decode`、`npm run gia:inspect`、`npm run gia:compare`、`npm run gia:diff`。
- 使用 `trace-dataflow --composite` 时，节点索引必须来自该复合 impl 图的 `--list-nodes` 输出；主图节点索引、impl-node-index 和 accessory-index 不可混用。
- 布局检查默认使用 `audit-layout.ts`；真实数据驱动 GIA 中无执行流的数据节点不应直接判定为 ORPHAN，需要严格检查时再使用 `--strict`。
- 需要查看复合 impl 布局时使用 `ascii-layout.ts --composite <名称>`；所有上述工具都应先用 `--help` 确认参数，而不是凭记忆猜测。

每个引用都要同时写清用途、读取条件和建议读取范围；读取范围至少给出章节名或关键词，不能只写“按需”。

#### P2：升级调查入口

这些资源只在出现歧义、来源冲突或架构影响时读取：

- `docs/documentation-map.md`：任务超出当前 handover 范围，需要重新路由资料时。
- `docs/documentation-governance.md`：需要判断真实 GIA、当前实现、历史记录和推测的证据等级时。
- 旧 handover：只查历史原因或失败路径，不作为当前 API 教程。

不要写“阅读所有相关文档”。引用应帮助模型按需定位，而不是形成隐性的全量阅读清单。

### 代码与测试入口

使用“文件或函数 -> 用途”的形式，不粘贴大段源码：

工具入口可按以下稳定优先级记录：

```text
Tier 1：trace-exec-flow.ts / trace-dataflow.ts / gia-inspect.ts
Tier 2：decode-gia.ts / gia-compare.ts / gia-diff.ts / verify-composite-gia.ts
Tier 3：ascii-layout.ts / audit-layout.ts / analyze-composite-gia.ts / topology.ts
Tier 4：tests/composite/_dump_*.ts 等专项调试脚本
```

除非任务需要专项字段，否则不要优先选择 Tier 4 调试脚本；具体参数和当前支持范围以 [`gia-tools-reference.md`](../../gia-tools-reference.md) 为准。

```text
src/.../file.ts :: functionName     当前编码入口
tests/.../case.ts                   最小回归
dist/.../output.gia                 当前生成物
```

### 真实样本与比较字段

记录能直接执行的证据：

```text
真实文件：<absolute-path>
目标 composite/node：<name/index>
比较字段：genericId / concreteId / pin kind+index / type / wrapper / connects
```

如果是类型族问题，分别记录：

- 通用实现覆盖范围。
- 自动回归覆盖范围。
- 真实 GIA / 游戏覆盖范围。

单个类型游戏通过不能写成全部类型均已游戏验证。

### 易错点与禁止事项

只保留会直接导致本任务失败的 3-7 条：

- 真实 GIA 与源码推测冲突时，以真实 GIA 为准。
- 不要手改生成目录或 thirdparty。
- 不要把自动验证写成游戏内通过。
- 涉及注入、覆盖、删除、结构歧义或游戏状态时先向用户确认。
- 写本任务特有的隐藏 pin、索引、构建清理等坑。

通用规则只链接 `layout-working-rules.md`，不要在每轮重复。

### 推荐工作流

写成可执行的 5-8 步，每一步只产生一个可检查结果：

1. 读取当前目标；按文档资源索引的优先级和触发条件加载必要小节，引用存在不代表需要加载。
2. 确认真实样本路径，解码并核对目标结构。
3. 编写或更新同构测试。
4. 结构化比较真实与当前 JSON。
5. 修改通用实现或目标复刻代码。
6. 运行针对性验证；共享行为受影响时才扩大回归。
7. 生成候选 GIA。
8. 经用户确认后注入、游戏测试、归档并提交。

常用命令不要整段复制；优先链接工作规则。只把本任务独有、无法从规则中直接得到的命令写在这里。

---

## 不应写入 handover 的内容

以下内容会稀释下一轮注意力，应迁到其他位置：

- 会话时间线、逐次尝试、完整终端输出、完整 diff。
- 已经解决且不会影响下一轮的失败过程。
- 通用 API 教程、架构说明和重复工作规则。
- 大段真实结构清单；可由脚本稳定得到时只写文件、命令和目标名称。
- subagent/agent 状态、模型讨论、探索过程。
- 与唯一目标无关的 TODO。
- “给下一位助手的一句话”等重复摘要；唯一目标本身已经承担该作用。

历史价值需要保留时，放入历史 handover、专题分析文档或 Git 提交；不要塞进下一轮的工作上下文。
