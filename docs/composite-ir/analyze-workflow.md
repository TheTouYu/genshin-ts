## 快速入口

| 你想做什么 | 从哪开始 |
|:---------|:--------|
| **分析新 GIA 文件** | → 从 Phase 0 开始，按顺序执行 |
| **检查我是否在正确的轨道上** | → 调用 `/think-check` |
| **看还有哪些已知问题没解决** | → 见 [todo.md §6（疑点表）](todo.md#6-核验发现物理运动gia-交叉审查) |
| **查某个文档有没有覆盖你的发现** | → 见 [index.md（文件列表）](index.md) |
| **遇到了我之前的错误模式** | → 调用 `/think-check`，技能会加载 memory 中的教训 |

## 工作流结构

工作流由 5 个 Phase 组成。前两个是**强制性的**，后三个有**守卫条件**。

```
Phase 0: 意图声明 _____ 必须执行，不可跳过
  ↓
Phase 1: 快速批判扫描 __ 必须执行，不可跳过
  ↓
Phase 2: 论断核验 ______ 必须执行，不可跳过
  │                          ↕ 如果 FAIL=0 → 停止，不加任何内容
  │                          ↕ 如果 FAIL≥1 → 进入 Phase 3
  ↓
Phase 3: 最小修正 ______ 只修改 Phase 2 发现的错误
  │                          ↕ 每次 edit 前调用 /think-check
  ↓
Phase 4: 自进化 ________ 更新 ①②③④
```

## Phase 0: 意图声明

**守卫条件**：必须先阅读 [index.md](index.md) 和 [todo.md §6](todo.md#6-核验发现物理运动gia-交叉审查)。

**步骤**：

### 0.1 明确目标

回答：拿到这个 GIA 文件，我最想回答的一个问题是什么？

> 如果答案是"描述这个文件的结构"或"看看它有什么新东西"→ 🚩 这是红牌。重新想一个可证伪的目标。
>
> 好目标示例："我想验证现有文档中关于 InFlow 数量的规律是否还成立"
> 坏目标示例："我想看看这个文件有哪些复合节点"

### 0.2 声明预判

回答：现有文档中，我最怀疑哪条论断会被这个新文件证伪？

> 如果答不出来 → 🚩 说明我对现有文档体系不够熟悉。回去读 docs/。
> 如果答得出来 → 写下来。这条预判就是 Phase 2 核验脚本的第一个测试用例。

### 0.3 阅读疑点表

阅读 [todo.md §6](todo.md#6-核验发现物理运动gia-交叉审查) 的"需后续验证的疑点"。如果当前文件能验证其中任何一条，把它加入核验清单。

### 0.4 写下承诺约束

写一句话，例如：
> "在找到至少一个现有文档错误之前，我不会在这轮分析中新增任何文档内容。"

**输出**：Phase 0 的结论应写成一个简短的对话消息，让我和用户都知道现在是什么方向。例如：
> "Phase 0 结论：目标验证 `compositePins` 数量规律，预判物理运动中有超过 7 条映射的复合。"

## Phase 1: 快速批判扫描

运行四件套工具，但目的**不是收集描述**，而是**找线索**。

```bash
# 1. 基本信息 + CPI 校验
npx tsx tools/analyze-composite-gia.ts <file.gia> 2>&1 | head -40

# 2. 覆盖率报告（已知模式分类）
npx tsx tools/coverage.ts <file.gia> 2>&1

# 3. 缺口扫描（启发式线索）
npx tsx tools/gap-scan.ts <file.gia> 2>&1

# 4. 执行流拓扑
npx tsx tools/topology.ts <file.gia> 2>&1
```

**每次扫描时问**：
- 这个工具输出的**哪一行**提示了现有文档可能有问题？
- 工具标记的"疑点"中，哪些是新数据才能暴露的？

> 🔑 不要记录"这个文件有多少个 CompositeDef"（描述），要记录"覆盖率 100% 但 gap-scan 有 32 个疑点"（矛盾信号）。

**检查点 1A**：对比 coverage.ts 和 gap-scan.ts 的输出。
- coverage 说"全部覆盖"但 gap 说"异常大" → 这是文档分类过于粗放的信号
- gap 的线索分布是否集中于某类复合 → 文档对这类复合的描述可能有缺口

> 💡 此时也可以调用 `/think-check` 检查一下是否有在积累描述性内容。

## Phase 2: 论断核验

**守卫条件**：Phase 1 完成。**核心原则**：不在文档中写任何内容，只写脚本验证。

### 2.1 提取可证伪论断

从现有文档中提取所有可以被新数据验证的论断。典型来源：

| 来源 | 论断类型 | 示例 |
|:----|:--------|:-----|
| 01-ir-types.md | 字段/数量规律 | "InFlow compositePins=1 条" |
| 03-validation-basics.md | 模式规律 | "有限循环 7 条映射最完整" |
| 04-validation-signal.md | 信号规律 | "每参数 2 条" |
| 06-advanced-patterns.md | 分类依据 | "事件触发复合 I=0/O=1" |

### 2.2 编写核验脚本

文件命名：`tools/_audit-<文件名>.ts`（下划线前缀 = 临时文件）。

脚本应：
- 对每条论断输出 PASS / FAIL / UNVERIFIED
- FAIL 必须附带"实际数据 vs 文档声称"的对比
- UNVERIFIED 必须说明"为什么无法验证"（例如：缺少对应数据）

### 2.3 解读结果

```
FAIL ≥ 1 → 文档有错误 → 进入 Phase 3
FAIL = 0 且 UNVERIFIED = 0 → 这个文件没有提供新信息 → 停止
FAIL = 0 但 UNVERIFIED > 0 → 部分论断无法用这个文件验证 → 更新 todo.md §6 "需后续验证"
```

**不要因为你花了很多时间分析就强行加章节。如果数据不支持，就不要写。**

---

## Phase 3: 最小修正

**守卫条件**：Phase 2 的 FAIL ≥ 1。

### 3.1 只修正 FAIL

**每一条修正都必须回答**：
- 原来的论断是什么？
- 新数据说了什么？
- 修正后的新论断是什么？

输出到 [todo.md §6](todo.md#6-核验发现物理运动gia-交叉审查) 的"已修正的错误"表。

### 3.2 标记推测

如果我在写修正时加入了一句"我觉得这是因为..."，必须标记。

> 🔮 标记格式：**（推测：这是我的推断，没有数据支撑。）**

### 3.3 每步检查

每执行一次 Edit 前，回答：
- "我刚才 edit 的那句话，有数据支撑吗？"
- "我是否引入了一个新的、未验证的分类/命名/关系？"

> 💡 每次 Edit 前调用 `/think-check`，特别是如果 edit 涉及新增内容而非修正。

## Phase 4: 自进化（更新 ①②③④）

**守卫条件**：Phase 3 完成，或 Phase 2 判定无需修正。

这个 Phase 不是"写文档"，而是"更新反馈系统的四个组件"。

### 4.1 更新工作流文档（①）

问：这次的经历暴露了工作流流程的什么问题？
- 某个守卫条件没有被触发？
- Phase 顺序需要调整？
- 工具输出需要新的解读方式？

→ 如果有，更新本文档的对应 Phase。

### 4.2 更新知识库（②）

- **memory**：写入本次的经验教训（文件前缀 `feedback-loop-lesson-`）
  - 我这次几乎犯了什么错
  - 是什么样的数据/谁纠正了我
  - 下次应该如何避免
- **docs**：如果 Phase 3 修正了文档错误，确保跨引用一致（例如修正了 01-ir-types 后，检查 05-gia-encoding 是否也有相关内容）

### 4.3 更新 /think-check 技能（③）

问：这次的经历能否让 /think-check 下次更好地拦截跑偏？
- 如果我的错误模式不在技能的【已知推测类型】或【危险信号】表中 → 加上去
- 如果 4 个检查问题没有覆盖这次的问题 → 修改【检查序列】

### 4.4 更新 todo.md（为④服务）

问：有哪些疑点需要记录，方便你和我在会话中快速定位？

更新 [todo.md §6](todo.md#6-核验发现物理运动gia-交叉审查) 的"需后续验证的疑点"表，或创建一个新的发现记录。

## 常见错误模式

基于过往分析的 memory 记录，以下是 /think-check 初始化时加载的已知错误模式：

*（随着每次分析增长——参见 memory 中的 `drift-pattern-*` 记录）*

| 模式 | 特征 | 预防 |
|:----|:-----|:-----|
| 描述陷阱 | 拿到新文件就统计"有多少个 X"，而不是"X 的什么属性与文档矛盾" | Phase 0 强制目标声明 |
| 章节扩张 | 看到新模式就加新章节，而不是先核验现有章节 | Phase 2→3 守卫条件 |
| 推测命名 | 给复合的功能起名（"角色状态信号"） | 检查点 3A |
| 孤立文档 | 修改了 01-ir-types 但没有更新 05-gia-encoding 的对应描述 | Phase 4 要求跨引用检查 |
