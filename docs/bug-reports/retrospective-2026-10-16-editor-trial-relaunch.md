# 完整复盘：千星编辑器「试玩归来再试玩」双病（2026-10-16）

> **范围**：2026-10-16 ≈19:00–22:40，原神 Linux（wine 兼容层）下官方 UGC 编辑器 BeyondEditor 的两个独立故障。
> **视角**：本会话（ds，宿主侧白盒取证 + 工具化）与并行会话（glm，行为/换药线）双线；用户为唯一验收人。
> **证据**：`.scratch/ys-*.log`（抓包/采样/NLog/验收器）、`~/.ys/BeyondAssets/BeyondAssistEditor/Log/log.txt`、记忆河流 genshin-ts D277/D279/D280、上游 bug 库（KDE 525590 / Wine 59965 / Wine 59610）。
> **状态**：真死=已建立防线（疫苗常驻 + 4 轮 PASS）；假死=根因锁定 + 修复条件已满足（kwin 6.8 升级中，下次登录生效）；Wine 侧第二条病未闭合。

## 二、最近一次故障的完整调查链（假死：现象 → 分层排除 → 根因）

**现象**：试玩循环之后，编辑器三个窗口（资源管理器/千星沙箱/日志）全部点击无反应；窗口可移动、可获焦、画面正常；游戏本体正常。

**分层排除（每一层都是活体读数，不是推断）**：
1. **X 抓取**：自建探针每 2 s 试抓指针/键盘并立即释放 → **174/174 次全为 GrabSuccess**（无人持有抓取）⇒ 排除「指针被抓走」。
2. **事件积压**：编辑器 X11 套接字 `Recv-Q = 0` ⇒ 排除「事件堆着没人读」。
3. **可点区域**：SHAPE 扩展查询 `ShapeInput` = **整窗一个矩形**（与可点的游戏窗同构）⇒ 排除「窗口不接受鼠标」。
4. **隐形模态窗**：11 个 X 窗口里只有 3 个真窗口（其余是 Wine 的 1×1 内部窗），几何全部正常 ⇒ 排除「看不见的对话框把主窗禁用了」。
5. **窗口管理器状态**：点击时 WM 正常置 `_NET_WM_STATE_FOCUSED`、指针所在窗口=沙箱窗、`_NET_WM_OPACITY` 不存在（无「无响应」变暗）⇒ 排除「焦点没给到」。
6. **渲染与进程**：截图逐字判读（菜单/树/表格/搜索框齐全，无白屏无弹窗）+ 主线程 37% CPU 运行中 + 协议层健康（最后一次循环 PASS）⇒ **排除进程死亡**。

**关键转折**：白盒手段全部否定后，才去查上游 bug 库 —— 一次搜索即命中**版本 + 配置双精确匹配**的 KDE 525590，以及症状逐字吻合的 Wine 59965。

**为何用户的 Win+右键拖动是有效解卡**：那是**显式用户操作**，KWin 必须放行激活 —— 而失败的那些尝试（`wmctrl` 激活/移动/缩放、KWin 快捷键触发、最小化→恢复、探针抢指针）**都没有让 KWin 放行激活**。这一条把「用户已知解法」变成了机制证据。

## 三、为什么反复出问题——系统性根因

1. **「同步读数」冒充「行为读数」，且仪器会静默失败**。
   本轮 3 例空实验：①用 `/proc/<pid>/fd` 的 mtime 断言「监听端口自 19:31 从未关闭」→ 被抓包推翻（该端口在风暴期直接回 RST）；②取证脚本 `ys-stuck-report` 里用了本机**没装**的 `xwininfo`，且 stderr 被吞 → 「全套快照」实际缺项；③`import -window root` 连试两次静默不产文件 → 截图对比计划落空，还让一个子代理在**不存在的文件**上空跑一轮。
   **对策**：取证脚本必须自证「拿到了读数」（非空校验 + 退出码 + 产物存在性），行为证据（包/事件/日志行）优先于文件属性。

2. **判据的覆盖面窄于用户感知的故障面**。
   验收器按「重连成功 + 30 s 内 `level state changed`」判 PASS，连报 **4 轮 PASS** —— 而同一时段用户看到的是「窗口点不动」。尺子量的是一条路径（协议），用户走的是另一条（输入）。
   **对策**：用户报出的每个症状都要在判据里有对应条目；「全部 PASS」必须附带「本判据不覆盖什么」的显式声明。

3. **环境层故障的排查顺序反了**。
   WM/合成器/Wine/驱动这类「外部环境层」故障，第一步就该做**版本比对 + 已知 bug 库检索**；本轮先做了数小时白盒取证才去搜索，而搜索一次就命中。
   **对策**：见到「渲染正常但行为异常」「只在某个桌面环境/某个版本出现」的特征，先查已知 bug（含版本号），再进白盒。

### 4.2 验收口径审计（六问，逐条作答）

1. **有无自写豁免清单？** 无。但判据（PASS=重连成功且 30 s 内有状态推进；FAIL(zombie)=连上后 30 s 零动作）**是我自写的** —— 已用健康代 `logPre` 基线（风暴 ~20 次/37 ms → 297 ms 后状态推进）锚定，非凭空设定。
2. **门禁覆盖了什么、没覆盖什么？** 覆盖**协议层**；**未覆盖输入通路**与用户可见恢复 —— 即第 3 条系统性根因。
3. **产物可复现？** 日志/脚本齐备，但 `.scratch` 是**临时区**；本轮把 `ys-*` 工具资产化进本仓 `tools/`（见产出清单）。
4. **多少结论建立在没发生的实验/量错对象上？** 3 例（见第三节第 1 条）。作废范围：**端口存活模型那一轮**（已由抓包重写）；`ys-stuck-report` 的窗口属性部分（改由 `xdotool`/`xprop` 重取）。
5. **被测对象是新的？** 用 PID + etime 核对；KWin 设置改后回读的是**运行值**（`supportInformation` → `focusStealingPreventionLevel: 0`），不是配置文件。
6. **样本量与窗口？** 风暴 4815 次 vs 健康代 ~20 次（对照窗按世代切，非按方便切）；4 轮试玩循环；174 次抓取采样；每项都有具体读数支撑。

### 4.3 可复用的分诊法（方法 > 结论）

**「假死 vs 真死」判别**：窗口**渲染正常 + 可移动 + 可获焦 + 全窗吞输入** ⇒ 故障在**进程内输入通路**；随后按序排除：X 抓取 → 套接字队列 → SHAPE 输入形状 → 隐形模态窗 → WM 焦点属性。**若 X 层全部干净，立即转查 KWin/Wine 已知 bug 库（带版本与配置值）**，不要再往应用内部挖。

**环境层故障的三件套**：①本机版本；②运行值（不是配置文件的期望值）；③上游 bug 库的「版本 + 触发配置」双比对。
