## 二、最近一次关键调查链（十字 BFS → 策略表）

1. 现象：文档标的"极小 BFS"，实测跨层十字 BFS visited 到 188,849。
2. 差分：换生成元（去 D、加 180°）visited 仍 ~190k → 不是生成元问题。
3. 转向：定义"确定性逐棱归位"，但单棱移动地图有 U↔FR 等交换，手工推导易错。
4. 定案：用单棱 BFS 生成「安全宏」首步策略表（safe=U + 未锁面 bare + 恢复共轭 gU g'），
   对 190,080 合法态穷举仿真，迭代到 0 失败。表形态 = (solvedMask×edgeState) → macro id，384 项。
5. 收益：运行时十字 = 读 4 棱状态 → 查表 → 应用 ≤3 move 短序列，完全无搜索。

## 三、系统性根因（2-3 条）

1. **"表 = 全覆盖"必须先量化再信**：OLL/PLL 都栽在"57/21 条公式默认覆盖全部状态"的假设上；
   一律先枚举合法态 × 表动作做离线覆盖断言，再决定"查表 vs 小 BFS"。
2. **搜索能不能进节点图，用"访问状态数/列表上限"当铁门**：先测 visited/maxQueue，>= 数千就改表驱动或
   定时器分片；不要凭"状态空间理论上 24^4≈33万"直觉判断。
3. **Genshin-TS 运行时/编译期是两级**：TS 编译过 ≠ .gia 编码过（信号要在地图先注册），
   npm run build 会被无关例子的既有 TS 错误挡住，验证要拆到"目标例子 + gsts dev"。

## 四、流程与方法论教训

- 用命令退出码判断成功，不要 grep | tail（管道退出码恒为最后命令）。
- 生成含模板字面量的代码文件时，外层用 String.raw，避免内层 ${} 被提前插值。
- 真实地图写回前先 sha256sum 锁源、用 assets:signals inspect --map-id 定位真实路径、
  写后 inspect 回读；--write 自动写 .gsts/backups。
