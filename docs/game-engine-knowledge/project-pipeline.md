# 游戏引擎知识与项目编译管线

> 状态：框架草案
> 来源：用户对项目转换层级及 GIA/GIL 关系的说明
> 最近校验：2026-08-01
> 适用范围：真实游戏规则如何逐层进入 Genshin-TS 实现

本知识目录描述游戏引擎真实存在的对象、能力和运行规则。项目代码负责把用户编写的高级 TypeScript，逐层转换成游戏可识别的资产。

两者不能互相替代：

- 游戏引擎知识回答“游戏真实支持什么、编辑器怎样表达”。
- 项目代码回答“Genshin-TS 当前已经实现到哪里、怎样生成”。

## 项目转换流程

```text
高级 TypeScript 语法
→ 展开成扁平的原生 API 调用 TypeScript
→ 转换成 JSON 中间表示
→ 应用游戏特殊编码规则
→ 调用第三方 GIA 编码库
→ 生成 GIA 部分资产包
→ 提取目标资产并注入 GIL 完整关卡包
```

## 第一层：高级 TypeScript

用户使用便于阅读和组织的高级语法描述玩法。这里可以包含封装、复合逻辑和更接近业务含义的表达。

目标是让作者关注“要做什么”，而不是手工编写每个底层节点和连接。

## 第二层：扁平原生 API 调用

高级语法被展开为更直接、更扁平的 TypeScript。这个阶段主要调用游戏原生 API 对应的项目接口。

它把复杂语法结构变成明确的节点调用和数据依赖，为后续转换做准备。

## 第三层：JSON 中间表示

扁平调用继续转换成 JSON 表示。JSON 描述节点、参数、控制流、数据流、变量、复合调用及其他编译所需信息。

JSON 是项目内部的中间语义，不等于最终 GIA，也不能单独证明编辑器真实编码。

## 第四层：GIA 生成

项目根据 JSON 中间表示：

1. 应用已经学习和实现的特殊游戏规则；
2. 解析节点、参数、引脚和连接；
3. 使用第三方 GIA 库编码；
4. 生成可导入的 GIA 资产。

第三方库负责底层文件表达，但项目仍需提供正确的游戏语义、节点身份和连接规则。

## 第五层：注入 GIL

生成的 GIA 可以独立导入游戏，也可以提取其中的目标资产并注入现有 GIL 关卡。

```text
GIA 中的目标资产
→ 定位 GIL 中的目标位置
→ 保留无关关卡内容
→ 替换或新增目标资产
→ 回读验证
```

GIA 和 GIL 的资产边界见[资产、关卡保存与导出文件](assets-and-files.md)。

## 新功能的正确顺序

```text
先查游戏引擎知识
→ 判断游戏概念和已有真实规则
→ 再查项目当前实现
→ 找到最早缺失的转换层
→ 只有真实编码缺失时才做编辑器增量实验
→ 规则闭合后写回对应代码层
→ 逐层验证直到 GIA
→ 最后按需要导入 GIA 或写回 GIL
```

### 情况 A：游戏规则和编码都已知

直接定位项目尚未实现的转换层，补测试和代码，不重复要求用户做编辑器实验。

### 情况 B：概念已知，但底层编码未知

通过[验证与规则学习流程](validation-workflow.md)进行相邻快照实验，先把规则写入本知识目录，再实现代码。

### 情况 C：游戏 API 已定义，但项目尚未实现

把 API 定义当作功能范围说明；仍需确认当前编译层是否支持其参数、节点和连接。API 文档不能代替真实 GIA 编码证据。

### 情况 D：游戏侧功能尚未设计或开放

例如当前尚未设计的自定义 UI 添加能力，只保留概念框架和待验证项，不提前虚构项目 API 或编码。

## 当前实现边界

项目已经完成较多节点和转换能力，但不同领域成熟度不同。例如：

- 创建模型是近期已经实现的能力；
- UI，尤其自定义控件添加，尚未设计；
- 组件当前只覆盖少量类型；
- 游戏 API 的功能定义较完整，但部分项目实现仍待补全。

这些状态会变化。具体实现结论应由当前源码和测试确认，本知识目录只保存稳定的游戏概念、真实编码规则和验证边界。

## 知识回填位置

- 游戏对象和运行语义：写入对应领域文件。
- 节点、参数、引脚和连接编码：后续写入具体编码主题文件。
- 编译层实现：写入项目架构文档、源码和测试。
- GIA/GIL 验证：写入[验证与规则学习流程](validation-workflow.md)。
- 文件之间的关联：登记到[index.md](index.md)。
