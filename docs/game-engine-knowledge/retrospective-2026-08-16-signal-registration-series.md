## 二、第 5 次错误的完整调查链（最曲折的一次）

### 2.1 现象与迷惑点
- 游戏代理（b914c930）用最新 CLI 完成 5 信号注册 + 4 图注入（73/73/73/123 节点）
- **静态检查全部通过**：版本 v4 一致、图内 sigVer=4、信号参数无默认值、挂载 21 个
- 但游戏拒载（用户：问题一样）

### 2.2 三版本差分（用户驱动的闭环方法论，本次核心）
用户操作：**逐个手动重建信号**（每次只修一个，方便差分比对）：
```
v0(CLI注册,拒载) → v1(用户修lamp_toggle) → v2(修win_check) → v3(修win_ack,可运行)
```

**差分结论**（lamp_toggle 三份定义逐字节对比）：
- 索引条目 #4：before/after **完全相同**（不是问题）
- 定义 #4 版本字段：4→5（版本策略，不是根因）
- **定义 #102/#103 参数条目 n3 field2：被编辑器重写** ← 真正根因

| 参数 | CLI 生成（错） | 编辑器重建（对） |
|---|---|---|
| senderPos（第0参）send/server | field2=2（vec3 模板常量）| 省略（=0）|
| hop（第1参）send/server | 省略（int 模板常量=0）| field2=1 |
| senderPos monitor | field2=5 | field2=3（3+0）|
| hop monitor | field2=3 | field2=4（3+1）|

### 2.3 根因（代码层）
`BUILTIN_PARAM_LAYOUTS` 每种类型的 n3 描述符硬编码了**历史样本遗留的 field2 常量**
（vec3=2/int=0/entity=1/guid=5/bool=4/float=1/list 系列 2-8）。`buildDefinition` 克隆模板时
`cloneParamEntry` 只改参数名，**n3 field2 原样沿用** → 参数序号错位。

**引擎真实规则**（三信号差分实证）：
```
n3 field2 = 参数在信号内的全局序号（0-based）
  send/server 定义（#102）：field2 = 序号（0 省略字段）
  monitor 定义（#103）：field2 = 3 + 序号（前 3 个固定字段：事件源实体/事件源GUID/信号来源实体占 0/1/2）
```

### 2.4 修复
`rewriteParamN3Field2`：克隆参数时按全局序号重写 n3 field2（0 删除字段、monitor 偏移 3）。

### 2.5 验证链（全闭环）
- 修复后 CLI 对 3 个已修信号生成结果 vs 用户修复版：**3/3+3/3+3/3 逐字节一致**（仅版本号）
- 2 个 int 单参信号：候选 = 源（本来就正确，field2=0 恰好符合规律）
- 新回归测试（vec3+int 双参断言 field2=0/1、monitor=3/4）+ 全部信号测试 PASS
- 用户游戏核验：**可运行** ✅

## 三、为什么"信号注册"反复出问题？——系统性根因

**不是运气差，是三个系统性缺陷叠加**：

### 缺陷 A：builtin 模板来自"单一样本"，缺少通用规则提炼
`BUILTIN_PARAM_LAYOUTS` 的 n3 field2 是从 verify_ping（str,str）等历史样本抄的**字节常量**，
从未提炼成"序号 = 参数位置"的通用规律。str/int 的 field2=0 恰好掩盖了问题，
导致"单参数/str 信号验证通过"的假象持续存在。

**教训**：从样本抄字节时，必须追问"这个字节代表什么语义"，不能只做"字节级复刻"。
**验证盲区**：builtin 测试用 str+str 信号（field2=0 恰好对）——**测试样本恰好避开了 bug**。

### 缺陷 B：静态检查 ≠ 引擎校验
我们的验证链（版本一致性、图结构、参数默认值）覆盖了已知规则，但**引擎的完整校验集合
从未系统闭合**。每次修一个规则，下一个规则又冒出来。

**教训**：验证链必须包含"**引擎接受的完整形态**"对照（编辑器重建样本），
而不是只检查"我们知道的字段"。

### 缺陷 C：一次修复掩盖下一个 bug
#4（默认值）修复后，靠"用户修复注册表+重新注入"通过游戏——**没有用修复后的 CLI 独立
验证全链路**，导致 #5 被掩盖。

**教训**：修复后必须用**生产工具独立跑完整流程**（register→注入→游戏），
不能依赖用户手工修复的中间产物通过。

## 四、流程与方法论教训（跨 5 次错误）

1. **游戏拒载类错误 = 无日志**：加载期错误级别极高，Beyond_Debug_Log 不产生新文件。
   排查顺序：确认进图 → 无新日志 → 走差分而非等日志（已沉淀到 debug-log-investigator）。
2. **用户驱动的三版本差分是最高效路径**：错误版/自动保存版/用户修复版三快照齐全时，
   逐字段对比直接定位"我们改了什么"——比在代码里猜快得多。
3. **"变更消失"先核对 hash**：旧编辑器内存保存覆盖磁盘写回（v19 教训复发两次：
   灯柱实体两次消失、信号 v4 出错版均因此）。排查前先核对当前 hash 是否等于写回后 hash。
   （v19 教训出处：2026-08-14 复盘 `retrospective-2026-08-14.md` 灯柱实体消失事件确立的
   "CLI 写回后旧编辑器内存保存会覆盖磁盘"纪律。）
4. **写回后必须提醒用户重新加载编辑器再保存**——每次写回（register/inject/import/attach）都适用。
5. **样本字节要问语义**：builtin 布局抄自编辑器样本，但没提炼"field2=参数序号"的规律。
6. **测试样本要覆盖"错误路径"**：现有 builtin 测试用 str+str（field2=0 恰好对），
   应包含 vec3/entity 等多参数场景（已补）。
7. **修复后必须用生产工具独立验证全链路**：不能靠用户手工修复的中间产物掩盖。
