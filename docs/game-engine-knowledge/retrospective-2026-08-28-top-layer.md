## 二、最近一次错误的完整调查链（死循环，日志 2964）

**现象**（用户）：前两层正常复原后没动静，日志显示死循环。

**取证链**：
1. 日志 2964 记录扫描：solverLPlan 反复执行（rec11 8262B → rec23 30744B → rec39 46172B），solverPlan/EPlan 恒 183B/184B 空转——solverLPlan 在反复规划不推进。
2. 帧级追踪：rec91 里 `sco=[0,0,1,1,...]`、`seo=[1,1,1,1,...]`、`solveMask=103` **都没变**——OLL 公式应用后朝向签名没归零 → 死循环。
3. 定位追加链：rec23 里 `solver_append_code > IN0:Integer=`（**空**）——追加的 code 是空。
4. 定位 longListGetInt9：帧 [36] `getCorrespondingValueFromList([12,2,14], 73)`——读 c8 块（只有 3 项）offset=73 **越界返回空**。
5. 根因：**乘法选择器里所有块都读同一 offset**（即使 sel(k)=0 也执行读），最后一块 < chunkSize 时越界读污染累加结果。

**修复**：生成器把所有表补齐到整块（最后一块用 18 填充），保证所有块长度 = chunkSize，offset 永不越界。

**验证**：离线 20000 样本 ALL PASS（填充值 18 不会被读到，mLen 限制读取范围）；编译 9 GIA 全绿；注入 ok 9 fail 0；GIL 核验所有表 length_field=100；resync md5 一致。

## 三、为什么反复出问题——系统性根因（2 条）

1. **「乘法选择器」模式的隐藏前提没被文档化**：longListGetInt4/6/9 的乘法选择器要求「所有块长度 = chunkSize」，否则越界读污染结果。之前 longListGetInt4 用的表（CF_X_POLICY 96×4、CF_PLL_SIG 96×3）恰好满块，掩盖了这个前提；顶层新表（803 项 = 8×100+3）最后一块只有 3 项，第一次暴露。**教训：写长列表查询复合时，必须显式确认每块满 chunkSize，或生成器补齐**。
2. **离线验证与真实 GIL 的差距**：离线验证（verify-top-layer.mjs）用 JS 数组直接 index，没有「越界读」问题；但真实 GIL 里 longListGetInt9 的乘法选择器会越界读。**离线验证通过 ≠ 真实图正确**——这个差距只能靠「读图核验」+「日志帧取证」发现。教训：新写长列表查询复合后，除离线验证外，必须读图核验 + 提醒用户游戏复测。

## 四、流程与方法论教训

- **有用**：日志帧级追踪「追加的 code 是空」→ 反推 longListGetInt9 越界读，是定位死循环的决定性一步。先看「状态为什么没变」（solveMask 不变），再追「追加了什么」（code 空），最后定位「为什么空」（越界读）。
- **有用**：GIL 回读表变量 length_field vs array_len 的对比，确认了「补齐成功」（length_field=100）。
- **绕路**：先怀疑了 llStage 未初始化（日志显示空）、方向映射反了（视角混淆）、表被截断（parse 显示 16 项）——都被排除后才定位到「乘法选择器越界读」。**教训：日志里「空」可能是 0 的解码问题，先确认是「真空」还是「0 显示为空」**。
