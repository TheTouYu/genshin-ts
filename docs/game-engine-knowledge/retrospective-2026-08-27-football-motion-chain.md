## 二、最近一次错误的完整调查链

**现象**：物化修复后用户测："足球还是高速运动然后光速停止"。

**第一步铁证——运动器速度分布**（全日志 105 条 Add Uniform）：
- TOP10：35/34.8/34.3/33.8/32.9/31.7/30.4/28.8/28.8/28.7
- 中位数 20.1，>10 m/s 的有 79 条
- 逻辑球速只有 3.45 → **运动器速度是球速的 6~10 倍**

**第二步——ballPos 序列**：完全平滑（-43.15→-31.8，每 tick ~0.5 米），逻辑位置正常。

**第三步——实体位置 vs ballPos**（motionToPoint 内 Get Entity Location）：
- rec2: 实体 -43.15（=ballPos ✓ 同步）
- rec9: 实体 -42.63（ballPos -40.6，滞后 2 米）
- rec25: 实体 -42.46（ballPos -38.19，滞后 4.3 米）

**根因链闭环**：
1. 实体位置因运动器被打断/替换而滞后 ballPos（累积）
2. motionToPoint 用 `delta = target − 实体实际位置` 反推速度 → delta 含滞后量（5 米 vs 应有 0.5 米）
3. 运动器速度 = delta/0.2 = 20~35 m/s → 超出引擎正常范围 → 引擎不驱动实体
4. 实体更滞后 → delta 更大 → 恶性循环
5. 视觉：每 tick 球"猛冲一下又停"（运动器 25 m/s 被加但被忽略）

**关键证据句**：rec2 运动器 3.35（正常）→ 实体动 0.5 米到位；rec9+ 运动器 25（巨大）→ 实体几乎不动（-42.63→-42.46）。

**修复**：新增 `motionByVel` 复合（直接给速度向量），`physApplyMotion` 从 `pos` 改 `vel` 驱动，
所有调用点（kickApply / physRollTick / physSlideTick / kickLaunch）传**物化逻辑球速**。
运动器速度恒在正常范围（3~4 m/s）→ 引擎正常驱动实体 → 实体每 tick 移 0.7 米与 ballPos 同步。

## 三、系统性根因（为什么反复踩）

1. **"速度"在代码里有两个真相源**：逻辑 ballVel（图变量）与运动器参数（Add Uniform）。
   排查只盯逻辑值（正确），没成对核对运动器参数（错误）——用户两次追问"运动参数怎么变化"
   才把视线拉到下游。**日志必须成对读：逻辑值 + 下游运动器参数**。

2. **用"位置差反推速度"是脆弱的模式**：`(target−loc)/0.2` 假设 loc 与逻辑位置同步；
   任何实体位置滞后（运动器打断/替换/超限）都会把误差放大进速度，且放大后超限又加剧滞后，
   形成正反馈。**运动器应该直接以逻辑速度为参数**，位置只做结果校验。

3. **验证链分层不完整**：注入成功 + 变量 pin 完整 ≠ 运动器行为正确。
   运动器参数（Add Uniform 的 IN3）在日志里可见，之前几轮读日志都没看它。

## 四、流程与方法论教训

- **用户的追问是雷达**："添加给足球运动参数呢？是怎么变化的？"——连续两次把排查方向
  从"参数大小"拽到"传导链"。遇到"怎么调参数都不对"，第一步查传导链两端是否一致。
- **分布统计胜过单帧抽查**：`grep Add Uniform | 算模长分布` 一眼看出 79/105 条 >10 m/s，
  单帧抽查（3.35、3.2）会误判为正常。
- **写修复时先枚举同族**：这次同族=所有"用实体位置反推 delta"的运动器驱动点，
  一次性全部改为 motionByVel（physApplyMotion 接口统一改 vel），不留第二个真相源。
