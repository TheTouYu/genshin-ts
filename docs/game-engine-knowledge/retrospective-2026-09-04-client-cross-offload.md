## 二、最近一次错误的完整调查链（客户端读空 → 根因）

1. **现象**（3138）：客户端任务拍 `rbx_sum=489`（读到），自算加权和 h 恒 0 → equal 失败 → 全 'xr'。帧级定位：`getCustomVariable(Entity2,'solver_ep')` 在客户端**无 OUT**；同实体服务端读 `[0,8,2,...]` 正常；同实体标量（rbx_t1/epoch/sum）客户端读正常。
2. **差分实验**（用户亲自做，3141）：在玩家实体建 int_list 变量 → 客户端测试图读回 `[4,2]` → **类型因子排除**。
3. **逐层核验**（用户指引三问：声明成功了吗？读的是哪个实体？实体上真的设了吗？）：CLI `--list` 显示 def(1077936200) 有 13 变量（声明成功）→ 用户查编辑器：**实体 1077936201 变量面板为空** → def 级声明不传导场景实例 = 真因。
4. **wire 学习**（用户 10 秒差分）：实体上建 probe_var → 字节定位 root5.1[entity].7{f1=1,f2=1}.11 容器 → 与代码既有 ENTITY_PATH 常量吻合，缺「容器创建」能力。
5. **修复**：CLI 三处 + 13 变量注册到实例 → 3143 行为层闭环（任务拍 1347~1405 帧，c0/xd 回传，十字完成→角块→E 层）。

## 三、为什么反复出问题——系统性根因

1. **元件/实例双数据模型（root4 def vs root5 摆放实例）的语义空白**：变量声明在哪一层决定客户端可见性——def 声明只服务端可见，客户端必须实例级声明。此前所有客户端读变量案例（fb E1/玩家实体）恰好都在 root4 元件族上，从未暴露此断层；知识库对「root5 实例变量 wire」无记录（CLI 代码有 ENTITY_PATH 但无建槽能力+报错误导）。
2. **诊断归因跳跃**：读空 → 直接归因「类型不支持」并准备绕行，未先穷尽「声明层/实体寻址/值是否存在」三问（用户教过的分层核验，现场又一次被跳过——用户原话三连问逐字见第四节）。
3. **错误掩蔽放大定位成本**：CLI catch-all 把「容器缺失」吞成「custom prefab not found」，把实体路径能力缺口伪装成地址错误，误导两轮排查。

## 四、流程与方法论教训（用户纠正钩子逐字）

1. 「先别着急跳过，让我来帮你做一个实验」——我准备直接上绕行方案时被拦下：**有用户可做的 10 秒差分就不该静态推断+绕行**（卡住三问②再次应验；绕行方案=标量寄存器+图内联表，若执行将带偏两轮）。
2. 「如果说你那边没读到，你应该先检查一下这个变量是不是声明成功了。然后你告诉我你读的是哪一个，我可以去游戏里面帮你看一眼。然后你看一下你拿到的实体，有没有成功拿到这个变量，拿到实体了，再看一下它是不是真的设置好了这个列表的变量」——**读空排查三连问：声明层 → 实体寻址层 → 值落位层**，逐层取铁证，不许跳跃。
3. 「我们命令行应该是能够支持变量操作，支持的对象包括：1. 实例…2. 元件…如果不支持，你就趁机修复一下」——**CLI 能力缺口=产品缺陷要修，不是绕过理由**；实例与元件是编辑器基础概念，工具必须同权。
4. 「我这边测试了，它能够读到整数类型的」「我检查了，我们用的这几个实体，它的变量都是空的，压根就没声明变量」——用户两次亲自取证（测试图+编辑器查看），比我的推断快且铁。
5. 「你看一下足球里面代码是怎么写的，如果你确定代码没问题，我就再跑一下给你补充日志」——对照**已验证的实证实现**自查，确认后才花一轮复测。
