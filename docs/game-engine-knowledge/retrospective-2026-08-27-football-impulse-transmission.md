## 二、最近一次错误的完整调查链（现象→铁证→根因→修复→验证）

**现象**：用户"速度快到直接瞬移到远方"，连续 8 轮参数调整都感觉不对。

**关键转折**：用户提问"速度等于这么多之后呢？添加给足球运动参数呢？是怎么变化的？"——**把排查从"参数大小"转向"传导链"**。

**铁证**（Beyond_Debug_Log 2026-08-27_16-43-43）：
```
[60]  Set ballPos = (-44.449, 0.25, -34.87)   ← 图变量先写位置
[114] motionToPoint 读实体实际位置 loc=(-43.657)  ← 实体还停上一帧
[118] 运动器速度 = (target−loc)×5 = 9.9 m/s       ← 位移算了 2 个 tick
[166] Set ballVel = 4.86                          ← 逻辑球速
```

**根因**：`kickApply` 里 `integ.npos`（`callComposite(physRollIntegrate)` 的输出）被消费两次——
`setPos`（写 ballPos）+ `motionToPoint` 的 target。中间 `setPos` 把 ballPos 更新了，
第二次消费时复合按新输入**重新求值**，npos 多算一个 tick 位移 → 运动器速度=逻辑球速×2。

**修复**：`kickApply` 改用**物化快照**（tmpPos/tmpVel/tmpSpin）——复合输出先物化到临时图变量，
所有消费点（setPos / motionToPoint / 状态判断）都读物化值，杜绝二次求值。

**验证**：编译注入成功、变量 pin 完整、无残留版本；物理上与 flyTick 既有模式一致。

## 三、为什么反复出问题——系统性根因

1. **传导链验证缺位**：8 轮全在调"逻辑球速"这个参数，没人验证"运动器参数 vs 球速是否一致"。
   kickApply 的复合输出二次求值 bug 一直存在（球速 4.5 上限后 ×2=9 才暴露）。铁证原则应用不彻底——
   读日志只看了逻辑值（ballVel），没对照运动器参数（Add Uniform 的 vel）。**验证链盲区：只看上游、不看下游传导**。

2. **参数调优无物理模型先导**：球速与玩家速度的关系（固定/比例/增量/领先量）来回试，
   没有先从用户要的"健康距离 2~3 米、2~3 秒追平"反推物理公式。每次调参都是"感觉不对换个公式"，
   参数域大导致反复震荡。

3. **同族风险未显式登记**：flyTick/rollTick 早已用物化模式（注释里明确写了坑），但新增复合
   （kickApply、physSlideTick）没有继承这个纪律——**"已知坑"没有沉淀为强制检查项**。

## 四、流程与方法论教训

- **用户的一句追问救了一整轮**："添加到运动参数是怎么变化的"——遇到"参数怎么调都不对"时，
  第一步查传导链（上游逻辑值 → 下游运动器参数是否一致），不要继续调参数。
- **日志铁证要成对读**：读 ballVel（逻辑）必须同时读 Add Uniform 运动器的 vel（视觉），
  两者不一致 = 传导 bug；只读一个会误判为"参数问题"。
- **物化快照是防翻倍的标准姿势**：callComposite 输出被消费 ≥2 次时，必须物化到图变量快照。
- **反复调参无进展的信号**：参数域来回震荡（固定→比例→增量→固定）说明模型层有 bug，
  不是参数层问题——停下来查传导。
