# 游戏运行生命周期

> 状态：框架草案
> 来源：用户对完整游戏执行流程的说明
> 最近校验：2026-08-01
> 适用范围：从开始游戏到结算退出的整体运行过程

游戏不是从任意节点直接开始，而是先初始化内置对象和关卡资产，再由创建事件、组件事件、玩家输入和 UI 事件持续驱动节点图。

## 总体流程

```text
点击“开始游戏”
→ 初始化内置且不可更改的内容
→ 创建关卡、玩家和角色
→ 加载并逐个创建预设实体
→ 启动配置为创建时运行的组件
→ 触发创建和组件事件
→ 进入等待玩家操作的运行状态
→ 玩家、组件或 UI 持续产生事件
→ 节点图处理事件并改变游戏状态
→ 循环等待和处理
→ 玩家退出或满足结束条件
→ 触发结算事件
→ 标记游戏结束并退出
```

## 第一阶段：内置初始化

点击“开始游戏”后，游戏先初始化一批内置且不可由普通关卡逻辑取消的内容，包括：

- 当前关卡；
- 玩家；
- 玩家对应的角色；
- 其他待确认的系统对象。

玩家和角色一定会被创建，它们与普通用户定义实体不同。多人模式下，每个玩家对应的初始化和事件次数需要单独考虑。

## 第二阶段：创建关卡预设实体

游戏开始加载关卡中预先摆放的实体，例如：

- 足球；
- 椅子；
- 桌子；
- 其他初始模型。

这些实体会被逐个创建，并触发相应的创建生命周期。

具体创建顺序是否稳定、是否并行，以及不同实体之间能否依赖创建先后，仍需通过真实实验验证。

## 第三阶段：组件自主运行

实体创建时，它配置的组件也进入运行状态。

部分组件可以设置为创建时直接运行。例如足球配置运动类组件后，实体一创建，组件就可以直接让足球开始运动。

```text
创建足球实体
→ 初始化足球上的运动组件
→ 组件按配置直接运行
→ 足球开始运动
→ 组件可能产生相应事件
```

这一过程不一定经过节点图。组件可以按照自身配置直接产生行为；只有当组件事件需要额外逻辑时，才进入挂载节点图。

## 第四阶段：等待与事件驱动

初始化、实体创建和自动组件行为完成后，如果玩家没有操作、组件没有继续产生事件，游戏可能暂时处于静止或等待状态。

这里的“静止”不是游戏停止运行，而是当前没有需要处理的事件。

## 第五阶段：实体组件事件

玩家接近带选项卡组件的足球并选择“起飞”时：

```text
玩家接近足球
→ 选项卡组件显示选项
→ 玩家选择“起飞”
→ 组件产生“选项卡选中”事件
→ 事件进入足球实体挂载的节点图
→ 从对应事件节点开始执行
→ 根据选项类型执行运动、爆炸、消失等逻辑
```

组件负责感知交互并产生事件；节点图负责解释事件并执行更复杂的逻辑。

## 第六阶段：UI 输入事件

屏幕按钮、按键和其他控件也可以产生事件。

例如“发射子弹”按钮：

```text
玩家按下 UI 按钮
→ 角色收到控件事件
→ 角色节点图读取控件或事件 ID
→ 按配置转发给指定实体
→ 目标实体节点图判断事件类型
→ 执行发射逻辑
```

控件 ID 或事件 ID 用于区分具体输入。ID 如何定义、携带和比较，需要在 UI 和事件编码实验中逐步确认。

## 持续运行循环

游戏运行期间持续重复以下模式：

```text
等待事件
→ 事件发生
→ 找到事件所属对象和节点图
→ 从事件节点执行控制流
→ 读取或计算数据参数
→ 修改实体、组件、变量、UI 或镜头状态
→ 执行结束
→ 继续等待事件
```

不同事件可能同时发生。事件排队、并发、打断和执行顺序属于后续需要专门验证的规则。

## 结束与结算

玩家点击退出，或游戏满足其他结束条件后，会触发结算相关事件：

```text
请求退出或满足结束条件
→ 触发结算事件
→ 标记游戏结束
→ 执行必要的结束逻辑
→ 退出本局游戏
```

结算事件与普通实体销毁事件是否存在固定先后，以及退出时哪些节点图仍可执行，需要后续验证。
