# 验证与规则学习流程

> 状态：当前推荐
> 来源：真实 GIL 批次调查流程 + 用户提出的编辑器增量学习和游戏验证方式
> 最近校验：2026-08-02
> 适用范围：从真实关卡学习规则，并通过 GIA 或 GIL 验证

游戏引擎规则优先通过真实编辑器的小步修改学习，而不是先根据当前代码推测。

## 第一阶段：编辑器增量学习

用户每次只修改一个能够明确描述的内容并保存地图。助手保存前后快照，比较发生变化的目标结构。

```text
保存修改前关卡
→ 用户只做一个小变化
→ 保存修改后关卡
→ 固化相邻快照和 SHA-256
→ 定点比较变化
→ 提炼一条可以验证的规则
```

典型的小变化包括：

- 新增一个节点；
- 给节点填写一个参数；
- 连接一条控制流；
- 连接一条数据流；
- 新增一个变量；
- 给实体增加一个组件；
- 修改一个控件设置。

如果同类规则已经有充分证据，可以一次组合多个已知变化，提高验证效率；但必须保证每项都能由已有规则解释，出现未知增量时停止推广。

### 整体语义树的章节式调查

需要还原完整 GIL 字段树时，不直接遍历所有未知字段并猜名称，而是先选择一个概念章节和一个未知子容器：

```text
根层有界 wire 摘要
→ 选择一个未知章节/子容器
→ 设计一个可唯一归因的编辑器单变化
→ 捕获相邻不可变快照
→ 定点比较字段路径和 presence
→ 用 schema、当前 reader、真实差分或 round-trip 闭合映射
→ 独立 Validator 裁决
→ Coordinator 合并 ACCEPT 结论
```

用户负责准确说明编辑器中唯一做了什么，并确认该操作属于哪个游戏概念；字段名和消息语义仍必须由差分及其他证据共同支持。不要按字段位置、相邻 ID、重复数量或“看起来像某类资源”命名。

每个字段结论使用：

- `CONFIRMED`：schema、真实差分、raw-wire/round-trip 或当前显式 reader 支持；
- `CONFLICT`：来源不一致，停止推广；
- `INSUFFICIENT`：只观察到结构，语义未知。

protobuf 字段缺失、显式空值和显式默认值必须分别记录。当前整体基线和下一缺口见[GIL 整体结构与语义树](gil-structure-semantics.md)。

并行调查时，每个 Agent 只能写自己的实验目录；独立 Validator 只写裁决文件；共享 Authority 和恢复锚点由 Coordinator 单写。未经 Validator 接受的结果不能进入总图。

### 用第二个同构样本消除 ID 与同步记录歧义

一次编辑器操作可能同步创建 definition、instance、owner registry 或派生记录。即使文件只改变少数根字段，也不能按相邻 ID 或数值相等直接决定哪个 ID 是用户对象。

当第一轮出现这种歧义时，优先让用户再创建一个**同类型、保持默认设置**的对象，并保留新的相邻快照：

```text
基线
→ 新增对象 A
→ 相邻快照 A
→ 新增同类型默认对象 B
→ 相邻快照 B
→ 分别计算两轮唯一新增记录和引用
```

只有满足以下条件才将映射标为 `CONFIRMED`：

1. 两轮都是用户声明的单一编辑器变化；
2. 两轮改变的根字段集合稳定；
3. 每轮目标容器都只有一个可归因的新记录；
4. 引用字段在两轮使用相同 raw-wire 子路径，并分别指向 A、B；
5. 独立 Validator 不读取 Investigator 结果，直接从原始快照复核哈希、presence、记录集合和引用；
6. 结论明确限定对象类型、地图和版本，不从两个样本推广为完整 schema。

若两轮仍出现额外记录、引用不唯一或根字段集合不一致，停止命名并标为 `INSUFFICIENT`。

### 自由新建与自由修改的组合调查

整体语义树调查可以先“自由新建”一个最小对象，再对同一 identity 做一次“自由修改”，但每次保存仍只能包含一个变化：

```text
基线
→ 自由新建默认对象 A
→ 自由新建同类型默认对象 B（必要时消除同步记录歧义）
→ 只修改 A 的一个显式属性
→ 再次修改同一属性为短值或边界值
```

这种顺序分别回答：

1. 新对象在哪个根容器新增记录；
2. 同步 registry、owner 或派生容器如何变化；
3. 哪个稳定 identity 字段关联同一对象；
4. 哪个显式 wire 字段承载可修改值；
5. 字段长度是否精确跟随 UTF-8 或其他值编码长度。

必须直接比较所有 root occurrence 的 raw bytes，不能只比较字段总大小。等长内容变化不会出现在大小摘要中；本轮调查正是通过独立 raw-byte Validator 发现 root `46` 的等长同步变化。未知同步字段保持 `INSUFFICIENT`，不要因为它每次保存都变化就命名为时间戳、校验值或缓存。

若用户声明“修改对象”，raw-wire 却显示新增 identity 或新增记录，则该轮标为 `CONFLICT`，不并入修改规则。后续以稳定 identity 的连续修改样本重新闭合，不用用户意图覆盖文件事实。

当前“自由新建 / 自由修改”受限实例见 [GIL 整体结构与语义树](gil-structure-semantics.md)，原始证据由独立证据仓库提交 `d1b8fad91bf3f07c3846b0f6e28fb85d0089de39` 锁定。

## 第二阶段：手工同构重放

规则闭合后，先在临时文件中重放观察到的变化：

```text
读取修改前结构
→ 只应用已确认增量
→ 生成临时候选
→ 注入临时 GIL 副本
→ 回读并与编辑器结果比较
```

这一阶段证明“学到的结构规则可以复现”，不等于已经写入真实地图，也不等于游戏行为正确。

## 第三阶段：选择游戏验证路径

### 路径 A：最小 GIA 资源包

优先产出只包含待验证资产的最小 GIA，由用户直接在游戏编辑器中导入。

适合：

- 单个节点图；
- 单个复合节点；
- 一组模型；
- 一组 UI；
- 不依赖完整关卡状态的最小实验。

优点：

- 导入快；
- 用户测试成本低；
- 失败时影响范围小；
- 更容易判断是哪条规则有问题。

### 路径 B：写回完整 GIL 关卡包

当实验依赖完整关卡、既有挂载关系、静态资源或无法由独立 GIA 表达的状态时，才写回 GIL。

适合：

- 修改指定已有节点图；
- 验证实体、组件和挂载关系；
- 验证关卡初始实体；
- 验证多个资产之间的完整引用。

代价：

- 用户通常需要退出并重新打开关卡；
- 操作耗时更长；
- 写回前必须保存备份并明确确认目标。

## 默认选择原则

```text
能用最小 GIA 验证
→ 优先 GIA

只有完整关卡关系才能验证
→ 使用 GIL
```

不要为了方便生成而扩大测试范围。选择依据是“最小能够证明目标规则的资产边界”。

## 证据层级

以下结果必须分开记录：

1. **真实编辑器观察**：用户修改后，关卡文件确实出现目标增量。
2. **自动结构比较**：工具确认哪些节点、参数或连接发生变化。
3. **临时回读**：手工候选写入临时副本后，目标结构可正确读回。
4. **真实写回**：候选已写入真实 GIL。
5. **编辑器导入**：GIA 或写回关卡能被编辑器正常加载和显示。
6. **游戏行为验证**：用户实际运行后确认行为符合预期。

只有用户完成最后一步并明确反馈，才能写“游戏行为验证通过”。

## GIL 写回安全门

写回完整关卡前必须展示并确认：

- 目标关卡；
- 当前文件 hash；
- 目标节点图或资产；
- 候选文件；
- 具体修改内容；
- 备份位置；
- 回滚方式。

任何 hash 漂移、目标不明确或存在无法解释的差异，都应停止写回。

## 学习结果如何进入本知识目录

每轮完成后，把稳定结论写入对应主题文件：

- 概念和对象关系写入领域文件；
- 具体节点规则写入后续节点目录；
- 参数和值规则写入参数类型目录；
- GIL/GIA 对应关系写入本流程和资产文档；
- 索引文件登记它与其他规则的关联。

临时快照和聊天记录不是长期知识。长期结论必须包含证据范围和验证层级。
