## 三、为什么反复出问题（系统性根因 3 条）

1. **"当前样本的状态"被我默认成"引擎的能力边界"**。造物装饰物如此，早前"CLI 不能加组件"亦如此。
   → 落点：文档 ⑥ + 日记；凡 `grep 不到 / 这轮没见` 一律先做最小差分。
2. **用户口径是唯一权威，我却在没有口径时自己造解释**（锚点、同步、缩放率三处）。
   共同特征：我用"合理的工程直觉"补了空白，而实际上引擎的行为跟直觉不同。
   → 落点：文档把用户原话固定在条款里（"用户 2026-10-23 口径"），并写出**反例**（我上一版错在哪）。
3. **读数与判据的粒度不匹配**：字符串计数 ≠ 事件数；频率读数 ≠ 配置正确性（要看距离节流）。
   → 落点：`debug-log-investigator` 新增"数对数"一行；`client-nodegraph-development` 写明测频前把造物挪到玩家附近。

## 四、流程与方法论教训

- **差分流水线这次很顺**：锁 before → 用户做**一个**最小变化 → `gil-quick-diff` → 定点 dump → 落文档 → 提交。
  10 轮里每轮都能在 1~2 次工具调用内定位，靠的是"一次只变一件事 + 快照/指纹核对"。
- **验证判据选对了**：CLI 的正确性用"**与编辑器产物逐字节相等**"，而不是"回读看起来对"。
  这个判据当轮就逮住两个静默无操作 bug——是最值钱的一次选择。
- **用户纠正必须当轮进文档**（三处都是当轮改的），否则下次压缩后我又会按旧理解写。
- 交付报告三栏（已验证/未验证/需用户确认）这次执行得比较到位：每轮都写清"编辑器未验证"。
