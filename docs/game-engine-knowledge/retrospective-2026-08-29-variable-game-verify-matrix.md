## 二、最近一次错误的完整调查链（dict 元数据语义）

1. **现象**：批次 9 客户端 dict 局部变量（gsts_d3）值 pin 与我方管线 hex 不一致——
   containerBinding `{mode,kind}` 与 structs.mapPair `{key,value}`：真实 1/1，我方 9/3。
2. **第一轮推断（错误）**：vendor 把 key/value 的 clientVarType（9/3）塞进 mode/kind，真实恒写
   1 → 在 client_graph.ts 加"强制 1/1"归一化 → 比对通过（entity→entity 的 1/1 恰好命中）。
3. **用户澄清**：dict 未指定键值类型，编辑器默认 entity→entity——1/1 是"entity=1"的巧合，
   不是恒写。
4. **撤销推断**：删掉强制归一化；用户把 dict 改为 int→entity 后重新比对 → 真实 mode=3/kind=1
   = **key/value 的 clientVarType（vendor 语义正确）** → 6/6 节点逐字节一致。
5. **根因**：在样本不足（仅 entity→entity）时做了"恒 1"的过度外推；int→entity 实样才暴露
   真实语义。教训：**单一形态的字节巧合不能当规律**，至少两个差异化样本才能定语义；
   inferred 段样本到位前不做代码级"修正"。
6. **闭环**：dict 转 verified（双实样）+ 规律表 fixture + variables.md 更新（提交 44599da）。

## 三、为什么反复出问题——系统性根因（3 条）

1. **手解/手抄字节必然出错**（#1/#2）：hex 是给人读的摘要，不是给人算的——所有字节操作必须
   程序化：从样本 decode 状态提取、从测试常量程序化回填、比对用结构级解析。本会话两次踩坑
   都是因为图省事手抄/手解。
2. **归一化函数内部顺序耦合**（#5）：先删字段再判断字段（index），同族 bug 两次——模式：
   归一化必须"先判断后删除"，判断用 `?? 0` 容忍已删字段。凡"先清理后分支"的代码都要查。
3. **证据不足时的先验外推**（#6/#7）：单一样本的"巧合值"（1/1）和"资产侧现象"（同步）被
   当作规律/行为结论，两次被用户纠正——规则：**推断必须标 inferred/待确认，代码级修正必须
   等差异化实样，行为结论必须分层（资产侧 vs 运行时）**。

## 四、流程与方法论教训

1. **游戏核验矩阵协议（本会话最大产出，可复用）**：
   - 双轨差分：我方管线在 /tmp 副本模拟注入（连续累积）→ 用户编辑器实样 → 逐批核验；
   - 每批 = 独立小操作（覆盖容器×类型×形态×操作种类），一次保存一批；
   - 比对口径：变量语义字节逐字节一致；**位置（布局）与编辑器归一化（dict f6/Map25 升级、
     root46 审计）不纳入 DIFF**（标注 NOTE）；
   - 操作偏差（类型看错/默认名/值输错）→ 以样本字节为准，模拟对齐后继续（顺带覆盖新形态）；
   - 产出：6 处管线/CLI 差异修复 + 12+ 编辑器实样形态补位（非默认 str 图变量、Get 非默认
     alreadySetVal、dict 双类型、i1/i2 省略等）。
2. **结构级比对 > 字节级比对**：字段长度变化会让逐字节比对整段错位（#9）——实体/图记录用
   字段解析比对（cmp-entities-all/cmp-graph-nodes），位置字段显式排除。
3. **矩阵即证据**：每批核验都产出一个新的编辑器实样（新形态），即时回填规律表/文档
   （dict verified、玩家同步、双形态），防止"核验完就丢"。
