## 二、调查链（现象 → 定位 → 根因 → 修复）

**现象**（用户）：步骤 1 十字正常；步骤 2 角块阶段打乱十字。

**取证链（按决定性排序）**：

1. **机器对齐全时间线**（一次锁定回退轮次）：把 solveMask 写入 / 查表(mP,mLen) / 发布(solve_len) /
   执行(op3) / 状态发布(solver_cp/co/ep/eo) 按 rec 号合并排序 →
   十字 mask 0,0,1,1,3,3,7,15 正常；角块 mask 0,0,1,1,**3→2→3** 回退；
   回退发生在「轮5（mP=48、mLen=15 的 16 步长宏）执行完之后」（rec2044：
   cp[4]=1 角块离位 + ep[7]=10/eo[7]=1 十字棱翻转）。
2. **查表侧全部正常**（排除查表/索引/表数据）：该轮 mask=3、idx=75、p=c0[75]=48、mLen=15 均正确，
   离线表展开 = [3,3,3,-3,-2,-3,2,3,-2,-3,2,3,-2,-3,2,3]。
3. **执行序列差异**（决定性）：运行时实际执行 = 前 11 步正确 + **第 12 步起全变 2**（= 残留 code 15 → face 2）。
4. **根因**：pStep4 角块分支 `multipleBranches(mIdx)` 有 16 个命名 case，超引擎 10-case 上限
   （fcc7663 规则）→ mIdx≥10 的 case 成孤立链 → 全走 default → **mCode 不更新残留上一次值**。
   仅 LEN 12~16 的长宏（40..59 号）会走到 mIdx≥10，短宏（≤10 codes）不触发——
   解释了「此前轮次/此前多轮复测都正常」的假阴性。
5. **根因模型闭环**（最强证据）：离线模拟「旧逻辑（case≤10 生效+残留）」展开宏 48 =
   [..,2,2,2,2,2] **逐位等于**运行时日志序列；模拟「新逻辑（两段 MB）」= 表期望完整序列。

**修复（用户方案原话）**：「用 default 分支使用多个多分支就可以支持超过 10 个分支的情况了」——
第一段 case 0..9，default 内嵌第二段 MB（control=Subtraction(Get(mIdx),10)，case 0..5→C10..C15）；
控制值在 default 内重新读 mIdx 图变量（防分支内二次物化，2899 教训）。

**验证**：编译 9 GIA 全绿（主图 259→262、MB 10→11）→ 注入 ok 9 fail 0 → md5 一致（db9d6b85）→
读图核验（n=174 case[0..9]+default→n=177；n=177 控制值 Subtraction←Get(mIdx) 直连、
case[0..5]→C10..C15 查表链 mP 直连）→ var pins 全绿。**待用户复测**。

## 三、为什么规则已闭合还会复发——系统性根因（3 条）

1. **规则落技能但不回扫存量代码（本家族核心根因）**：MB 10-case 上限 08-27 已实锤、已写进
   `dsl-nodegraph-development` 技能（242-249 行）与 control-flow cookbook，但 solverPlan 的
   16-case 是**更早**（08-23 CFOP 移植）写的存量代码——规则落地那轮只修了当轮爆的视觉图，
   没有全项目回扫。规则对新代码生效、对存量沉睡，6 天后以完全不同的症状复发。
   **教训：每闭合一条「存量代码可能违反」的引擎限制，必须当轮做全项目静态扫描**
   （本轮扫描脚本见产出清单，可作断言雏形）。
2. **离线验证的图结构盲区**：verify-corner-macros（2000/5000 样本）验证的是**表数据**的
   保持性/收敛性，不含「图结构是否满足引擎限制」。表全绿 ≠ 运行时对。
   验证链分层应为：表数据（verify-*.mjs）→ 图结构（静态断言+读图核验）→ 行为（日志）。
3. **日志「Integer 空 vs 0」判读语义未闭合（本轮误导两次）**：p=0 的**有效表值**在日志
   `Get OUT0:Integer=`（空）显示；`Set IN2:Integer=`（空）写入后 dbgVal（DTC int→str）显示 "0"；
   而技能既有判读门说「空 ≠ 0（真 0 显示 Integer=0）」——三种表现并存，本轮先后误导出
   「查表读空失败」「solveMask 写空」两个错误假设（后被离线对照推翻）。**观察记录**：
   该语义与变量类型/int_list 上下文有关，尚未闭合——判读时**不要单凭空/0 显示定性**，
   必须与源码表值离线对照（本轮的做法）。

## 四、流程与方法论教训

**有效（可复用）**：
- **机器对齐时间线**：多源事件（状态写入/查表/发布/执行/发布回读）按 rec 号合并排序成单表，
  回退/破坏发生在哪一轮一眼锁定——比逐帧 grep 单点快一个数量级，且不会凑错轮次对应。
- **「旧逻辑模拟 = 日志序列」根因模型闭环**：2954 的「不可能序列判别」只证明序列非法；
  本轮更进一步——**把假设根因写成代码逻辑跑离线模拟，逐位复现错误序列**，根因即实锤。
  配套「新逻辑模拟 = 期望序列」双验证，修复正确性在编译前就有算法层证据。
- 先穷尽工件再下结论：mP/idx/solve_len/宏表全部离线对照后，才把嫌疑收敛到「展开环节」。

**绕路（3 次）**：
- 误判「16 步 = 两宏拼接」（实为单宏+残留尾巴）——被 solveBuf 残留历史经验锚定，
  未先核对 mLen=15 与序列长度的一致性。
- 误判「mP 读空 = 查表失败」（实为 p=0 有效值显示为空）——见根因 3。
- awk/JS 大整数精度坑**二次踩中**（技能警告在，写命令时未自查）：
  `v+0>9223372036854775807` 在 awk 中丢精度把 -1 算成 0，险些把「大量 val=0 非法 moveId」
  写进结论。**定则：负整数解析一律 python BigInt，禁 awk 数值运算。**
- JSON 层重建控制流邻接太费劲（4 轮工具调用后放弃）——应尽早换 explain/trace 官方工具。
