# 完整复盘：灯阵信号注册第 4 次错误——信号节点参数默认值（2026-08-16）

> 范围：从"信号注册反复报错"到"游戏正常进入"的完整差分闭环
> 核心：三版本差分方法论 + 同类风险探索 + 流程纪律教训

## 一、背景：信号注册为什么"一直出问题"（前 3 次 vs 第 4 次）

灯阵项目（1073741891「信号回归验证」）在 4 轮中反复出现"游戏拒载"类错误，前三次已闭合：

| 轮次 | 根因 | 修复 |
|---|---|---|
| 1 | `repair` 复刻模板 field5=2 但保留目标 f6=3 → 版本不一致 | 顺序反转（先读目标 f6 再改写定义 field5） |
| 2 | builtin 复刻版本 2 但 vec3 类型被拒 | 统一版本 >=3 |
| 3 | 逐个 register 旧信号版本停留偏低，新信号加入后未全表回填 | register 全表回填（只升不降） |

第 4 次（本轮）：**信号节点参数默认值**——与版本完全无关的全新根因。

## 二、第 4 次错误的完整调查链

### 2.1 现象
- 灯柱实体、挂载、信号版本（v5=5 一致）、84 节点图全部正确
- 游戏报"参数错误"，**级别极高，游戏根本进不去 → 无 Beyond_Debug_Log 日志**
- 用户试玩时游戏自动保存一次（v4），随后在编辑器手动修复（v5）

### 2.2 三版本差分（用户驱动的闭环方法论）
用户要求："用我们的机制再注册一次 → 对比我的版本/出错版本/修复版本 → 找出我们改了什么导致不可用"。

```
v3（我们注入）──试玩自动保存──> v4（出错）──编辑器修复──> v5（正常）
```

差分结果（发送信号节点参数 pin 逐字段对比）：

| 信号 | 参数 | v3 我们 | v4 引擎 | v5 用户修复 |
|---|---|---|---|---|
| lamp_toggle | vec3 senderPos | `i2={3,0}` + **空 VectorBase 默认值** | `i2={3,2}` 无默认值 | `i2={3,0}` **无默认值** |
| lamp_toggle | int hop | `i2={3,1}` + int:1 ✅ | `i2={3,0}` + int:1 | `i2={3,1}` + int:1 ✅ |
| win_check/win_ack | vec3 | 空默认值 ❌ | i2=2 | 无默认值 ✅ |
| level_clear | int | int:1 ✅ | 一致 | 一致 ✅ |

**关键结论**：v5 与 v3 的 `i2.index` 完全一致（vec3→0、int→1），**唯一差异 = vec3 参数的空 VectorBase 默认值**。
i2.index 不是问题，默认值才是。

### 2.3 根因定位（代码层）
1. vendor `Pin.encode()`：`value ?? undefined` → `simple_value_var()` 对 Vector 类型在 value=undefined 时
   **自动生成空默认值** `{class:VectorBase, bVector:{val:{}}}`（"编辑器兼容"策略，本意是让未使用的
   列表 item pin 通过上传校验）
2. post-encode 阶段已有两处同类清理：复合调用 InParam（有连接→value=null）、LocalVariable（type=16）
3. **信号节点（占位 300000/300001）遗漏**——这是同类规则的第三个应用点

### 2.4 修复
`src/compiler/ir_to_gia_transform/index.ts`：post-encode 对占位信号节点（300000/300001）的
已连接 InParam 统一 `value = null`。注意：此阶段信号节点仍是**占位 ID**（kind=22000），
SysGraph kind=22001 的改写发生在 encode 之后，因此不能用 kind 判断，必须按占位 ID 识别。

### 2.5 验证链
- 修复后 GIA 产物：信号节点已连接 InParam 带默认值 3 → **0** ✅
- 与 v5 用户修复版逐字段一致（vec3→NULL、int 字面量保留）✅
- 注入真实地图（备份 v5 → 注入 → 回读）✅
- 信号版本 v5 一致、挂载保留、84 节点 ✅
- **用户游戏核验：正常进入** ✅

## 三、风险探索（一处出错 → 检查覆盖面）

| 触点 | 检查结果 | 证据 |
|---|---|---|
| 服务端 send_signal conn 参数 | ✅ 已修复 | 本轮闭环 |
| 普通 SysCall 节点 conn 参数带默认值 | ✅ 无风险 | 注入后 11 处与编辑器保存版（v5）一致，游戏通过 |
| 复合 impl 内信号节点 | ✅ 无风险 | 扫描 0 处 |
| 客户端 send_signal_to_server conn 参数 | ⚠️ **未闭合** | 默认载荷源自 2026-07-11 编辑器样本（形态正确），但客户端信号游戏行为从未端到端验证；若引擎对客户端同样严格校验则存在同类风险，需后续实验（signals.md 已记录） |

**方法论**：默认值策略（"未设置 → 空默认值"）是 vendor 的全局行为，凡"已连接 InParam"都可能受影响。
已处理三类（复合调用/信号/LocalVariable），普通节点被引擎容忍。客户端信号是唯一形态可疑的未验证点。

## 四、流程纪律教训（最重要）

1. **写回后必须提醒用户重新加载编辑器再保存**（v19 教训复发！）：
   本轮前两次灯柱消失、第 4 次信号错误的 v4 版本，都是"CLI 写回 → 用户旧编辑器内存保存覆盖磁盘"。
   灯柱实体两次消失与此完全同因，不是结构问题。**写回后：用户重新加载 → 确认 → 保存 → 游戏测试**。
   （v19 教训出处：2026-08-14 复盘 `retrospective-2026-08-14.md` 灯柱实体消失事件确立的纪律。）
2. **游戏拒载类错误可能无日志**：加载期错误级别极高，Beyond_Debug_Log 只在游戏运行后落盘。
   排查顺序：确认进入目标地图 → 无新日志 = 启动期失败 → 走差分而非日志分析。
3. **用户驱动的三版本差分是最高效路径**：错误版/自动保存版/修复版三快照齐全时，
   逐字段对比直接定位"我们改了什么"——比在代码里猜快得多。
4. **同类清理要一次扫全**：修复同类 bug 时检查所有应用点（复合调用/信号/LocalVariable），
   并明确"引擎容忍范围"（普通节点带默认值无害）避免过度修复。
5. **插分技能必须先加载**：本轮曾绕路写多个临时脚本，实际差分流程、快照规范、
   compare-gil-root-wire.py 等资产都在 `editor-incremental-gia-investigator` 技能中。
