## 二、最近一次错误的完整调查链

现象：用户指出第一层求解未考虑单位时间负载，且断言「转动一个面，间隔 0.3s 就是比较极限的负载」。
要求：据此估算游戏可接受负载（节点数/秒）并合理修 tick。

1. **锚定安全基线**：读回真实 GIL，`flow_do_move`（一次转动主路径）完全展开 = **553 节点**；
   用户 0.3s/转是极限 → 可接受负载 ≈ 553 / 0.3 ≈ **1843 节点/s**。
2. **量化单 tick**：`solver_cross_step` 展开 736（含 `solver_cross_mask` 359、`solver_apply_code`×3 位 207 等），
   phase2 每个 tick 还额外跑一次外层 `solver_cross_mask` 359 做完成判定，单 tick 最坏 ≈ **1095 节点展开**。
3. **反推间隔**：1095 / 1843 ≈ 0.59s。留约 15% 余量取 **0.7s**。
4. **修改 + 验证链**：`solver_start_tick` 的 `start_timer` 延迟列表 `[0.7]` → 编译 → `decode-gia` 核验
   `solverTick` 延时 float=0.699999988079071 → 注入真实地图。
5. **耗时重估**（对 190080 合法十字状态穷举平均 7.56 步、最大 12 步）：
   - 规划完成：平均 8.56 tick × 0.7 = 6.0s；最长 13 tick × 0.7 = 9.1s。
   - 播放阶段不变（1.2s/转）：平均 22.32 转 = 26.8s；最长 40 转 = 48.0s。

## 三、为什么反复出问题——系统性根因

1. **重计算 tick 间隔先拍值后标定**：第一次修改直接用了建议值 0.2s，没有先把「可接受负载」
   锚定到一个已知安全操作上。正确顺序是先找用户确认一个安全基线（什么操作、多大间隔不踢），
   再算节点率，最后反推参数。
2. **节点量级不是直觉能估的**：求解单 tick 展开约 1095 节点，是面转主路径 553 的近 2 倍——
   这直接解释了 0.2s 可能仍然偏危险。图预算工具 `assets:node-graphs nodes` 给出的是展开口径，
   应作为负载粗估的第一工具，不能凭感觉。
3. **日志口径与展开口径混用风险**：本次用的「展开节点/s」是静态口径；真实被踢指标是
   Beyond_Debug_Log 的「每秒负载」（f6 负载求和）。静态展开只用于快速粗估，精确定位必须回日志
   `perf` 每秒负载表复核（debug-log-investigator 技能第 4 步）。

## 四、流程与方法论教训

- **锚点标定法（本次沉淀，可复用）**：
  1. 找用户确认一个已知安全操作及其极限间隔（如「转动一个面间隔 0.3s」）；
  2. `assets:node-graphs nodes --graph <id>` 读该操作主路径的展开节点数；
  3. 算可接受节点/s = 操作展开节点 / 间隔；
  4. 读重计算单 tick 的展开节点数；
  5. 安全间隔 ≥ 单 tick 展开 / 可接受节点/s，并留 10%~20% 余量；
  6. 有日志后必须用 `scripts/gia_log.py <日志.gia> perf` 的每秒负载表复核真实值。
- **仿真先行**：CFOP 十字策略在本地用 CubeLib 穷举 190080 状态，得到平均 7.56 步/最大 12 步，
  让间隔=步数×tick 的耗时估算有据可依，不需要游戏内盲测。
- **小步快改 + 单点提交**：两次修改各自独立提交，commit message 带锚点和公式，方便回溯。

## 五、风险探索与未闭合项

- **单 tick 重复计算**：`solverCrossStep` 内先算一次 `solver_cross_mask`（359 展开），外层判定又算一次。
  若合并可把单 tick 降到约 736+根图≈780 展开，同等间隔下负载再降约 28%，或可支持更短间隔。
- **F2L/OLL/PLL 更重**：后续层求解每步查表/应用开销预计远超十字，必须用同一锚点标定法预先评估
  tick 间隔与单 tick 拆分粒度，不能再拍值。
- **日志复核**：0.7s 是否真的安全，需要在用户游戏内核验后抓一次日志 `perf`，确认求解秒段内
  「每秒负载」低于历史被踢分水岭（参考 debug-log-investigator：10s 窗口 ~3.4 万为分水岭，需重新读当轮口径）。
