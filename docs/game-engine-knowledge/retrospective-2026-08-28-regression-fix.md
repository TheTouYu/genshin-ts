## 二、回归事故的完整调查链（现象→定位→根因→修复）

**现象**（用户）：转动时出现黑块、直接收进去、位置错乱——最基本的渲染都坏了。

**定位链**：
1. 日志 2956 rec13 帧 [9]：`复合:发送信号` 节点吃到 `String=bufPos` 参数——set 图变量被错误路由到发送信号节点。
2. rec22 帧 [8]：pStep=3 时 `stage` 图变量读空（OUT0 空）——无关图变量被污染。
3. GIL 回读：solverPlan 里 append 调用节点 `outputs: [('next','Integer')]` 悬空——**数据边错乱**。

**根因**：37584a8 的修复方案把「写址游标」设计成复合的 `pos` 入参 + `next` 出参，且 `nextOut` 在 doubleBranch 的两个分支内各自赋值。**给带 doubleBranch 的复合新增数据输出引脚、且输出值在分支内赋值 = 高危反模式**——分支 join 时数据边错位，悬空的 next 引脚被相邻节点（发送信号）的参数污染，进而污染无关图变量（stage）和视觉状态（blockOrient）。

**修复**：撤销数据引脚设计，游标改回「复合内读写独立图变量 bufPos」闭环（bufPos 由 pStep4 追加链独占、与 solveLen 同步清零/推进），调用方零引脚变化。回读核验 call node `inputs=[code,raw] outputs=[]`。

**验证**：编译 8 GIA 全绿 → 注入 ok 8 fail 0 → GIL 回读确认无悬空引脚 → resync md5 一致 → **用户复测通过**。

1. **「修 bug 引入更严重 bug」的元教训**：37584a8 的竞态修复方向（消除 solveLen 二次物化）是对的，但实现手段（复合数据引脚）踩了另一个更深的坑。**教训：修复方案要选「已验证过的安全模式」，不要为了"更干净"引入新的 DSL 特性组合**——复合内读写图变量是项目里反复验证过的模式，复合数据引脚+分支赋值是未验证的高危组合。
