## 二、最近一次错误的完整调查链（28 模板 root20 状态误判）

- **现象**：`buildSkillConfig` 对 v10（28 创建前）输入抛「root20 状态未采样 fail closed」，最小复现稳定。
- **差分**：直接检查输入快照 root 字段 → 发现 **v10 root20 字段存在且 len=0**（空占位），
  而非「缺失」——此前 extract-root20.ts 输出空被误读为「无字段」。
- **根因**：CLI 状态机只处理「缺失 / 1970B 创建态 / 2955B 绑定态」，漏了「len 0 空占位」；
  而 28 创建前的真实地图状态恰是空占位。
- **修复**：三态 + 空占位四态处理；`isCreated/isBound/isEmpty` 显式判断。
- **验证**：v10 → 创建 → root15/16（除模型外）+ root20 与 v11 逐字节一致；v10 → 创建+绑定 → 与 v12 一致（6/6 PASS，已固化 tests）。

## 三、为什么反复出问题——系统性根因

1. **字段树 dump 的静默盲区是模板提取的唯一盲区来源**：walk 递归对空消息（len 0）无输出，
   「看起来完整」的字段树实际缺字段；所有手抄常量直接继承盲区（#1/#2/#7 同源）。
   教训：**模板必须来自逐字节 hex 对比，不能只信字段树 dump**；空消息字段要专门检查。
2. **相邻快照的验证基线纪律缺失**：快照对是「v_n-1 → v_n」差分的，重放/验证必须用前驱快照；
   一步生成场景（创建+绑定同时）要从最早的合适基线直接到终态（#4 四次踩中）。
   教训：**先画快照时间线，再选基线；「同 ID 已存在」是基线选错的哨兵**。
3. **wire 嵌套层级是最高频错误源**：同一字段号在不同层级语义不同（30.1.1.4 vs 30.1.4、
   78.1.1.f2 vs 78.1.f2），解析（list）与构造（build）各踩两次（#3）。
   教训：**层级深（≥4）的字段先写完整字段树路径再写代码；解析和构造复用同一路径常量**。

## 四、流程与方法论教训

- **同构重放是 CLI 生成类代码的黄金验证**：CLI 输出 vs 编辑器快照逐字节一致（19 快照 × 20+ 断言），
  比「回读语义正确」强一个量级——本任务 3 个模板字节错误全部由它抓出。
- **用户实测/澄清闭合「分配类」规则**：客户端图 ID 段起始（用户初始地图实测）、固定造物模型
  （用户确认遗迹守卫 10005001，快照 10007001 非默认）——比多样本推断更快更权威，且纠正了
  「快照即正确」的假设。
- **重放基线选择 = 先画快照时间线**：差分轮次是链式的（v0→v1→…→v18），每步验证用前驱；
  一步生成（create 带绑定）从最早无该 ID 的快照起。
- **空消息/空字段是 wire 解析的常漏点**：len 0 的 wire2 字段在 dump 与对比脚本中都要显式显示。
- **注入链路**：客户端图注入用主配置编译（单文件 entry 配置触发 ctxType 断言失败）→
  单文件注入自动改写图 ID → 注入后图名变 `_GSTS_<基名>`、nodeCount 变化是回读哨兵。
