## 二、调查链：从 E2 假设到判负

1. 基线事实（票13）：近距施放 71-76/s、客户端 P 发送 11-12/s（gate 掐住）、apply 3.9-4.6Hz、
   送达 ≈0.08s；推论 gate 常开后 apply≈1/(cast gap+0.08)≈10-11Hz。
2. E2 改造（去 fb_ball_gate 读，条件 hasTask ∨ (eEq ∧ state≠4)）+ 注入（SHA 1898c6ae…）+ 读图自检全绿。
3. R0（3129）：cast 80.4/s、P 发送 72.5/s（gate 常开机制生效 ✓），但 75% P 为垃圾
   （tick=None、Vector nan——镜像空读/撕裂快照，引擎侧 0 nan=发送即拒）；服务端只收到有效 P 17.4/s；
   apply 7.5/s、流速 0.75。用户手感"与之前一样"。
4. R1（3130，加 mirrorTick>0 有效镜像门）：垃圾 P 75%→~1/s；apply 8.0-8.5/s；流速 0.81-0.85；负载仍高。
5. R2（3131，dt 0.1→0.12）：apply 6.9-8.0/s 分阶段、流速 0.83-0.96（仅高到达段达标）；用户"手感一般…
   负载踢出…不是核心原因"。
6. 假设审计：apply 4.6→8.5Hz（+85%）未转化为手感 → "applyHz 是手感杠杆"被证伪；
   实测 ~8Hz 为闭环锁步天花板（客户端须等服务端镜像 tick 回写才发新版本，2×0.08s+处理≈0.12-0.15s/圈），
   E2 无法触达用户定义的核心目标（同步率≥20/s）。→ 判负、回退、主线转票14（原生写通道，打破锁步）。

## 三、为什么反复出问题——系统性根因

1. **中间指标冒充最终目标**：applyHz 是可测中间量，但用户最终判据=手感（=同步率≥20/s 级 + 无抖/无迟）。
   三轮实验只盯 Hz 表，未把最终目标先量化（20/s）再反推候选线，直到用户第 3 轮才给出真目标。
   教训：实验立项先问"用户感知到的差=哪几个具体现象 + 目标数值"，再用数据归因。
2. **引擎节流被当纯瓶颈，忘了它也是负载保护**：gate 关门/重开把 apply 掐到 ~5Hz 的同时把客户端计算与
   详情日志量掐在 ~12/s。移除节流前未做负载预算（日志体积/服务端执行面 vs 引擎踢出阈值），
   导致 2.0MB/s 详情洪泛与服务端 30-40/s 处理面直接触发超限踢出。
   教训：动"节流"类机制前先量化其保护面；高频实验先降详情日志配给或用活动画像粗测。
3. **会话内知识未即时回灌**：日志 schema 形态（records=repr、f3 裸键）、"退出才落盘"话术、
   P 载荷垃圾判读形态（tick=None/nan、0 向量归一化异常）等均为可复用判读知识，散布在会话里，
   复盘统一回灌 debug-log-investigator 与 client-nodegraph-development。
