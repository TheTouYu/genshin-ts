## 二、最近一次错误的完整调查链（日志 2954 帧级取证）

**现象**（用户）：①复原第一层时十字被破坏，卡在十字/角块循环（非 100% 复现）；②缺速度切换选项，且日志收集依赖慢速模式（快速模式会卡退）。

**取证链（按决定性排序）**：
1. **部署表 vs 离线表逐字节差分**（先排除表错）：CF_E_POLICY 四块/宏 LEN/C0-C7 与 tools/e-layer-policy.json 全一致（C1-C7 的 18 vs -1 是表内无效位哨兵，mLen 之内不会读）——算法表没问题。
2. **extract 铁证 A**：rec138（op5 重算入口）读到 solveBuf 残留 `[255×9, 1, 3, 3, 1]`——9 连 255（负 moveId 的 int8 投影）。
3. **宏表穷举**：离线全部角块宏的负 moveId 最长连发 = **3**（例 p48: [3,3,3,-3,-2,-3,2,3,...]），9 连 -1 不可能由任何单一宏产生。
4. **extract 铁证 B**：提取全部 28 次 op3 发码序列（rec40→1177），实测出现 **-1×6 连发**（rec829-961，两次 3 步间隔）——印证 solve_seq 内含重复段。
5. **根因**：solverAppendCode 的 `sl = getNodeGraphVariable('solveLen')` + 尾部 `setNodeGraphVariable('solveLen', sl+steps)` 在 IR 里是表达式；pStep4 每 tick 一个 code 的追加链与 op5 重算入口（solveLen=0 + clearBuf）在相邻 tick 交错时，sl 的物化时机与 solveLen 写序不一致 → 下一个宏从错位起点追加 → 序列重复/跳码 → **宏残缺**（十字只在宏内部临时破坏、靠宏尾恢复——残缺 = 永远停在中途）。
6. **与用户现象完全吻合**：十字被破坏后卡循环 + 非 100% 出现（竞态窗口取决于 op5 与最后一个 append tick 的相对时序）。

**修复**：solverAppendCode 改显式 pos 入参；pStep4 用独立 bufPos 图变量推进写址（append 后 bufPos=next、solveLen=next 同步）；op5/op12/op13/op8/stage 转场所有入口统一清 bufPos+solveLen。

**验证**：编译 8 GIA 全绿；离线 E 层宏验证 300 样本+U/E 二层测试 151 样本全过（追加语义未变，仅显式化）；预算 128 ✅；注入 ok 8 fail 0；resync md5 一致。

## 三、为什么反复出问题——系统性根因（2 条）

1. **「图变量多次读 = 多次物化」是本引擎 DSL 的一级陷阱**（O-2026-08-27-05 → 本次实锤#2）：IR 表达式里的图变量读取在物化时机上有自由度，跨 tick 链共享的图变量（solveLen/solveIdx/mIdx）一旦被并行的 timer/signal 链写入，就会产生"读旧值"。**教训：跨复合/跨 tick 的位图推进改用显式入参（pos 传入、返回 next 输出），复合内只做纯数据运算**——把状态机的所有权收敛到单一链。
2. **多规划器/多执行器共享实体上的让位入口分散**（op5/op12/op13/op8 散在 handler），每加一个新变量（bufPos）都要记得清所有入口——本次靠全局 search&replace 覆盖。**教训：让位清理应集中成一个复合（如 solverResetPlanState），新增共享状态只改一处**（本轮用 5 处重复 set 已是坏味道，登记风险）。

## 四、流程与方法论教训

- **决定性的一步**：把日志里的 op3 发码序列**完整抽取**（28 条），离线重放+穷举离线宏比对"不可能序列"——比逐帧比对变量快一个数量级，且直接排除/锁定"表错 vs 管线错"。
