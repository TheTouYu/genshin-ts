## 二、最近一次错误的完整调查链（"游戏 UI 慢"这条假结论）

- **现象**：`ys-playtest-start` 58s、`stop` 19s；弹窗"要等 7~25s"；据此我曾把"UI 抖动 5~25s、固定 sleep 必漏"写进技能。
- **差分（逐环节计时）**：全窗 `import -window` **5893ms** ／ 40×40 裁切 **84ms** ／ `magick` 采样：大图 105ms vs 小图 11ms。
- **根因**：判据本身用全窗截图，成本记到了"游戏 UI"账上。**真实 UI 时延只有 1~2s**。
- **修复**：判据只截 40×40（`_ys-ui.sh`）⇒ 轮询间隔 2s→0.25s ⇒ start **8.3s**、stop **8.2s**（合计 16.5s，用户手工宽松基准 43s）。
- **验证**：同机同版本前后对照；两轮独立会话复测。
- **教训**：**仪器成本与被测行为必须分开量**——凡"被测对象慢/抖/不稳"的结论，先给测量链路计时。

## 三、为什么反复出问题——系统性根因（3 条）

1. **仪器盲区**：我做的是"用截屏观察程序"，却从未给观察者本身计时。整波 1 小时返工都源于此，且错误结论一度被写进技能（污染面 = 后续所有据此设计的等待逻辑）。
2. **没有成本链框架时会打错主导项**：**进程启动 > I/O 面积 > 计算**。不排序就会去优化"计算"——第一版 NCC 我写的是 Python 双层循环，比 GPU 版本慢几个数量级；修好算法后主导项又变回进程启动，于是才有了常驻服务。
3. **规则与方法落点错位**：写进项目文件而非全局、只留文档不进技能 ⇒ 下次不生效。用户两次纠正都指向这里（位置 + "优化方法的方法也要沉淀"）。

## 四、流程与方法论教训（用户原话逐字）

1. 「**改错地方了，全项目通用，不是改这里**」→ 落点判据：**跨项目行为纪律进全局守则；项目专属细节进项目文件/技能**。且"条数上限"是坏判据——一条长条目可以比五条短条目更贵 ⇒ 已改为**体积判据 ≤4KB**（用户裁定接受）。
2. 「**我说：全部项目通用！执行的所有命令，如果可能超过5s，都要特别注意优化时间！除非是真需要，禁止一个类型命令跑超过20s，确实是长任务就放后台。**」→ 全局守则第 5 条。
3. 「**还有，识别图片本身，用上gpu优化，本机有3060，cpu兜底。注意这些方法是可以复用的。然后优化方法的方法也一样。**」→ `ys_look.py`（GPU 优先 / CPU 兜底 / 成本链自适应）+ 元方法写进 `computer-use` 技能。
4. 「**这个会话学习到元方法和核心规则，优化到全项目的AGENTS.md里面去吧。……你说gpu启动时间长，那你可以做成一个系统服务呀。**」→ 全局守则第 6 条 + `ys-lookd` 常驻服务。
5. （基准）「**试玩和退出试玩两个流程，我总计用非常宽松的方式，跑了，加起来才43s**」→ **用户给的是可比较的基准数字**，比"再快点"有用得多；把基准写进任务目标，优化才有停止条件。

**方法论收获（可复用）**：
- **优化四步**：拆环节计时 → 按成本链找主导项 → 一击打主导项 → **复测留前后数字**。
- **沉淀三层**：可复用资产（工具/判据库/常驻服务/包装器）→ 方法进技能 → 纪律进守则。
- **重型依赖常驻化**：任何"每次调用付固定启动成本"的东西（模型/CUDA/大索引）→ 常驻服务 + 客户端自动回退。
