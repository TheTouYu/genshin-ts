## 二、最近一次"错误"的完整调查链（以第 8 项：抽查→全量→缺陷群暴露）

1. **现象**：抽查断言 9/9 PASS、`npm run build` PASS，但用户问：50+ 个差分快照有没有挨个跑过、分级对不对、概念是否都出现。
2. **用户重新定义验收**：全量枚举 + 人工结论对照（原话见第四章），而不是"代表样本变绿"。
3. **第一次全量体检（审计脚本）**：80 个快照全部构建成功，但发现 `flat` 数量普遍 < root9 记录数（模板根/系统记录/未归属缺失）；同时 `unknown=未归属:未归属` 是虚拟根误计。
4. **根因定位**：记录家族与内容组件混淆（谱系 #1）→ 模板根没进树、素材组没挂上；再顺藤摸出 #2/#3。
5. **修复 + 重跑**：通用不变量（每条记录出现、无重复、无 unknown 误归类）→ 80/80 PASS。
6. **逐轮人工结论对照**：47 项（重启 1–66 key 概念 + 旧轮概念）又引出 #4（几何垃圾值）、#5（消息项样式序号）、#7（diff 重锚）——全部修完后 127/127 PASS。
7. **真 CLI 端到端**：`assets:ui list --flat/--tree --format json` 对 80 个快照逐个执行 → FAIL=0；`diff --anchor` 冒烟 → 仅 2032 geometry PLAYER，源 GIL sha 前后一致。
8. **可复查**：补 `ui/verification/ticket04-command-output-samples.md`，输出落盘可复现。

## 三、为什么反复出问题——系统性根因（3 条）

1. **验证设计是"代表作抽样"，不是"全量枚举"**。9 项抽查样本对应 9 个已知结论，天然只覆盖"我已知的路径"；family/geometry/message 这些缺陷藏在**没被抽查的轮次与结构**里，抽查全绿只是假象。教训：样本/快照类验收必须先列出**全量清单**，再写**通用不变量**（记录覆盖、无重复、无 unknown），最后才是逐项人工对照。
2. **语义层对 wire 的分层建模不完整**：记录"家族"与内容"组件"是两层 type 码，领域模型（类型注册表）里没有把它们分开建模，实现时临时拼"comps 签名"导致判别短路。类型注册表应明确声明"家族槽 + 内容组件签名 + parent 上下文"三要素。
3. **只验证了库函数，没验证"真命令 + 可读性 + 可复查性"**：断言脚本直接调 `buildSemanticView`，没有对 80 个快照跑真实 CLI；输出也只活在终端。后续验收应三件事一起做：库函数断言 + 真实 CLI 端到端 + 输出落盘样例。

## 四、流程与方法论教训（含用户原话）

1. **用户原话（逐字，2026-09-03 核验纠偏）**：
   > "我这边希望你的核验要求高一点。比如说我们这边有 50 多个进行插分的快照，你有没有挨个对这些快照的地图去执行列出的命令，看一下列出的分级是不是正确的，这些概念是不是都出现了？如果全部都 OK 了，那自然就是测试通过了。"
   > "你刚刚跑的那个结果有记录吗？我想看一下我们这些命令的输出长什么样"
2. **可复用方法论（已回灌部位见第五节）**：
   - 快照/样本/日志类验证：先枚举**全量清单** → 通用不变量断言（覆盖/唯一/无 unknown）→ 逐条对照人工结论；**禁止**只抽查代表样本。
   - 验证必须走**真实命令入口**（CLI 端到端），不能只调库函数；输出要**落盘可复查**（样例文档/断言脚本），不能只活在会话里。
   - 审计脚本先行（跑全量体检列出 BAD），再修，再写正式断言——避免边写断言边猜缺陷。
3. **帮助定位的方法**：`audit-ui.ts` 第一版（80 文件统一输出 records/flat/dup/unknown/missing）是最早上手的工具；它把"覆盖面"变成了可打印的差量，比逐个读人工结论快得多。
