## 二、拒载（#4）完整调查链——本轮最硬的教训

**现象**：游戏报"复合节点内部参数不匹配"（phys_fly_tick(1) 内部 dbg_tag tag 参数）。读图工具（explain/parse）
显示一切正常——报错位置在源码里根本不存在。

**关键转折**：用户提示"真实地图里的复合节点有两个版本，带小括号 (1) 的是刚刚注入的版本"。

**差分定位**：`parse-gil-node-graph --list` 全量复合目录 → 实锤两个版本并存：

- 正确版 1610700000~1610700020（主图/impl 引用全部指向此区间）
- 错误版 `phys_fly_tick(1)` 等 9 个（id 21-29）+ carry_spin 残留（0006），**零引用**

**根因确认**：读 `phys_fly_tick(1)` impl 图内容——装着 `dbg_phys_snapshot` 调用和 4 个 done 出流
（正确版只有 1 个），内容完全错位。游戏加载时校验**目录里所有复合**（包括零引用条目）→ 错误版本触发拒载。
注入器的同 id 覆盖（mergeWrappedFieldMessages）不会删除地图多余条目，错误版本长期残留。

**修复**：删除 10 个无引用错误复合（def+impl）→ 回读核验目录只剩正确版 → 用户游戏验证通过。

**未闭合**：`(1)` 版本的**产生路径**未锁定（某次编译/注入把复合改名追加而不是同 id 覆盖），
存在复现风险——见第五节。

## 三、为什么反复出问题——系统性根因

1. **读图核验工具只解析"被引用版本"，不枚举"目录全量版本"**：explain/parse 默认展开主图引用链，
   错误副本不在引用链上就永远看不见。工具侧全绿 ≠ 游戏侧能载——游戏校验目录全集。
2. **注入器只做合并覆盖、不做清理**：同 id 覆盖正确，但地图中"历史遗留的异 id 错误条目"无人负责删除。
3. **把默认参数当生效配置、把事件 payload 当 any**：两次都靠运行时炸出来才纠正；类型化 API（Signal.xxx → evt 类型化）
   和官方文档（教程 3.10 配置范本）其实早就存在，是"没查透 + 写 any 习惯"掩盖了它们。

## 四、流程与方法论教训

- **游戏报错与工具读图矛盾时，第一步列全量复合目录**（`parse-gil-node-graph --list`），先看有几个版本，
  再看引用关系——用户"两个版本"一句话省掉了三小时猜 wire。
- **注入后核验清单补一条**：复合目录无重名（无 `(1)` 后缀）、无未引用的历史版本、主图引用全部落在最新版。
- **onSignal 永远不要写 `(evt: any)`**：用 Signal.xxx 定义时 evt 类型化（evt.params.<名>），笔误在编译期就死。
- **贴地球用命中检测默认槽有"创建即被地面消耗单次触发额度"风险**，必须在编辑器把触发类型/筛选/延迟配好（官方教程 3.10 范本）。
