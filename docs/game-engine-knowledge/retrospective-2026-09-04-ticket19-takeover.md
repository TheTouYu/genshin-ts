## 三、系统性根因（3 条）

1. **引擎语义铁律只认受控实测，我却反复用推断先行**：技能变量"全局"（文档层推断，实测=实例隔离）、节流源（球距推断，实测=玩家距离）、渲染节拍（代码读数 0.09，实测驱动节奏 0.6s）——三连推断错。教训：**凡影响架构/协议设计的前提，先做最小实测（客户端帧/逐拍重放），推断只能当候选假设**。
2. **用户模型是架构裁决者，别在错误架构上做局部优化**：用户在 apply 率/帧负载数字上两次叫停并教架构（"客户端算好只发对的/服务端只写变量/渲染独立调频"）——2800 帧/s 的账是在"每信号驱动渲染"的旧结构里算的；架构按用户模型重拆后同目标自然轻一个量级。教训：性能目标撞墙时先问架构前提是否成立，再谈系数。
3. **判读纪律有规则不执行**（详情开窗规则 2026-09-02 已入技能，09-04 仍犯）——规则存在≠执行；需要"判读前强制步骤"而非"注意事项"。已补流程 0.4。

## 四、流程与方法论教训（用户纠正钩子逐字）

- "服务端不能太高的频率，2800绝对不行。我们停下来，说清楚这个原理。" → 性能账先分清客户端/服务端面与每信号成本构成，超线先停手讲原理
- "说一下我的想法：1. 所有数据在客户端算好，定时发送给服务端。2. 服务端接收频率大概每秒 20 次，收到后把变量写入。3. 渲染服务可独立调频……" → 架构类问题先问用户模型（接收=写变量/渲染=独立调频/客户端=计算），按模型拆图
- "这个降频行为发生在造物和玩家距离变远的时候" → 节流源实测修正（AI 射程=玩家距离）；推论类归因必须标注"待实测"
- "我全程都没有进行移动……只有用户选择性的打开了一些节点的日志详情，这上面才会有记录" → 详情开窗=记录边界；无记录≠未执行（技能 0.4 固化）
- "感觉每次落地的瞬间，它这个旋转一下就转起来了……我想知道你这个算法是怎么算的？" → 算法变更交付时先讲清模型与预期量级，给用户可对照的数学预期
- "碰到地面后，速度在一瞬间又变快了，而且全体现在一个旋转上，这明显就是 bug" → 用户物理直觉=能量守恒检查（旋转凭空建立=真 bug 探测器）
