## 二、最近一次错误的完整调查链

**现象**：悬浮交互页创建后编辑器显示"内置了之前的控件"（页签/视窗/按钮）

**差分**：用户修复版 vs 我的候选逐字节对比

**根因链**：
1. 模板 t4 的 packed 实例回指未重映射 → 新模板指向旧实例
2. 旧实例 t42 → 旧实例侧组 → 含页签/视窗/按钮 → 编辑器显示旧内容
3. 此外关闭按钮 t52 被 parse→emit 损坏（max-uint64 精度丢失）→ 编辑器识别为无效记录 → 全局重建

**修复**：原始字节重映射 + 显式 packed 处理 + 4 条记录规范结构

**验证**：用户编辑器核验通过（"是对的"）

## 三、系统性根因（3 条）

1. **样本时效性**：用轮1 样本（6 条记录、t42 末尾）作为源，但编辑器版本已更新（4 条记录、t42 第二位）。真实地图必须从最新编辑器版本提取源。
2. **parse→emit 往返不可靠**：TS 的 `parseWireMessage` + `emitWireMessage` 对 max-uint64、packed 流、wire type 3/4 有精度损失或静默丢弃。字节级操作（`remapVarintBytes`、`replaceAllVarints` 加 packed 处理）更安全。
3. **知识落盘赶不上开发节奏**：差分的 wire 结论学完就写代码，但"编辑器自动补全控件组"这类行为级的发现没有第一时间验证 → 导致第一次写回后编辑器自动修复才暴露。

## 四、流程与方法论教训

- **+** 用 Python 先验证 wire 提取再写 TS 代码（t41 变量、状态块）——有效防止多次 rebuild
- **+** 用户修复版逐字节对比 → 一次性暴露 3 个问题
- **-** build 太慢（tsc 全量编译 3-5 分钟，残留进程导致更慢）——后续优先用 `npx tsx` 直接运行 src 测试，确认后再 build
- **-** 构建残留进程：`npm run build` 被 SIGTERM 后 tsc 子进程存活 → 后续 build 出现多 tsc 竞争 → 构建时间从 1 分钟激增到 10 分钟。应在 kill npm 时同时 kill tsc 子进程。
