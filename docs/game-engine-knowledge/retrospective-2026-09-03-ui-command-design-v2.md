## 二、最近一次纠偏的完整链路（V1 → V2）

现象：v0.1 交付后用户反馈"有一些是错误的，而且没有经过严格的推导"。
差分：把设计逐条对照 63 轮领域知识 → 发现三个结构错误（页签 placement 无约束 / 缺两代体系模型 / 缺推演验证）。
根因：①wire 规则学得多但**产品语义约束**（什么能放哪里、什么操作根本不存在）没有单独收集——
差分只能学到"允许的操作怎么做"，学不到"不允许的操作"；②设计没有把规则当作验收用例。
修复：V2 = Surface 放置面模型 + placement 表 + **推演验证法**（56 条规则假装实现映射：51✅/5⚠）
→ 定向差分轮 64-66（placement 三控件样本、删除两件套、默认选择序号 varint）+ 用户结论（A7）→ 56/56 全绿。
验证：推演表成为设计冻结门禁（任何命令改动重跑受影响行）。

## 三、系统性根因（2-3 条可复用规律）

1. **领域约束与 wire 规则是两类知识，收集路径不同**：wire 靠差分轮（用户操作样本）；领域约束
   （可放置面/操作存在性/父子关系）靠**用户口述与官方文档**——差分学不到"不允许"。设计前先问：
   "这个操作在编辑器里存在吗？能放哪里？"（A7 教训：我设计了不存在的实验）。
2. **设计必须带验证器**：推演法 = 设计的编译期检查（规则→假装实现的命令调用，映射不出/麻烦=设计错）。
   没有推演的设计 = 未验证的断言；推演表要成为设计的常驻门禁（V2 已固化到 DESIGN 第五章）。
3. **复杂层级先建领域模型再谈命令**：两代体系（布局 vs 悬浮页-容器）并行+递归（容器套控件、页签管容器显隐），
   命令面形状完全由领域模型决定；模型错则命令面全错（V1 教训）。类型注册表须含 placement 与 parent 上下文
   （轮64：控件与 member 签名相同，判别必须带 parent）。

## 四、流程与方法论教训（用户纠正钩子逐字）

- 用户纠正 1（领域模型）："页签实际上不能直接存在布局里…悬浮交互页是一个较大的范畴…里面可以创建容器。有了容器概念后，容器层级跟布局很类似…页签可以管理（控制）容器的打开/关闭…"
- 用户纠正 2（验证方法）："推演就是拿着你的设计，假装已经实现了这个命令，然后去对应所有的规则。如果能映射出来，设计就是 OK 的；如果映射不出来，或者用起来很麻烦，那设计就不太行。"
- 用户纠正 3（体系史）："老版本里直接有布局概念…后来游戏进行了一波升级，出现了悬浮交互页。它可以理解为一个像网页一样的大浏览器…它的优点在于可以直接使用页签来控制里面控件的属性…传统做法在布局里控制开关需要使用节点图，而使用悬浮交互页就不用写节点图。"
- 用户纠正 4（差分边界/结论优先）："布局里不能添加'悬浮交互页'这个控件…但别的普通控件是可以的…这些可以直接放在容器里（包括悬浮交互页的容器），或者直接放在默认布局、自定义布局里。这是结论。"
- 方法论提炼：设计被否时不要只修表面——先问"我的哪类知识缺了"（此例=领域约束类）；用户给出结论性纠正时（"这是结论"）立即落盘为权威并收窄实验范围，不追问"要不要我再差分验证"。
