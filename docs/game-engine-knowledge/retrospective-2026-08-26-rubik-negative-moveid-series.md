## 二、最近一次错误的完整调查链（2899）

1. **现象**：用户最小复现——反向开关 + 手动面转，旋转面错位（少 90°）。
2. **物料**：2899 仅 7 次请求（3,3,3,-3,2,2,-2）。
3. **差分取证**：
   - `pendingMove` 写入序列 → 两个负值各自应产生 3 逻辑 + 1 视觉；
   - 事件计数：execMove 14 / negDone 4（turn 记录）/ unlock 3；
   - **帧签名**：negDone 记录帧数呈 25/22 → 25/22 交替（25=请求逻辑-only 步进、22=请求视觉）——每负值只走 2 步 + 1 视觉；期望应为 25/25/22。
4. **根因**：negDone 分支复用 `ph` 表达式（写回后二次物化——与 solveIdx 2887 同族，代码注释已双重标注）。
5. **修复与验证**：分支改读 post-set 值；真实 GIL 读图确认 `Less Than` 数据源直连 `Get(negPhase)`，不再经 Addition。
6. **同族扫描**：`f.addition(f.getNodeGraphVariable(...))` 全家扫描——rubik-2x2 game.ts、rubik-3x3 flow.ts 均为「写后重新 get」安全写法；football goalCount 单次消费无分支复用。**仅本处，已修。**

## 三、为什么反复出问题——系统性根因

1. **「推进计数器：先写回、再显式读回判断」铁律第 3 次被踩，且是本轮自己写的代码在明知铁律下重犯**。
   防线有两道都失效：设计时无 checklist 强制；仓库已有 `gsts/server-repeated-evaluation` ESLint 规则，但 examples 没有 lint 门禁，从未在此类代码上跑过。
2. **单轮改动变量过多，违反「每轮一个可归因变量」**。`542c763` 一轮同时改：节拍 3 参数、折叠机制、执行器状态机、publishShared 减负、调试标签裁剪。2897 串台与 2899 跳步都是上一轮新塞入的 bug——每次修复都靠用户下一次复现补课。正确姿势应为：先回退求稳 → 单变量重构 → 逐个验证。
3. **折叠/分片类优化缺少「帧预算与日志签名即设计输入」**。7748853 设计时没算 3027 > 3000（差 27 帧）；542c763 拆分正确，但注入前没有预设「负向期望日志签名 = 3×逻辑-only 记录 + 1×视觉记录」作为验收，2899 才发现跳步。教训：新状态机必须**先写期望的执行序列签名**，再以日志逐项对照。

## 四、流程与方法论教训

- **帧数交替签名 = 状态机跳步**的超强判据（25/22 一眼定位），已入 debug-log-investigator 技能帧模式表。
- **用户最小复现日志协作链**非常高效：2897/2899 都是单变量复现，一轮定位。继续保持「请用户做最小操作 + 一个日志」的节奏。
- **读图核验（explain）在三轮修复中每次都发挥终审作用**（flowDoMove 分支链、negDone 数据源），没有一次误判——保持强制。
