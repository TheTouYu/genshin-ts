## 二、最近一次错误的完整调查链（日志 2976）

**现象**（用户）：还是有索引越界，复合节点 solver_append_code 就出现了。

**取证链**：
1. 日志 2976 rec675（46520B 大记录）：`solver_append_code > bufPos OUT0:Integer=485`——**bufPos=485，solveBuf 只有 100 项，写越界**。
2. 帧级确认正常性：mLen=18（真实逆公式长度）、mAlgOff=74（合法偏移）、mSub 9→10 正常推进——**追加逻辑本身正常**。
3. 定位 bufPos 为何累积：485 ≈ 72×7，说明**同一序列被追加了 7 轮**（每轮 ~72 codes）。
4. 反查完成路径：solverLPlan pStep3 的三个「追加完成」分支（OLL a2<0 / OLL default / PLL default）都只 `pStep=1`（重新读状态），**没有发布 solve_seq/solve_len + 发 op6**。
5. 后果链：追加完 → 没发 op6 → solver 不执行 → 魔方状态不变 → 重新读状态签名不变 → 又查表得到同一 action → 又追加 → bufPos 累积（无 op5 回来清零）→ 越界。

**修复**：新增 llPublishSeq 复合（set solve_seq → set solve_len → phase=2 → send op6），接入三个完成分支，完成后 pStep=0 停 tick 等 op5。

**验证**：编译 9 GIA 全绿；注入 ok 9 fail 0；读图核验（llPublishSeq 内部发送信号 op=6、主图 3 处调用、op=7 保留）；用户实体 17/17 零差异；resync md5 一致。

## 三、为什么反复出问题——系统性根因（2 条）

1. **「规划→执行」握手协议是隐式约定，复制模式时容易漏**：solverPlan/solverEPlan 的 pStep4 完成分支都有「发布 solve_seq/len + 发 op6」三件套，但这是**写在每个图里的重复代码**，没有抽成共享复合——写 solverLPlan 时照抄状态机模式，漏了完成分支的握手。**教训：跨图复用的「规划完成协议」应抽成共享复合（本次抽了 llPublishSeq），并在新规划图 checklist 里显式列出「完成分支必须发布+发 op6」**。
2. **「同一症状多个根因」的盲区**：索引越界/死循环这个症状，第一轮修复（长列表越界读）是**真实的根因之一**，但它掩盖了第二个根因（漏发 op6）——两个根因都会导致「状态不变死循环」，修掉一个后症状仍在（或者换了表现：从「追加空 code」变成「追加有效 code 但累积越界」）。**教训：症状修复后用户反馈「还是有问题」时，不要假设修复无效，先对比新旧日志的症状差异（2964 是 code 空、2976 是 bufPos=485），差异指向不同根因**。

## 四、流程与方法论教训

- **有用**：日志帧对比法——2964（code 空 → 越界读）vs 2976（bufPos=485 → 累积越界），症状差异直接指向不同根因。
- **有用**：bufPos 数值分析（485 ≈ 72×7）快速锁定「同一序列追加 7 轮」→ 反查完成路径 → 找到漏发 op6。
- **绕路**：第一轮把「补齐表」当成了死循环的完整修复——离线验证（20000 样本）只验证了「表正确」，没验证「真实图的握手协议完整」。**教训：离线验证模拟的是算法逻辑，不含「图与图之间的信号握手」——握手协议只能用读图核验（对照 solverPlan 的完成分支）或日志验证**。
