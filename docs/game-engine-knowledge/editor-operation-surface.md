# 千星编辑器操作面（Operation Surface）与覆盖率机器

> **状态**：当前实现 + 实测读数（2026-10-19 起）
> **来源**：真实编辑器 GUI 实测（`import -window 0x1800001`）、官方文档 `docs/ui-tutorial/official-guide-editor-interface.md` 机器抽取
> **适用范围**：任何要「驱动千星编辑器」或「度量编辑器被覆盖了多少」的工作
> **配套**：`.scratch/gui-stack/EDITOR-COVERAGE-PLAN.md`（口径与分母定义）、`.scratch/gui-stack/ops-ledger.tsv`（台账）

## 一、为什么要有这份文档

编辑器有 **13 大类界面、458 个文档记录的操作点**。靠"记得怎么点"来驱动它，每次换会话都要重新摸索；
靠"我觉得都点过了"来报覆盖率，是不可复算的自证。

这份文档把两件事固定下来：**界面怎么进（可复现的稳定判据）** 与 **覆盖率怎么算（分母 + 台账 + 一行命令）**。

## 四、覆盖率机器（四件套）

| 件 | 命令 | 作用 |
|---|---|---|
| **分母 A** | `python3 tools/ys-docops/ys_docops.py extract` | 从官方文档抽操作点 → `ops-inventory-doc.tsv`（**458 点**） |
| **分母 B** | `tools/ys-editor/ys-enum <帧.png> --json` | 从界面帧枚举候选（**P 65–85% / R 83–85%**，只能当雷达） |
| **台账** | `tools/ys-editor/ys-ops add --id X --control 名字 --text 名字` | 点一次 + 记一行（调用方式 / 观测差异 / 判据值） |
| **面板驱动** | `tools/ys-editor/ys-cover [面板名]` | 归位 → `ys-pick` 算入口 → 点进去 → 面板内逐点覆盖（不按 ESC） |
| **入口定位** | `tools/ys-editor/ys-pick <look.json> <名字>` | 从 bbox 现算可点中心，`tile > row > button` 优先 |
| **爬取器** | `tools/ys-editor/ys-crawl --from-look --by-name --goto-text <标记>` | 自己归位 → 自己枚举 → 逐个点 → 自己回退 |
| **覆盖率** | `tools/ys-editor/ys-ops coverage --inventory .scratch/gui-stack/ops-inventory-doc.tsv` | 按控件名把台账对齐到分母，输出百分比与未覆盖清单 |

### 覆盖判据（缺一不算）

```
covered(P) ⟺ 台账里存在一行 P，且该行同时有：
  ① 调用方式（坐标 或 名字解析结果）—— 可重放
  ② 观测差异（前后帧差异区 / 落盘物 / 状态迁移 / 文本变化 至少一项）—— 行为读数
  ③ 判据值（具体数字或字符串，不是"看起来变了"）
```

## 五、稳定判据与坑（换会话必须知道的）

1. **坐标是位置，名字才是身份**：一律用 `act --text <名字>` 在点击那一刻解析；预存坐标会在界面滚动后静默点错。
2. **编辑器里点开的是「页签」不是弹窗**：一次 `ESC` 会把页签和系统菜单一起关掉 ⇒ 回退要**最多按 3 次、每次比一次基线帧**。
3. **枚举前必须归位**：ESC 先关页签、都关完才开系统菜单。不归位会在别的界面枚举出噪声名字（实测抓到「久」「UI」「max:」）。
4. **噪声过滤**：DXVK 叠加层的 `FPS:` / `GPU:` / 纯数字 / `{X}` 残片不是操作点，必须过滤。
5. **进面板要用「look 的 bbox 现算中心」（`ys-pick`），不要用预存坐标也不要裸名字**：
   预存坐标实测只差 **0.007 帧差**（= 没打开，菜单滚动位置会变）；裸名字在页签已开时**歧义**（磁贴 + 页签名都命中 ⇒ 解析器 fail-closed）。
   从 bbox 取中心 + `tile > row > button` 优先，实测入口 diff **0.99**（面板真开了）。
6. **`ys-state` 在编辑器里只粗分**：它把各种面板报成 MENU / GAME_WORLD / EDITOR，**与具体面板无关** ⇒ 面板级判据只能靠屏上文字。

## 八、未覆盖项的结构性原因（判据③，2026-10-19 20:4x）

覆盖率 **30 / 458 = 6.55%** 时，未覆盖 **428** 点的分布与原因（**按类给原因，不是逐条编**）：

| kind | 未覆盖 | 占分母 | 结构性原因（为什么现在这批机器覆盖不到） | 需要的机制 |
|---|---:|---:|---|---|
| `setting` | **173** | 38% | 面板内字段（开关/下拉/输入框）。**整帧帧差对它们不敏感**——一个 checkbox 只占几百像素，全帧差异 ~0.0001，必然判成"没变化" | `ys-field`（已建，按字段区域取读数）；需批量跑 |
| `nav` | **130** | 28% | 需要进入对应面板：部分面板在系统菜单列表**下方需滚动**；4 个列表项当前滚出视野；还有跨面板层级 | 列表滚动 + 面包屑导航 |
| `create` | **59** | 13% | 多是"新建/添加"按钮，点了会**弹二级对话框**（输入名/选模式/确认），当前爬虫不处理对话框 | 对话框识别 + 二次确认 |
| `scene` | **48** | 10% | 场景操作（拖实体/笔刷/框选/gizmo）：**没有可点的 bbox**，交互区是整幅画布 | 画布手势 + 坐标读回 |
| `destructive` | **18** | 4% | 上传/删除/覆盖：只允许在一次性存档里做，且必须能证明"操作前/后磁盘 `.gil` 变了或没变" | `.gil` 前后 SHA 校验链 |

**结论**：当前机器只能覆盖「看得见、有名字、点一下就换界面」这一层。
要往 99.5% 走，短板不在"跑得不够多"，而在**上表右侧那五个机制还缺四个**。

### 已建但未批量跑的通道

- **`ys-field`**（本轮新建）：`ys-field --path "关卡设置 > 基础" --field 是否启用全额绽放伤害`
  从 look 找到字段行 → 取该行右侧"值区"矩形 → **只对值区做前后差** → 连续点 K 次各记一条读数。
  为什么必须按区域：整帧差判不出 checkbox/下拉的微小变化（见上表 `setting` 行）。

## 九、`setting` 类（173 点）的当前真实卡点（2026-10-19 21:0x）

进了 `关卡设置` 面板后 dump `look` 的对象（33 个带文字），**只看到左栏 10 个导航项**
（复苏点/人数设置/加载界面/结算/地形导航/协作模式/优化选项…），
**右侧设置区的字段标签一条都没读到**（`运行后场景生效范围` `是否启用全额绽放伤害` `关卡环境等级` …）。

⇒ `setting` 那 173 点现在卡在**两层之外**：
1. 第一层：字段标签没有进入 `look` 的对象文字（右侧面板的行没被检测成对象，或 OCR 没接住）；
2. 第二层：即使读到了标签，还要按「字段行右侧值区」取微小前后差（`ys-field` 已实现，但缺输入）。

**所以下一轮的第一步不是跑 `ys-field`，而是先把「右侧设置区的字段行」变成可枚举对象。**
候选路线（按成本排序）：
① 用 `ys-enum` 对编辑器帧做切块 OCR（它已验证 t17 上能读右栏标题「默认布局」）；
② 直接对右侧面板区域做局部 OCR（`ocr_objects` + 指定 ROI），绕过检测框；
③ 放宽 `_attach_text_to_dets` 的覆盖率阈值（现在是 0.5，右侧行可能是宽条被大 panel 吞掉）。

## 十、更正：上一轮「全帧 OCR 返回 0」的结论作废（2026-10-19 20:4x）

**作废的结论（原文）**：「对 2560×1440 全帧跑 `ys_ocr.py ocr` 返回 0 条，是工具缺陷。」

**真相**：`ys_ocr.py ocr --json` 的返回结构用 **`boxes`** 键。我按 `items` / `results` 取，
于是**稳定地**拿到空列表——看起来像"OCR 读不到"，实际是**读错了字段**。
正确解析后同一帧 **38 条**，且包含全部字段标签：

```
阵营 / 出生点 / 复苏点 / 人数设置 / 加载界面 / 结算 / 地形导航 / 优化选项 / 协作模式
碰撞触发器 / 实体离场时碰撞触发器检测优化
```

⇒ **OCR 通道一直是好的**，`setting` 那 173 点不缺 OCR，缺的是「字段行 → 可操作控件」的判定。
污染半径：只影响上一轮的一条结论与一个提交信息，未据此改过代码路径（`ys-field` 的兜底逻辑现在是对的）。

**教训（第三次同族）**：拿到空列表先问「是真的空，还是我读错了键/层/口径」。
`ys-field:ocr_boxes()` 里已写死注释，别再按 items/results 取。

### 新发现的更本质问题：分母里混进了「说明行」

实测「实体离场时碰撞触发器检测优化」这一行，右侧**没有控件**（截图核过），是「问号图标 + 说明文字」。
点它 `region_diff = 0.0`。

⇒ 分母 458 里**有一部分是不可操作项**。若不清洗，99.5% 永远达不到，而且**不是能力问题、是口径问题**。
下一轮要做：给分母加 `operable` 列（yes/no/unknown），把说明行单列并从分母剔除。

### 可操作性探针 `ys-field --probe`（本轮落地，口径要看清）

判据：**取标签右边缘右侧的一条带**（宽 60–360px），看这条带的亮度方差。
- 说明行右侧是纯背景 ⇒ `stdev ≈ 0.7–1.3`、`range 0–7` ⇒ `operable=no`
- 有开关/下拉/输入框 ⇒ 会有边框与色块，方差显著更高

**踩过的坑**：第一版把值区取成「行宽 45% 之后的一段」，结果把**标签自己的文字**框进去了，
方差被文字撑到 21，把「右侧纯背景的说明行」误判成 operable=yes。改成"标签右边缘 +10px 起"才对。

**当前局限（必须一起看）**：这条探针只回答「**紧邻标签右侧**有没有控件」。
如果某个设置项的控件在很右边（超过 360px 带），会被判成 no。
下轮要么把带放宽到面板右边界，要么改成"整行找控件样团块"。

### 剩余卡点：`ys-field` 点不准控件位置

`ys-field --clicks` 现在按"值区 35% 处"点击，实测对 `是否启用全额绽放伤害` **两次都是 region_diff=0.0**
—— 勾选框不在那个位置。⇒ 需要**控件定位**：在值区里找出真正的控件（勾选框/下拉/按钮）再点，
而不是猜一个比例。候选：值区内的连通域/高对比团块检测。

### 控件定位试了两版都不成，且发现第二行也没控件（2026-10-19 20:4x）

`locate_control()` 按列方差找值区里的「控件样团块」：
- 取最左段 → 点到 x=1227（标签尾巴/分隔线），`region_diff=0.0`；
- 改取最右段 → 点到 x=1247，仍 `region_diff=0.0`。

截图核对 `是否启用全额绽放伤害` 这一行（980..1420 × 555..645）：

```
? 是否启用全额绽放伤害
```

**又是一个「问号图标 + 文字」的说明行**，行里没有可见勾选框。

⇒ 这加强了上一轮的判断：**分母里混着大量「说明行」**。
「是否启用…」这类读起来像开关的条目，在界面上可能只是说明文字，真正的开关在别处（或需要先选中某实体才出现）。
