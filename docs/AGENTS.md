# `docs/` 文档维护规则

## 适用范围

本规则适用于项目文档、架构说明、维护记录和文档站内容。文档不是代码行为的替代来源；当前源码、测试和真实 GIA 证据决定结论。

## 修改前

- 先读 [`documentation-governance.md`](documentation-governance.md) 和
  [`documentation-map.md`](documentation-map.md)，再读取目标文档及其直接引用的权威来源。
- 涉及 Composite、GIA、IR、地图或注入时，按相关 skill 路由读取最小必要文档；真实 GIA 任务还要保留样本、命令和观察字段。
- 需要大规模移动、重命名、合并文档或改变文档结构时，先向用户提交方案并确认。

## 写作规则

- 默认使用中文，表达清楚直接；面向用户的文档与内部逆向/维护文档必须分开。
- 需要时在文档开头保留状态、来源、最近校验日期和适用范围。
- 明确区分：当前代码实现、自动回归、真实 GIA 观察、注入结果、用户游戏验证、历史记录和待验证推测。
- `composite-ir/handover/` 是历史背景，不能写成当前 API 或当前行为依据；应链接到当前权威入口。
- 不要把自动测试或注入成功表述为游戏行为已验证；真实 GIA 结论要说明样本范围，不能无证据推广。
- 每轮结束时，检查适用的 `AGENTS.md`、协作经验手册和权威文档是否仍与本轮证据一致。
  只把已证实、可复用且可行动的规则更新到适用范围最小的文件。

## 验证

- 检查相对链接、文件路径、命令和术语是否仍有效。
- 运行 `git diff --check`；若修改当前 Composite 文档，按需检查是否误用了已废弃 API 名称。

## 不要做

- 不要删除有证据价值的历史记录；应补充状态或指向当前权威文档。
- 不要在文档中暴露不应进入用户文档的内部游戏路径、未验证 wire 结论或破坏性操作步骤。
