# GUI 操作资产化（2026-10-17 设计）

> **状态**：待验证（设计，未实施）
> **定义来源**：`docs/ui-tutorial/`（官方综合指南 207 页整理）。本文件的**操作清单与术语一律取自
> `official-guide-editor-interface.md`（界面介绍：系统菜单/资产栏/快捷设置/详情面板/模式切换/相机操作）
> 与其余 6 份官方文档**，不自行发明名字。
> **一句话**：资产化不是"把 50 个脚本装上壳"，而是**先把官方 UI 树变成操作清单（定义层），
> 再把每个操作的实现变成可校准、可回归、可替换的绑定（实现层）**。

---

## 一、为什么先要"定义层"

现在的 `tools/ys-editor/` 是**从事故里长出来的**：50 个工具，按"哪一步坏了就补一个"堆起来。
它没有操作清单，所以：

- 同一个操作有多份实现（状态判据曾有 6 份）；
- 官方有的操作我们完全没有（上传关卡、外围系统管理、商店模板管理、局内存档管理、技能资源管理……）；
- 名字是我们起的（`ys-switch-save`），不是官方术语，换个人看不懂它在官方 UI 的哪个节点上。

**资产化的第一步不是写代码，是建清单**：官方 UI 树 → 操作 ID → 谁实现了它 → 缺口在哪。

## 二、两层分离（核心）

| 层 | 内容 | 变更频率 | 谁维护 |
|---|---|---|---|
| **语义层** | 操作 ID、官方章节锚、意图、前置态、后置态、参数、失败模式、回退 | 低（官方文档变才变） | 人工 + 官方指南 |
| **绑定层** | 像素坐标、按键序列、时长、判据阈值、窗口条件 | 高（改版/换分辨率/换皮肤就变） | 校准工具 + 回归帧 |

> 关键：**判据（"现在是哪个界面"）是资产，不是实现细节**。所有操作引用同一个 `ysd`，
> 不许各自写一套（今天的 6 份重复判据就是反例）。

## 三、操作资产 schema（每个操作一个 yaml）

```yaml
id: menu.savelist.open              # 官方：系统菜单 → 打开存档界面
official: official-guide-editor-interface.md#系统菜单功能
intent: 从任意非菜单态进入存档选择页
pre:   { state: any }               # 谓词，引用 ysd 的状态名
steps:
  - { act: key, code: ESC,                 wait: { state: MENU,   timeout: 8 } }
  - { act: click, at: [39, 176],           wait: { state: SAVELIST, timeout: 12 } }
post:  { state: SAVELIST }
evidence: { frame: crop 900x520+0+0 }
cost:  { expect_ms: 3000, last_ms: 2140 }
failure_modes:
  - id: modal-block        detection: state 不变且 (x,y) 命中模态区域   remedy: 先关模态
  - id: focus-lost         detection: 点击后 30s 无状态变化              remedy: 重新抢焦点
revert: null
confidence: stable          # draft | calibrated | stable | deprecated
```

**判定资产（ysd）单独一份**：

```yaml
id: state.machine
states: [MENU, SAVELIST, EDITOR, LOADING, PLAYTEST, PAUSE, SETTLE]
criteria:                       # 每态 ≥2 条独立判据，投票
  SAVELIST: [{px: [300,300], rgb: [<60,<60,<90]}, {px: [2273,1357], white: false}]
regression: calib/regress/manifest.tsv    # 每条样本 = 一张帧 + 期望态 + 说明
```

## 四、盘点：三本账（先算清楚再动手）

| 账 | 来源 | 用途 |
|---|---|---|
| **官方面** | `official-guide-editor-interface.md` 等 7 份官方文档 | 定义全部操作（系统菜单约 30 项功能 + 4 种模式 + 相机 7 个动作 + 详情面板） |
| **我方面** | `cmdmon audit`（GUI 类 1131 次/30 天）+ `tools/ys-editor/` 50 个文件 | 哪些操作真的在用、各花多少时间 |
| **缺口面** | 官方 − 我方 | 官方有、我方无资产 ⇒ 能力缺口（按项目规则**不得判"不支持"**，须报告并裁决） |

**排序依据只能是数据**：`cmdmon` 里 GUI 类调用按"操作"聚合后的 **频次 × 单次耗时**。
一轮 pipeline 大约 8~10 个操作，先资产化这些就覆盖 80% 的时间。

## 五、录制优先于手写（对抗"UI 一改全废"）

手写坐标的资产在编辑器改版后全部失效。所以：

1. **录制一次**：`ys-asset record <op-id>` 在真机走一遍操作，同时记录
   `(动作序列, 每个动作后的帧, 状态变化, 耗时)`；
2. **自动生成骨架**：从帧里提取候选判据点（变化区域），生成 yaml 草稿；
3. **人工只做语义标注**：这是哪个官方操作、前置态是什么、失败模式叫什么；
4. **UI 改版时**：只重录变化的步骤，语义层不动。

## 六、验证与覆盖（资产没有回归 = 不是资产）

| 层次 | 手段 | 频率 |
|---|---|---|
| 离线回放 | 用录制的帧序列跑判据与步骤规划，**不需要 GUI** | 每次改判据/绑定 |
| 真机冒烟 | 每个资产在真机上跑一次，断言 post + 记录耗时 | 每 N 轮 / 每日 |
| 覆盖率 | 一轮里"有资产的操作" / "全部 GUI 操作" | 进 `round-report` |
| 成本 | 每资产实测耗时 vs 上次 | 进 `round-report` |

**目标线**：一轮 pipeline 的 GUI 操作 **100% 有资产**；UI 改版后修复只改 yaml 的绑定段。

## 七、里程碑（每步都有可验读数）

| 阶段 | 交付 | 判据 |
|---|---|---|
| A0 | 官方操作清单（从 7 份官方文档抽取，带章节锚） | 清单条目 ≥ 60，每条有 `official:` 锚 |
| A1 | 我方映射 + 缺口表 | 50 个 ys-* 全部映射到操作 ID；缺口条目登记 |
| A2 | 资产 schema + `ys-asset lint/run` | lint 能拒收缺 pre/post/evidence 的资产 |
| A3 | 先做 8 个高频操作（覆盖一轮 pipeline） | 一轮里 ad-hoc GUI 命令 = 0 |
| A4 | 录制器 `ys-asset record` | 新操作从 0 到 calibrated ≤ 15 分钟 |
| A5 | 覆盖与成本进 `round-report` | 每轮自动报覆盖率与单操作耗时 |

## 八、不要做的事

- **不要把 50 个脚本原样资产化**——那只是把混乱形式化；先并判据、再建清单。
- **不要手写坐标做新资产**——先录制，再标注。
- **不要给"用不到的操作"建资产**——排序只看 cmdmon 实测。
- **不要发明操作名**——一律用官方指南里的名字与章节锚。
