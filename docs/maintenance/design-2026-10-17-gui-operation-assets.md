## 一、v2 的五个转向

| # | v1（专用） | v2（通用） |
|---|---|---|
| 1 | 步骤写**坐标** `click [39,176]` | 步骤写**目标描述** `click {role: button, name: 存档}`，运行时由 resolver 绑定 |
| 2 | 判据是**像素点阈值** | 判据是**状态机资产**（一等多源判据），像素只是其中一类证据 |
| 3 | 资产=**yaml**，人读人写 | 资产=**可执行 plan（小程序）**，yaml/json 只是序列化；**录制一次自动生成** |
| 4 | 入口=`ys-xxx` 50 个脚本 | 入口=**一句话**：`gui do "打开存档界面并切回我的图"` |
| 5 | 增长靠**我手写** | 增长靠**闭环**：尝试 → 成功 → 归纳 plan → 入库 → 检索复用 → 失败自动变回归样本 |

## 二、架构（四层，下三层通用，最上层挂项目 profile）

```
┌─ L4 入口层  gui do "<自然语言>"  |  gui skill list/show/lint  |  gui rec <id>  |  gui replay <id>
│     职责：把意图变成 plan；命中技能库就直接跑，没命中就现场合成+录制
├─ L3 技能层  技能库（plan + 前置/后置断言 + 证据策略 + 成本统计 + 失效模式）
│     检索键：意图文本 / 目标应用 / 屏幕状态组合；置信度随成功率涨落，长期不用则降级
├─ L2 动作层  原语：see / find / act / type / assert / wait_until / capture
│     参数是**目标描述**（role+name+文本+图像特征），不是坐标
├─ L1 解析层  resolver ladder（从便宜到贵，命中即停）
│     ① AT-SPI 语义树（cu state/find，~8ms 级，零像素）
│     ② GPU 模板匹配（ys_look.py，已有一批素材）
│     ③ OCR / 文本定位
│     ④ 视觉模型定位（多模态子代理）
│     ⑤ 坐标兜底（人工校准的绝对位置，带过期时间）
└─ L0 观测层  帧 + 语义树 + 应用元信息；统一带时间戳与新鲜度，供判定与证据
```

**要点**：`千星编辑器` 只是 L1 的一个 **profile**（该应用没有 AT-SPI，resolver 主要走 ②③⑤），
而不是整个系统。换到浏览器/计算器/任意 Qt 应用，L2–L4 一行不改。

**2026-10-17 本机实测（决定 L1 权重，不是推测）**：
| 读数 | 值 | 含义 |
|---|---|---|
| `cu apps` 暴露 AT-SPI 的应用数 | **9 个，其中仅 3 个有子节点（树可用）** | 语义树在本机≈不可用 |
| `cu state <app>` 端到端 | **3348ms**（GTK 应用） | 即使有树，也比一次裁切截图贵 20 倍 |
| 原神/千星（Wine） | **无 AT-SPI**（已 grep 确认） | 目标应用必须走视觉 |
⇒ **L1 的现实重心是 ②模板 ③OCR ④视觉模型，①语义树只作为"有就用"的加速档**；
"每步 ≤300ms"在无语义树的应用上不成立，必须靠**常驻观察进程 + 批量动作**换取，而不是靠单步优化。

## 三、技能（资产）的格式

```jsonc
{
  "id": "menu.savelist.open",
  "intent": "打开存档选择界面",
  "official": "official-guide-editor-interface.md#系统菜单功能",   // 本体论锚（可选，来自官方文档）
  "app": "原神编辑器",                                              // 目标应用（L1 profile 选择器）
  "pre":  {"state": ["EDITOR", "PLAYTEST", "SETTLE", "ANY"]},
  "steps": [
    {"act": "key",  "key": "ESC", "wait": {"state": "MENU", "timeout": 8}},
    {"act": "click","target": {"role": "button", "name": "存档", "fallback": {"template": "assets/save-icon.png"}},
     "wait": {"state": "SAVELIST", "timeout": 12}}
  ],
  "post": {"state": "SAVELIST"},
  "evidence": {"frames": ["post"], "keep": 1},
  "stats": {"runs": 12, "ok": 11, "p50_ms": 2140, "last_ok": "2026-10-17T15:20"},
  "failure_modes": [
    {"id": "modal-block", "detect": {"state_unchanged_s": 3}, "remedy": "skill:modal.dismiss"},
    {"id": "focus-lost",  "detect": {"no_state_change_s": 30},  "remedy": "primitive:reclaim_focus"}
  ],
  "confidence": "stable"          // draft | calibrated | stable | deprecated
}
```

**判据（状态机）也是技能库的一员**（`state.machine`），所有步骤的 `wait/assert` 引用它，
不许各自实现——这是把今天「6 份重复判据」从制度上堵死的方式。

## 四、录制 = 技能的唯一生产方式

```
gui rec menu.savelist.open
  → 边做边记：(观测, 动作, 观测, 耗时) 三元组，动作由用户/代理在真机完成
  → 归纳：动作归类到原语；目标归类到 resolver（能命中 AT-SPI 就存 name，否则存模板/坐标）
  → 生成 plan 草稿 + 自动插入 wait（动作前后状态变化点）
  → 立刻回放一次（同一环境），通过则 confidence=calibrated
```

**归纳是从轨迹自动提取的，不是我手写的**——这是"能力自增长"的落点：
新应用/新操作 = 录一次，不是写一遍代码。

## 五、闭环与自增长（AGI 的那个环）

```
意图 ──检索技能库──► 命中 ──► 执行 ──► 断言通过? ──是──► 成功计数++ / 成本更新
  │                              │否
  └─未命中──► 现场合成/录制 ──► 否 ──► 失败归因 ──► ① 修 plan（自动重试一次）
                                              ├──► ② 新回归样本（永久）
                                              └──► ③ 失效模式登记（下次先检测）
```

**判据**：技能库的**能力密度**（技能数 × 成功率）随使用单调上升；失败率不升。

## 六、通用性 / 易用性的验收判据（可机器检查）

| 维度 | 判据 |
|---|---|
| **通用** | 换 1080p↔1440p、换语言、换皮肤：同一技能成功率不变（只允许 resolver 换层） |
| **通用** | 新增一个应用：只写 profile（应用名 + resolver 偏好），不改 L2–L4 |
| **通用** | 技能文件是**可读文本**，别的 agent/会话能直接读用，不依赖本机状态 |
| **易用** | 用户只需一句话；不需要知道坐标、不需要知道工具名 |
| **易用** | 新技能从 0 到 calibrated **≤15 分钟**（录一次 + 一次回放） |
| **易用** | 失败信息是「哪一步、期望什么、看到什么」，不是退出码 |
| **自增长** | 一周内技能库净增 ≥5，且无人工改代码 |

## 七、落地顺序（每步都能独立验收）

| 阶段 | 交付 | 判据 |
|---|---|---|
| G0 | `gui` 统一入口骨架 + 技能库目录 + `lint/show/list` | 空库也能跑；lint 拒收缺 pre/post 的技能 |
| G1 | L2 原语 + L1 resolver（先接 `cu` 的 AT-SPI 与坐标兜底） | 用一个**非千星**应用（如计算器）录 1 个技能并回放成功 |
| G2 | 千星 profile + 把现有 8 个高频操作录成技能 | 一轮 pipeline 的 GUI 操作 100% 走技能 |
| G3 | 录制归纳自动化（三元组 → plan） | 新技能 ≤15 分钟；归纳出的 plan 与手写版一致 |
| G4 | 失败闭环（自动回归样本 + 失效模式） | 任一失败 30 秒内出现在回归集 |
| G5 | 检索与复用（意图文本 → 技能；跨会话共享） | 新会话无需提示即可复用 |

## 八、不要做的事

- **不要把坐标写进技能**（只能进 resolver 的最后一级，且带过期时间）。
- **不要让每个技能自己实现判据**（一律引用 `state.machine`）。
- **不要手写新技能**（先录制；手写只在修 plan 时）。
- **不要为「用不到的操作」建技能**（排序只看 cmdmon 实测）。
- **不要把千星的特例当通用假设**（Wine 窗口没有 AT-SPI 是 profile 的事实，不是 L2 的规则）。

## 九、v3：GLM-5.3(max) 评审后的修正（2026-10-17）

> 评审人：GLM-5.3（reasoning=max），读源码验证了 ys-state/ys-fast/ys_look/ys-observe/manifest 的实际实现。
> 下面只保留**改变了设计**的部分。

### 9.1 被推翻的三条

| v2 说法 | 评审裁定 | 替代 |
|---|---|---|
| ladder ①AT-SPI 是台阶 | **装饰品**：9 应用/3 有树、`cu state` 3348ms、Wine 无树 | 纯视觉代理；AT-SPI 只在恰好可用时升级（如 GTK 对照应用） |
| 每步 ≤300ms | **物理不可达**：ROI 取帧 166ms + 决策 10~150ms + 注入 10ms + **按住 120~1200ms** + 验证 166ms | 改两档：**快路径 350~500ms；含长按 1.5~2s**。真杠杆是**一次焦点租约内批量执行 N 步**，不是压单步 |
| 录制→归纳可产出技能（不手写） | **最可能错的假设**。证据就在自家 manifest：SETTLE 有 4 种视觉版式 = 1 个逻辑态——**视觉等价类必须由人声明** | 录制产**素材**（轨迹+状态对+diff），人工每步 ~10 秒确认意图/参数锚点/失败模式；两次录制同一技能 diff 出的差异 = 参数 |

### 9.2 grounding 的正确做法：锚图（Anchor Graph），不是模板匹配

- 节点：文本锚（OCR 中文串 + bbox + conf）/ 图标锚（NCC，**只作投票成员**）/ 结构锚（ys-fast 像素探针是其退化形态）
- 边：归一化相对位移（吃掉分辨率）→ 最小二乘解 4 参数相似变换（尺度+平移）
- 决策：inlier < k 或残差 > ε ⇒ 报「锚图失配」，**不猜坐标**
- 模板匹配降级为 **ROI 内验证器（±32px）**，永不单独决定全局位置
- 实测约束：tesseract 全屏 2291ms 且中文质量差（"输 入 探 针"勉强），裁切 642ms 可用 ⇒ 必须换 OCR 引擎或只对 ROI 跑

### 9.3 状态判定：AMBIGUOUS 是合法输出，缺的是序贯仲裁

- 判据 → **LLR**（用 manifest 拟合混淆矩阵），不是 bool
- **FSM 合法迁移边**：不合法 ⇒ `INVALID_PATH`（独立错误码，处置=重取帧）
- **AMBIGUOUS 触发区分性探针**：查混淆矩阵两态列差最大的判据，主动 `ys-fast px`（30ms）取证——Wald 序贯检验，带停时规则
- **liveness = 对输入的响应性**：连续 k 帧 `diffFromPrev==0` 且探针后仍静止 ⇒ DEAD

### 9.4 时序：区分「还没到」与「永远不会到」

- **新鲜度门**：`t_act − t_cap > 2×帧间隔` ⇒ 强制重取（spectacle 2893ms 意味着一次观测可能是 3 秒前的世界）
- **转移先验库** `TransitionStats{(s_from,s_to): {p50,p95,n}}`：录制期自动累积，是录制必须产出的第二资产
- 终止：目标态达→成功；**世界静止 + 超 p95×k + 非目标态 → FAIL(action_not_effective)**；仍在变化+超时→继续

### 9.5 动作自适应与技能健康

- `PressProfile{(app,control_class): {dur_p50,dur_p95,cap}}` 在线校准（失败×2，上界 1.5s，成功后向下探）
- **每次点击强制绑定效果断言**，无断言不进技能库——否则"点错位置"会被重试放大成连点
- **canary probe**：每技能编译出「只跑 pre + 全部 find、不 act」的探针；漂移 = 锚图 inlier 率下跌，信噪比高于端到端成功率两个量级

### 9.6 评审给出的"我会做得完全不同"

**把 `docs/ui-tutorial/` 207 页官方 UI 本体论编译成结构先验，锚图从文档生成而非从录制归纳。**
千星是已知应用（UI 树/菜单层级/控件语义是文档化的），这是本项目独有资产，v2 完全没用。
⇒ 已知应用：**文档给拓扑与语义 + 实拍补 bbox/颜色**；陌生应用才靠录制。
这把 9.3 的 FSM 迁移边、9.2 的锚点集合大半变成**编译期产物**。

### 9.7 下一步（评审建议，我采纳）

**离线 grounding/漂移基准**（锚图最小实现 + 合成变换曲线），1.5~2 天：
对 `calib/regress/` 11 帧合成 0.75×/1.1×/1.25×/平移，比较「纯 NCC」vs「锚图」的 top-1 定位准确率与**假命中率**。

### 10.1 由此定下的运行模型（成本驱动的必然结论）

- **grounding 按"屏幕状态变化"触发，不是按步触发**：一次全帧锚图 ≈1.4s（+RapidOCR ≈0.7s）。
  状态不变时，步骤复用已解析的坐标，只用 **166ms 裁切**做新鲜度/漂移抽查。
- **多尺度全帧匹配（6.3s）只进"标定模式"**：换分辨率/换主题后跑一次，重建锚图模板尺度，不进运行时。
- **锚点候选必须多尺度**（当前 ±25% 档全灭，是唯一的已知缺口）。
- **state 判定禁止单模板**：任何"匹配分 > 阈值 ⇒ 判定某态"的写法，实测 5% 假命中率 ⇒ 一律走**锚图几何一致性 + 多判据投票**。

### 10.2 剩余未验证（写进 open items，不当作已知）

1. 真机时序：锚图在 6~11 FPS 动态画面下的稳定性（实验用的是静态帧）。
2. 3D 游戏区（非 UI 区）能否作锚——大概率不能，需实测。
3. 多尺度网格中间档（如 0.83×）的残余误差未测。
4. SETTLE 四种视觉版式在锚图判据下的区分度（现在是"都判不一致"，是否够用待验）。

## 十一、v5 修正：v4 的成本结论建立在 **CPU 路径**上（2026-10-17 用户追问后实测）

> 用户问："现在用 GPU 跑的是？它提供的模型没有 GPU 版本吗？" —— 这两问推翻了 v4 的成本论断。

**事实**：
- 实验脚本 `expA`/`expB` 显式 `NCC = ys_look._ncc_np`（numpy FFT，CPU）；仓库里另有 `_ncc_gpu`（torch CUDA），全程未被使用。
- 生产代码 `ys_look.ncc()` 有后端自适应：`work = H×W×h×w`，`> 3e9` 走 GPU。我们场景 `work≈5.3e10` ⇒ **生产会走 GPU，实验没有**。

**实测（同一张 menu.png、同一 120×120 模板、RTX 3060 Laptop）**：

| 场景 | CPU（实验） | GPU | 加速 |
|---|---|---|---|
| 单尺度匹配 | 1275 ms | **31 ms** | **41×** |
| 多尺度 ×5 | 7587 ms | **155 ms** | **49×** |
| 10 锚点 单尺度 | ~14 s（推算 10×1.4s） | **344 ms** | ~41× |
| 10 锚点 ×5 尺度 | — | **2024 ms** | — |

**因此 v4 的三条结论要改**：
1. ~~"多尺度 6.28s 只进标定模式"~~ → GPU 下 155ms/模板、10 锚点×5 尺度 2.0s：**多尺度可进运行时**（按状态变化触发），±25% 缩放缺口变得可负担。
2. ~~"锚图 1.4s/帧太贵"~~ → GPU 单尺度 **344ms/帧**；配合状态变化触发，可接受。
3. `ys_look.ncc()` 的 3e9 交叉点阈值是按"torch import 2~3s"定的；在**常驻服务 `ys-lookd`** 里 import 已摊薄，阈值应重调（否则大图以外的匹配仍会被错误地派给 CPU）。

**顺带发现一个未覆盖面**：`_ncc_gpu` 直接吃 `uint8` 会崩（`mean(): could not infer output dtype ... Got: Byte`）——
说明 GPU 分支缺类型断言与回归测试。修法：入口统一 `astype(np.float32)` + 一条 GPU/CPU 结果等价的回归样本。

**OCR 侧**：当前装的是 `rapidocr-onnxruntime`（CPU，0.65~0.73s/图）；GPU 变体存在
（`onnxruntime-gpu` / `rapidocr_paddle`），但本机 paddle 3.0.0/3.3.1 有版本雷，未验证。

## 十二、v6：GPU 重跑全套实验（用户追问后执行）

> 用户补充："我们 GPU 之前有使用，还有做了常驻的系统服务，并非只有游戏在跑" —— 属实：
> `ys-lookd.service`（常驻图像识别服务，GPU 常驻）已 active 近 4 小时，PID 833。

**实验 A 用 GPU 重跑（同一 60 正 + 60 负样本）**：

| 指标 | CPU（原报告） | GPU（重跑） | 变化 |
|---|---|---|---|
| 单尺度命中率（全量） | 68.3% | **68.3%**（完全一致） | 算法不变 ✅ |
| 多尺度命中率 | 100% | **100%** | ✅ |
| 单尺度耗时 | 1.01 s | **0.031 s** | **33×** |
| 多尺度×5 耗时 | 6.28 s | **0.145 s** | **43×** |
| 异态帧 ≥0.9 假命中 | 3/60 | **2/60**（0.9167 仍在，另一笔 0.9371→**0.8997**） | 阈值附近不稳定 |

> **重要发现**：同一对样本 CPU 判 0.9371、GPU 判 0.8997——**跨过 0.9 阈值**。
> 这直接证明「用单一分数阈值判态」在 float32/float64 差异下都不稳定，
> **必须用几何一致性（锚图 inlier）而不是分数阈值**。

**锚图在 GPU 上（±384px 局部窗口，10 锚点）**：

| 配置 | 耗时 | 每次匹配 |
|---|---|---|
| 10 锚点 单尺度 | 690 ms | 69 ms/锚点 |
| 10 锚点 ×5 尺度 | 991 ms | 19.8 ms/匹配 |

> 结论：**瓶颈已经从"数学计算"转移到"Python 胶水"**（ROI 切片、PIL 重采样、numpy↔tensor 转换）。
> 单次全帧匹配只要 31ms，但每个锚点的准备开销 ~50ms。要进一步提速，要么**把锚点批处理成一次 GPU 调用**，
> 要么让常驻的 `ys-lookd` 内部完成 ROI 切片与多尺度（现在它还是一次一调用）。

**对运行模型的最终修正**：
- grounding 单次成本：全帧单模板 31ms、全帧多尺度 155ms、10 锚点×5 尺度 ~1.0s（含胶水）。
- ⇒ **状态切换时做一次全锚图（~1s）+ 步内用 31ms 级单模板做 ROI 复核** 是现实的；
  "每步都做全帧 grounding"仍然不经济（1s × N 步）。
- ⇒ `ys-lookd` 应该内部支持"一次调用、多锚点、多尺度"，这是下一个真正的性能杠杆。

## 十三、v7：`ys-lookd` 批量化落地（本机实测）

**改动**（`tools/ys-editor/ys_look.py` + `ys_lookd.py`）：
1. 抽出 **`ncc_t(It, Tt)`**：张量原生 NCC（GPU 张量进、坐标+分数出），`_ncc_gpu` 改为它的薄封装
   —— **数学只有一份**，不产生第二实现。
2. 常驻服务新增 **`batch` 命令**：一次请求跑 N 个锚点 × M 个尺度；
   帧与模板按 `(路径, mtime)` **缓存成 GPU 张量**；模板缩放用 `F.interpolate`（不再走 PIL）。
3. 顺带修：`_ncc_gpu` 现在入口统一转 float32（此前直接喂 `uint8` 会崩）。

**实测（10 锚点，menu.png，±384px ROI，RTX 3060）**：

| 配置 | 进程内逐个调用 | `ys-lookd batch` | 加速 |
|---|---|---|---|
| 10 锚点 单尺度 | 690 ms | **60 ms** | **11×** |
| 10 锚点 ×5 尺度 | 991 ms | **441 ms** | 2.2× |
| 10 锚点 全帧 单尺度 | — | 262 ms | — |
| 10 锚点 全帧 ×5 尺度 | — | 1220 ms | — |

**定位正确性**：5/5 锚点 `score=1.000`、**误差 0px**（期望坐标逐点核对）。

**结论**：**grounding 不再是瓶颈**。
- 换一屏（状态切换）做一次「10 锚点 × 5 尺度」全量解析 = **441ms**；
- 步内的漂移复核用单尺度 ROI = **60ms/10 锚点**（比一次裁切截图 166ms 还便宜）；
- 对比：CPU 时代同任务 ≈ 35 s。**设计空间因此变了**：不必"只在状态切换时 grounding"，
  高频复核与"每步校验"都负担得起。

## 十四、v8：G1 通用性验证通过（2026-10-17，自建沙箱应用）

**做法**：不去碰用户的任何应用，自建一个 GTK3 沙箱（`.scratch/gui-sandbox/app.py`：1 个标签 + 3 个按钮），
用**同一套 `tools/gui` 原语**（目标描述 + 效果断言）跑通操作。这证明"换应用只换 profile，L2–L4 不动"。

**技能文件**（`.scratch/gui-skills/sandbox.pick-green.json`）：
```json
{"id":"sandbox.pick-green","app":"app.py",
 "pre":{"text":"当前: 无"},
 "steps":[{"act":"click","target":{"role":"button","name":"绿色"}},
          {"act":"assert","text":"当前: 绿色","timeout":5}],
 "post":{"text":"当前: 绿色"}}
```

**实测**：
| 场景 | 结果 | 用时 | 分解 |
|---|---|---|---|
| 成功路径 | ✅ exit 0 | **4.06 s** | pre 784ms + click 2465ms + assert 810ms |
| 失败路径（断言不可能成立） | ✅ exit 3 | **5.51 s** | 报「期望含『当前: 紫色』，实际=[…当前: 红色…]」+ 落 `run.json` |

**关键读数**：每次 `cu` 调用 ~800–900ms（每次都起短命 MCP server + 热遍历）——
**这是通用层当前最大的固定开销**，下一步应做常驻 cu 客户端（与 `ys-lookd` 同思路）。

**新发现的失效模式（已记入技能文件设计）**：同一 app 起两个实例时，AT-SPI 树里会同时出现
**两个 frame + 一个陈旧 label**（`当前: 无` 与 `当前: 绿色` 并存），导致断言读到旧节点而误判失败。
⇒ resolver 必须**按 pid/窗口去重**，或在多候选时取最新并告警。

**判定**：G0（入口骨架 `tools/gui` + lint）+ G1（第二应用跑通）**已完成**；
下一步 G2 = 千星 profile + 把 8 个高频操作录成技能。

## 十五、v9：AT-SPI 的真实成本与"视觉更快"的反转（2026-10-17 实测）

**测量**（sandbox GTK 应用，单次调用端到端）：

| 方式 | 单次 | 说明 |
|---|---|---|
| `cu state <app>`（含进程启动） | **~800–900 ms** | 每次起短命 MCP server + 热遍历 |
| MCP `get_app_state`（**作用域限定 app**） | **677 ms** | 进程启动约 150ms，**遍历 ~650ms 是大头** |
| 同上，一次会话连发 3 次 | **647 ms/次** | 批量只摊掉进程启动，摊不掉遍历 |
| 不加作用域（全桌面树，183 节点） | ~1.3 s/次 | 一定要传 `app_name_or_bundle_identifier` |

**结论（与我们先前假设相反）**：
1. 先前以为瓶颈是"每次起进程"，实测**瓶颈是 AT-SPI 热遍历**（~650ms）。常驻客户端只能省 ~150ms，不是 10× 级的杠杆。
2. 对比视觉路径：`ys-lookd` 10 锚点单尺度 **60ms**、×5 尺度 **441ms**（含帧缓存与 GPU）。
   ⇒ **在我们真正要驱动的应用上（Wine/无 AT-SPI），视觉已经比"有 AT-SPI 时的语义读"更快**。
   AT-SPI 的价值回到它本来的位置：**提供语义名字（role/name）**，不是提供速度。
3. 因此通用层的默认路径应该是：**视觉定位优先（有缓存、GPU、批量），AT-SPI 用于命名与兜底验证**。

**已做的工程改动**：`tools/gui` 加**树缓存（TTL 0.8s，动作后失效，断言强制 fresh）**——
同一步骤内的多次查询只遍历一次。实测技能端到端 4.06↔4.18s（差异在噪声内），说明
**单步仍必须一次读+一次动作+一次断言**，这与 AT-SPI 的 650ms/次叠加成 ~2.4s/步。
⇒ 想再快，只有两条路：事件驱动的 AT-SPI 常驻模型，或彻底走视觉。
