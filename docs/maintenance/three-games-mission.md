## 四、完整开发流程环节表（官方指南为准）

**权威环节表见 `docs/maintenance/m1-full-flow-inventory.md`**（官方 A~F 六段 + 逐环节覆盖 + GUI 通道实测）。
摘要：A 立项（打开编辑器→**新建/打开存档**→关卡设置）→ B 场景（地形/实体/元件库）→ C 系统（UI/镜头/外围系统/背包货币/变量/结构体/局内存档…）→ D 逻辑（**千星沙箱**：服务器图/客户端图/复合/信号）→ E 验证（试玩校验→进关卡→日志/负载）→ F 收口（保存存档）。

**关键成本模型（决定编排）**：千星编辑器是 Wine 应用，**无 AT-SPI 语义树** ⇒ GUI 只能走
**坐标 + 像素判据 + 视觉判读**（`ys-gui-slot` 硬通道 / `ydotool` 注入 / `ys-shot`+`ys_lookd` 判据）。
**每新增一个编辑器界面 = 一轮坐标/判据/坑实测** ⇒ **能用 CLI 的一律走 CLI，GUI 面尽量少**。

## 五、三个游戏选题（自选；K1 轴判据）

### 5.1 选题判据（`docs/knowledge-graph/k/k1-选题与赛道.md`，语料实测）

- **首选赛道 = 休闲益智**（实测第一：前八平均推荐率 **95.1**、总热度 **71.1 万**、1.5 万+ **39 个**）
- **避开七类**：传统 RTS / 自走棋 / TPS-FPS 竞技 / MOBA / 解谜 / 纯剧情 ADV / 氪金页游
- **好选题前二硬条件**：①上手难度低 + 目标明确 ②操作易、可精通难
- **单人优先 PVP**；**大流程玩法系统性吃亏**（流程越长越易被抓 bug）
- **地形不是必争项**（精力留给玩法）
- **动工前必须验证"关键技术可控"**（失败实录：3D 合成大西瓜卡在"镜头无法被节点图控制"）

### 5.2 三选题（v1 草案，**待关键技术验证后定稿**）

选型原则：三种**不同类型题材** + 覆盖**不同引擎能力面**（运动/物理/UI/客户端图/变量），
且每型都能用 CLI 主生产线做出来。

| # | 类型 | 玩法内核 | 要验证的关键技术 | 状态 |
|---|---|---|---|---|
| ① | **3D 平台跳跃闯关** | 跳跃躲陷阱 → 检查点 → 终点结算 | 运动器 + 碰撞触发器 + 检查点/复活 + 计时 | 待验证 |
| ② | **3D 塔防** | 沿固定路线行进的怪 + 自动攻击范围内的塔 | 路径/波次生成 + 单位状态 + 攻击判定 + 计分 | 待验证 |
| ③ | **休闲 PVP 对抗** | 双人抢分/推挤，短局快节奏 | 多输入 + 计分板 + 结算 + 客户端图（可选） | 待验证 |

> ⚠️ 草案，**动工前逐项做"关键技术可控性"最小验证**；不可控就换型（K1 明文教训）。
