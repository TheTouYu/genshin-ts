# OCR 性能专项：全帧地板 529ms、缓存稳态 1.1ms（2026-10-22）

> 状态：当前实现（含一处**未拍板**的默认值：`use_cls` 保持开）。
> 来源：本机实测，固定帧 `.scratch/gui-corpus/f06.png`（2560×1440），常驻服务 `tools/ys-editor/ys_lookd.py` 的 `cmd=ocr`
> 与客户端 `tools/ys-editor/ys_ocr.py`；历史对照取自记忆 D393 / D373 / D466 / D501 / D502。
> 最近校验：2026-10-22

## 0. 结论（数字先行）

| 通道 | 改前 | **改后** | 判定（≤250ms 热态门槛） |
|---|---|---|---|
| **同帧重复（缓存命中，服务端往返）** | 无缓存，每次 529ms | **1.1ms**（p95 1.1ms，n=12） | ✅ **PASS** |
| 同帧重复（CLI 端到端，含进程启动） | 每次 577–583ms | **49.1ms**（p95 52.4ms，n=10） | ✅ **PASS** |
| **每次真推理（禁用缓存）** | 546–593ms | **529.3ms**（p95 539.6ms，n=12） | ❌ 差 2.1×（硬件地板，见 §4） |
| 冷启动（daemon 重启后第一次） | 16.6s（用户实测） / 12s 级 | 单独报，见 §2.3 | 不进热态分位 |

> ⚠️ **给用户的读法（别把 1.1ms 当成"OCR 已经 1ms 了"）**：`1.1ms` / `0.5ms` 只在**"同一帧重复看"**成立。
> `look` 走的是**活体帧**——屏幕像素每次都在变，缓存**不会命中**。**实时路径的真实成本是 465–529ms**
> （换帧必 miss，n=8 实测 p50 465ms / p95 719ms）。1.1ms 不是实时延迟，是"同一张图再问一次"的价格。

**一句话**：这次把「同帧重复 OCR」从 529ms 打到 **1.1ms**（服务端）/ **49ms**（CLI 全程），并给 `cmd=ocr` 补上了
**分阶段计时**与**真实引擎上报**（此前 daemon 通道只会说 `via=daemon`，看不出实际跑在 cuda 还是 cpu——
这正是"显存不足静默走 CPU"看不见的根因）。**但"每次真推理"进不了 100–200ms**：这台机器上全帧 OCR 的地板
是 529ms（今天，GPU pin 在 855MHz）/ 371ms（2026-10-18 空闲台，D393）。

**100–200ms 那个记忆，对得上的是别的通道**（不是全帧 OCR）：
| 读数 | 出处 | 今天复测 |
|---|---|---|
| 模板匹配 NCC **147ms** | D373（`ys-lookd batch`，GPU） | 未复测（本轮不动模板通道） |
| 同帧 OCR 缓存命中 **14ms** | D393 | ✅ 复测 **1.1ms**（本轮新缓存） |
| **ROI 小图 OCR 231ms / 242ms** | 本轮（300×300 / 1280×720） | ✅ 见 §3.3 |

## 1. 口径（读这张表之前必须知道的三件事）

1. **A 段 / B 段分开**，绝不混报：
   - **A = 原神在跑**：GPU 显存余 **856–903 MiB**，`utilization.gpu` 60–99%，GPU **855MHz**。
   - **B = 原神退出后**（19:03–19:14 独占窗口，显存余 1069 MiB，GPU 855MHz、util 4%）。
2. **GPU 时钟是硬环境**：本机常态 pin 在 **855MHz**（`clocks.max.sm=2100`，P3）。同一份代码在 2100MHz 与
   855MHz 下不可比（D497 已实证此坑）。所有延迟读数都必须带时钟，否则 929ms 与 14ms 会被当成同一个"OCR 延迟"。
3. **热/冷定义**：热 = daemon 引擎已加载（预热完成日志出现 + 至少跑过一次）；冷 = 重启后第一次。
   本报告里**冷启动单独一节**，不进任何 p50/p95。

> 显存口径交叉引用（`ocr-vram` 2026-10-22 19:0x 实测，D514）：daemon **A 段 2588 MiB→B 段 1492 MiB**，
> 连打 110 次 `cmd=ocr` 显存不涨（稳态无泄漏）；全帧 det 输入 2000×1125 是显存主导项。本报告不再另编一套显存数。
>
> 改前基线是在**旧代码 + 游戏在跑**下取的（A 段 929ms）；改后在 **B 段干净窗口**取的（529ms）。
> 两段不可直接相减当"优化幅度"。同段对照见 §2.2 的三组 A/B（同一窗口、同一 daemon 进程、只差被测开关）。

```

```

**缓存稳态（同一条命令 `--cache`，n=12）**：

```
服务端往返 : p50 = 1.1ms   p95 = 1.1ms   （daemon 自报 0.5ms）
CLI 端到端 : p50 = 49.1ms  p95 = 52.4ms  （其中 ~48ms 是 python 进程启动 + import）
```

**同帧热 vs 换帧（cache 开，直接连 daemon，n=8）**：

| 场景 | p50 | p95 | 说明 |
|---|---|---|---|
| 同一帧连打 8 次 | **0.5ms** | 0.8ms | 全部 `cached=true` |
| 连换 8 张不同帧（f00–f05/f07/neg-world） | **465ms** | 719ms | 全部 `cached=false`；随帧内文本量波动（719ms 是文本最多那帧） |

⇒ **缓存只对"同一帧重复看"有效**；`look` 走活体帧、像素每次都在变，**不会命中**（这一点必须写清，
不能让"1.1ms"被当成实时感知的延迟）。实时路径的真实成本就是 465–529ms。

**往返 vs 推理**：`rpc_ms` 与 daemon 自报 `ms` 差 **0.6–6.2ms**（A 段 928.9 vs 928；B 段 529.3 vs 529.0）
⇒ **socket 往返不是成本项**；CLI 端到端多出来的 ~48ms 全是**客户端进程启动 + import**。

### 2.3 冷启动（单独一档，不混进热态）

| 时刻 | 读数 | 说明 |
|---|---|---|
| daemon 重启 → listening | 19:03:34 | 预热线程先跑完才 accept |
| OCR 引擎就绪（CUDA） | 19:03:38 | `[ys_ocr] 引擎=CUDA` |
| OCR 预热完成 | 19:03:40（**6048ms**） | 引擎 + 首跑 kernel |
| **首次 `cmd=ocr`（冷）** | rpc **22147ms**，进程内 **4412ms** | 分段 `det 2418 / cls 316 / rec 1260 / load 161` |

冷的 det/rec 是热的 10 倍量级（CUDA 首次 kernel 初始化 + 与预热线程抢锁）。**结论：冷启动必须靠常驻服务规避，
不能靠"多跑几次就快了"。**

## 3. 成本分解（B 段，热，cache 关）

### 3.1 全帧 f06（2560×1440，39 个文本框）

| 阶段 | 读数 | 占比 | 机制 |
|---|---|---|---|
| **load**（PNG 解码，`cv2.imread`） | 75.5–97ms | ~15% | 3.4MB PNG → 2560×1440 uint8；换 PIL 更慢 |
| **det** | 132–145ms | ~26% | 输入被 `Det.limit_type=min/736` + `Global.max_side_len=2000` 定到 **2000×1125** |
| **cls** | **118.6ms** | **~22%** | 只对每个裁片做 **0°/180°** 判定（`cls_batch_num=6`） |
| **rec** | 188ms | ~35% | 39 框 / `rec_batch_num=6`，每批 padding 到批内最宽行的 `max_wh_ratio` |
| 其余（前后处理/序列化） | ~20ms | ~4% | — |

> 改前 A 段同帧是 929ms；差异主要来自 GPU/显存争用（游戏 1962 MiB + daemon 2588 MiB 常驻），
> 不是代码。

### 3.2 det 的"固定成本"（决定 ROI 能省多少）

| 输入 | det | 说明 |
|---|---|---|
| 300×300 | 77.8ms | 被放大到 736×736 再跑 |
| 640×360 | 100.2ms | 放大到 1310×736 |
| 1280×720 | 48.9ms | — |
| 2560×1440（全帧） | 138–145ms | 缩到 2000×1125 |

**det 有 ~50–100ms 的固定成本，与面积弱相关** ⇒ "只裁 ROI"省不到你以为的那么多；ROI 主要省 rec 与 cls。

### 3.3 ROI 实测（`region=` 路径，cache 关，plain）

| ROI | 端到端 | load | det | cls | rec | 框数 |
|---|---|---|---|---|---|---|
| 300×300 | **231ms** | 81.4 | 77.8 | 2.9 | 67.2 | 4 |
| 1280×720（右下） | **242ms** | 75.5 | 48.9 | 53.8 | 59.1 | 1 |
| 640×360 | 442ms | 75.0 | 100.2 | 120.9 | 143.1 | 10 |
| 1440×900（左面板） | 483ms | 84.5 | 110.5 | 114.0 | 166.6 | 20 |

注意：这些 ROI 读数的 **load 仍是整帧解码**（75–85ms）。若调用方在常驻进程内直接给内存帧
（`cmd=world` 的路径就是这样），300×300 ROI 可落到 ~150ms。

## 4. 主导项与"100–200ms"的对齐

**主导项 = rec（188ms）+ det（138ms）+ load（75ms）+ cls（119ms）四段相加，没有单一"元凶"**；
能省的只有 cls（119ms，见 §5.2 的代价）和"第二次起直接不跑"（缓存）。

**为什么全帧进不了 100–200ms**（三条独立证据）：
1. 今天热态实测地板 **529ms**（B 段，干净窗口，cache 关）。
2. 历史同口径地板 **371ms**（2026-10-18 空闲台，D393：det 130–150 + cls 120–180 + rec 150–700）；
   当时结论已经写明「全帧 OCR 在这台机器上进不了 200ms，换实现/调参都救不了」。
3. **解码一项就 75–97ms**：任何"2560×1440 进、文本出"的通道，光把 PNG 读成数组就吃掉目标的一半。

⇒ 用户记忆里的 100–200ms 更可能是：**模板匹配 NCC 147ms**（D373）、**缓存命中 14ms**（D393，今天复测 1.1ms）、
或**对一个小 ROI 做 OCR**（今天 231–242ms；若省掉整帧解码可到 ~150ms）。这三条都与"全帧 OCR 529ms"不矛盾。

## 5. 改了什么

### 5.1 已落地（`tools/ys-editor/ys_lookd.py`、`tools/ys-editor/ys_ocr.py`）

| 项 | 内容 | 效果 |
|---|---|---|
| **帧级内容寻址缓存** | `cmd=ocr` 按 `(abspath, mtime_ns, size, ROI, pipeline, det_max, parallel, rec_batch, use_cls, 规则版本, engine)` 缓存整份结果；`cache=false` 可关 | 同帧重复 **529ms → 1.1ms**（CLI 49ms）；缓存键含 mtime+size ⇒ 文件改了必然失效 |
| **分阶段计时** | 回执新增 `timing{load, decode, det, cls, rec, infer, total, pipeline, n_det, …}` | 从"只有总 ms"到"能看出是解码/det/cls/rec 哪段慢" |
| **真实引擎上报** | daemon 回执新增 `engine=cuda\|cpu`（此前只有 `via=daemon`）；客户端 `ys_ocr.py` 透传 `engine/timing/cached/pipeline` | "显存预检把 daemon 切成 CPU"从此在回执里可见 |
| **`pipeline` 开关** | `plain`（默认，= 原行为）/ `buckets`（det 一次 + 按行宽分桶 + 并行 rec，跳 cls） | buckets 约 1.0–1.1×（在这台 855MHz 的卡上收益不稳定），**默认不开** |
| **`use_cls` 开关** | 请求级 `use_cls=false`，共享引擎用完**立即还原** | 省 **118.6ms**（546.6 → 415.9），但有反例（见 §5.2） |
| **`det_max/parallel/rec_batch` 请求参数** | A/B 不用重启 daemon | 本轮三组对照就是靠它做的 |
| **客户端排障参数** | `ys_ocr.py` 新增 `--no-cache/--pipeline/--use-cls/--no-cls/--det-max/--region` | 同口径 A/B 的命令入口 |

### 5.2 文本一致性门禁（这才是"能不能默认开"的判据）

`tools/ys-editor/tests/ocr-pipeline-parity.py` + 6 帧 inline 比对（文本多重集 + 框中心 ≤8px）：

| 帧 | baseline n | `use_cls=false` | `buckets` | 竖排/旋转框 |
|---|---|---|---|---|
| f06 | 39 | **DIFF（少 1 框）** | DIFF（5 处） | 0 |
| f07 | 36 | SAME | DIFF（1 处） | 0 |
| f04 | 30 | SAME | DIFF（4 处） | 0 |
| f00 | 28 | SAME | DIFF | 0 |
| f01 | 25 | SAME | DIFF（多 1 框） | 0 |
| neg-world | 2 | SAME | SAME | 0 |

- `use_cls=false` 的唯一反例：f06 上一个 **107×112px、score 0.51** 的低分框 `'入'`（(885,1291)）——关掉 cls 后它**识别为空**。
  差异很小，但按"任何一帧不一致 ⇒ 不可默认开"的规则，**它只能做可选开关**。
- `buckets` 差异形态：`maxt`↔`max:`、`一官方社区`↔`mm官方社区`、`!`↔`！`、个别框多/漏。
  **默认不开**；要用必须过 `ocr-pipeline-parity.py`。
- ⚠️ **反例覆盖不足**：6 帧里竖排/旋转框 = **0**，所以"跳 cls 对旋转文本无影响"**没有被验证**，
  只能说"横排 UI 上 5/6 帧一致"。要证伪需要一帧含竖排/倒置文本的界面（未找到）。

## 7. 未闭合项（按优先级）

1. **`use_cls` 默认值待拍板**：省 118.6ms，但 f06 丢一个低分框 `'入'`。现状=**保持开启**（不改默认）。
   要拍板需要：①确认 `'入'` 对判态/门禁是否有用（它不在任何 state 判据里）；②找一帧竖排/旋转文本做反例覆盖。
2. **`buckets` 管线的收益不稳定**：本轮三组里 575ms（比 baseline 慢），早前 n=12 是 548ms（比 baseline 快 8%）。
   在当前 855MHz 的卡上，跳 cls 已经吃掉大部分收益。要复评需在 GPU 提频（非本机常态）或换 batch 组合。
3. **"竖排/旋转文本"反例未覆盖**（见 §5.2）—— 跳 cls 的风险面没有被验证，只有"没测到反例"。
4. **全帧 OCR 的 100–200ms 目标不可达**（硬件地板 529ms@855MHz / 371ms@空闲）。除非：改用模板匹配通道
   （147ms 级，D373）或按 frame_id 缓存。**这不是本轮能修的回归，建议在 AGI-BAR 的口径里把"OCR 全帧"和
   "OCR 缓存命中/ROI"分成两个指标**，否则永远恒红。
5. **显存预检阈值 900 MiB 与"游戏在跑"的实际余量（856–903 MiB）重叠**：A 段实测就在阈值线上，
   一次重启可能随机落到 CPU 通道（结果正确但慢 ~3×）。**Lead 裁决（2026-10-22）：登记为 open item，下一轮做**——
   要补的不是再写一条断言，而是 **daemon 侧引擎选择的独立门禁**：`cmd=ocr` 回执必须给出 `engine` 的选择**理由**
   （显存不足 / 强制 CPU / 正常 三条），并有一条用例覆盖"阈值卡在边界"的取值。
   现有底座：`ocr-channel.selftest.py` A3（`YS_OCR_MIN_FREE_MIB=999999` ⇒ `engine=cpu` + `gpu_note` 说明原因）已覆盖
   "显存不足⇒CPU 且报原因"，缺的是 daemon 进程自己的选择理由与边界取值。
6. **`cmd=world` 的 OCR 段（B 段单次 439ms）没动**：那里已经复用对象层结果（`ocr_source=objects`），
