## 八、系统性根因（2 条）

**A. 成本链没拆到"系统调用/进程启动"这一层，算法优化就是够不着。**
398ms 的账里，抓帧 116ms + UID 条 82ms = **166ms 全是进程启动**，而我先前的诊断口径停在"抓帧/判据"这种阶段粒度。
拆到 `parts{}` 之后，改动只是把两次子进程换成一次进程内 XShm，立刻 3.2×。
**可复用判据**：单帧感知类工具若耗时 >100ms，先问「这一步是不是起了一个外部进程」，再谈算法。

**B. "只验正例"是隐性欠账的温床。**
19 道门禁全绿却 `unproven=16`——它们从没被喂过会失败的样子；子代理自述被当成证据用了很久。
两条是同构的：**只验证"对的路径通过"，不验证"错的路径会被抓住"**。
**可复用判据**：任何门禁/守卫上线时，必须同轮给一个"它应该报红"的注入用例；引用任何子代理结论前，先跑 `tools/subagent-verdict`。

## 二、最近一次错误的完整调查链（焦点夺屏，用户可感知）

**现象**：用户报「严重bug：导致无论做什么都强制切回原神那个桌面」。

**取证**：`~/.dsh/cmdlog/ys-focus-guard.log` 16:50:00→16:50:19 连发 6 条 `RESTORE_FAILED(target_idx=8 game_idx=8)` + `lease_kept: true` + `stacking_tail: [8] 原神 |ACTIVE`。

**根因链（四环）**：① 我做 live 验收时 `ys-scroll --lease` 套在 `ys-gui-slot` 内，内层 `acquire` 时焦点已是原神 ⇒ `prev==target`；② `idx(prev)>idx(game)` 恒不成立 ⇒ 恢复失败；③ 失败后 `lease_kept: true`，租约文件一直存在；④ 守护每 0.5s 轮询、**无限重试**，而 `restore` = `activate+raise` ⇒ **每次重试都把原神抬起来**。

**放大器**：游戏处于独占全屏时会在 ~1s 内把焦点/桌面抢回去（`guard-dev` 实测），所以"重试"变成"反复夺屏"。

**修复**：限次 3 + 指数退避 + `abandoned` 标记 + 失败路径只首试 raise + 连续 5 次自停。失败路径自测 `first_calls=3 no_more=1 abandoned=1 fuse=1 noop_raises=0 prevgame_raises=0`。
**打扰次数**：`prev==game` **0 次**、`prev` 消失 **1 次**、最坏 ≤3 次（原事故 19 秒 6 次）。

**止损**：`disable --now` → 修完复验 → 用户选 A 后重新启用。

## 三、为什么反复出问题——四条系统性根因

### 1. 「结构在位 ≠ 信号在产」——**恒定值是没接线的指纹**
- `structure[].scroll_hint` **8/8 帧恒 `unknown`**
- `released.ok` **恒 `false`** 却被调用方忽略
- `uncertainty` 被三处白名单**恒丢弃**

> 判据：某字段在 N 帧 / N 次调用里**恒为同一值**，先怀疑"没接上"，再怀疑"判据不准"。

### 2. 「只验成功路径」——这是本波最贵的一条
`ys-focus-guard` 自测 **5/5 全绿**、kill -9 后 1.9s 自动归还，看起来非常完整。
但它**没有一条验"永远恢复不了时会收敛到哪"**——于是把一次故障放大成用户被反复夺屏。

> 判据：任何重试/守护/看门狗，必须回答「连续失败 N 次之后它做什么」。答不出 = 没做完。

### 3. 「用便宜代理指标代替真实判据」——**第三次复发**
| 便宜指标 | 真实判据 | 差多少 |
|---|---|---|
| 文本集 Jaccard | 像素变化 | 0.78（判"没变"） vs 0.6553（实际大变） |
| 单帧计数 | 8 帧计数 | 20/0/46 vs 19/3/385 |
| micro mAP | 分 kind / 分族 P、R | menu 被说成"中等"，实际 P=1.000 / R=0.463 |

前一次（10-17~18）复盘已把这条列为系统性根因，**本波又犯三次**。⇒ 说明"写进复盘文档"不生效，必须落到**评测口径文件**（已建 `CALIBER-v2.md`）与**采集器**（`ys-collect` 已把「必须多帧」写进默认参数）。

### 4. 「接收补充 ≠ 改变优先级」——抗漂移
用户说「这只是我**额外补充**的额外建议」，我却把数据+训练升成主线、丢掉自己刚给出的 L6 优先序。
用户原话纠正：「你前面提出的点，难道因为一句话就动摇了吗？」

正确形态：**接收补充 → 判断与既有优先级的冲突 → 明确报告冲突 → 并行但守住主线**。

## 四、流程与方法论教训

1. **报告与事实不一致比缺功能更危险**：`worldsvc act` 正例 CLI 打印 `INJECT_FAILED`，而 `meta.json` 是 `ok=true`。根因是 `ys-scroll` 的 `rc=5` 同时代表"注入失败"和"焦点归还失败"。已改按 JSON 三态区分。
2. **门禁判据必须探对象，不许探记录**（同族第 6 例）：`systemctl is-active`/`MainPID` 是记录，socket 才是对象。已机械化为 `G-OBJECT` 守卫。
3. **唯一性判据优于阈值**：`uncertainty` 的排名测试（4 个背景假阳性必须全部排在 18 个真命中之前）比"绝对分数阈值"稳定得多。
4. **闭环能抓自己的错**：`uncertainty` → `ys-detail` 的第一个真实用例，就抓到 `uncertainty` 自己把**滚动指示器**误标成背景（3 个里 2 个误标）。
5. **用户抽审不可替代**：所有"我标好了"的结论，在用户看一眼之前都只是候选。

## 五、未闭合（按重要性）

1. **世界态对准 ≤20px**：两次测量都失败（请求 (1667,700) 落 (2500,1050)），L5 的真实缺口。
2. **滚动真值一条都没有**：背包那次测错了对象；`ys-scroll-scan` 在指针瞄不准时给的是**无效测试**却报 `at_bottom=true`。
3. **本体界面状态机为空**：只知道 `GAME_WORLD`，不知道在背包还是好友列表，L7 编排因此无法开始。

5. `live_accept.sh` 的 `| tail -6; echo $?` 记的是 `tail` 的退出码——会骗下一个人。

### 二、系统性根因（三条）

**A. "多路径共用的判定/取数"没有单一实现纪律（3 次）**
state 判定、字段透传、类别白名单——三次都是**同一份逻辑存在两处，只改了一处**。
门槛⑤ 早就写了"界面态判定全仓只有一处实现"，但**没有把这条推广到"所有共用取数"**。
⇒ 本部把判据扩写为：**任何被 ≥2 条路径消费的判定/取数，必须只有一处实现；新增字段必须逐层查重建点**
（daemon 输出 → `schema.new_world` → `_TOP_ALLOWED` → worldsvc 组装 → `KINDS` 白名单）。

**B. 条件回退在噪声下失效**
"容器为空才回退到检测框"读起来完全合理，但它默认**噪声不存在**。
真实世界里 CV 吐 1 个假 panel ⇒ 57 个真框全被压掉，而**没有任何地方报错**。
⇒ 判据：**写"条件回退"时先问「该条件在噪声下会不会永远不成立」**；能不用条件就不用（本例改成按已知的可信 state 直接分派）。

**C. 验收只覆盖一个场景就当成通用**
scoped NMS 在 v2 上 +0.2pp 就上线，v1 上却是 −0.3pp；菜单行以为是阈值问题，实为表示层。
⇒ 判据：**A/B 结论必须报"在哪些场景/权重/数据上验过"，没验过的场景要显式标注"未验"**，
且回退清单里要写清依赖关系（回退 v1 权重必须连 scoped NMS 一起回退）。

### 四、方法论教训

1. **"恒定值 / 空列表"先判它是读数还是没接上**。本部三个 bug 全部同形态：
   判据写在一半路径上、结果算出来没透出去、条件回退被假阳性短路。看到 `objects=0` / `state` 恒 PLAYTEST，
   第一反应应是"哪一层把它丢了"，不是"模型不行"。
2. **评测通道过了 ≠ 生产线过了**。trainer 的 cap12 在评测台涨了 4.5×，但 `ys_lookd` 是常驻进程、
   `Detector` 按路径缓存在 `_DETS` 里——**改代码不重启就等于没改**。本部要求任何检测器改动必须同时报
   「生产入口 `Detector.detect()` 的读数」，这一条当轮就抓到了差异。
3. **小样本结论要把置信区间写死**。cap12 的新 val 只有 33 GT / 3 界面，报告里写的是
   「从 .061 到 .273，区间宽，只作方向性结论」，而不是「行检测达到 .273」。
