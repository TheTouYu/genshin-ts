## 二、系统性根因（三条）

**A. "看起来成功"比"失败"更危险。**
11 条里第 2/3/4/5/6/7 条全是**静默失败或静默降级**：命令返回 0 但没产物、字段缺失但不报错、
变量未定义但异常被吞、账本重复但去重键没校验。**判据必须锚在产物上**（文件大小/哈希/唯一键/产物存在），
不能锚在返回码或"看起来很快"上。

**B. 判据没有单一源 = 修一处骗一处。**
6 份状态判据各写一套坐标与阈值，`ys-fast` 说 SAVE、`ys-state` 说 AMBIGUOUS；
同一界面两个工具给出相反答案时，**下游所有结论都不可信**。判据必须是一等资产。

**C. 测量没锚在对象上，专家结论没被复核。**
"18ms"（失败耗时）、"21274 次调用"（来自直读会话文件，可信）与"9272 行账本"（重复记账）混在同一份报告里；
GLM 第一版评审看似严密、实则零实测。**别人的结论也要按同一条标准复核**——我复跑 expA/expB 才发现
它们测的是 CPU 路径。

## 三、方法论教训（可复用）

1. **耗时不带产物校验 = 伪读数**。"很快"可能是"失败得很快"。
2. **复跑一致 ≠ 结论正确**：复跑只能证明可重复，不能证明测的是对的路径（CPU vs GPU）。
3. **worst-case 判据 > best-case**：锚点/样本/回归集都按"最差那张"选，否则过拟合单帧。
4. **快路径可以慢，不能错**：两段式判态先快后慢，余量不足就升级；快路径不许牺牲正确性。
5. **瓶颈会转移**：单次匹配 31ms，但 10 锚点流水 690ms——**先量胶水，再量计算**。
6. **委托要写"取证义务"**：每条结论必须带命令+输出+产物路径，否则子代理会写一篇像样的幻觉。
7. **静默失败会繁殖**：`except: pass` + 未定义变量 = 一个坏掉的"自愈"伪装成正常代码。

## 四、用户纠偏（逐字）

- 「你的 gui 操作总链路执行效率还可以提速十倍，停下来和我找问题吧」
- 「遇到问题，修改问题，不是高手的做分。这个时候应该停下来反思，我们这个模块的设计，反馈链路，监控系统，证据留存等系统」
- 「画个 html 展示。请变为准则防止遗忘」
- 「分析没错，但是不够细，就不能够用这些数据，给出更好的工程上的优化实现……创建 glm 代理，分给它去做」
- 「看它的执行过程，它的结论不可信。要的是解决问题，它没有实测，没有自己做写脚本实验，没有查论文，没有看 github 现成成果。所以它的回答带了不少幻觉。心法：大模型在没有和环境做出合理的交互下就给出的答案通常存在幻觉」
- 「既然全项目通用，为什么不试试全项目抽样」
- 「现在用 gpu 跑的是？它提供的模型，没有 gpu 版本吗？」（→ 暴露我"复跑一致≠路径正确"）
- 「别急，把你认为的可能遇到的技术细节难点，交给 glm5.3 思考 max 去回答，等它带来惊喜」
- 「原神 这个是平常的工作流，这个不行就只能继续换更低精度方案。或者云端。可以估算一下，用本地在速度上和云端的差异吗？」

## 五、未闭合与风险

1. **技能层未开工**：8 个高频操作尚未做成技能；`tools/gui run` 已支持锚点目标/按键/状态断言/`--dry-run`，但没对真实编辑器跑过一次完整技能。
2. **真实编辑器一次没碰**：本会话所有验证都在回归帧 + 自建 GTK 沙箱上做（避免干扰用户），**未验证真实窗口下的稳定性**。
3. **判态端到端 266~296ms**（目标 200ms）：抓帧 140ms 是主要项，需要更快的抓法或复用帧。
4. **锚点库只覆盖 6 个态、单分辨率**：未验证换分辨率/换语言（worst-case 判据已就位，样本不足）。
5. **云端 OCR 优化未做批量并发**（多图仍串行）。
6. **本地 VLM 判死**（内存约束），前提是 int4/int8 量化，未实施。
