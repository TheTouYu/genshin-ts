# 仪器路线图（2026-10-17 起）

> **状态**：待验证（P0 已落地并有真实读数；P1–P4 未开工）
> **来源**：`docs/maintenance/design-2026-10-17-ys-editor-system.md`（诊断）+ 本会话实测
> **用户裁决**：「关键 GUI 模块未高质量验收前不进下游」；「做一个独立的、监控全部执行命令的监控模块」

## 计划（按 依赖 × 收益 排序）

| 阶段 | 交付物 | 判据（可跑） | 状态 |
|---|---|---|---|
| **P0** | `tools/cmdmon` 独立命令监控：账本 + 五条报警 + systemd 守护 | `cmdmon report` 能给出类别占比/最慢/失败/裸 sleep；守护增量采集延迟 ≤2s | **已完成** |
| **P1** | `ysd` 单一状态源：一份判定 + 帧缓存 + `state.jsonl` | 取帧 ≤12 次/轮；回归 ≥16 样本（含 5 负样本）双通道 100% | 未开工 |
| **P2** | `wait_until` 谓词等待 + 禁裸 sleep | `cmdmon report` 的「裸 sleep」计数 = 0；离开+切回 263s → ≤40s | 未开工 |
| **P3** | `ys-run` 单槽执行器：声明式计划 + 前置断言 + `round.json` | 失败轮 ≤10s 停；`round.json` 含断言/观测/判据值/耗时 | 未开工 |
| **P4** | 回游戏主线：三个 3D 游戏用新仪器跑通 | 每个游戏「玩家能玩通 + 日志有通关证据」 | 未开工 |

## 为什么 P0 先做（已完成的选择理由）

1. **零风险**：只读 DSH 会话事件流（`~/.dsh/sessions/*/session.v4.jsonl.zstd`），不改任何现有工具、不重启任何进程。
2. **它同时是 P1–P3 的尺子**：P2 判据「裸 sleep = 0」、P3 判据「取帧 ≤12 / 失败轮 ≤10s」都要靠它自动度量——没有 P0，后面每一步都只能靠"感觉"验收。
3. **全项目收益**：任何项目的任何命令都在账本里，不止 GUI。

## P0 首日实测（本会话 324 次调用）

```
仪器耗时 23.4 分钟   人等待 12.3 分钟（单列，不计入仪器）
gui       182 次  18.4m  79%  均 6.1s     ← 仪器仍是最大头
explore    55 次   4.5m  19%  均 4.9s
memory      5 次  12.8s   1%
build      12 次  10.1s   1%
报警：slow=19  fail=9  sleep=48  guistorm=1
```

**立刻看出的三件事**
1. **裸 sleep 48 处**——"用时长冒充同步"不是个别现象，是系统性习惯（P2 要清零的就是它）。
2. **GUI 类均时 6.1s**——单次调用就比一次编译贵两倍，仪器成本主要在这里。
3. **人等待 12.3 分钟（3 次提问，均 4.1 分钟）**——问一次问题的代价 ≈ 跑两轮试玩；提问要"一次问全、问完能自己往前走"。

## 使用方式

```bash
tools/cmdmon report --since 30m     # 一轮结束后看账
tools/cmdmon alerts --since 2h      # 只看异常
tools/cmdmon scan                   # 手动补采（守护已在跑时通常不需要）
systemctl --user status cmdmon      # 守护状态
tail -f ~/.dsh/cmdlog/alerts.jsonl  # 实时异常
```
