## 一、结论先行

## 二、测量方法（只读、离线帧、不占屏）

工具全在 `.scratch/vram-probe/`（不进仓库主线，可重跑）：

- `probe.py`：向常驻服务发 N 次 `cmd=ocr`，每 10 次用 `nvidia-smi --query-compute-apps` 取**本进程**显存 + `/proc/<pid>/status` 取 RSS/Swap，落 TSV。
  - `cache:false` 必带——`cmd=ocr` 有按文件身份的内容寻址缓存（同帧二次 ≤3ms），不关就测的是缓存不是推理。
- `stage.py`：**每个 mode 独立进程**做分阶归因（`torch` / `det_init` / `det_one` / `full_init` / `full_one`），per-pid 读显存；`--variant` 覆盖 ORT 的 `cuda_ep_cfg`。

复现命令：

```bash
# A/B 曲线（200 次、10 帧轮转、强制真推理）
FRAMES=$(ls .scratch/gui-corpus/f0*.png | paste -sd,)
python3 .scratch/vram-probe/probe.py --pid "$(systemctl --user show -p MainPID --value ys-lookd)" \
        --n 200 --frames "$FRAMES" --out /tmp/curve.tsv

# 分阶归因（每个 mode 一条命令，进程退出即释放显存）
for m in torch det_init det_one full_init full_one; do
  python3 .scratch/vram-probe/stage.py --mode "$m"
done

# 参数变体（852 → 644 那一档）
for v in base same heur both cap384; do
  python3 .scratch/vram-probe/stage.py --mode full_one --variant "$v"
done
```

环境读数（两组 A/B 都在同一台机器、时钟未变）：`nvidia-smi clocks.sm = 855MHz / max 2100MHz`（41%）、
`power.draw ≈ 22W`。**时钟降频是本机已知问题（D497），A/B 延迟差里含它，不能全算给"抢 GPU"。**

## 四、2.6GB 花在哪：分阶拆解

每个 mode 一个独立进程，读完显存后进程退出（per-pid 读数，不受守护自身占用干扰）：

| 阶段 | 该进程显存 | RSS | 说明 |
|---|---|---|---|
| `import torch` + 1 个小 CUDA 张量 | **150 MiB**（`empty_cache` 后 128） | 715 MB | torch 的 CUDA context + cuBLAS/cuDNN 句柄。**这一份无法与 ORT 共享** |
| 只建 ORT det 会话（不推理） | **0 MiB** | 419 MB | ORT 会话懒创建 context：init 只花 11ms、只吃 CPU 内存 |
| det 会话 + 1 次全帧推理 | **694 MiB** | 1685 MB | ← **主导项** |
| 三会话（det+cls+rec）init | **0 MiB** | 423 MB | 三个会话**共用 ORT 的 context**，不是"每会话一份" |
| 三会话 + 1 次推理（plain 管线） | **852 MiB** | 1825 MB | cls+rec 只再要 ~158 MiB |

**det 的算式**（为什么是 694 而不是 9.5MB）：

- 整帧 2560×1440 → `limit_type=max, limit_side_len=2000`（`ys_lookd.py:945` 把 `det.limit_side_len` 临时设成 `det_max`）⇒ 输入 2000×1125，对齐 32 ⇒ **1984×1120 ≈ 2.22 Mpx**
- 首层 conv 32 通道 fp32：`1984 × 1120 × 32 × 4B ≈ 284 MiB`（输入张量本身只有 26.7 MiB）
- 再叠 BN/推演中间张量 + **`kNextPowerOfTwo` 分配器倍增**（要 200MiB 先要 256MiB）+ **cudnn `EXHAUSTIVE`** 的算法搜索 workspace ⇒ 观测到 694 MiB

**守护总显存的合成**（B 段 1492 MiB）：torch 侧 ~150（context）+ ORT 侧 ~852（三会话 + 一次推理）= ~1002，
余下 **~490 MiB** 落在感知层（`ys-screen` 容器层、ys-state 的 12 个锚点 NCC 张量、帧缓存 `_FRAME_CACHE`、
两个 D2 检测器 `gui-det-v2.pt`）——这部分是**推导值**，待空闲释放实验复核（§7-3）。

**权重/线程**（排除项，别再把它们当嫌疑）：`PP-OCRv6_det_small.onnx` 9.5MB + `PP-OCRv6_rec_small.onnx` 21MB +
`cls` 0.57MB = **31MB**；`intra/inter_op_num_threads=-1`（OMP 线程池）只吃 CPU 不计显存；
`_OCR_RES_CACHE`（32 条回执）与 `_OBJ_CACHE` 是**小字典**，不持 GPU 张量。

## 六、落地改动与效果（前后对照）

> **三条口径（读这张表之前先读，否则会误读）**
> ① **512 MiB 是「每个 ORT 会话」的上限**（det/cls/rec 各一份，理论 3×512=1536），**不是进程总上限**；
>    进程总占用看"守护"那几行的整块数字（544 / 952）。
> ② **544 / 952 是「新进程」的读数**；A 段的 **2588 是跑了 4h26 的旧进程的历史高水位**，
>    两者**不能并列成"优化前后"**（那不是同一个东西的两次测量）。能被当作硬证据的是：
>    *同一口径下的* 852→644（独立进程、同帧）、1492~1548→544（都是新进程、预热完）、1836→952（都跑过混合负载）。
> ③ f06 热态 **582ms** 与 ocr-perf 的 **593ms** 是**不同人、不同时间**测的；差 11ms **不构成"变快"**，
>    只能说明**没有退化**（p50 的口径受 GPU 时钟与本机邻居影响，见 §三 的三元组）。

## 八、未闭合项

1. **A/B 差 1052 MiB 的因果**。两个判据实验：①B2 = 干净进程跑 200 次混合帧，若爬到 ~2500 ⇒ **arena 历史高水位**成立（修法=加顶）；②若稳在 1492 ⇒ 另找（共存期 cudnn 选不同 workspace / 驱动侧 context 预留）。
   ③共存模拟：用气球进程把 free 压到 ~900 MiB 再打 50 次，看守护是否被撑大（游戏关了无法复现原状，气球是等效替代）。
2. **A 段 110 次跑被他人重启切断**（18:59:12 / 18:59:41 / 19:01:04 各重启一次，非我所为）；200 次 A 段曲线未拿满，只有"恒定不涨"的定性结论。
3. **感知层 ~490 MiB 是推导值**：需在 `_release_idle` 触发前后各取一次显存，看掉多少（它清的是 torch 侧缓存与帧/模板张量）。
4. **改动后验收已跑（2026-10-22 19:30~19:35）**：200 次不增长 ✓、f06 p50 582ms 无退化 ✓、`selftest.py` 123/123 ✓、`ocr-channel.selftest.py` 5/5 ✓。
   **但"启动基线 1492→544（−950）"里，只有 −208 能用引擎参数解释**：差额来自"改前那个进程预热时已经把整帧 OCR 的 arena 撑起来"这一推断，
   **没有做 `YS_OCR_GPU_MEM_LIMIT_MIB=0` 的对照重启来钉死**（那会占一次重启窗口）。
5. **气球共存模拟未做**：脚本已就绪 `.scratch/vram-probe/balloon.py --target-free 900`（把 free 压到 ~900MiB ≈ 原神在跑时的余量，再打 50 次），
   需要一段独占窗口（约 1 分钟）。它回答"和游戏共存时守护会不会被撑大"。
6. **`det_max>2000` 的调用方**（`cmd=ocr` 的 `det_max` 参数、`ocr_blocks`/`ocr_page`）在 384MiB 硬顶下会显式报错；需要盘点是否有生产调用方真的传 >2000。

## 九、复盘（这轮哪里绕了、下次怎么更快）

1. **"每请求新建 500MB context"是历史，但差点被当成结论**。任务书给的线索指向 context 泄漏；分阶实验（每个阶段一个新进程）10 分钟就把真身换成了 **det 全帧 arena**。
   教训：**活进程里的显存数字永远是历史高水位**，读代码得到的"嫌疑"必须用 per-stage 独立进程读数替换后才能进结论。
2. **"重复调用不增长" ≠ "没有高水位问题"**。200 次同尺寸/混合尺寸都不涨，但多套管线、多套 `det_max` 会一路把 arena 顶高且**永不回落**（实测同一进程 1540 → 1852，代码一个字节没改）。
   ⇒ 判"有没有泄漏"要连**形状变化**一起测，只看同一帧会得到假阴性。
3. **`_release_idle()` 的名字骗人**：它只释放 torch 侧（实测 −236 MiB），ORT arena 与引擎原地不动。想真正让闲置态掉到 ~640 MiB，得 unload 引擎（候选改动 2，默认关）。
4. **验收口径必须"同进程同帧只差参数"**：852→644 是硬证据；跨进程的 2588 vs 544 只能当旁证（一个是 4.5 小时旧进程的历史高水位）。
5. **本机有邻居**：`dsh-game-mode` 会在游戏退出后拉起 `dsh-embed`(1266) + `dsh-decision`(1850) 合计 3.1GB。任何显存/延迟读数都要带三元组（`used/free`、`clocks.sm`、邻居是否 active），否则 A/B 会被读成因果。
6. **时间分配教训**：为拿"空闲 10 分钟"这一条读数花了约 13 分钟挂钟，而它在验收里权重最低（且只掉 236 MiB）。
   下次这类"长等待的低权重读数"应放到最后并行做，先把主导项（改参数 → 重启 → 200 次 → selftest）跑完。
7. **可复用资产**：`.scratch/vram-probe/` 下的 `probe.py`（N 次调用 + 显存曲线）、`stage.py`（分阶归因，`--variant` 可测任意 `cuda_ep_cfg`）、
   `ratchet.py`（形状棘轮）、`balloon.py`（共存模拟）、`wait_idle.py`（谓词等待闲置释放）。这套工具对任何"常驻 GPU 服务吃多少显存"都通用。
