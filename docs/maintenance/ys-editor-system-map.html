ys-editor GUI 自动化模块 · 系统地图

2026-10-17 实测诊断 · 50 个文件 / 约 1.5K 行核心 · 数据来源：/tmp/round2.log 时间戳 + 源码 + calib/regress/ 11 样本
一句话结论：环境层做对了，判定层与编排层没有设计—— 状态判定有 6 份重复实现、同步靠 sleep、反馈环是开环、证据只留截图不留断言。 一轮 426 秒里 92% 是仪器开销，真正必须花的只有 33 秒。

一、模块分层（按层看责任与缺陷）

编排层 ys-round · ys-play · ys-loop · ys-nav · ys-reload-keep · ys-map

  • 线性脚本：无前置断言、失败继续跑、固定 sleep 30、一轮 6~7 分钟
  • 失败成本 = 一整轮（前置条件不成立也照样跑完）

判定层 ys-fast · ys-state · ys-where2 · _ys-ui.sh:judge · switch-save:st() · wait_light

  • 6 份重复实现——同一个错（结算页判成存档页）在两处同时存在，修一处另一处继续骗人
  • 全窗 import 实测 2893ms；一次状态读要 3~6 次独立取帧

感知层 ys-observe · ys_look.py + ys-lookd · ys-shot · ys-shape.c · calib/regress

  • 有 GPU 模板匹配 + 11 张回归集（这是全模块唯一成型的测试资产）
  • 帧无缓存、无时间戳契约：同一时刻多个工具各取一次

驱动层 ys-gui-slot · ys-pointer-click · ys-put · ys-drag · ys-esc · ys-act · shims/

  • 焦点「取-用-还」有结构性保证（KWin 直赋 + 严格回读）——这是全模块最扎实的设计
  • 每子工具重取焦点（一轮 6~8 次 ×1~2s）；编辑器点击仍用 1.7s 长按（Wine 只要 120ms）

环境层 ys-env.sh · ys-game-env.sh · ys-wins · ys-atop · ys-preflight

  • 唯一做对的一层：X 授权自动发现（重启后随机名）、项目事实与桌面环境分离、栈顶判据

监控 / 证据 ys-time-audit · accept-meter.py · ys-stuck-report · ~/ys-round/<ts>/

  • 工具都写好了但没接进主链
  • 证据 = 5 张截图；没有「断言了什么 / 观测到什么 / 判据值多少」⇒ 复盘只能靠回忆

二、反馈环：现在是开环

现在 · 开环

计划 ─► 动作1 ─► sleep ─► 动作2 ─► sleep ─► … ▲ └─ 中间发生什么都不会改变后续路径 失败成本 = 一整轮 6~7 分钟

应有 · 闭环

前置断言 ─假─► 停 + 记账 (≤10s) │真 ▼ 动作 ─► 观测（一帧多点）─► 后置断言 │假 ▼ 重试 n ─仍假─► 停 + 记账

三、一轮 426 秒花在哪

切回我的图115s · 27%
试玩启动74s · 17%
固定死等30s · 7%

退出试玩15s · 4%

真正必须花的 ≈ 构建 13s + 游戏加载 ~20s ≈ 33s；其余 92% 是仪器开销。 离开/切回共 263s，其中 ys-switch-save:63 一句 sleep 22 就占 22s × 2 次，另加两次 2.9s 全窗截图。

读法：不是「能不能做」，而是「做对了几次」。驱动层与感知层的单点能力够用（焦点保证、GPU 模板匹配、11 张回归集）， 但被判定层与编排层吃掉了：判定层是唯一出现「同一错误两处并存」的层（可维护 1）； 编排层四项全 ≤2（无断言、无记账、无性能预算、不可单测）。

五、由此决定的优化方向（影响 × 风险）

序方向打掉什么可验数字
S1单一状态源 ysd：一份判定实现 + 帧缓存 + state.jsonl6 份重复实现；每轮 ~50 次取帧取帧/轮 ≤12；回归 11 张全绿 + 新增 5 张负样本
S2谓词等待 + 禁裸 sleep（wait_until + lint）sleep 22 / sleep 30 冒充同步固定 sleep = 0；离开+切回 263s → ≤40s
S3单槽执行器 + 断言记账（ys-run）开环反馈；证据只有截图失败轮 ≤10s 停；每轮产出可复算的 round.json
S4点击时长分级（Wine 120ms / 游戏内 ≥500ms）单点 1.7s单点 ≤0.4s
S5输入塞进加载期（见游戏画面即注入）死等 30s起游戏 → 注入 ≤5s
为什么先修 S1/S2 而不是更慢的驱动层：驱动层与感知层当前没有制造错误，它们只是慢； 判定层的重复实现正在持续制造误判——本轮 3 次「以为失败其实成功 / 以为成功其实失败」全部来自这里。

六、模块自身的验收门槛（不过线不回游戏开发）

  1. 判定：回归集 ≥16 张（11 现样本 + 5 张负样本：结算/加载/存档/菜单/游戏内互判），两条独立通道一致率 100%；不一致必须解释清楚，不许调阈值糊过去。
  2. 假成功：注入 3 类失败（前置不成立 / 动作无效 / 日志未落盘），执行器必须在 ≤10s 内停止并给出「哪条断言为假 + 观测值」。
  3. 性能：写盘轮 ≤90s、纯试玩轮 ≤40s、取帧 ≤12 次/轮、取焦点 1 次/轮、固定 sleep 0 条。
  4. 证据：随机抽一轮，只给 round.json + 引用帧 + .gia，没参与的人能重算出同一结论。
  5. 可维护：全仓 grep -l "LOADING\|SETTLE" tools/ 只命中一个文件。
心法：「在关键的 GUI 操作模块没有完成高质量验收就强行进入后续游戏开发和核验反馈迭代， 只会加大问题的复杂度，最终拖垮整个项目。」
本轮实测正是它的反面教材：仪器不确定 → 每轮多花 5 分钟 → 一轮只敢做一个实验 → 参数只能猜 → 猜错要重跑 → 更不敢做实验。先把仪器做对，是把这条负反馈掰成正反馈的前提。
