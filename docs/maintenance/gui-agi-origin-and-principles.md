## 一、起点（2026-10-17）

用户起点不是"做一个 GUI 工具"，而是：**用千星开发三个完整 3D demo，再由此递归进化到 AGI 门槛**。

> "我们项目完整覆盖了使用千星开发游戏的 70%+ 的内容。但是交给 ai 完整的去开发，还差一些环节。我先要需要补齐，请调查，给出最佳优先级"

> "你应该完整参考官方的指南，从新建项目开始，（计算机视觉 / device-test-loop 技能），完整的体验几次真实的游戏开发全部流程（要求开发出三个 demo 游戏项目，不要偷懒，是完整的 3d 游戏项目）"

**GUI 模块的地位**（2026-10-17 转入 GUI 专项时定的）：

> "现在是最关键的 gui 模块，它即是你的最薄弱的一个环节也是通向 agi 的最基础的模块，所以我会高度陪同你，参与到你的反馈回路里面来，在这个模块上抵达 agi"

> "总目标是三个高质量游戏并递归进化到 AGI 门槛，当前阶段先把 GUI 操作能力层做到过五条验收门槛"

> "用 agi 的标准来看，我们的 gui 模块，就要拥有完整，方便的操控能力，非单个项目独有。而对于我们这个任务，大概就是你对照官方千星奇域的指南，就可以轻松完成编辑器的全部操作并资产化。所以，从 agi 的角度看，你认为我们现在的设计能接住吗？"

## 二、验收哲学（"仪器优先"的由来）

> "心法：在关键的 gui 操作模块没有完成高质量验收就强行进入后续游戏开发和核验反馈迭代，只会加大问题的复杂度，最终拖垮整个项目。"

> "先跑时间受控的真实窗口验证，（每次窗口占用小于 30s），熟悉切验证可行再逐渐增加信任。（有失败先例，单跑每轮 10 分钟，无法发现问题，缺少我的关键核验反馈，到最后都是无用功）"

> "你的 gui 操作总链路执行效率还可以提速十倍，停下来和我找问题吧"

> "我们的 ocr，获取原始输入这个链路，是硬性要求，只能看前台画面吗？只是确认"（→ 引出后台抓帧能力）

## 三、方法与反面教材（用户当场纠正过的）

> "你看，你又缺少探索就定目标。"

## 四、反馈轮（用户主动进场的机制）

> "p1 这一层做什么？我如何参与组合反馈轮提高质量？"

> "3. 我额外提议：做一个独立的，监控全部执行命令追踪的监控模块。它简单但是有效，可以快速发现一些执行过程中的坑，全项目收益"（→ cmdmon）

> "记忆系统很好用，你和队友可以共享记忆，记忆不仅支持跨项目主动查询/改写，还支持主动召回，但是也要注意写入知识的质量和定期维护，记忆系统的上限在知识本身。"

> "难或不确定的任务点必须停下来把用户引入反馈轮"（AGI-BAR §六，2026-10-18 裁决 A 形态时确认）

## 五、由此固化的原则（本模块必须遵守）

1. **仪器优先**：GUI/自动化模块没过五条门槛，不进下游任务（`tools/AGENTS.md`「仪器优先」）。
2. **小步验证**：窗口占用 <30s / 单次操作可复核；不要"跑十分钟再回来看"。
3. **留痕优先于自信**：每步留可复盘证据（日志/读数/截图），别太信自己写的脚本。
4. **递归迭代**：每轮做—复盘—沉淀技能/记忆，不只交付结果。
5. **反馈轮**：难/不确定 → 停下来把用户引入；用户进场时要给"可点的东西"（审阅页/决策卡）。
6. **非单项目独有**：所有能力按"任何 GUI 都能用"设计，游戏/编辑器只是测验场。
7. **抓帧与工具分工**：素材工具只做"选窗口+触发+落盘"，抓帧归抓帧层。

## 七、本会话（2026-10-18~19）的起点与主线衔接

### 7.1 会话开场四问（用户原话）

1. **开工前先报计划，不许动手**：
   > "先读 `.scratch/gui-stack/PROMPT-next-round.md` 和它点名的五份材料，读完先别动手——回来告诉我：你打算建哪几张票、第一张做什么、怎么验证、哪些你自行决定、哪些要我拍板；我确认之后你再开工。"

2. **先对齐目标与程度**：
   > "问一句：我们的在做的事情是？要做到什么程度？反馈轮怎么跑？"

3. **程度不够，且丢了细节**：
   > "大方向没错。但是程度不对，**我们要达到 agi 基准，同时你丢细节了。**"（并指定用 `/context-loss-recovery` 去恢复上个会话原文）

4. **形态之问（决定性）**：
   > "你认为我们做 gui 模块的 agi 落地实现，应该是什么样的形态？完成之后，给你安装上，你能达到什么样的能力？**用这个模块，再去看主线的 3 个高质量游戏交付，你会怎么做？**"

### 7.2 用户裁决（形态 A）

> "**A，这就是我要的。** 持久化文档落盘。创建你的队友，开工。唯一注意：**你认为难或者不确定的任务点，把我引入到反馈轮。**"

形态 A = **常驻世界状态服务 + 单一 schema + 三动词（look / act / wait_until）**；
旧工具（ys-screen / ys-observe / ys-do / gui）退化为其内部实现。详见 `AGI-BAR.md §三`。

### 7.3 主线衔接：GUI 模块怎么服务"三个高质量游戏"

这是用户第 4 问的第二半，此前没有单独落盘，补在这里：

| 主线环节 | GUI 模块提供什么 | 验收 |
|---|---|---|
| **开发期** | 看得懂编辑器（L1–L2）：找得到资源树/属性面板/时间轴，点得准 | 一个真实编辑任务（改存档名/加节点图）端到端成功 |
| **调试期** | 看得懂游戏画面（L3–L4）：状态、可点性、红点 | 能从画面判断"当前在哪个界面/是否卡住" |
| **试玩期** | 看得懂反馈（L5–L6）：滚动补全 + 否定闸门 | 不把"没看到"说成"不存在" |
| **复用期** | 世界状态服务被三个 demo 共用 | 同一套 look/act 不改代码换游戏 |

**判据**：GUI 模块的验收不靠"检测框多准"，靠**主线任务能不能少掉人工接管**——三个 demo 各跑一遍，统计人工介入次数。

### 7.4 一条被现实推翻的早期指令（记录在案）

> "我们开始 A，**你 1s 一张图片**，我这边进行操作。"

这是当时的采集节奏；后来实测证明**对游戏窗口持续抓帧会拖死 presentation**（10fps×15min ≈ 9000 次 → GPU 0%、画面冻结）。
现行口径：**按需单帧**，或按页采 N 帧后停（`ys-snap` 薄客户端 + `ys-capture --source window`）。
