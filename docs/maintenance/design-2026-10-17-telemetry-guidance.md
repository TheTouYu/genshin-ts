# 设计：命令遥测 → 行为纠正闭环（telemetry guidance）

> 日期 2026-10-17 · 状态：设计定稿（机制待落地）
> 数据基础：`tools/cmdmon`（采集/报警/审计）+ `tools/cmdmon-mine`（深挖）+ `tools/agent-coach`（实时教练卡）
> 本文回答一个问题：**测出来的浪费，怎么变成模型行为的实际改变**。

## 0. 结论先行

- 30 天全项目实测（161 会话 / 21342 调用 / 仪器 30.12h）：**43%（12.87h）按显式判据属于可避免**，
  其中空等后台任务 4.19h > 裸 sleep 3.58h > 10 分钟内重跑同命令 3.44h > shell 读文件超时部分 1.43h。
- 机制选择：**触发式注入为主（检测到浪费模式当场注入教练卡），会话开始注入为辅（冷启动 30 秒版）**，
  不选每 N 轮定时注入（噪声大、时机错），不选只写 AGENTS.md（静态化无法携带"当下数字"，且无淘汰通道）。
- 每次注入留档（`~/.dsh/cmdlog/injections.jsonl`），事后用同一套 cmdmon 数据判定卡片是否改变行为，
  指标连续两个观测窗不回落即自动下架——**没有淘汰通道的提醒机制最终会变成噪声源**。

复现命令：

```bash
python3 tools/cmdmon-mine --since-days 30 --json /tmp/mine.json   # 本文所有 30 天数字
tools/agent-coach --window 30m --dry-run                          # 实时教练卡
```

## 1. 闭环图

```
数据                信号                 卡片                注入              行为变化            复测
───────            ──────              ──────             ──────            ──────────         ──────
session.v4.jsonl  → cmdmon daemon     → alerts.jsonl     → agent-coach     → 下一窗口的      → cmdmon-mine
.zstd (事件流)      (2s 增量, 账本)      (slow/fail/        生成教练卡         调用分布           (周级)
                    commands.jsonl       sleep/repeat)      ≤600字,带数字      (sleep↓ 内置↑)     + 注入留档对比
                                                        ↓                                        ↑
                                       coach-cards.md ←── 挑选/淘汰 ←── 指标: 该卡片对应误区 ──┘
                                       (素材库 10~15 张)              的发生率是否回落
```

闭环的关键不是"注入"那一步，而是**两头都有数据**：注入前有基线（该误区的发生率/耗时），
注入后有复测（同一指标在窗口间的变化）。中间的卡片只是把信号翻译成模型可执行的指令。
卡片无效时的淘汰路径：指标不动 → 降级观察一个窗口 → 仍不动 → 从注入池下架，卡片留在
`coach-cards.md` 归档区供人看（详见 §5）。

## 2. 注入点比较与选择

| 注入点 | 成本 | 时效 | 失效模式 |
|---|---|---|---|
| **会话开始注入**（AGENTS.md 或任务书引用 coach-cards 精选版） | 每会话 ~300 字 ≈ 300 token，全会话占用 | 最早，但数字是上一会话的 | 数字过期后可信度衰减；对长会话后段的失误无补救 |
| **每 N 轮定时注入** | N 轮一次，看似便宜 | 中 | 时机错配：没浪费时也注入=训练模型忽略它；恰好是"提醒疲劳"的标准成因 |
| **触发式注入**（检测到连续 3 次同类慢命令/裸 sleep 才注入） | 仅在需要时 ~200 字 | 最准：浪费正在发生时注入 | 需要一个检测器在会话内运行；注入点要能到达模型上下文（当前用"模型自查 agent-coach"或 hook） |
| **写进 AGENTS.md 静态化** | 每轮 ~100 字 | 永久 | 无数字无淘汰通道；规则越攒越多 → 触发 AGENTS.md 体积上限（本仓已定 ≤4KB 目标），且"静态规则无证据"最容易被模型忽略 |

**选择：触发式为主 + 会话开始 30 秒精选版为辅。** 理由：

1. 遥测的价值在于**当下性**——`sleep 60; tail` 正在跑时提醒"用 wait_until"才有用；
   会话开始 10 分钟前提醒早已被后续上下文冲淡。
2. 定时注入的失效模式（提醒疲劳）在我们自己的数据里有对应物：裸 sleep 1020 处说明
   "已有守则禁止裸 sleep"这件事本身证明了静态规则的失效——**守则已经在 AGENTS.md 里，行为没变**。
3. 静态化只保留给"内化完成"的卡片（指标回落后从注入池毕业进 AGENTS.md 一行版，见 §5），
   这也解决了 AGENTS.md 体积约束：只有被证明有效的规则才值得占每轮预算。

落地形态（最小实现，不改现有文件）：daemon 侧新增"会话内触发器"——`cmdmon alerts` 检出
连续 3 次同类报警时，把对应卡片追加到 `~/.dsh/cmdlog/injections.jsonl` 并打印到 daemon.log；
模型侧约定（写进任务书/技能）：每完成一个阶段自查一次 `agent-coach`。若 DSH 未来提供
轮间 hook，再把该触发器挂到 hook 上，去掉对模型自觉的依赖。

## 3. 卡片格式

一张卡片五个字段，缺一不可（全部模板见 `docs/maintenance/coach-cards.md`）：

```
### 卡片名
- 误区：一句话描述行为模式（正向表述目标在"做法"里，误区允许点名行为）
- 实测证据：带数字、带窗口、带复现命令
- 正确做法：可直接执行的具体动作（含命令/工具名）
- 可验证判据：改了之后 cmdmon 里应该看到什么读数变化
- 观测窗口：多久后复查、淘汰条件
```

例（卡片 C1 摘录）：

> **误区**：用 shell `cat/sed -n/head` 反复读同一批文件。
> **证据**：30 天 shell 读文件 3004 次 1.67h，内置 `read/grep/glob` 同类 1512 次仅 2.5 分钟，
> 单价差 20 倍；`tools/ys-editor/` 被反复读 103 次共 25.8 分钟（`tools/cmdmon-mine --since-days 30`）。
> **做法**：读文件一律内置 `read`（offset/limit 翻页）；搜索用 `grep`/`glob` 工具。
> **判据**：周复盘 `explore` 类 shell 调用占比从 47% 降到 <15%；重复读路径 top 无 ×50 以上项。
> **窗口**：两周，两窗不回落 → 检查卡片措辞/注入点。

## 4. 反馈环的证据要求

每次注入必须留档，一行 JSON：

```json
{"ts":0,"card":"C1","window":"30m","evidence":{"sleep_n":6,"sleep_ms":96000},"source":"trigger|session-start|manual"}
```

判定流程（全部用已有 cmdmon 数据，无新增采集）：

1. **基线**：注入时刻该卡片对应指标在**前一窗口**的值（如 sleep_ms、explore_shell_n）。
2. **复测**：注入后下一窗口（30m 或一轮任务）同一指标。
3. **判**：指标下降 ≥50% → 本轮有效；下降 <50% 且连续 2 个注入周期 → 卡片进观察；
   观察期仍不动 → 下架（§5）。
4. **归因护栏**：同时段全项目指标也在降（例如因为换任务类型）时不算卡片功劳——
   复测必须对比"注入过的会话"与"未注入的会话"（账本按会话可分）。

这套证据要求本身就是"行为改变"的可复现定义：**卡片是否有效 = 注入会话与未注入会话
在下一窗口的指标差**，而不是"感觉模型变好了"。

## 5. 淘汰与防噪

| 状态 | 判据（全部可机检） | 动作 |
|---|---|---|
| **候选** | 深挖发现新模式 | 入 coach-cards.md 待选区，不自动注入 |
| **在架** | 注入 ≥3 次 | 正常注入轮换 |
| **已内化** | 对应指标连续 2 个观测窗回落 ≥70% 且维持 | 从注入池毕业；一行版（≤40 字）进 AGENTS.md 静态区 |
| **无效** | 注入 ≥5 次、每次复测指标变化 <20%（对比未注入会话） | 下架到归档区，附"为何无效"一句（措辞问题/时机问题/本来就该是工具问题） |
| **噪声嫌疑** | 卡片本身引用的数字 < 阈值（如 sleep_n < 3） | 当次跳过注入（触发式的天然防噪：没有信号就没有卡片） |

防噪的三道闸：①触发阈值（无浪费不注入）；②轮换上限（同一会话同一卡片只注入 2 次，
第二次起模型已见过，重复注入只剩成本）；③总量预算（每会话注入总量 ≤600 字符 ≈ 600 token，
与 agent-coach 的字符上限一致——这个预算本身是实测出来的：教练卡平均 350 字即可覆盖 3~5 条）。

## 6. 已知数据质量约束（使用本机制前必读）

- **账本重复行**：daemon 与手动 scan 并发时 `commands.jsonl` 会出现同 callId 重复行
  （实测 30 分钟窗内 1260 行只有 119 个 callId）。所有读取侧必须按 callId 去重
  （`agent-coach` 已做；`cmdmon report` 未做，引用其数字前先去重复核）。
- **失败两态**：1075 次失败里 539 次只有 `isError` 没有退出码（工具层错误，如 edit 匹配失败），
  429 次 exit=1。只盯 `[exit code]` 会漏掉一半失败。
- **归因是启发式**：mine 的"可避免"判据全部显式写在报告里（如 shell 读文件超 1s 部分记可避免），
  换判据结论会变；引用时带上判据，不引用裸百分比。

## 7. 落地顺序建议

1. **先落地 C8（裸 sleep → wait_until）+ C4（空等 job_output）**：两项合计 7.77h/30 天，
   占可避免时间的 60%，且判据清晰、不改任何工具。
2. 触发式注入先用"模型自查"形态（任务书约定阶段边界跑 `agent-coach --dry-run`），
   等跑出 2 个复测周期后再决定是否做成 DSH hook。
3. 卡片库先只上架 5 张（C1/C3/C4/C7/C8），其余留在待选区——注入预算有限，先打大头。
