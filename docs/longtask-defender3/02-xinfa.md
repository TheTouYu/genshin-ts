## A. 设计律（本项目判断"好不好玩"的四条尺子）

### A1 短循环：配点从"关卡之间"搬进"每一波结束"
**要做什么**：每波结束给一次三选一，30~60 秒一个决策点。
**为什么**：原作靠关卡之间的研究树配点，10 分钟只有 1~2 次权衡；玩家要的是"思考→反馈"的高频循环。
**判据**：前 5 关（约 12 分钟）内，玩家做出 ≥10 次选择。
> 2026-10-28：用户原话「很多选择分支，需要让玩家思考，怎么加点会更赚……玩家付出了思考，付出知识……游戏正好给了足够的反馈，就会形成正反馈回路」

### A2 每次选择必须跨阈值（可计算，不靠运气）
**要做什么**：每个选项在 UI 上标注"当前 → 选择后"的 **TTK / DPS / 箭速 / 箭数**，并保证一半选项当场少一箭。
**为什么**：原作早期给弓 +3 攻击（20→23）打 50 血怪仍是 3 箭，**Lv3（26）才变 2 箭**——好玩的不是数值，是"跨过阈值"。
**判据**：设计表里每个怪的血量都能被"当前伤害档位"整除出可见台阶；模拟器自动对局能统计出每次选择后的 TTK 变化。
> 出处：原作 `project` 表 atk 20/+3、`monster` 1001 blood 50（实测 2026-10-27）；用户原话「前期关卡的时候，弓箭速度很慢，怪物血量很低，玩家每次升级完速度或者攻击力，立刻就可以在一个小怪身上看到明显的提示」

### A3 质变优先于数值
**要做什么**：三选一里至少一个选项**改变行为**（穿透/多重/减速/召唤/击退/反伤），最多一个纯 +x%。
**为什么**：原作 236 件装备/技能里绝大多数是线性 +x%，真正质变的很少；我们没有那个内容产能，只能用更高的质变密度补。
**判据**：选项池里"行为类"≥40%；每局结束能说出"这局我靠什么机制赢的"。
> 出处：`skill`/`skill_v2` 62 条技能清单（2026-10-27 实测），其中被动纯加成约 20 条

### A4 节奏用预算模型 + 自动回归
**要做什么**：每波给"怪物总血量预算"，由玩家 DPS 消化；用模拟器跑 N 局自动对局，卡通关率/时长分布。
**为什么**：原作 `hp_rate` 1→690、`single_cd` 400→2000ms 是表驱动；"刚好"的难度只能靠读数收敛。
**判据**：模拟器 200 局统计：新手模型通关率 60~70%，时长中位数 2~3 分钟/关；曲线抖动 <10%。
> 出处：`stage_info` / `battle` 表（2026-10-27 实测）+ 用户原话「太简单和太难都会劝退玩家，要达到刚刚好，这个很难」

## B. 从原作提取信息的方法（可复制）

### B1 先拿数据表，再谈设计
**要做什么**：APK 解包 → `assets/data/data.json`（67 表 / 5802 行）+ `data_ch.json`（中文文案）→ TSV 导出。
**为什么**：原作的数值、文案、关卡曲线全在这两个 JSON 里，**比读代码便宜 100 倍**。
**判据**：`~/re-targets/defender3/out/tables/_index.tsv` 有 67 行；`monster.tsv` 1207 行且带中文名列。
> 命令：`python3 ~/re-targets/defender3/tools/extract_assets.py`（幂等）

### B2 用原生符号反推系统边界
**要做什么**：`nm -D -C lib/arm64-v8a/libcocos2dcpp.so` → 类名（`BattleService` / `TowerParamConfig` / `ArcheryUpgradePopup`…）→ 对照表名。
**为什么**：符号未剥离时，类名就是"这游戏有哪些系统/面板"的免费目录，能验证表没抄全。
**判据**：每个数据表都能找到一个 `*Config` 类；每个 UI 系统都能找到 `*Panel/*Popup` 类。
> 命令见 `references/original-data-map.md` §四

### B3 教程文本是"操作契约"
**要做什么**：`data_ch.json.tutorial`（48 条）逐条读，抽出"玩家到底怎么做"。
**为什么**：它明确写了「长按/滑动连续射箭，手指位置=目标」「拖动魔法图标，松手位置=目标点」这类代码里要猜的细节。
**判据**：核心循环的每条操作都能在教程里找到原话。

### B4 素材解码（含伪装格式）
**要做什么**：998 张图里 141 张是 `zcim` 包装（假 PNG 头 + JPEG 负载），用"找 JPEG 起点"剥壳；再按 plist 拆图集。
**为什么**：不剥壳 PIL 直接报 `UnidentifiedImageError`，会把"能拿到的美术"误判成"没有"。
**判据**：`out/images` 1160 张可打开；`out/atlas` 1010 帧。
> 出处：2026-10-27 实测（`flash/bow_soul/bow_soul.png` 尾字节 `ffd9` = JPEG EOI）

## C. 工程纪律

### C1 数值先行、代码后行
**要做什么**：任何战斗参数先写进 `design/*.md` 的表，再进代码；改数值要同步表。
**为什么**：数值是这个游戏的命根子，散落在代码里就调不动。
**判据**：`design/` 里的每个数字都能被代码里的常量注释引用回来。

### C2 先模拟器后真机
**要做什么**：机制/数值先在模拟器（2D UI + Lua，我方成熟产线）验证，再上 3D 真机。
**为什么**：真机试玩要占用户的手和屏幕，模拟器可以跑自动对局与回归。
**判据**：真机验证前先有一次模拟器全绿的记录。

### C3 节点预算与负载
**要做什么**：战斗逻辑拆图，单图 <2000 节点；单 tick 帧数 <3000。
**为什么**：千星硬限制，超了直接拒载（项目既有教训）。
**判据**：`gsts` 编译产物节点数 + 真机日志负载读数。

### C4 分层证据
**要做什么**：报告"已实现"必须分三层写：结构层（编译/注入）/ 行为层（真机帧值/日志）/ 用户层。
**为什么**：结构在位 ≠ 行为正确。
**判据**：三栏报告模板。
