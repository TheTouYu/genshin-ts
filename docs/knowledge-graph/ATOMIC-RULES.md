## 一、硬规则（实现可直接依赖）

### R1 单张节点图节点上限存在两个口径，实现取严

- **断言**：官方限制表写「单张节点图节点最大 3000」；我方生产红线为 2000。**实现按 2000**。
- **边界**：超 2000 应按职责拆新图，不是"优化到 2000 以下"。
- **锚点**：`docs/ui-tutorial/official-guide-auxiliary-appendix.md:2056`（官方口径）；
  `src/cli/assets_node_graphs.ts:237`（我方红线）
- **证据等级**：硬规则（两侧皆是）
- **影响面**：所有节点图设计与拆图决策；D3a / D7

### R2 悬浮交互页内控件的显隐无法用节点图控制

- **断言**：悬浮交互页**内部**控件的显示/隐藏节点图控制不到，只能把状态挂到**页签序号**上，
  通过切页签间接控制。
- **边界**：必须**开工前**按页签粒度切分界面；事后再补无解（实测作者因此放弃细节优化）。
- **锚点**：`docs/knowledge-graph/d/d5-表现层.md`（源 `BV1s6LB6WEF4` 实测）
- **证据等级**：实测
- **影响面**：所有悬浮交互页设计；D2b / D5

### R3 客户端节点图只能读、不能写自定义变量

- **断言**：客户端图**没有**"设置自定义变量"节点 —— 官方全文档 0 命中，我方 vendor
  客户端节点表 `setCustomVariable` 亦 0 命中（双向互证）。故"客户端写变量→服务端读"结构性不可行。
- **边界**：叠加"技能实例不能携带参数"（必须走实体自定义变量）→ 必然产生数据同步问题；
  视频唯一可靠化招式是 sequence（序号）匹配法，其上限是**只保证玩家身上的变量最新**。
- **锚点**：`docs/knowledge-graph/d/d3b-客户端图与通信.md`（官方 `official-guide-nodes-client.md` + 我方 vendor 表）
- **证据等级**：硬规则（官方与代码互证）
- **影响面**：客户端算力分载、双端通信设计；D3b

### R4 字符串无任何拼接节点，打表映射是当前唯一路

- **断言**：节点图不提供字符串操作节点，字符串值不能拼接。可行方案 = ASCII/字符映射表
  存关卡实体 + 玩家实体预留定长槽位 + 五步生成管线（返回编码列表→转字符串列表→映射表查不到返回占位
  →循环插槽→不足补空白）+ 巨无霸 switch 或字典打表赋值。
- **边界**：**槽位数就是字符串长度上限**；拆多字典再合并可绕开"单节点过长"。
- **锚点**：官方服务端节点文档中唯一的"拼接"是【拼接列表】`official-guide-nodes-server.md:112-118`；
  我方 `grep "拼接" src/runtime/value.ts` = 0；节点定义 `src/definitions/nodes.ts:3889` 仅列表。
  案例 `docs/knowledge-graph/d/d3c-架构与变通.md`（源 `BV1dNkDBgEUn`）
- **证据等级**：硬规则（官方+代码+实测三方）
- **影响面**：任何需要动态文本的玩法（自定义名字/计分板文案）；D3c（邪修轴）

### R5 变量写入负载排序：局部变量 < 节点图变量 < 自定义变量

### R11 白盒物件 11 种基础几何体的元件常量表（本会话实测枚举）

- **断言**：官方 11 种白盒几何体各有固定的元件 ID，且**基础几何体满足 `resourceId == definitionId`**：

  | resourceId | 名称 | resourceId | 名称 |
  |---|---|---|---|
  | `10009001` | 长方体 | `10009007` | 五棱锥 |
  | `10009002` | 球体 | `10009008` | 圆柱 |
  | `10009003` | 平面 | `10009009` | 圆锥 |
  | `10009004` | 三棱柱 | `10009010` | 线框长方体 |
  | `10009005` | 五棱柱 | `10009011` | 线框圆柱 |
  | `10009006` | 三棱锥 | | |

- **边界**：这是**基础白盒物件**的 ID。自定义元件从这些几何体派生时会**保留 `resourceId` 不变但升到自己的 `definitionId`（≥1077936129）**——
  例：地图 1073741890 的「灯柱_A1」是 `resourceId=10009001` + `definitionId=1077936129`。
  故批量生成几何必须用 `resourceId == definitionId` 的基础件，不要用派生件的 definitionId 当几何体。
- **锚点**：`research/千星知识图谱/../..` → 本会话对 20 张已有地图执行
  `gsts assets:entities --map-id <id> --output <json>` 后聚合枚举（命令与结果见
  `docs/knowledge-graph/reproduction/maze-entities.json` 的生成脚本 `gen-maze.py`）；
  官方几何体清单见 `docs/ui-tutorial/official-guide-concepts.md:1203-1225`（11 种）
- **证据等级**：我方实测（枚举 20 张图）+ 官方清单（11 种数量吻合，互为印证）
- **影响面**：所有需要批量创建几何的场合；`assets:entities --entities <json>` import 的 `definitionId` 取值
- **配套事实**：`EntityImport.id` **可省略**，CLI 自动分配下一个空闲系统 GUID（≥1077936129）
  —— 见 `src/cli/gil_entities.ts:44` 注释。所以批量生成**不需要也不应该**硬编码 GUID（AGENTS.md 红线）。


### R12 编译节点图必须走正规入口 `node ./bin/gsts.mjs`

> 来源定性更正（2026-09-15 复盘）：本条不是本会话新发现——dsl-nodegraph-development 技能 SKILL.md:645 早已逐字记载同一故障与正解。本会话因未加载该技能而重复发现。保留本条是因为 PKC 侧原缺此 claim（技能与 PKC 是两个载体），但不得记为「新发现」。

- **断言**：编译节点图必须用 `node ./bin/gsts.mjs -c <config>`（= `dist/src/cli/gsts.js`）。
  用 `npx tsx src/cli/gsts.ts -c <config>` 会因为 src/dist 双副本问题，
  在 GIA 生成阶段抛 `[error] gsts.f is only available in server_* ctxType (current: javascript)`。
- **边界**：最小复现是「只做 `f.get`/`f.set` 的空图也失败」，所以与图内容无关，是加载路径问题。
  诊断法（根 CLAUDE.md 记载）：`node --import tsx -e "console.log(import.meta.resolve('genshin-ts/runtime/core'))"`
  —— 输出 `src/...` 即落到类型检查侧副本。
- **锚点**：`bin/gsts.mjs:3`（`import '../dist/src/cli/gsts.js'`）；
  `src/runtime/core.ts:670-673`（`kCtxStack` 是 `Symbol()`，两份 core.ts 各持一个 → 栈不共享）
- **证据等级**：我方实测（2026-09-15 T12 复现第一次编译即撞）
- **影响面**：所有本地编译/注入操作；用 tsx 直跑 CLI 的脚本全部受影响

### R13 信号节点需要目标地图的注册表，无地图编译不了

> 来源定性更正（2026-09-15 复盘）：同上——该技能 SKILL.md:251-252 已记载「地图注册是编译的硬前置」，且 :3 还给了更省事的 GSTS_LOCALLOW_DIR 副本验证通道（本会话未看到，自己从零重新发明了夹具法）。

- **断言**：图中一旦使用信号节点（如 `f.sendSignal`），GIA 生成阶段会要求**目标地图的信号注册表**：

  未注册的信号名也会报 `signal is not registered in target map`。
- **边界**：这是**编译期**约束，不是运行期。故"先写图、后挑地图"的顺序对含信号的图不成立。
  无信号的可编译（T12 实测：去掉 `f.sendSignal` 后同图编译通过）。
- **锚点**：`src/compiler/ir_to_gia_transform/build_signal_definition.ts:867`（缺注册表抛错）、
  `:871`（信号名未注册抛错）；`src/compiler/ir_to_gia_transform/client_graph.ts:1355`
- **证据等级**：硬规则（编译器强制）
- **影响面**：含信号的所有图（跨图通信、事件解耦设计）；施工顺序与地图选择


### R14 实体 import 的输入颜色是字符串，导出读到的是整数

- **断言**：`assets:entities import` 的输入 JSON 里 `color` 必须是 **`'#RRGGBB'` 字符串**，
  写成整数（哪怕语义等价的 0xAARRGGBB）会被直接拒绝：
  `[error] entities[0].color must be '#RRGGBB'`。
  而**导出**出来的实体里 `color` 是**整数** `rgb: 4288323750`（= 0xAARRGGBB）。
  **导入与导出的颜色表示不是同一种** —— 拿导出样本当 import 模板会踩。
- **边界**：`'#RRGGBB'` 无 alpha；导入后 CLI 解析成 `0xFFRRGGBB`（alpha 固定 FF）。
- **锚点**：`src/cli/gil_entities.ts:42` `EntityImport` 类型注释
  「0xAARRGGBB（解析自 '#RRGGBB'）」；实测报错与产物核验见
  `docs/knowledge-graph/reproduction/gen-maze.py` 注释与 `examples/maze-repro/PROGRESS.md`
- **证据等级**：我方实测（2026-09-15 T12 几何导入）
- **影响面**：所有用脚本批量造实体的场合

### R15 `assets:entities` 省略子命令时不报错，而是静默产出错误的小文件

- **断言**：`gsts assets:entities --gil X --entities Y.json --output Z.gil`（**不写 `import`**）
  不会报错，会产出一个约 6.7KB 的**残缺文件**（实体数读回为 0），而不是完整地图。
  必须显式写子命令：`gsts assets:entities import --gil X --entities Y.json --output Z.gil`。
- **边界**：本项目实测；子命令族为 `[export|import|patch|apply-candidate]`，
  但顶层 `--help` 的短用法行（`Usage: gsts assets:entities [options]`）**看不出需要子命令**。
- **锚点**：`src/cli/assets_entities.ts:49-51`（用法行与子命令列表分列两处）；
  实测：无子命令产出 6,709 字节 / 实体 0，带 `import` 产出 492,983 字节 / 实体 166
- **证据等级**：我方实测
- **影响面**：所有 assets: 子命令的调用（**用前先确认子命令名**，别被短用法行误导）
- **配套**：核验产物要**读回数字**（实体数/字节数），不能只看命令有没有报错
  —— 这次正是"没报错但产出错"的典型
