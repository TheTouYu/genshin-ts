### 3.1 六类图的节点库边界（**决定"这张图里能不能这么写"**）

- **HR-01｜五段分类的有无就是能力边界**。角色技能图 `:17`、造物技能图 `:2713`、造物状态图 `:5247`、造物状态决策图 `:7013`、角色操控技能图 `:8408` 五章**都有**「查询节点 / 运算节点 / 执行节点 / 流程控制节点 / 其它节点」五段；**过滤器节点图只有「查询节点 `:11741` / 运算节点 `:12606` / 其它节点 `:13261`」三段——没有执行节点、没有流程控制节点**。→ 过滤器图**不能写执行流**，只能做"查询→运算→出结果"。出处：`:17,940,1752,2660,2695` / `:11741,12606,13261`（**硬规则**）

## 四、实操细节（来自视频语料）

### 4.1 最小通路：怎么把一段计算真的搬到客户端

- **通路五步（照抄）**：①创建一个**瞬发技能** → ②在技能里挂上一个客户端节点图 → ③服务端节点图中**创建技能实例** → ④**释放**该技能实例 → ⑤客户端图算出结果后发信号回服务端。出处：`BV1oaDrBuE11` `[00:02:17]` "现在我们只需要创建一个瞬发技能在里面挂上一个客户端节点图再在服务端节点图中实例化并释放这个技能就可以实现客户端节点图运算了"（**硬规则**）
- **技能实例的语义（讲师转述月之六官方能力）**：服务端图可为**一个角色**创建技能实例并**持久化**，在其生命周期内随时"释放指定技能实例"**强制该角色使用技能**——"不需要绑定到实际的技能槽位也不需要玩家进行任何操作"。出处：`BV1oaDrBuE11` `[00:02:17]`（**硬规则**）
- **落地时套用我方标准模板**：`verify/d2-client/d2-skill.ts`（服务端施放图）+ `d2-client-skill.ts`（客户端图）+ `signals.ts`，见 `.agents/skills/client-nodegraph-development/SKILL.md`「一、调用链模板」（**我方实测**）

### 4.2 异步是**本质**，不是实现细节（最影响架构的一条）

- **调用客户端 = 完全基于回调的纯异步**：服务端释放技能实例后"**他的逻辑就在这里中断了**，直到客户端节点图发出若干信号之后，在相应信号的监听事件中整个流程才能继续下去"。出处：`BV1oaDrBuE11` `[00:04:36]`（**硬规则**）
- **与服务端内部拆信号的差别**：后者"充其量只需将某些逻辑推迟到当前逻辑的后续执行，总体上仍然属于**同一个时间周期内**"。出处：同上（**硬规则**）→ 即：拆信号仍是同步的，调客户端是**跨时间周期**的
- **服务端对客户端状态完全无能为力**："客户端可能由于延迟而需要较长时间响应，甚至可能在多人游戏中这个玩家刚好退出了，因此服务端**永远无法保证客户端节点图的结果能够及时返回甚至是否能够返回**"。出处：`[00:05:22]`（**硬规则**）
- **"全局暂停"代价**：若游戏必须等客户端结果，"在释放技能实例后服务端会直接开启 **stop the world 暂停全部逻辑**直到客户端汇报结果才能继续游戏"——**多人游戏下玩家掉线/中退会让全局暂停不可行**，且多人对实时性要求更高。出处：`[00:09:15]`（**实测**）
- **设计结论（讲师口径）**：调用客户端本身有延迟，"**比较好的实践是在服务端先对当前的情况进行评估，确实需要调用客户端算力了再进行调用**；如果不太复杂且较为有效则绕开客户端"。出处：`[00:15:24]`（**经验共识**）

### 4.3 数据同步：sequence 匹配法（本轴唯一的"可靠化"招式）

- **问题**："一般而言，如果在**同一个事件的处理程序内**更改自定义变量后立刻调用客户端运算，则客户端**不能读取到最新的值**"。出处：`BV1oaDrBuE11` `[00:10:01]`（**实测**）
- **做法（六步，照抄）**：
  1. 客户端侧配一个**技能变量**"异步调用客户端 sequence"；
  2. 玩家实体上配一个**自定义变量**"异步调用服务端 sequence"，初始值 = 1；
  3. 每次调用客户端运算前，服务端先把它 **+1**；
  4. 客户端开始逻辑时**比对两个 sequence 是否相等**；
  5. **相等** → 才进行计算并返回结果，同时把客户端 sequence **+1**；
  6. **不相等** → 说明版本已过期，**发回一个特别信号要求服务端重新释放技能实例**。
  出处：`BV1oaDrBuE11` `[00:10:01]`–`[00:10:46]`（**实测**）
- **它的上限（必须记住）**：sequence 匹配法"**并不一定能保证全局的数据同步，最多能保证玩家身上的自定义变量数据最新，其他实体不一定**"——没有条件解决也可以不管，"大部分时候还是很稳定的"。出处：`[00:13:53]`（**实测**）
- **它为什么必须用技能变量**：技能变量是客户端唯一持久化手段，且服务端无法读写（`[00:06:08]`，**硬规则**）——所以 count 只能由客户端自增、服务端只维护另一半。
- **更重的方案（我方实测，非视频内容）**：需要**多变量批量下发且零丢失零撕裂**时，sequence 不够用，走 **seqlock 门 + 单写者仲裁**（寄存器组 + dispatcher + 15Hz 门控轮询 + 二读 epoch），实测单通道 ~5 任务/秒、11/11 零丢失。见 `.agents/skills/client-nodegraph-development/SKILL.md`「五D」与 `docs/game-engine-knowledge/retrospective-2026-08-31-compute-lane-sync.md`（**我方实测**）
- **反向（C→S 结果回传）的节拍问题**：客户端读服务端数据存在 **~10/s 硬上限**，这是"锁步"真凶；破除办法=客户端不再读服务端状态，改**自写自读自持存储**（技能变量）+ 结果信号直传。出处：SKILL.md「五E」（**我方实测**）

### 4.4 技能实例不能带参数 → 一切走变量 → 于是必然有同步问题

- **原文**："用技能实例时**不能直接携带参数**，因此如果我们要携带任何参量或是单纯的状态量，都**必须通过实体的自定义变量来进行传递**……这不仅仅是带来一些麻烦，主要是会带来**数据同步**的问题"。出处：`BV1oaDrBuE11` `[00:03:02]`（**硬规则**）
- **推论链（本轴核心因果）**：不能带参 → 走实体自定义变量 → 而自定义变量是有复制延迟的 → "同事件内改完立刻调客户端读到旧值" → 所以**必须**上 sequence（§4.3）或 seqlock。这条链是"为什么客户端通信难"的完整答案。

### 4.5 客户端图的**硬限制**（讲师截图版，实现前逐条对照）

- **三条硬限（原文）**："最显然的就是**不能创建复合节点**、**不能修改自定义变量的值**、以及**不能修改引用类型（如列表、结构体）的值**"。出处：`BV1oaDrBuE11` `[00:03:02]`（**硬规则**）
  - 官方侧交叉验证：客户端全文档无 `设置自定义变量`（§三 HR-06），与"不能修改自定义变量"完全一致（**硬规则 + 我方实测**）
- **改列表的邪修（唯一合法绕法）**："虽然客户端节点图不允许修改列表，但如果确实有此类需求可以使用**多分支加局部变量**来模拟，操作时确实需要进行**大量的重复**，但这是目前的设计所决定的"。出处：`BV1oaDrBuE11` `[00:12:20]`（**实测**）
- **不能创建复合节点的后果**："影响很大，但由于客户端的局部变量和自身角色等级均不需要连线，可以在编写时基本避免飞线的现象，再通过核心的分区就可以创造更适合维护的节点图"。出处：`[00:13:53]`（**个人经验**）
- **浮点精度**："客户端运算非常容易遇到**浮点数精度问题**，建议在传递数据时尽量使用浮点数本身，取整使用服务端的正规节点进行四舍五入"。出处：`[00:13:53]`（**个人经验**）

### 4.6 动画技能互斥与它的空子

- **互斥规则（硬）**："一个角色**同时只能释放一个技能**"。在玩家释放动画技能的过程中，服务端再释放技能实例会互斥：如果新技能是**瞬发技能**则"**完全无法执行**"；如果也是动画技能，则"根据**原技能的允许打断配置**决定是原来的留下还是切换到新技能"。出处：`BV1oaDrBuE11` `[00:03:48]`（**硬规则**）
- **空子**："错开调用客户端算力和玩家可释放技能的时段；在**单个动画技能时长小于 0.5 秒**时，实测瞬发技能大部分时候也可以正常释放"。出处：`[00:03:48]`（**实测**）
- **不影响的一面**："**瞬发技能之间是不会有影响的**……很多奇遇永远都不会用到动画技能"——所以动画技能互斥"并不否定客户端运算策略"。出处：`[00:13:53]` `[00:13:07]`（**实测**）
- **策略自证**：讲师该关卡同时用了 2.5ms 级输入检测（动画技能）**和**大量瞬发技能做客户端运算，两者共存不干扰。出处：`[00:06:54]`（**实测**）

### 4.7 邪修通道：把定时精度抬到 2.5ms 级（技能编辑器"循环轨道"）

- **背景限制**：月之六的**单位状态定时触发技能**能在客户端唤起一个定时器释放指定槽位技能，但"它的 **tick 间隔最小只支持 0.1 秒**"。出处：`BV1oaDrBuE11` `[00:06:08]`（**硬规则**）
- **邪修做法**：用**技能编辑器的新特性「循环轨道」**——"在 **0.01 秒**的时间间隔中放置**四个节点图调用**，在**循环 25 次**，我们便实现了一个调用角色输入检测节点图 **100 次**的动画技能"。出处：`[00:06:08]`（**实测**）
- **副作用实测**："由于技能动画时间较短，虽然它属于动画技能并且开启功能后会全息覆盖，但实测**并不会**对我们使用瞬发技能进行客户端运算的策略造成干扰"。出处：`[00:06:54]`（**实测**）
- **只在该发时才发**：该资产"在最高可以达到 2.5ms 精度的同时完全不需要服务端定时器介入；虽然客户端 tick 频率非常高，但**只会在玩家输入状态变化时才会发送信号**，故在几乎可以忽略不计"。出处：`[00:05:22]`（**实测**）→ 高频采样 + 事件驱动发送 = 本邪修的正确形态

### 4.8 邪修通道：用"单位状态层数"当客户端→服务端的数字管道

- **动机（当时的通道现状）**："目前客户端是很难向服务端发送数字的，**只能靠全局变量或写一套字典**之类的"——而全局变量"在单人地图没影响，但**多人地图大概率会出现奇怪的 bug**"。出处：`BV1h1qeBgEnt` `[00:00:46]`（**实测**）
- **做法**："**单位状态层数**本身是一个整数变量，可当客户端→服务端的数字通道用：用状态层数承载镜头参数，就能在**不修改服务端节点图**的前提下实现任意镜头效果"。出处：`BV1h1qeBgEnt` `[00:01:31]`（**实测**）
- **它的价值**："既不写长字典，也不吃多人地图下全局变量那类玄学 bug"。出处：切片（**实测**）
- **同族邪修（另一源，D3a 收录）**：用"添加状态"代替"发送信号"传整数参数——"发送信号太频繁了一直发送……堆积会很多会炸"，而状态可以携带一个整数参数（用**状态层数当参数**），塞进去时 +1、取出来时 -1。出处：`BV1xFu26AER3` `[00:10:14]`（**实测**）→ 两个源独立指向同一机制：**单位状态层数 = 现成的整数寄存器**

### 4.9 选哪个客户端来算（多人在线）

- **做法**：定期令**全部在场玩家**发回通过"获取当前客户端时间（高精度）"（`official-guide-nodes-client.md:555`）取得的毫秒时间；服务端收到信号后**再发起一次相同的调用**，通过比较两次调用的**时间差**计算一个客户端延迟的**定性值**——"相当于**两次握手**的过程"。出处：`BV1oaDrBuE11` `[00:07:40]`（**实测**）
- **可以不做同步的前提**："由于这个场景对于**状态的精确度要求不是很高**，我们可以不需要考虑数据同步的问题"。出处：同上（**实测**）

### 4.10 什么场景该用客户端算力（选型判据）

- **四类适用场景（原文）**：①各种复杂的 **AI 决策逻辑**（实时性要求不高或可容忍一定延迟）；②略复杂的**界面逻辑**（字符串拼接、素材 id 更改等，能容忍较大延迟但要处理数据同步）；③**随机事件**（准确性要求低，甚至可容忍**调用失败**）；④其他复杂但可容忍延迟的逻辑（**统计类运算**）。出处：`BV1oaDrBuE11` `[00:13:07]`（**个人经验**）
  - ⚠️ 讲师标注为个人经验，但与我方"事件驱动 → 低频定时器 → 高频轮询"的负载铁律方向一致（**我方实测**）
- **真实案例的可拆清单（俄罗斯方块）**：①消行连锁（遍历所有行检查消除条件、为所有行记录状态、剩余行下落）②维护每列最高方块位置做落点预测（**预览方块落点多达 15 行**）③分数计算（含 5 个可自由加点乘积）④界面"消球倍率"说明的复杂字符串拼接——**全部由客户端算，服务端只需"直接取用"或做"基本的合法性校验"**。出处：`[00:08:28]`（**实测**）
- **耗时判定也适合塞进角色技能图**："运行速度很快而且基本上不会超载"（讲师只见过一次客户端超载）；典型用例=五子棋落子后横/竖/斜判定连五（循环次数非常多）。出处：`BV1K4tH6GE4k` `[00:39:35]` `[00:40:20]`（**实测**）

### 4.11 负载真相（**反直觉，但很重要**）

- **信号本身不是负载**："多发送信号这些**并不会产生什么很大的负载，也没有硬性的陷阱**；**唯一决定负载的只有服务端收到信号后进行的处理逻辑**"。出处：`BV1oaDrBuE11` `[00:12:20]`（**实测**）→ 优化点永远在**服务端 onSignal 的处理链**，不在客户端发得多不多
  - ⚠️ 与我方定则的关系：我方"打印纪律/事件门控"约束的是**观测打点**（每拍 2 行 × 5Hz × dup 回声实测拖卡），与"信号节点本身不重"不矛盾——重的是服务端**每拍都要跑的处理逻辑**。出处：SKILL.md「五C·高频观测打点必须事件门控」（**我方实测**）
- **客户端算力的体感上限**："客户端的算力非常充足且**永远不会导致关卡崩溃**，但也不要完全放飞；个人体感客户端**单次运算节点数的极限在数万左右**，太多会导致客户端出现明显卡顿甚至无响应"。出处：`[00:14:38]`（**个人经验**）
- **真实信号量级**：讲师俄罗斯方块的消行逻辑"常规情况就会发送约 **44** 个信号，大部分都是对列表的某个值进行修改或者位移实体这样的简单任务"。出处：`[00:12:20]`（**实测**）

### 4.12 五条实操经验（讲师原话，逐条可直接执行）

1. **监听信号最好放在关卡实体节点图里**，不要放在玩家/角色等实体节点图内——"如果在玩家角色等实体节点图内监听，会导致**多人游戏下多个实体重复收到同一信号**，如果信号不是按广播来设计的就会出现逻辑错误"（这个约束在**服务端拆逻辑**时同样成立）。出处：`BV1oaDrBuE11` `[00:10:46]`（**实测**）
2. **不要在"实体创建时"事件中调用释放指定技能实例**——"角色不会生效，**可以等待一秒再进行**"。出处：`[00:11:34]`（**实测**）
3. **养成在节点图最开始初始化全部局部变量的习惯**（客户端/服务端同理）——"很大的不同就是不存在的局部变量、未在编辑时预定义的实体自定义变量，读出的都**不是默认值而是一个空值**；进行运算时确实可以当成默认值来使用，但**直接将空值作为信号的参数会导致信号无法发出**，这种问题很难进行排查"。出处：`[00:11:34]`（**实测**）
4. **客户端不允许修改列表时的替代**：多分支 + 局部变量模拟（见 §4.5）。
5. **保存两次**："请在（沙箱）里保存后**再在游戏里保存一次**才算真正保存了，否则遇到重连或者电脑崩溃会**直接回滚丢失进度**"；另"注意请（及时）把自己的客户端节点图拉出来，没人会想写第二遍"。出处：`[00:14:38]`（**实测**，工程纪律）

### 4.13 过滤器图的**业务侧**：选项卡显隐（官方文档不写的用法）

- **官方只给了节点表，没给用法**。视频补上："**本地过滤器呢它是一个节点图**，那么它可以用来过滤，比如说某些情况下这个按钮是不显示的、某些情况下这个按钮是显示的"（选项卡的"本地过滤器"配置项）。出处：`BV1uUJCzMEfs` `[00:23:27]`（**硬规则**）
- **它住在哪**："所谓的服务器节点图就是它是在服务器上运行的……相对的呢还有一个叫**客户端节点图资源管理器**……就是刚才我们提到的比如说过滤器就是放在这个**客户端节点图管理器**里面的"。出处：`BV1uUJCzMEfs` `[00:25:02]`（**硬规则**）
- **完整实战（布尔过滤器做"开门条件"闭环）**：给门加一个**布尔自定义变量"允许开门"（初始化=否）**→ 过滤器里 `查询自身实体` → `获取自身实体的自定义变量`（允许开门）→ 作为**输出结果**；未拿到钥匙时选项卡不会显示，拿到钥匙把变量改成"是"后**选项卡自动浮现**——"比用状态或信号实现更干净"。出处：`BV1K4tH6GE4k` `[00:41:05]` `[00:42:44]`（**个人经验**）
  - ⚠️ 注意字幕把"布尔过滤器"误作"布尔攻击器/布尔功率/布尔控制器"（**术语校正**）

### 7.1 官方文档自身的不一致（**按"两个都保留"处理**）

### 7.3 需游戏内核验 / 尚未闭合

- **单位状态层数通道**（§4.8）：两个源独立实测但**均无脚本地图级复现**；且层数是否有上限、多人下是否按持有者隔离，均未知。
