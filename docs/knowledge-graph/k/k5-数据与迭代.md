## 一、这是什么（定义与官方命名）

- **官方/社区命名**：这个轴没有单一官方名字，它由三块拼成——
  - **数据统计**（游戏内量测）：官方在**月之四**加入的「**伤害测试木桩**」功能（社区也叫"木桩""打桩"），是千星奇域第一个**官方数据统计能力**；创作者侧则用节点图自建统计（如定时器自动截停的 DPS 面板）。
  - **迭代运维**：上线后按版本号持续更新内容与平衡性（讲师自称公开版已到 `7.1.6`），并管理反馈/投诉/整改。
  - **数据导向（data-oriented）**：把"会变的东西"先写成表（卡牌表 / 棋盘表 / 生成规则表），再让节点图读表；以及用「结构体 / 结构体列表」承载存档与配置数据。
- **它在「做优质游戏」里的位置**：**没有这一轴，前面所有轴都停在"能跑"**——数据决定"改哪里"（平衡性/难度/内容长度靠胜率与好评率定位），迭代决定"改完还活着"（不更新则通关即弃、推荐位掉光、流量死亡）。
- **出处**：`BV1PXrpBrEYk` `[00:00:00]` "伤害测试木桩就这玩意儿可以说是最具有里程碑意义的一次更新了"；`BV1ehYGzxEJe` `[00:04:33]` "像我那个地图公开的版本已经到7.1.6了"；`BV1d1UYB6EtS` `[00:01:31]` "这就是数据导向先把会变的东西写成数据再让逻辑去读表就会更加的快捷"

## 三、规则与做法

### A. 生产阶段：先有数据表，再有节点图

- **打开节点图之前先写三张表，一次把"会变的东西"全部外置成数据**
  - ①卡牌表：表头＝`元件 id / 所在格子 / 出现概率`，一行＝一张卡；②棋盘表：每格记录`我是谁 / 第几层 / 第几行 / 第几列 / 是否会被挡住`，**格子里填卡牌 id 而不是把卡牌贴上去**；③生成规则表：把三条约束逐条写成逻辑（每种卡牌数量是 3 的倍数、上层挡下层、奇数层偶数层位置交错）。
  - 出处：`BV1d1UYB6EtS` `[00:00:46]` "第一行写表头原件id所在格子出现概率每一行就代表着一张卡牌"；`[00:01:31]` "这就是数据导向先把会变的东西写成数据再让逻辑去读表就会更加的快捷"
  - 证据等级：个人经验（单作者开源实践，未做 A/B 对比）
  - **收益口径**：初始化流程直接照着表格填信息——"虽然我们还没拉节点图，但开局要用到的信息已经被我们拆解完成了"。
- **循环一次别超过沙箱保护阈值；把"一次性处理 N 个"拆成"每秒处理 20 个"**
  - 具体步骤：开一个**循环定时器**，每 `0.05` 秒触发一次，第几次触发就是第几次循环 → 读格子 → 判断抽卡 → 填上去 → 处理完停定时器。
  - 出处：`BV1d1UYB6EtS` `[00:03:07]` "为什么循环跑到一半突然停了明明我没写错啊这不是bug是千星沙箱的保护机制"；`[00:03:53]` "原来是一口气数到100现在改成每秒数20个下一秒再数20个这样沙香就不会掐你了"
  - 证据等级：个人经验（讲师自述的可用规避手法；引擎真实阈值未在语料闭合 → 见 §七）
  - **可迁移性**：讲师结论"各种玩法都可以拆开做"——换玩法照样按 表 + 定时器分批 拆。

### B. 游戏内数据统计：怎么做、怎么降误差

- **官方木桩（伤害测试木桩）：完整操作面**
  - 进入路径：大厅 → 右上角**搜索奇遇** → 输入"木桩" → 选一个可选角色的木桩关卡开始游戏（语料给出的样本作者名"空中劈叉清洁工"、关卡名"木桩伤害关卡"）。
  - 左侧控制台＝**敌人属性**，两种模式：**深渊**（开局能量已满，木桩默认 100 级，可选标准 10% 抗性 / 极端 70% 抗性）、**幽静**（清空能量模拟零能量开局，默认难度六的 110 级）。
  - 右侧＝**实时面板**：当前造成的**总伤、DPS，以及每名角色各自的总伤害**。
  - 打完按 **Z**（右下角元素爆发图标上方那个"绿色钩子"）→ 计时器停止 → 弹出**黑色统计界面**，最下面是**时间轴**（＝本轮每个角色切出来的时间）。
  - 清空本轮：先按 Z 关掉黑色界面（右侧统计仍在）→ 点下方**红色垃圾桶** → 数据清空、计时归零；**清空前先截图保存**。清空后深渊模式回满能量 / 幽静模式清空能量。
  - 换武器圣遗物：ESC → 左上角最下面"角色"按钮，**不需要退出千星奇域回提瓦特**；但进了木桩关卡**不能切换角色和队伍**，换队伍要退出重开。
  - 出处：`BV1PXrpBrEYk` `[00:01:31]` "右侧会实时显示当前造成的总伤DPS以及每名角色各自的总伤害"；`[00:02:18]` "最下面的是时间轴指的是这一轮输出你每个角色切出来的时间"；`[00:03:03]` 同上引文；`[00:04:34]` "右边这个是真实模拟右键卫战的有难度和难度六两种选择"
  - 证据等级：**实测**（操作后即得可复核数值）
- **用"定时停止"替代手按钩子——把人为反应误差压到最小**
  - 左侧控制台内置**定时停止**：**标准 16~24 秒**涵盖几乎所有队伍的输出轴，另有 **1 分钟 / 2 分钟**用来模拟深渊 / 幽静。设好 18 秒后，**18 秒之后无论怎么打都不再统计**，再按绿色钩子看这 18 秒的数据。
  - 队伍时长选型参考：菲林斯 / "那台战舰" → **18 秒**；斯科克 / "龙王" → **21 秒**（按自己队伍的输出轴长度挑）。
  - 出处：`BV1PXrpBrEYk` `[00:03:49]` "标准时长有16~24秒涵盖了几乎所有队伍的输出轴也可以选择一分钟和2分钟用来模拟深渊幽静"；同上"这里我演示的队伍是菲林斯因此选个18秒来举例"
  - 证据等级：实测（功能行为）+ 个人经验（时长选型）
- **手动截停的误差量级必须量化——这是"统计工具必须自动截停"的硬依据**
  - 一轮 300 万伤害、标准 18 秒 → 应得 **DPS 16.7 万**；**钩子按慢 1 秒 → DPS 15.8 万，直接少 1 万**。讲师结论："人的反应是有限的"，所以必须用内置定时停止。
  - 出处：`BV1PXrpBrEYk` `[00:03:03]` "如果你钩子按慢了比如慢了一秒那么DPS就会降到15.8直接少了1万误差大的离谱"
  - 证据等级：实测
  - **设计可迁移规则**：任何统计类工具（含我方自建 DPS 面板）**都要提供自动定时截停**，不能依赖人工按键。
- **降误差两手法 + 数据权威性的来源**
  - 相同手法打两遍取平均；每轮数据清空前截图（"垃圾桶一点数据即消失"）。
  - **数据"权威感"来自与主游戏面板严格一致**：角色配置和面板跟提瓦特**一模一样，不允许随意改配置**，所以比对更直观更权威；一旦允许自由改配置，可比性就没了。木桩关卡只能模拟**理想上限**（敌人不反抗、不跑位），**不考虑生存与操作难度**。
  - 出处：`BV1PXrpBrEYk` `[00:02:18]` "比如以相同的手法打两遍然后算一个平均值减少误差"；`[00:05:20]` "对于角色实测确实是极大地减轻了工作量数据比对也更直观更权威"；`[00:06:07]` "得到的数据基本上就是最理想的情况属于是上限"
  - 证据等级：个人经验（方法论）/ 实测（面板一致性为功能事实）

### C. 上线前：数据存哪、结构怎么拆（决定能不能迭代）

- **配置与存档数据一律走结构体，不要用一堆散变量**
  - 实测案例：某关卡 15 个关卡参数全部存成一个结构体；某元素地牢图 **40~50 把弓**的`名称/颜色/伤害/攻速/装填`等数值全存结构体，**49 把**导出后约 **228K** 数据量。
  - **结构体是局内存档的强制前提**："你存存档你必须要用结构体了…只存一个整数你也要用结构体"。
  - 硬限制（讲师实测）：结构体**参数上限 50 个**；**不允许递归套娃**（"非法结构不能保存"）；**结构体里塞字符串会让数据量暴涨**（"加一个字符串就直接变1000多了"），字符串多了存档"数据量炸了的话就运行不了了"；**浮点数的数据量比整数稍小**。
  - **局内存档 = LV4 以上**才能用的功能；**消息队列无等级限制**。
  - 出处：`BV1K4tH6GE4k` `[00:39:30]` "这里是我们的结构体类型它的这个参数的上限是50个啊…你不能去去无限递归它"；`[00:44:13]` "你也要用这个结构体就只存一个整数你也要用结构体啊这是直接存档的一个比较一个现状"；`[00:37:06]` "一个是我们的绝对存档第二个是消息队列…这个是LV4以上才能做的一个功能"
  - 证据等级：实测（限制为课程实测口径）
  - **存档初始化是必做步骤（经典坑）**：玩家第一次进游戏时存档变量是**长度为 0 的结构体列表**，"里面是啥都没有"；必须用**拼接列表**拼一个开局存档进去，再读第 0 个值并拆分。"千星刚出的时候就是很多人都在问这个绝对存档他他怎么没有啊之类的问题就是因为他没有初始化"。
  - 出处：`BV1K4tH6GE4k` `[00:44:59]` "在你的玩家身上去做一个初始化的这么一个操作…这个结构体列表里面啥都没"；`[00:48:03]` 同上引文。证据等级：实测。
- **负载可以用数字量出来，且"存到变量里"是稳定可控的前提**
  - 负载三档（讲师实测口径）：**设置局部变量负载最小 < 设置节点图变量 < 设置自定义变量（写入实体变量最大）**；频繁写实体自定义变量会导致负载超载。
  - 降低负载的两种手段：①**开定时器把写入操作拆到不同定时器**；②**减少使用实体上的自定义变量**。
  - 拆结构体的真实数字：某对话节点结构体**拆好几次加起来只有 80**（专门优化过的版本，"只有500多"是未优化版）；做法是**把拆出来的值先存进节点图变量缓存**再复用。**结论句："只有存在变量里面才是稳定可控的"**。
  - **列表迭代必须先存变量**：`列表迭代循环`每次迭代都会重新"获取一次列表值"，中途列表变化会读出不同结果。反例："五个实体销毁，销毁第一个后再迭代 → 把第三个销毁了、第五个也销毁了，二和四没变化"。
  - 出处：`BV1K4tH6GE4k` `[00:32:36]` "设置局部变量它是负载最小的然后设置节点图变量它是附带中的设置自定义变量…对他负债是最大的"；`[00:52:47]` "你看这拆一次我们的对话节点这个结构体…他加起来只有80发"；`[00:53:34]` "只有存在变量里面才是稳定可控的"
  - 证据等级：实测
- **逻辑与数据必须解耦，否则迭代只能改节点图**
  - 反模式（讲师点评学员作品）："我们把这个文本全部都写在节点图里面了，也是一种比较经典的**逻辑和数据耦合**起来的问题"——结果"我写了大量的设置自定义变量，明显我们有很多重复的行为"。
  - 正解一句话骨架：**谁触发 / 谁处理逻辑 / 谁保存数据 / 谁执行 / 谁需要知道**（＝输入 → 控制器 → 存储器 → 输出设备），并对照**冯诺依曼架构**。
  - **收益（直接服务于迭代）**："假设调试出问题了…如果显示黑幕出问题了，那我们可以很快锁定到是**渲染部分**出错，而不是前面或后面出错"。
  - 出处：`BV1K4tH6GE4k` `[00:03:06]` "我们把这个文本全部都写在节点图里面了也是一种比较经典的逻辑和数据耦合起来的问题"；`[00:11:43]` "关于这个方法呢其实我想应该挺多人会知道这个叫嗯冯诺依曼架构的"
  - 证据等级：经验共识（南航课程口径）

### D. 上线后：改什么、怎么记录（迭代运维）

- **一个数值改动要同步 ≥3 处，否则必出"数据对不上"的 bug 报告**
  - 场景：某侦查塔建造时间 10 秒 → 5 秒、侦查范围 700 → 800。必改：**①物体编辑器里的属性 ②玩家鼠标点上去看到的说明文本 ③游戏的更新补丁介绍**；另需确认**配套数值（人口 / 资源 / 金币 / HP）与配套触发器**是否一起改。
  - 出处：`BV1ehYGzxEJe` `[00:10:07]` "你要在更新补丁介绍上就要去改就是你这物体上改了之后物体的鼠标点上去的说明要改然后游戏的更新补丁介绍要改三个地方要改"
  - 证据等级：实测（讲师以自身地图 bug 报告为证）
  - **粒度提醒**："单位名称是一个数字、快捷键是一个数字、图标是一个内容、蓝量的消耗也是一个内容——简简单单几个字有一二三四四个位置。"（`[00:12:26]`）
- **改动台账（防"迷糊 bug"的硬手段）**
  - 每个地方改完**立刻**记录"改了啥"；**重要变动单独成文**（笔记本 / 文本文档）。规范命名与结构目录，否则图一大就找不到要改的地方。
  - 为什么必须：地图更新周期 1~3 个月，"你这一个月之前改的东西你记得吗？"→ 不记录就得每天把每个地方都点开检查一遍，最费时间。
  - 出处：`BV1ehYGzxEJe` `[00:11:40]` "每次改了之后你要找个地方记录一下特别是重要的项目啊重要的变动你要找找个文本文档去把这个记录修改记下来"；`[00:13:12]` "就是每个地方都点开去检查一遍你要不浪费时间啊"
  - 证据等级：个人经验（但讲师以自身事故背书，实际操作层面可直接采用）
- **持续更新与版本号：不更新 = 不产生持续价值**

### G. 上线前测试：QA 三段 + 提单五要素（迭代的入口）

- **测试分三类，各测什么**
  - **①烟雾测试（smoke test）**＝基本操作：游戏能否正常启动、基本玩法循环能否跑通、**基本指标反馈是否正常**（生命值/饱食度/受伤等 UI 数值，"因为有的时候你真的可能自变量就装错了"）。"如果烟雾测试都过不了那绝对会有差评，那玩家就来帮你测了。"电脑端由创作者完成，其他设备端"你们测一测就好了"。
  - **②逻辑测试（讲师自称"中间那个好像没有一般的名字"）**＝按策划案/程序目标**逐条测试**每个 UI 能不能正常打开、同时按 U 和 Q 会不会出 bug、**有没有连招能卡出地图**。做法："列个表杠（checklist）对着这个目标一条条测试"。
  - **③回归测试（retest）**＝"创作者说这个 bug 修了，然后你上号一看——我去这个 bug 怎么还在"，即**声称被修复的 bug 是否真的被修复**；作者发**更新日志**说修了哪些，要测就按更新日志再测一遍，**各设备各测一遍**。
  - 出处：`BV19ab76LE6c` `[00:10:56]` "像这种基本操作测试的话我们把它叫做烟雾测试叫smoke test然后对于最下面那一种的话叫做回归测试retest"；`[00:14:02]` "如果烟雾测试都过不了那绝对会有差评那玩家就来帮你测了"；`[00:14:48]` "你可以列个表杆然后对着这个目标然后一条条测试"
  - 证据等级：经验共识（讲座口径）
- **bug 提单五要素（另有严重性/优先级两列）**
  - ①**标题**（概括问题，如"UI 重叠了""基本移动出现问题"）②**复现步骤** ③**预期情况** ④**实际情况** ⑤**严重性**；提单表另含：**测试者名字**（"方便我们后面统计的时候发福利"）、**测试日期**（"给出一个你测的是哪一版"）、**设备端**（原神是多设备游戏，必须写明确）、**多语言**（可选）、**建议的修改方式**（可选）。
  - **P0 / P1 定级口径**：**P0＝不修不能玩的 bug**（例："手柄按键完全冲突"——一个 UI 三个按钮都绑同一个手柄键，"那显然这个游戏是玩不了的"）；**P1＝能玩但有恶劣影响的 bug**（例："UI 重叠"）。**引导找不到物资**这类"程序对不对？他也对…但引导就是有问题"的问题，因为"找不到物资的玩家很多"，**可以直接点到 P0**。

### I. 把统计/判定卸载到客户端（压低服务端负载的架构手法）

- **"全部计算都要在服务端节点图完成"是开发过程的一大痛点**；月之六的技能实例功能让服务端能唤起客户端节点图（服务端创建技能实例 → 释放指定技能实例 → 客户端图执行 → 信号回传），从而把 AI 判定、动画、复杂判定条件搬到客户端，"大大降低了服务端的负载"。
- **实测数字与边界**：单位状态定时触发技能的 tick 最小只支持 `0.1` 秒；为达到更高精度，用**循环轨道**在 `0.01` 秒间隔放 4 个节点图调用、循环 25 次 → 实现一次调用输入检测节点图 **100 次**的动画技能，最高可达 **2.5ms 精度**，且"完全不需要服务端定时器介入"。
- **统计场景实例**："服务端每隔 3 秒释放一个技能实例来唤起客户端节点图，请求决定星辰道具的类型和位置"——客户端图"会对当前场下的情况进行**全面的统计**，最后决定道具生成的数量及位置"；服务端只做**基本合法性校验**。
- **多人下"选哪个客户端算"**：定期让全部在场玩家回传客户端毫秒时间，服务端再发一次相同调用，比较两次调用时间差 → 得到客户端延迟的定性值（"相当于两次握手"），据此**动态维护最低延迟客户端**。
- 出处：`BV1oaDrBuE11` `[00:00:00]` "一大痛点就是几乎全部计算都需要在服务端节点途中完成"；`[00:06:08]` "最高可以达到2.5ms精度的同时完全不需要服务端定时器介入"；`[00:06:54]` "这个节点图会对于当前场下的情况进行全面的统计最后决定道具生成的数量及位置"；`[00:07:40]` "定期令全部在场玩家发回…毫秒时间服务端收到信号后再发起一次相同的调用通过比较两次调用的时间差"
- 证据等级：实测（作者自述项目经验与实测数值）
- **四个已知坑（做客户端统计前必读）**：①技能实例**不能直接携带参数**，状态要用实体的自定义变量传递（并带来同步问题）；②`客户端图不能创建复合节点 / 不能修改自定义变量的值 / 不能修改引用类型（列表、结构体）`；③客户端运算与动画技能**互斥**（动画技能时长 <0.5 秒时瞬发技能"大部分时候也可以正常释放"）；④**不要在玩家/角色实体的实体创建事件中调用释放指定技能实例**（不生效，"可以等待一秒再"）；另外"直接将空值作为信号的参数会导致信号无法发出"。
  - 出处：`BV1oaDrBuE11` `[00:03:02]` "不能直接携带参数因此如果我们要携带任何参量或是单纯的状态量都必须通过实体的自定义变量来进行传递"；`[00:11:34]` "不要在玩家习题角色实体的实体创建习事件中调用释放指定技能实力橘色不会生效可以等待一秒再进行"
  - 证据等级：实测（作者实测口径）
