## 一、这是什么（定义与官方命名）

- **官方命名**：平台侧的检测功能叫 **试玩校验**（阻止试玩）与 **风险检查**（不阻止，仅提示）；
  运行期数据采集叫 **负载计算功能**（静态/动态）与 **节点图日志** / **客户端节点图日志**。
  开发流程侧的动作叫 **试玩**（编辑器左上角按钮）。出处：`docs/ui-tutorial/official-guide-auxiliary-appendix.md:258-266`（**硬规则**）
- **视频口语**：讲师把它叫「测试」或 **QA（质量保证）**，并明确指出 **「测试」也是团队分工里正式的一环，别名就是质量保障**。出处：`BV19ab76LE6c` `[00:07:53]` "测试（也叫质量保障）"（**经验共识**）
- **它在「做优质游戏」里的位置**：这是**上线前的最后一道闸**。讲师给的四阶段（预制作/制作/测试/发布运营）中，测试阶段是唯一能把「创作者觉得没问题」翻译成「玩家不骂」的环节；官方 FAQ 侧的口径更硬——**试玩校验不通过的功能根本跑不起来**。
  出处：`BV19ab76LE6c` `[00:50:17]` 四阶段划分（**经验共识**）+ 官方指南 `official-guide-auxiliary-appendix.md:266`（**硬规则**）
- **为什么玩家视角是第一手判据**：`COMMENTS-INSIGHTS.md:16`（378 赞）"真真说到点上了吧，**没有清晰的引导和UI，奇遇本身再牛逼，我都玩不下去**"——测试阶段放过的引导/UI 问题，会直接变成差评。证据等级：**个人经验/玩家共识**（按赞数加权）
- **边界**：本轴只讲「怎么测、怎么报、怎么判级」，不讲「怎么修」。修图逻辑见 `k` 轴相邻专题与 `gil-node-graph-editing` 技能。

## 三、规则与做法

### 3.1 先分清三类测试，别只测 bug

- **三类测试**（⚠单源）：
  - **①烟雾测试（smoke test）**：基本操作能不能过——「传统意义上……一般都只只测bug」，但这是最低档。
  - **②逻辑测试**：游戏逻辑实现是否有问题（按策划案逐条对照）。
  - **③回归测试（retest）**：作者宣称修了的 bug 是否真的修了——「创作者说我这个bug修了然后你上号一看……这个bug怎么还在」。
  - 出处：`BV19ab76LE6c` `[00:03:09]` `[00:09:25]`–`[00:10:56]`。证据等级：**经验共识**
- **三类之外还有一等：主观感受**。只测 bug 是不够的，「每一个玩家的意见尤其是测试阶段的意见都很宝贵」。
  出处：`BV19ab76LE6c` `[00:03:55]`。证据等级：**经验共识**
- **官方机制层面的分类是另一套（两者并存，不是同一分类）**：**试玩校验**（错误会**阻止试玩**，属严重阻碍性错误，会导致功能无法正常运行）vs **风险检查**（提示**不阻止**试玩，一般是数据上的错误）。
  出处：`docs/ui-tutorial/official-guide-auxiliary-appendix.md:266`。证据等级：**硬规则**
- **测试者的验收视角**：测评者拿到一张图会直接给出「**我甚至有点怀疑作者是不是没有认真测试过自己做的奇遇**」的判词——判据是空气远景/任务链断/默认挂节点挡字这类**走几步路就能发现**的问题。
  出处：`BV1Uq6vBLEJP` `[00:00:00]`、`[00:23:36]`。证据等级：**实测**

### 3.2 烟雾测试四件事，一条一条过（⚠单源）

按顺序过，全过才算「能进下一步」：

1. **游戏能否正常启动**——千星里点开始按钮能进。
2. **基本操作是否正常**——移动 / 射击 / 装弹；**多设备都要过**（键鼠 / 触屏 / 手柄）；「如果你有做大的野心的话你还可以再看看**多语言**」。
3. **基本关卡逻辑是否跑通**——敌人能否正常出现、能否被击杀、敌人能否击杀玩家 = 讲师的 **「基本玩法循环」**。
4. **基本指标反馈是否正常显示**——生命值、饱食度这类；理由是「因为有的时候你真的可能**自变量就装错了**」。

出处：`BV19ab76LE6c` `[00:12:31]` `[00:12:43]` `[00:13:17]`。证据等级：**经验共识**（第 4 条为 **实测**）

- **分工硬约定**：**电脑端由创作者自己跑完，其他设备端交给测试者过一遍**。理由与后果：「如果烟雾测试都过不了的话那**绝对会有差评**，那玩家就来帮你测了」。
  出处：`BV19ab76LE6c` `[00:14:02]`。证据等级：**经验共识**
- **自测闭环的正确姿势（实录印证）**：改图 → 点试玩 → 发现问题 → 改 → **再试玩验证**。讲师修完塔的两个缺陷后原话「我们再去试玩一下……**这中间肯定还是有些小bug**」。
  出处：`BV1uUJCzMEfs` `[00:50:43]` `[00:53:00]`。证据等级：**实测**

### 3.3 逻辑测试用 checklist，别靠脑子（⚠单源）

- **做法**：按**策划案 / 程序实现给出的目标**列成表格，一条条打勾。
- **至少覆盖**：每个 UI 能不能正常打开；**UI 同时打开会不会出 bug**；有没有连招能**把角色卡出地图**。
- 出处：`BV19ab76LE6c` `[00:14:02]` `[00:14:48]`。证据等级：**经验共识**
- **讲师的分工坦白**：很多创作者不写复杂文档，checklist 这部分「靠经验」——所以**写 checklist 本身是加分项**，不是标准动作。出处同上。

### 3.4 逻辑测试的第二层：事件的效果与顺序

- **每个事件是否达到对应效果**：声音响度是否上升/下降、物品是否丢失、道具能否获得。
- **事件的顺序关联不能倒**：必须先「丢了钥匙」再「来找钥匙」——倒过来就是 bug。
  出处：`BV19ab76LE6c` `[00:26:21]`。证据等级：**经验共识**
- **失败案例（实测）**：任务链断——要你组建队伍召唤元素法师，召唤完却让你去买/找药水商店商人，而**作者没做完后续任务，玩家卡在任务里做不下去**。
  出处：`BV1Uq6vBLEJP` `[00:05:22]`。证据等级：**实测**

### 3.5 极限情况测试清单（创作者绝对测不出来，必须专人跑）

创作者的盲区：「**肯定是没有这种情绪去测**」。必须专门跑这几类：

| 极限情况 | 具体现象 |
|---|---|
| 卡在物体上 | 跳到物体上**飞着下不来** |
| 卡进缝隙 | 掉进两个物体的**缝**里 |
| 穿模 | **贴墙穿墙** |
| 碰撞范围越界 | **碰撞触发器的范围边界延伸到不该存在的地方**——门后要操作的设备，人还在门前就能触发操作选项卡 |
| 可跳出去 | 屋顶和墙壁中间有个缝，从墙爬到屋顶边上之后**就可以爬出去** |
| 站在空气上 | 「甚至可以站在一个没有地板的地板上都不会掉下去……你这个怎么能站在空气上呢」（实测缺陷） |
| 逃出地图 | 连招把角色卡出地图（见 §3.3 checklist） |

- 出处：`BV19ab76LE6c` `[00:21:00]` `[00:45:37]`；`BV1Uq6vBLEJP` `[00:11:36]`。证据等级：前两类 **实测**，其余 **经验共识**
- **新手教程是极限情况的重灾区，必须主动限制自由度**：「所有游戏的新手教程都是要**限制空气墙还有选项卡**这些都要限制的不让你做其他事情，因为你做了其他事情会导致这个新手教程都会卡关」——可判 P0。
  出处：`BV1Uq6vBLEJP` `[00:06:54]` `[00:07:39]`。证据等级：**实测**

### 3.6 严重性分级判据（可直接照用，⚠单源）

| 级别 | 判据 | 实例（讲师原例） |
|---|---|---|
| **P-1** | **能速通**——严重性与优先级**都最高** | 结算逻辑漏洞导致可以跳过流程 |
| **P0** | **不修不能玩** | ①手柄端三个按钮映射到同一个键（开始/教程/退出），游戏玩不了 ②引导缺失导致卡关——「找不到物资的玩家很多你可以直接点到P0」 ③手机端通关后提示可退结算，但**点不到左上角退出按钮**（讲师判"非常严重"） |
| **P1** | **能玩但有恶劣影响** | UI 重叠但没完全叠住、错开的地方**还能按到** |
| **P2** | **修不修影响不大** | 没子弹时**短暂显示 -1** |

- 出处：`BV19ab76LE6c` `[00:17:09]` `[00:18:39]` `[00:47:11]`。证据等级：**经验共识**（实例为 **实测**）
- **速通是红线，强调三遍**：「**不能给速通**」——观察多设备适配、多语言适配；严重 bug 优先级压在一切之上。出处：`BV19ab76LE6c` `[00:21:45]` `[00:22:30]`。证据等级：**经验共识**
- **速通的真实判定边界（消消乐实例，实测）**：结算有四种结果——未完成 / 完成 / 胜利 / 失败，**只有「未完成」不算结算** → 给到「完成」**也算速通**。所以判速通前必须先搞清「什么叫结算完成」。出处：`BV19ab76LE6c` `[00:25:34]`。
- **引导问题的特判规则（重要，反直觉）**：「程序对不对他也对，只要你按照他的步骤走他肯定是能过得下去的，**但是引导就是有问题**」→ 程序正确不豁免。找不到物资的玩家很多 → **可直接判 P0**。
  出处：`BV19ab76LE6c` `[00:27:53]`。证据等级：**经验共识**
- **成熟作品的不对称性**：作品越成熟，bug 越少，但**引导问题会长期存在**（讲师举例：心跳通讯录原本没有记录回看）。出处同上。

### 3.7 bug 提单模板（五字段 + 表单四字段，⚠单源）

**五字段正文**：
1. **标题**——一句话概括
2. **复现步骤**——最正式要从「**启动游戏 → 60 秒流程 → 打开 UI → 点放大镜格子 → 背包点不亮**」这样写全
3. **预期情况**——按策划案**应该发生什么**
4. **实际情况**——**实际发生了什么**
5. **严重性 / 优先级**——按 §3.6 判据

**表单另加四字段**（讲师「我在暑假里面干过一件事情叫做我们写给了个bug提单」）：
- **测试者名字**——**便于统计发福利**（激励设计的隐藏目的）
- **测试日期**——**标明测的是哪一版**
- **设备端**、**语言**
- 另有一条可选：**近似的修改方式**（给程序参考）

出处：`BV19ab76LE6c` `[00:17:54]` `[00:19:26]` `[00:15:36]`。证据等级：**经验共识**
- **反馈粒度**：讲师建议**一次至少给 5 点**；他也坦白**严重性和优先级这两个字段「暂时没看出来区别大不大」**（→ 说明这两个字段在实践中会混淆，实现时**必须把判据固化成 §3.6 的表**）。出处：`BV19ab76LE6c` `[00:15:36]`。

**引导专项反馈模板**（另一条，引导问题专用）：
> 测试名字 / 设备端 / 基本内容 / **引导线圈的位置** / **引导目的** / **引导后果** / 严重性

- 配套态度：「**发现不符合习惯的先不要怀疑自己，先发出去反馈**」。出处：`BV19ab76LE6c` `[00:23:17]`。证据等级：**经验共识**

**野路子（最高效通道，⚠单源）**：简单 bug **跳过提单**，直接**录屏（最好）**/截屏多张**甩给程序或作者**——不用填表，「**作者一看就会知道他是有什么问题**」。
出处：`BV19ab76LE6c` `[00:20:13]`。证据等级：**经验共识**

### 3.8 回归测试（retest）流程

- **标准流程**：作者发**更新日志**说修了哪些 bug → 测试者**拿到最新版本** → **按原路径再走一遍** → **各设备单测一遍**。
- **原路径的例子**（速通 bug 声明修了）：一进游戏**直接点结算**，看是不是给「未完成」。
  出处：`BV19ab76LE6c` `[00:27:07]`。证据等级：**经验共识**
- **更新日志是回归的前置条件**：「建议及时写更新日志」——没有它，回归测试者不知道要重测什么。出处：`BV19ab76LE6c` `[00:15:36]`。证据等级：**经验共识**
- **作者的自我版本纪律（配套，实测/经验共识）**：改任何一个数值（如 hp）**忘记改配套的文本/内容/触发器** → 「迷糊了」；「**你每次调完一个地方你得自己搞一个笔记本……自己去标一下自己改了啥**」；地图要更新 1~3 个月，**一个月前改的记不住** → 「特别是重要的项目，重要的变动你要找个**文本文档**去把这个记录修改记下来」。
  出处：`BV1ehYGzxEJe` `[00:10:54]` `[00:11:40]` `[00:13:12]`。证据等级：**经验共识**

### 3.11 平台侧测试机制（官方硬规则，必须按它走）

- **动态负载计算的启动顺序**：菜单栏 **窗口 → 负载检测** 窗口 → 打开左上角 **开启负载测试** 开关 → 进行关卡 **试玩** → 结束试玩后**动态负载日志自动导入**。

- **静态负载的边界（别误当验收）**：静态计算只评估编辑态，「**并不能评估节点图等动态运行逻辑带来的负载消耗**，不能杜绝运行时可能的卡顿等问题」；静态不超标 ≠ 试玩不卡。另外 **存档大小超出上限会禁止创作者上传**。

### 6.3 证据分层纪律（报告时必须分栏，见 `AGENTS.md` 修复报告三栏门禁）

- **结构层**（编译通过 / 注入成功 / 回读 .gil 核验）= 一个层级，**不等于**行为正确
- **行为层**（日志帧值、读回的真实 GIL）= 铁证层级
- **游戏内验证** = 需用户确认的层级
- ⚠ 不得把多层级证据合并成一个 ✅；编译通过 ≠ 注入正确 ≠ 游戏行为正确
