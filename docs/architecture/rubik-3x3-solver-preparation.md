# 3×3 自动求解：游戏内可行性准备基线

> 状态：待验证
> 来源：推测（基于现有约束与公开算法估算，未实现、未游戏验证）
> 最近校验：2026-08-17
> 适用范围：3×3 自动求解的游戏内可行性准备；不作为当前代码或真实 GIA 结论
>
> 本文件不是最终算法选型，而是先固化的约束、状态模型、候选路线和接入点；已收到外部研究报告，当前优先方向为“宏库 + 微型 PDB”。

---

## 1. 目标与允许的妥协

### 1.1 目标

给定一个任意合法 3×3 魔方状态，程序能够：

1. 在游戏节点图内（或通过外部研究成果接入游戏）自动计算解法；
2. 自动把解法转换为现有 R/L/U/D/F/B 旋转机制；
3. 播放完整解法，使魔方回到还原态。

### 1.2 当前允许的妥协

- **解法步数可以增加**：不要求“最短解/最优解”，接受 100～300 步甚至更多。
- **处理时间可以延长**：接受较长的计算时间，只要最终能跑通。
- **暂不允许的妥协**：不通过“放弃在游戏内求解、完全依赖外部求解器”来绕开问题；外部研究成果作为输入，但最终目标是游戏内可运行。

## 2. 已知引擎约束（截至准备基线）

来自用户实测与仓库既有结论，后续如有新实测应更新本节。

| 约束项 | 已知结论 |
|---|---|
| 单图节点数量 | 有硬上限，约 2000 量级；复合节点可封装逻辑、降低顶层节点数，但底层 impl 仍计入整图负载 |
| 单列表容量 | 实测约 500 条数据 |
| 多列表扩容 | 可通过复合节点封装“由多个列表组成的列表容器”提升容量；示例：10 个列表 → 5000 条；再乘 100 → 5 万条级别 |
| 运算能力 | 足以支撑复杂三维运算（重力、速度、旋转等），已有足球运动模拟达到几十帧的参考 |
| DSL 限制 | 无递归、无 Promise/async；条件必须为 boolean；循环/定时器/字典/列表/数学运算可用 |
| 运动器 | 只有匀速旋转/直线等有限类型，无圆弧运动器；已有 2×2 魔方用分段折线逼近圆弧的成熟方案 |

## 3. 3×3 逻辑状态模型

### 3.1 最小状态表示

3×3 的可见逻辑单元：

| 单元 | 数量 | 需要记录 |
|---|---|---|
| 角块 | 8 | 位置（0～7）+ 朝向（0～2） |
| 棱块 | 12 | 位置（0～11）+ 朝向（0～1） |
| 中心块 | 6 | 纯色 3×3 可忽略；带图案时需额外记录朝向 |

推荐存储：

```text
cornerPos[8]     // 每个角位上的角块编号
cornerOrient[8]  // 每个角块的朝向 0/1/2
edgePos[12]      // 每个棱位上的棱块编号
edgeOrient[12]   // 每个棱块的朝向 0/1
```

合计约 **40 个 int**，加上解法队列预留 **32 步**，总存储量远小于单列表 500 上限，不需要多列表容器。

### 3.2 坐标系与 WCA 约定

- 沿用 WCA 符号：R/L/U/D/F/B，以及后续可扩展的 M/E/S、x/y/z。
- 轴方向、颜色方案、角/棱编号必须与现有 Demo 的 axes 字典和实体命名统一。
- 最终状态编码必须与外部研究成果中的算法输入格式对齐；本文件先固定“位置+朝向”模型。

## 4. 候选求解路线（不选型，只评估）

### 4.1 路线 A：外部求解器 + 节点图播放

- 优点：游戏内只存状态 + 解法列表，空间开销极小。
- 缺点：不是“游戏内全算”，与当前目标不完全一致，但可作为保底方案或验证链路。
- 结论：保留，但不作为主目标。

### 4.2 路线 B：游戏内搜索算法（IDA* / BFS / Kociemba 表）

- 搜索本身的递归栈很小，但依赖的剪枝表/模式数据库很大：
  - Kociemba 剪枝表：约 600 万～800 万条条目；
  - Korf 最优模式库：数千万到数亿条。
- 即使按多列表扩容到 5 万条，仍差 2 个数量级以上。
- 无表纯搜索则分支因子约 10～13，深度 18～20，时间不可控。
- 结论：**完整搜索表直接放入节点图当前不可行**；除非后续研究报告给出可压缩到 5 万以内的表结构。

### 4.3 路线 C：固定套路求解器（层先/CFOP 风格）

- 不搜索，而是“识别状态特征 → 查小算法表 → 执行固定公式序列”。
- 存储量主要是算法序列本身：
  - 简单层先法可能只需十几到几十条公式；
  - CFOP 需要 OLL/PLL 约 78 条公式，仍在几百条以内；
  - 每条公式长度约 5～20 步，总存储量数千个 int，适合多列表容器。
- 解法步数通常较长（100～300 步），符合“允许更多步骤”的妥协。
- 主要难点从“存储”转移到“节点图逻辑”：
  - 状态识别；
  - 十字/F2L 的启发式决策；
  - 公式表查询与播放。
- 结论：**这是当前最可能“在游戏内跑通”的方向**。

### 4.4 路线 D：混合方案

- 外部研究报告给出新算法后，评估其核心表能否压缩/分块到节点图容量内。
- 若能：把表拆到多列表容器复合节点中；
- 若不能：保留固定套路求解器作为游戏内实现，外部成果用于改进公式集或状态识别。

## 5. 研究报告落地（2026-08-17）

### 5.1 结论摘要

外部研究报告（本地索引：`/home/h/test/flash-思维链+jspace/魔方/research/papers/00-索引与低空间算法方向.md`）给出了三个候选方向：

1. 宏库 + 微型 PDB 混合（最稳、本周可验证）；
2. 紧凑启发式函数替代表（DeepCubeA 路线，存参数不存表）；
3. πDD / 决策图表示状态集合（最创新、风险最高）。

报告同时确认：

- Kociemba 非对称全表约 7.5M 条目、min2phase 对称表 1,444,204 条目、torjusti 左桥表约 311k 条目，全部超出 500 预算 2～3 个数量级；
- 单 F2L 对微型 PDB（1 角 + 1 棱）为 576 项，处于预算边界；
- F2L 宏库（41 case × ~8 步）约 330 个移动记号加识别表，天然落在预算内；
- 加法 PDB 不可用于魔方（一次转动影响多个子集），已排除。

### 5.2 对准备基线的影响

- 原“路线 C：固定套路求解器”升级为“宏库 + 微型 PDB 混合”；
- 下一步优先做“宏库 + 微型 PDB”的变量预算精确核算（见下节）；
- πDD 作为并行调研方向，等到有可行性结论后再决定是否进入新算法设计。

## 6. 宏库 + 微型 PDB 变量预算核算

> 假设：节点图每个列表项 = 1 个整数存储单元；不计变量元数据开销。
> 这是准备阶段的理论核算，真实节点图行为待实测。

| 数据 | 原始整数条目 | 500 列表拆分 | 压缩打包后条目 | 说明 |
|---|---|---|---|---|
| 3×3 状态（角/棱位置+朝向） | 40 | 1 条 | 40 | 状态本体，必须保留 |
| 解法队列 | 32 | 1 条 | 32 | 预留 32 步；非最优解法更长时可扩 |
| F2L 宏库（41 case × 8 步） | ~328 | 1 条 | 5-bit 打包约 55 | 每个 move 用 0..17 编码，需 5 bit |
| F2L 识别表（576 状态 → case id） | 576 | 2 条（288+288） | 6-bit 打包约 108 | case id 0..40 需 6 bit；暂不依赖对称缩减 |
| 微型 PDB（单 F2L 对距离表，兜底） | 576 | 2 条（288+288） | 4-bit 打包约 72 | 距离值 0..15 需 4 bit；对称缩减可更小 |
| 常量/临时/槽位变换 | ~50 | 1 条 | ~50 | 索引、槽位映射、临时量 |

合计：

- 不打包：约 **1,600 个整数条目**，拆成 **4～5 条物理列表**即可；
- 打包：约 **350～400 个整数条目**，可放入 **1～2 条物理列表**；
- 即使不做任何打包，也在用户给出的“多列表 5000/50000”容量范围内。

### 6.1 对称缩减说明

576 条识别表在单列表 500 边界附近，拆成 2 条列表即可解决。若进一步做对称缩减，需按“固定 F2L 槽位的稳定子”计算，而不是简单 576/48；预期可降到 100～200 条量级，但具体数值需要本地实验验证。

### 6.2 结论

“宏库 + 微型 PDB”在存储上是可行的：

- 最坏情况不到 2,000 个整数条目；
- 最优打包后不到 500 个整数条目；
- 运行时以查表 + 少量搜索为主，符合低时间预算目标。

## 7. 存储与复合节点方案

### 7.1 单列表上限应对

单列表实测约 500 条，但可以通过复合节点封装“多列表容器”：

- 逻辑上把一个大数组视为 `N` 条列表；
- 每条物理列表 500 条；
- 寻址方式：`listIndex = index / 500`，`offset = index % 500`；
- 读写封装在复合节点内，对外表现为一个大数组。

### 7.2 容量估算

| 数据规模 | 物理列表数（500/条） | 复合容器（10 列表/组） |
|---|---|---|
| 5000 条 | 10 | 1 |
| 50000 条 | 100 | 10 |
| 数百万条（Kociemba 表） | 数千～上万 | 数百～上千 |

结论：

- 状态表（40 int）不需要容器；
- 固定套路公式表（数千 int）**可以**用 1～10 个复合容器装下；
- 搜索剪枝表（百万级）当前不可行。

### 7.3 代价评估

多列表容器不是免费的：

- 每次读写需要做除法/取模和跨列表路由；
- 复合节点会占用节点预算；
- 容器层数越多，单次操作节点数越多；
- 对算法的时间复杂度影响需在真正实现时实测。

## 10. 公式构造器 / 宏挖掘 + setup 小搜索（用户启发式方法）

### 10.1 来源

用户基于自创的“对称交换”经验提出：

- 只靠少量基础公式（位置交换 + 朝向抵消）就能构造出任意角/棱交换、3 循环、翻转等复杂宏；
- 用户并不需要提供 WCA 公式，工程上可以让计算机自动发现/验证这些宏。

### 10.2 方法

```text
1. 建立 3×3 魔方模型（位置 + 朝向）与标准转法（WCA）
2. 离线宏挖掘：
   枚举短序列 A、B、C
   构造交换子 [A, B] = A B A' B'
   构造共轭 C [A, B] C'
   筛选“局部影响小、合法、长度短”的宏
3. 建立小型宏库：
   角块 3 循环
   棱块 3 循环
   两棱翻转
   两角扭转
   双交换
   位置 + 朝向复合宏
4. 在线自动求解：
   读取当前状态
   找到未归位的块/组
   选择对应宏
   用浅层搜索找 setup（建议 ≤ 5 步）
   执行宏 → 逆 setup
   重复直到还原
```

### 10.3 与空间/时间预算的关系

- 宏库本身只有几十条公式，空间远小于全局搜索表；
- setup 小搜索只搜短序列，时间可控；
- 解法步数较长（可能 100～300 步），符合“允许更多步骤”的妥协。

### 10.4 必须处理的边界

- 奇偶性校验：纯“两角单交换”单独出现不合法，宏必须由程序在完整合法状态下验证；
- 状态模型必须同时跟踪位置与朝向，否则宏会执行错误；
- setup 搜索深度要限制，避免退化成全局搜索；
- 求解循环要有终止性：每个宏必须明确“解决的是哪个子目标”，确保每一步都减少未还原量。

### 10.5 落地路径

1. 网页原型：先实现宏挖掘器 + setup 小搜索 + 自动复原循环；
2. 验证通过后，把小型宏库迁移到游戏节点图；
3. 游戏节点图中的存储形式可沿用“宏库列表 + setup 规则表”，估计仍在 500～2000 条目量级。
