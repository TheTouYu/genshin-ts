# 魔方完整游戏关卡：基础设施与架构设计

> 状态：设计定稿，代码实现中
> 来源：rubik-2x2 demo（已验证转动机制）+ 外部受限求解研究（/home/h/test/flash-思维链+jspace/魔方/）
> 最近校验：2026-08-17
> 适用范围：把 2×2 魔方 demo 扩展为"完整游戏关卡"（胜利判定/结算/打乱/自动复原/重置），并为 2×2→3×3 自动求解铺路

---

## 1. 目标

把现有 2×2 魔方 demo（地图 1073741882、玩法图 1073741825）从"可转动的魔方"升级为**完整游戏关卡**：

1. 胜利判定与结算（拼好之后）——当前缺失；
2. 支持魔方操控的选项（打乱 / 自动复原 / 重置）——当前缺失；
3. 自动复原流程（解法队列播放）——当前缺失，且是 3×3 受限求解的落地点；
4. **受限环境约束显式化**：节点图数量、运算量、变量（单变量/列表/字典）上限是自动求解可行性的前提，基础设施必须把预算作为一等公民设计。

约束：保留已验证的转动表现机制（自旋+分段公转，位置+朝向全精确）；不引入新资产即能跑通核心流程；每一步新逻辑都能在单图 2000 节点预算内落地。

### 2.2 缺口（本轮基础设施覆盖）

1. **无逻辑状态模型**：当前"层判断"依赖物理坐标，"朝向"只存在于实体 rotation。自动求解与胜利判定需要独立于表现的逻辑状态（位置+朝向 int 编码）；
2. **无胜利判定/结算**：没有"拼好"检测，没有 setPlayerSettlementSuccessStatus；
3. **无操控选项**：打乱/自动复原/重置/开始均无；
4. **无自动复原流程**：解法队列的产生与播放机制未建立；
5. **受限预算未显式核算**：节点/列表/字典/变量的开销没有逐项记账。

## 4. 总体架构：五层分离

```text
┌────────────────────────────────────────────────────────┐
│ 输入层 Input      tabBar 选项事件（转动/打乱/复原/重置）   │
├────────────────────────────────────────────────────────┤
│ 流程层 Flow       游戏状态机 + 输入锁 + 模式(MANUAL/AUTO) │
├────────────────────────────────────────────────────────┤
│ 逻辑状态层 Logic   单一事实源：位置+朝向编码；move 应用；   │
│                   isSolved 判定；求解器表(后续)          │
├────────────────────────────────────────────────────────┤
│ 表现层 View       现有已验证机械：自旋+分段公转(纯视觉)    │
├────────────────────────────────────────────────────────┤
│ 结算层 Settlement solved → 反馈 → 结算成功状态           │
└────────────────────────────────────────────────────────┘
```

**核心原则（沿用用户 2026-08-10/12 教学"两大块独立"）**：

1. **逻辑状态与表现完全解耦**：`applyMove(moveId)` 先更新逻辑状态（内部状态变化），再驱动视觉（旋转效果表现）。视觉完成 → 解锁 → 检查胜利。表现层不感知逻辑状态，逻辑层不依赖物理坐标。
2. **单一事实源**：所有判定（胜利、求解输入、复原进度）只读逻辑状态，不读实体位置/rotation（组合旋转后实体 rotation 的欧拉表示有环绕歧义，不可作事实源）。
3. **数据驱动**：转动/表查询/队列播放一律循环+表，不用分支展开（2400→240 节点实证）。
4. **复合节点强制细分（用户 2026-08-17 强约束）**：任何算法/逻辑块都必须按项目已验证的"递归拆分法"拆成足够细致的复合节点——每个复合 4-7 节点、职责单一、数据流清晰；禁止把复杂算法写成宿主图里的一坨密集节点。复合 impl 计入宿主图，但拆分换来：布局清晰、复用、避免表达式被多消费点重复求值、循环体只物化一次。新增逻辑一律先画"数据流 → 复合边界"，再写代码。

## 5. 各层设计

### 5.1 输入层：选项设计（tabBar）

| tabId | 选项 | 行为 | 状态 |
|---|---|---|---|
| 1-6 | R/L/U/D/F/B | 单步转动（MANUAL 模式） | 已就位 |
| 7 | 打乱 | 生成 N 步随机队列 → AUTO 播放 | 本轮新增 |
| 8 | 自动复原 | 求解器产出解法队列 → AUTO 播放 | 本轮新增（求解器先占位，2×2 轮实装） |
| 9 | 重置 | 重建角块/重置逻辑状态 → READY | 本轮新增 |
| 10+ | 预留：阶数切换(2×2/3×3)、难度(打乱步数)、复原策略 | 后续 | 预留 |

> tabBar 资产更新（7-9 选项）需要改控制器组件配置，见 §10 开放问题与 TASKS。

### 5.2 流程层：游戏状态机

流程由三个图变量表达（实测实现，未用单一枚举）：

```text
lock: bool      输入锁（转动期间 true，忽略一切输入）
autoMode: bool  队列播放模式（打乱/自动复原共用）
settled: bool   已结算（防重复胜利结算）
```

状态转移：

```text
[创建] blocks/逻辑状态=已还原, lock=false, autoMode=false
玩家点 R/L/U/D/F/B → 锁门(lock=free) → do_move(逻辑+视觉) → 完成解锁 → afterTurn → 胜利检查
玩家点 打乱 → 生成随机队列 → autoMode=true → 队列播放 → 完 → autoMode=false → 胜利检查
玩家点 自动复原 → 求解器(占位) → （真求解器接入点：queue+qLen → 队列播放）
玩家点 重置 → 宿主销毁+重建角块 + 逻辑/流程复位 → lock=false
```

- 每个转动动作完成后统一走 `afterTurn()`：AUTO 模式取队列下一动，MANUAL 模式做胜利检查；
- 打乱/复原共用统一队列播放机制（qLen/qIdx/queue，逐动播放，播放自然串行）。

### 5.3 逻辑状态层（本轮实现 2×2，3×3 预留扩展）

**状态编码（对齐 3×3 准备基线 §3）**：

```text
cornerPos[8]     dict<int,int>：位置 i 上的角块编号（初始 pos[i]=i）
cornerOrient[8]  dict<int,int>：位置 i 上角块的朝向 0/1/2（初始全 0）
```

2×2 共 **16 个 int**，3×3 扩展 corner+edge 共 **40 个 int**，远小于单列表 500 上限。

**位置编号（WCA 角块名 ↔ 坐标符号，中心 (3,3,3)）**：

| id | 名称 | 坐标符号 |
|---|---|---|
| 0 | UBL | (-,+,-) |
| 1 | UBR | (+,+,-) |
| 2 | UFL | (-,+,+) |
| 3 | UFR | (+,+,+) |
| 4 | DBL | (-,-,-) |
| 5 | DBR | (+,-,-) |
| 6 | DFL | (-,-,+) |
| 7 | DFR | (+,-,+) |

**move 定义（demo 已验证的世界轴约定）**：

| move | 层 | 旋转 | 角位环（顺时针） |
|---|---|---|---|
| R | x+ | 绕 X −90° | UBR→DBR→DFR→UFR→UBR |
| L | x− | 绕 X +90° | UBL→UFL→DFL→DBL→UBL |
| U | y+ | 绕 Y −90° | UBL→UBR→UFR→UFL→UBL |
| D | y− | 绕 Y +90° | DBL→DFL→DFR→DBR→DBL |
| F | z+ | 绕 Z −90° | UFL→UFR→DFR→DFL→UFL |
| B | z− | 绕 Z +90° | UBL→DBL→DBR→UBR→UBL |

**朝向 delta 表**：离线计算（工具脚本 `tools/gen-2x2-move-table.js`），用 CubeLib（原型项目）交叉验证；结果作为静态 dict 数据嵌入节点图。朝向编码约定：块的 U/D 贴纸指向 U/D 面 → 0；指向 R/L 面 → 1；指向 F/B 面 → 2；move 后新朝向 = (旧朝向 + delta) mod 3。

**复合节点划分（预算友好）**：

- `gsts_logic_init`：初始化 cornerPos/cornerOrient（8+8 项 set_or_add，纯数据）；
- `gsts_logic_apply_move`：输入 moveId，循环 4 槽查表（move 表 3 个 dict：pos_from/pos_to/orient_delta，key = moveId*4+slot），更新两个状态 dict；
- `gsts_logic_is_solved`：循环 8 位置，AND(pos[i]==i && orient[i]==0)。

### 5.4 表现层

不动。现有 `gsts_turn_block` / 轨道定时器 / 自旋局部轴全部保留，作为 `applyMove` 的视觉回调。

### 5.5 结算层

- 胜利条件：`isSolved()==true` 且未结算过；
- 动作（沿用 lights-out 已验证模式）：`getPlayerEntityToWhichTheCharacterBelongs(self)` → `setPlayerSettlementSuccessStatus(player, SettlementStatus.Victory)`；
- 反馈：打印 + 可选庆祝（控制器旋转，复用 motion device）。

## 6. 自动复原流程设计

### 6.1 统一队列播放机制（打乱与复原共用）

```text
图变量：queue(dict<int,int>：moveId 序列), qLen, qIdx, autoMode(bool)
playQueue(queue, len)：
  qIdx=0 → 应用 queue[0]（lock 持有）
afterTurn()（每次转动完成解锁时）：
  if autoMode:
    qIdx+1 < len → 应用 queue[qIdx]
    else → autoMode=false；isSolved() ? SOLVED→结算 : 反馈未还原
  else:
    isSolved() ? SOLVED→结算 : 继续等待
```

- 单步应用 = 现有 whenTabIsSelected 的转动链（applyMove 逻辑态 + 视觉），从"选项分派"中抽出为 `gsts_apply_move(moveId)` 复用；
- 播放节奏 = 转动 1s + 解锁，天然串行；无需额外定时器。

### 6.2 求解器接口（本轮占位，2×2 轮实装）

```text
solve(mode) → queue + qLen
  2×2 第一版：查表（宏库/微型 PDB，预算见 3×3 准备基线 §6）
  3×3 后续：宏库 + 微型 PDB（外部研究主方向）
```

本轮只留 `gsts_solver` 占位（返回固定/空队列），保证流程链完整；2×2 实装时替换为真求解器。

### 6.3 打乱

- `getRandomInteger` 生成 N 步（可配置，默认 20 步）1..6 move 码 → queue → playQueue；
- 冗余消除（连续同层/连续相反可合并）属优化，2×2 轮再做。

## 11. 2×2 自动求解游戏内落地方案（2026-08-17 设计，I3 任务蓝图）

### 11.1 求解输入

求解器直接读逻辑状态层（cornerPos/cornerOrient，与 cube.js twist 编码一致），
产出解法为 moveId 序列（1..6），写入 queue+qLen → 复用 gstsScramble 的队列播放尾部
（gstsSolve 接入点已就位）。

### 11.2 策略（受限预算，来源=原型已验证路线）

2×2 状态空间 3,674,160，全表不可行；采用**分层 + 小表**（原型 first-layer/third-layer 均已 8/8 验证）：

```text
阶段 1 第一层（D 面 4 角归位）：
  识别 4 个 D 面角块 → 逐个用 3 循环宏 + ≤5 步 setup 放入正确槽位（朝向一并归位）
  （参考原型 first-layer-solver；2×2 无十字，直接角块阶段）
阶段 2 最后一层（U 面 4 角）：
  OLL（2×2 共 7 case，公式 ~6-10 步）+ PLL（2 case + AUF，公式 ~9 步）
  （表数据参考原型 algs.js / third-layer-solver，压缩打包后 <100 整数）
```

### 11.3 预算核算（估算，实装时实测）

| 数据 | 条目 | 放置 |
|---|---|---|
| 状态识别表（阶段1 槽位/宏映射） | <100 int | 1 dict |
| OLL+PLL 公式表（打包） | <100 int | 1 dict |
| setup 小搜索（≤5 步，复用原型） | 运行时 | 循环+定时器 |
| 节点成本 | ~250-350 | 总 419 + 求解 ≈ 700-800 < 2000 |

### 11.4 落地步骤（I3）

1. 离线：用 verify-2x2-logic-state.mjs 逻辑模拟求解器（表+状态一致，CubeLib 对照）；
2. 表数据固化：原型 cfop 路线 OLL/PLL 表 → 压缩打包 → 生成器产出 dict 片段；
3. game.ts：gstsSolve 占位 → 真求解（识别→查表→queue）；
4. 编译 → 注入 → 游戏核验（打乱→自动复原闭环）。

### 11.5 跨图扩展（3×3 预留）

求解器若超单图预算，拆独立节点图：逻辑状态经**信号**（打包 int 序列）传递，
或同一实体多图共享变量（待验证）；3×3 用宏库 + 微型 PDB（准备基线 §6）。
