# 静态 `.gil` 模型元件与装饰物结构

> 状态：待验证
> 来源：真实地图 `.gil` wire 扫描 + 候选自动检查 + 写回实验 + 用户游戏反馈
> 最近校验：2026-07-25
> 适用范围：当前地图的静态模型实验；各结论按章节证据等级区分，不等同于通用 GIL 协议

本文档记录在地图 `.gil` 中研究静态模型资产、基础元件、自定义元件和装饰物的结构观察。它是持续维护文档：后续每获得一个新的真实地图样本，应优先补充“样本登记”和“A/B 差分记录”，再更新结构结论。

GIL 根字段的当前整体语义树、跨域 evidence 状态和最新 `4/5/6/8` 元件/场景实体相邻差分，以 [`../game-engine-knowledge/gil-structure-semantics.md`](../game-engine-knowledge/gil-structure-semantics.md) 为 Authority。本文保留静态模型专项历史、组件、Transform、装饰物闭包和生产工具细节，不再重复维护完整根字段总图。

## 1. 证据边界

必须区分以下证据层级：

- **真实地图观察**：来自实际 `.gil` 文件的字段路径、实例 ID、资源 ID、wire 类型和 fixed32 字节。
- **用户编辑器操作**：用户说明某个对象基于哪个元件、修改了哪些属性；这是操作来源，不自动证明字段语义。
- **自动解析**：脚本对 protobuf-like length field 的结构化扫描，只证明文件中存在对应字节结构。
- **写回/注入**：本研究截至当前没有执行，不能据此判断游戏是否接受复制后的资产。
- **游戏内验证**：截至当前没有针对静态模型 `.gil` 写回方案完成验证。

protobuf 默认值不能替代字段存在性。文档中“缺失”表示原始 wire 中没有该字段，不表示其语义值一定不是零。

## 3. 用户操作与文件中可观察对象

当前研究的比较主线已按用户确认固定为逐层复杂化：

```text

    ↓ 基于球体创建
自定义元件：新测试球体
    ↓ 基于新测试球体创建，并增加装饰物列表
自定义元件：新测试球体2
```

这三层不能只按场景实例的 Transform 比较，必须分别比较：元件定义记录、元件 ID、基础资源/父元件引用、场景实例引用、装饰物列表和装饰物子实例。

用户提供的编辑器操作为：

1. 新增基础元件：`球体`。
2. 新增自定义元件：`新测试球体`。

   - 修改了旋转、缩放等参数。
3. 新增自定义元件：`新测试球体2`。
   - 基于自定义元件 `新测试球体`。
   - 增加装饰物列表 `球体`。
   - 装饰物使用基础元件 `球体`。
   - 设置装饰物的缩放、相对自身的位置偏移和旋转。

## 4. 顶层分区：`field 4` 与 `field 8`

在当前样本 payload 顶层：

```text
field 4：长度 4583 bytes
field 8：长度 3045 bytes
```

当前观察显示：

- `field 4` 内有一组元件/Prefab 定义样式的记录。
- `field 8` 内有地图中实际摆放的实例记录。
- 两个区域可能复用相同的数字 ID，但数字 ID 不能脱离父容器和字段路径解释。

`field 8` 的路径为：

```text

```

该容器当前有 5 个重复的 `field 1` 实例消息，长度分别为：

```text
765, 561, 571, 580, 553 bytes
```

## 6. 通用实例字段形状

当前几个模型相关实例都呈现类似的外层结构：

```text
field 1：实例 ID
field 2：资源、定义或父实例关系
field 5：实例元数据列表
field 6：属性列表，其中 field 1 = 1 的条目包含 Transform
field 7：关联/附加记录列表
field 8：资源或 Prefab 标记
```

这些是当前样本中的字段编号观察，不是已经确认的官方 protobuf schema 名称。

### 6.1 名称

实例名称常见路径：

```text
field 5
└── field 1 = 1
    └── field 11
        └── field 1 = <名称>
```

例如：

```text
8.1.3.5.11.1 = `新测试球体`
8.1.4.5.11.1 = `新测试球体2`
8.1.5.5.11.1 = `球体`
```

### 6.2 Transform

当前观察到的 Transform 路径：

```text
8.1.<实例序号>.6
└── field 1 = 1
    └── field 11
        ├── field 1：位置
        ├── field 2：旋转
        └── field 3：缩放
```

当前样本中这三个子字段使用 length-delimited 外层消息，位置和缩放内部使用 fixed32 little-endian 浮点。

### 6.3 其它稳定出现的元数据

多个模型实例都包含以下样式字段：

- `field 5.field 1 = 13`，内部出现 `field 22.field 4 = 4294967295`。
- `field 5.field 1 = 14`，内部出现 `MPActionGroup`。
- `field 5.field 1 = 38`，内部 `field 48.field 1` 为 fixed32 `1.0`。
- `field 5.field 1 = 111`、`61`、`62` 等空消息条目。
- `field 6.field 1 = 11`，内部包含 `GI_RootNode`、`中心原点`、`RootNode`。
- `field 7.field 1 = 18`，内部包含 `受击特效`、`被击倒特效` 和 `GI_RootNode`。

这些条目目前只能作为复制时需要保留的结构记录；不能仅凭字段号给出正式语义名称。

## 12. 已确认、待验证与禁止假设

### 已确认的样本事实

- 当前样本 `8.1` 下有 5 个独立实例容器。
- 实例容器具有独立的实例 ID、元数据、属性和 Transform。
- `新测试球体`、`新测试球体2`、装饰物 `球体` 都能在实例记录中定位。
- 自定义元件相关实例存在对其它记录/实例 ID 的引用。
- `新测试球体2` 中的 `1077936131` 至少出现在 `field 2.field 1` 和 `field 5.field 50.field 501` 两个路径。
- Transform 使用稀疏的 length-delimited 子消息和 fixed32 浮点；零旋转可以编码为空消息。
- 装饰物球体有独立实例和独立 Transform。

### 待验证

- `field 4` 中各记录的正式容器语义，以及定义 ID 与场景实例 ID 的分配规则。
- `field 2.field 2 = 1` 的正式含义。
- `field 5.field 1 = 40` / `field 50.field 501` 是否专门表示自定义元件来源、嵌套层级或装饰物关系。
- `field 7`、`field 8` 是否存在必须同步更新的反向索引。
- 装饰物位置是否是父级局部坐标、地图坐标，或另一种编辑器坐标。
- 删除、复制多个相同装饰物后，列表记录和实例顺序的变化。
- 实例 ID 是否在地图范围内单调递增、是否存在回收或跨区域唯一约束。
- 同一资源 ID 是否跨地图稳定可用。
- `.gil` 写回后编辑器和游戏的接受规则。

### 元件 ID 分配规则（用户确认）

用户确认当前地图的自定义元件 ID 采用连续递增规则：

```text
新测试球体   = 1077936130
新测试球体2  = 1077936131
后续新自定义元件继续递增：1077936132、1077936133、...
```

这组规则来自用户对参考地图的确认，当前文档将其作为该地图/该编辑器样本的操作规则记录。它不能自动推广为所有地图、所有版本或所有 ID 命名空间的通用协议；后续写回仍需检查是否与现有定义 ID 冲突。

必须区分：

- **元件 ID**：用户确认的自定义元件连续 ID，例如 `1077936130`、`1077936131`。
- **场景实例 ID**：`field 8.1` 中实际摆放对象的实例 ID，例如参考样本中的 `1077936132`、`1077936133`。
- 两类 ID 在当前样本中数值相邻，不能只凭数值大小判断其语义；必须结合 `field 4`/`field 8` 和引用路径判断。

### 禁止提前假设

- 不要把 `createPrefab()` 运行时能力当作静态 `.gil` 编码证据。
- 不要只复制一个实例容器并替换一个 ID。
- 不要把 `10009002` 当作所有地图都稳定可用的全局球体资源 ID。
- 不要把名称字段当作资源 ID，也不要把 UI 名称 `装饰物列表` 当作文件字段名。
- 不要把缺失的 fixed32 分量自动补写为显式零。
- 不要把自动解析、文件成功写回或注入成功表述为游戏内验证。

### 19.2 静态模型拼装工具（当前实现）

> 状态：当前实现 / 已验证
> 来源：当前代码实现 + 自动回归 + 真实地图写回回读 + 用户游戏内验证
> 最近校验：2026-07-29
> 适用范围：当前静态拼装实现及既有受限生产证据；其它模板、资源和地图待逐项验证

当前公开入口包括只读 `gsts maps --format json`、`gsts assets:static-assemblies inspect`、确定性 `plan`，以及兼容保留的 preview/output/write。共享只读实现位于 `src/cli/static_assembly/`：`wire.ts` 提供受限 protobuf-like 原语，`map_index.ts` 一次建立定义、实例、两侧辅助和占用 ID 索引，`closure.ts` 只在当前已知检查全部通过时返回 `complete`。`inspect`/`plan` 不生成候选、不写源文件；`complete` 不证明模板或资源兼容，JSON 固定保留 `compatibility=unknown` 和“未编辑器/游戏验证”边界。

原有写入实现入口为 `gsts assets:static-assemblies`，核心代码位于
`src/cli/gil_static_assemblies.ts`，命令包装位于 `src/cli/assets_static_assemblies.ts`。工具以
配置中的 `assets.staticAssemblies` 声明每件装饰物的本地 Transform。公开 `GstsConfig`、
`GstsStaticAssembly` 和 `GstsStaticAssemblyItem` 类型已包含该配置。模板主定义 ID 与主实例 ID
在真实地图中不保证相同，当前配置必须分别显式提供 `templatePrefabId` 和 `templateInstanceId`。
`position`、`rotation`、`scale` 都直接使用游戏单位；对原始长方体模型，`scale: [1,1,1]`
对应游戏中 `1×1×1` 的原始尺寸。每件 `position` 相对组件原点，组件自身 `position` 是场景位置，

            position: [-1, 0, 0],
            rotation: [0, 0, -20],
            scale: [0.2, 2, 0.2]

          { resourceId: 10009001, position: [0, 0, 0], scale: [1, 0.15, 0.2] }
        ],
        definitionAuxiliaryIds: [1073741878, 1073741879, 1073741880],
        instanceAuxiliaryIds: [1073741881, 1073741882, 1073741883]
      }

  }

默认命令只在临时文件中生成并输出摘要，不会修改地图：

```bash
node bin/gsts.mjs assets:static-assemblies --asset-config gsts.static-assemblies.config.mjs --map-id <mapId>
```

`--output <candidate.gil>` 只允许新建候选文件；`--write` 才会覆盖已选地图，并在目标同级
`.gsts/backups/` 创建备份。创建操作必须显式提供 `prefabId`、定义侧辅助 ID、实例侧辅助 ID；工具先扫描
目标地图的 `field 4/8/27` 记录，遇到冲突 ID、模板缺失、辅助 ID 数量不等于 items 数量或模板缺少
`field 6` 登记时直接失败。它不会猜测下一可用 ID，也不会自动写回。

自动回归：`npx tsx tests/gil_static_assemblies.ts <map.gil> <prefabId> <definitionStart> <instanceStart>`。

定义/实例辅助颜色、启用字段 presence、RGB/ARGB、33/50/66% Alpha 量化以及覆盖/正片叠底；
不能替代编辑器/游戏验证。

自 2026-07-28 起，`GstsConfig.assets.staticAssemblies`、`GstsStaticAssembly` 和
`GstsStaticAssemblyItem` 已成为 npm 根入口公开类型，CLI 不再维护私有配置副本。preview 会打印来源与
候选 SHA-256、assembly/template/resource/辅助 ID 计划、候选大小、触及的顶层字段和
`writePerformed=false`；`--write` 另打印备份与写后哈希。中英文 CLI help 和项目模板已明确区分
静态 `.gil` 元件拼装、GIA NodeGraph 注入与运行时 `createPrefab`。这些是当前实现和自动构建证据，
颜色公开配置支持主体和逐 item 的 `enabled`、`rgb`、`opacity`、`overlay`。编码器只替换

两侧辅助记录使用相同颜色快照。颜色行为已有 raw-wire 自动回归和 §19.2.2 的受限游戏验证。

复杂模型还可使用 `structureFile` 将可移植结构从配置中分离。公开配置使用互斥联合：内联分支提供
`items`/`color`，文件分支只提供 `structureFile`；地图相关名称、模板 ID、新 prefab ID、两侧辅助
ID 和场景 Transform 始终留在配置。`src/cli/static_assembly_structure.ts` 将相对配置目录的严格
JSON 解析为 `GstsResolvedStaticAssembly`，再交给现有 `applyStaticAssembly()`，因此文件解析不直接
读写 `.gil`。格式固定为 `schemaVersion: 1`，只允许 `$schema`、`color`、`items` 及 item 的
