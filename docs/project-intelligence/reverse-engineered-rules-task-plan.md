# 逆向规则工具化任务计划

> 状态：当前推荐
> 来源：真实 GIL/GIA 相邻快照、当前代码实现、自动回归、用户编辑器/游戏反馈、历史会话交叉核对
> 最近校验：2026-08-05
> 适用范围：Genshin-TS 编译器、GIL/GIA 工具和真实游戏验证；不代表未列内容已经全量支持

本文把已经通过逆向调查解释过、但还没有完全工具化或完成游戏验证的规则整理成后续任务清单。
它不是完整的 GIL schema，也不是“所有 API 已支持”的承诺。

## 证据分层

每个任务都必须分别记录：

1. **真实规则**：来自用户编辑器的单变化快照、raw wire、独立 Validator 或真实参考 GIA。
2. **当前实现**：源码、工具和测试现在能做什么。
3. **自动验证**：focused test、结构回读或 round-trip 通过什么。
4. **编辑器/GIA 验证**：候选是否能被游戏编辑器导入并保留结构。
5. **游戏验证**：用户在游戏中看到的节点、资产或行为是否正确。

自动生成成功、自动测试通过、GIA 复制成功、注入成功和游戏行为通过不能合并成一个“通过”。

## 执行纪律

- 每轮只处理一个任务编号中的一个最小测试点。
- 开始前先复述本轮唯一变化或唯一待验证行为。
- 未知的 `mapId`、`nodeGraphId`、信号 ID、pin index 和版本字段必须从当前文件读取，不能猜。
- 真实 GIL/GIA 规则尚未闭合时，不用待验证的 production lowering 证明规则。
- 先生成最小候选，再由用户在编辑器/游戏中逐项核验；不要为了提高数量一次生成大量无关样本。
- 涉及真实地图写回、覆盖、删除、清理或注入时，必须单独展示目标、当前哈希、命令、范围和回滚方式，并取得明确授权。
- 用户反馈“通过”后才把对应候选标记为游戏验证通过；失败候选不能归档为通过。

## 推荐执行顺序

1. 先完成 P1，收口当前信号注册表初始化和生产信号参数引脚问题。
2. 完成 P2、P3、P4，闭合普通信号发送/监听，再扩展列表参数。
3. 完成 P5、P6，补齐 Composite 特殊节点和复杂参数。
4. 完成 P7、P9，验证自定义变量全类型以及选项卡/实体工具。
5. 开始 T1、T2、T3、T4、T5，建立通用 GIL/组件/关卡资产工具的只读入口。
6. 最后扩大 P10、P11、P12、P13，逐项扩展客户端、诊断和静态资产覆盖。

每个任务的结束条件必须是：

```text
自动回归通过
→ 候选结构/回读通过
→ 编辑器导入或写回状态单独记录
→ 用户游戏测试通过（若该任务涉及行为）
→ 更新本表状态和对应 Authority 文档
```

## 工作目标

根据任务计划中的优先级，从一个尚未完成的任务开始，逐项把已经逆向解释出的 GIL/GIA 规则变成可靠工具或生产能力。
当前默认优先级是：

1. 先处理 P1：信号注册表初始化、信号生产参数引脚和当前信号 Bug。
2. 再处理 P2/P3/P4：普通信号发送、监听消费和列表参数。
3. 再处理 P5/P6：Composite 特殊节点和复杂参数。
4. 再处理 P7/P9：自定义变量全类型、选项卡和场景实体。
5. 再处理 T1/T2/T3/T4/T5：通用 GIL、组件、关卡变量、镜头和计时器只读工具。

如果当前会话或用户明确指定了其它任务编号，以用户指定为准。

## 第一阶段：恢复与选点

1. 先检查 `git status --short`，保护已有工作树变化，不要重置、清理或覆盖其他人的修改。
2. 只读取任务编号对应的最小 Authority 文档、源码入口和 focused test。
3. 用大白话向我报告：
   - 这条规则在游戏文件里是什么；
   - 当前代码已经做到什么；
   - 缺的到底是工具、自动测试、编辑器导入，还是游戏行为；
   - 本轮准备测试的唯一小点是什么。
4. 每轮只能选择一个最小测试点。不要把多个独立未知变量放在同一轮。

## 第二阶段：自动验证和候选生成

1. 先复用现有 CLI、脚本、解码器、Validator 和测试，不要重复编写已有工具。
2. 如果规则仍未闭合，先使用真实编辑器相邻快照和 raw-wire 证据，不要用待验证的 production lowering 证明规则。
3. 先建立最小红灯或最小结构断言，再做最小实现。
4. 生成一个最小候选 GIA/GIL，保留路径、大小、SHA-256 和适用范围。
5. 分开报告：自动测试、结构回读、候选复制/注入和编辑器导入，不要把其中任何一项称为游戏通过。

## 第三阶段：配合我做游戏测试

这是本任务的核心纪律：你必须配合我在游戏内逐项测试，每次只测试一个小点。

每次生成候选后，只告诉我：

- 候选文件路径和 SHA-256；
- 本次唯一测试点；
- 游戏里应该观察什么；
- 如果失败，应该反馈哪一个具体现象。

然后等待我去游戏里测试并反馈。不要在我反馈前同时生成下一批候选，不要把多个节点、多个参数或多个组件混在一张待测文件里。

我反馈“通过”后，才记录为“用户游戏验证通过”；我反馈失败后，保留失败证据，重新定位差异，不要直接猜测或静默修改多个地方。

涉及真实地图写回、覆盖、删除、清理或注入时，必须先展示目标路径、当前哈希、命令、修改范围和回滚方式，并等待我的明确授权。不要猜 `mapId`、`nodeGraphId`、信号 ID 或 pin index。
