# PROMPT — 千星编辑器「假死」根因定位与根治（单指令长跑）

## 定位
千星编辑器（Wine）的「点不动」假死——从输入链路机制到根治。

## 交付形态（锁死）
**诊断报告 + 代码改动（提交）+ 验收读数**，三件齐全才算交付：
1. 机制说明：从「用户手势可解卡」反推到 Wine/WM 的哪一段代码/状态机，带证据链（每条结论标出处：实测读数/源码行号/上游 bug 编号）。
2. 改动：补丁或配置，落在仓库里并提交（含回滚方式）。
3. 验收读数：同一探针在「修复前/修复后」各跑至少一次完整的「试玩→归来→再试玩」，并给出可点性对比数字。

## 任务（唯一目标）
把《原神》千星编辑器（Wine 下 BeyondEditor.exe）的「**假死**」查到**机制级根因**，并给出**不需要用户手动操作**的根治方案。

**假死的定义（用户原话逐字）**：「沙箱窗/资源管理器/日志**全部点不动**，但渲染正常、可移动、可获焦」。它**不是**假死画面冻结，也不是进程死亡——事件进不去应用内部。

**完成的标准只有一个**：用户能**连续走完一次「试玩 → 归来 → 再试玩」**，全程**不需要按 Win+鼠标右键拖动窗口**，且编辑器始终可点。任何以「看门狗自动强杀重启」「自动替你拖一下窗口」为交付的方案都算**未完成**（用户已明确否决：`它的思路不能从根本上解决问题，效率太低`）。

## 已知事实（全部实测，禁止重新发明；违反其一即为返工）

1. **解卡手法有效且可编程**：`Meta↓ + 右键↓ + 指针相对移动 + 右键↑ + Meta↑`（`tools/ys-editor/ys-gesture-cure full`），经 `ys-gui-slot` 执行 2–3 秒，用户当场口头确认「恢复了」。**净位移为 0（移出再移回），不改变窗口几何**。
2. **假死可反复复发**，与**焦点切换强相关**：解卡后正常 → 做几次「槽位」（激活编辑器→动作→还焦点）→ 又点不动；再解卡 → 又可点。Wine Bug 59965 的机制正是「持 grab 时失焦 → WM_CANCELMODE → 应用内部捕获状态错位」，但该 bug 在 WineHQ 状态为 **UNCONFIRMED、无修复版本、无 regression SHA**。
3. **X 层已全部排除**（负结论都有正对照）：无残留指针/键盘抓取（自建探针 174/174 = 0/0）；X11 socket Recv-Q 全 0；SHAPE 输入区=整窗；无隐形模态窗（11 个 X 窗口只有 3 个真窗口）；点击时 WM 正常置 FOCUSED；无 OPACITY 变暗；截图渲染完整。
4. **不是 KDE 焦点回归**：运行中 KWin 6.8.0 + `focusStealingPreventionLevel=0` 下**仍复发**（旧结论已证伪，见记忆 D446）。
5. **进程活着**：主线程持续有 CPU（健康态一样烧，不是判据）；NLog 在假死期**零新增行**；三窗口同属一个 `beyondeditor.exe` 进程。
6. **抓帧通道选择有历史结论**：`import -window <编辑器窗口>` 在本机是**冻结缓冲**（连续抓帧 0 差异）；`spectacle` 605ms 且**试玩全屏下会 core dump**（已淘汰）；项目自有快通道 `ys-capture`（XShm，1.4–8ms）当前守护能启动但**不产帧**（`state.tsv` 不出现，`latest` 报 DAEMON_DOWN）——这三条都已实测，别再花时间重新横评。
7. **点击/菜单/树的正常行为**：单击树=选中、双击=展开（双击必须 0.12s 内连发两击，`ys-pointer-click` 每次闭环 1–3s 会把双击拆成两次单击）；**菜单必须与点击在同一个槽位/租约内完成**，跨槽位时菜单会因失焦关闭，点击落到空白——肉眼看起来非常像「点不动」。

## 工具与环境（照抄，别自造）

- 记忆：`memo_recall folder=genshin-ts`（本项目全部前史：D279–D449；先召回再动手）；跨项目环境事实看 `dsh-plugins` 桶。
- 工具箱：`~/genshin-ts/tools/ys-editor/` — `ys-lease`（焦点租约：一次取焦、期间多动作 ~50ms/动作）、`ys-gui-slot`（申请制占用：记原焦点→激活并核验→硬时限→trap EXIT 严格还原）、`ys-gesture-cure`（解卡手势六变体：`full/metric/rclick/rdrag1px/rdrag/mdrag`）、`ys-ops`（动作台账 + 覆盖率）、`ys-pointer-click`（闭环定位点击）、`ys-capture`（XShm 快抓帧）、`ys-states/ys-field/ys-rowclass/ys-goto/ys-crawl`（UI 感知与导航）。
- **注入纪律**：`ydotool` 被 shim 拦，必须经 `ys-gui-slot`（或 `YS_ALLOW_RAW=1` 且已获用户同意）；所有注入前后焦点必须还原，占用超过 30 秒要先报时长。
- 取证纪律：不要 glob `/proc`；不要用 `pkill -f <自己的命令行里含有的串>`（会自杀，用 `ys-kill`）；每条 bash 调用都是新 shell，`DISPLAY`/`XAUTHORITY` 不继承。

## 请你做的事（按顺序，每步都要有行为读数）

1. **先建可复现的反馈回路**：写一个判定「可点 / 不可点」的探针（建议：点一个已知会改变 UI 的元素，比较真屏像素差；噪声基线=纯光标移动约 2950px，树展开约 6035px）。没有它，后面所有结论都无法验证。
2. **二分解卡手势**：用 `ys-gesture-cure` 的六个变体在同一批假死标本上逐个试，找出**最小有效动作**（只按 Meta？只右键点？抓取+2px？拖动？）。最小动作直接指向机制：需要「别人的指针抓取」⇒ Wine 的 grab 状态机；需要「位移+ConfigureEvent」⇒ 另一条路。
3. **从最小动作反推机制**，并在 Wine 源码/fork 里找对应代码路径（`dlls/winex11.drv/event.c` 的 WM_CANCELMODE 分支是已知嫌疑，但**先用数据证明它**，不要直接套用别人的补丁）。
4. **给出根治方案**并落地验证：它必须能在用户**不手动操作**的情况下，让编辑器扛住「试玩→归来→再试玩」。可选方向（自己判断、自己验证）：修 runner 里的 wine（打补丁重编）、换 runner、在 X/WM 层做「等价的输入状态复位」、或证明触发源可被消除。
5. **交付**：机制说明（带证据链）+ 改动（提交）+ 验收读数（对比试玩循环前后的可点性）+ 未解决风险清单。

## 硬约束

- 不把「自动强杀+重启」「自动替你拖窗口」当交付（用户已否决）。
- 不动游戏本体与反作弊环境（`spritz-wine-tkg-staging-wow64-11.14-1` 是游戏侧硬要求）。
- 不引入 `spectacle` 作为抓帧通道（历史结论：慢且试玩全屏会 core dump）。
- 每次注入都经槽位/租约，焦点必须还原；用户在场时先报「做什么+几秒+占哪个窗口」。
- 结论必须有行为读数（点得动/点不动 + 像素证据），不接受「配置改了所以应该好了」。
