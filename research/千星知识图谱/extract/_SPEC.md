# 精读规范（T03 · 子代理必读）

> 你的任务：把 B站教程的 AI 字幕全文，转成**知识图谱条目**。
> 工作目录 `/home/h/genshin-ts`。产出目录 `research/千星知识图谱/extract/`。

## 一、为什么这份规范这么严

本项目的目标不是"看过视频"，而是**建立一份能当开发手册用的知识图谱**——
拿它当指导要能真的做出一款优质游戏，每个细节都不丢。
所以：**空泛的总结 = 无效产出**。判据只有一条：**别人能不能照着你的条目做出来**。

## 二、术语校正（必做，AI 字幕有系统性误识别）

| 字幕原文 | 正确 |
|---|---|
| 白模 / 白膜 / 白蘑菇 | **白盒物件** |
| 绝对存档 / 举内存档 / 直接存档 | **局内存档** |
| 布尔过滤器 / 布尔功率 / 布尔工具器 | **本地过滤器节点图（布尔型）** |
| 尸体 | 实体 |
| 截点图 / 经验图 / 检验图 / 景点图 / 极限图 | 节点图 |
| 负 / 负债 / 附带（性能语境） | 负载 |
| 起价 / 谦信 / 铅芯 / 天津 / 亲信 / 轻音 / 千金 | 千星（千星奇域） |
| 奇遇（指编辑器时） | 奇域 |
| 剑（键名语境） | 键 |
| 四（判断语境） | 是 |

**注意**：语料是**未校正的原文**——引用原句时保留原样（取证），但你在陈述时用正确术语。

## 三、提取要求（严格）

### 1. 具体到可执行

- ❌ "要注意性能问题"
- ✅ "单节点图节点上限 2000，超了要按职责拆新图；单 tick 帧数预算 <3000"

保留**具体数值、节点名、UI 路径、参数、命令**。数值是这个知识图谱的核心资产。

### 2. 三类内容分开（每类一个二级标题）

| 标题 | 收什么 |
|---|---|
| `## 规则与机制` | 引擎事实：是什么 / 边界 / 上限 / 约束 / 触发条件 |
| `## 做法与技巧` | 怎么做。**必须包含邪修、野路子、非常规但有效的做法**（用户点名要这类） |
| `## 设计经验与教训` | 为什么这样做才"好玩/优质"：设计思路、引导、难度节奏、失败复盘、玩家反馈、避坑 |

### 3. 每条必须带三个字段

```
- **<一句话结论，具体到可执行>**
  - 出处：`[HH:MM:SS]` "原样引用的关键句，可被 grep 到"
  - 证据等级：硬规则 | 实测 | 经验共识 | 个人经验
  - 维度：D? <名称>
```

**证据等级判据**：
- `硬规则` = 官方文档/引擎事实（编辑器明确规定的）
- `实测` = 有人真做过并给出了数据/现象（如"我测了 1000 个件会卡"）
- `经验共识` = 多个来源/弹幕/评论都在说同一件事
- `个人经验` = 单一讲师的主观建议

### 4. 维度标注（**关键**）

优先从 D 骨架选：
`D0 元知识` / `D1 概念模型` / `D2 编辑器资产` / `D3 逻辑编写` / `D4 玩法系统` /
`D5 表现层` / `D7 工程化工具链`

**若都不合适 → 自拟一个新维度名并在名字后加 `⊕`**。
这一步是本项目的核心方法论（用户明确要求）：**维度要从语料里长出来，不要硬塞**。
自拟维度请用 2–6 个字的名词，如 `引导设计⊕`、`项目管理⊕`、`玩家心理⊕`。

### 5. 禁止

- ❌ 写"本视频介绍了…"这类总结陈词——只要条目
- ❌ 把讲师的每一句话都收录（那是转录不是提炼）——只收**有信息量的结论**
- ❌ 想象补充视频里没说的内容
- ❌ 丢掉数值精度（"大概几百个"→ 写原话数值）
