# 主流工作流程 × 我们的七步工作流：对照与借鉴

## 1. 阶段映射总表

| 行业阶段 [A1] | 我们的对应 | 判定 |
|---|---|---|
| concept/pitch（+平台概念批准） | **步骤1 GDD**：核心循环/输入/胜负/P0 范围/风险 | 对齐 |
| prototype / find the fun | **步骤3 HTML 效果展示**（先于一切工程投资验证体验） | 对齐，但顺序有代价（§3.4） |
| vertical slice（go/no-go 评审物） | 步骤3+4：体验确认 → 美术方案 | 半对齐：**缺 kill 出口**（§3.1） |

| 里程碑付款合同 [A2] | production-plan 步骤推进 + 用户四个裁决点（玩法语义/HTML 体验/美术方向/真机结果） | 已有 demo 级形态（验收人=用户） |

## 2. 已对齐、行业证据背书应坚持的

1. **验证左移结构优于行业均值**。行业 postmortem 第一教训=「测试开始得太晚」[C5]；我们把体验验证（HTML）放在工程投资之前、用例定义放在代码之前、真机只验平台行为——整体是比行业主流更左的验证结构。
2. **判据式步骤定义**。行业里程碑的精华是判据式语义（alpha=feature complete、beta=+content complete 只修 bug）[A1][A2]；我们每步都有「产物与完成条件」，同一形态。区别只在行业无标准定义、我们也无需行业化——**不要**为了对齐行业词汇改步骤名。
3. **用户裁决点收敛为四个** ≈ 行业 milestone 由发行商验收 [A2]：我们的「发行商」就是用户，验收点已经显式化且没有泛滥（技能明言实现细节不问）。
4. **runtime=html|simulator|device 证据分层、模拟器绿灯≠真机** ≈ 行业认证用零售机测而非开发机 [A6]——同一条工程智慧，我们已写成硬约束。
5. **复用优先**（复合资产「能复合一定复合」）≈ 行业 middleware/引擎复用与 co-dev 生态 [C2] 的低成本化形态。

## 3. 缺口与建议（按价值排序，全部待裁决）

### 3.1 HTML 步骤缺显式 kill gate（借鉴价值最高）

- 行业：vertical slice 评审是显式 go/no-go——XCOM 2009 切片被判「不好玩」，整块推翻重做，五年磨成正品 [A10]；推翻在早期成本最低，这是行业用真金白银换来的机制。
- 现状：步骤3 完成条件=「可打开试玩的演示、用户反馈和不可移植项」——有反馈收集，但流程语言里**没有「不好玩就推翻/换玩法」的合法出口**，默认轨道是继续。
- 建议：步骤3 完成条件增加一条裁决记录：**go**（按案进 4）/ **rework**（改核心循环后重做 demo）/ **kill**（此玩法放弃，回步骤1 换案）。裁决写入 production-plan.md。
- 落点：qxqy-game-studio 步骤3 文档 + 主表「何时读取」列。

### 3.2 playtest 与 QA 双轴未分离

- 行业：定义级共识 playtest（验证设计/好不好玩，观察行为）≠ QA（找软件缺陷）[C9]；ND 的 17 制作人本质也是在把「流程健康」从「做内容」里分离出来 [B]。
- 现状：步骤6 全是 QA 轴（用例/回归/截图）；步骤7 真机天然是 playtest 轴（用户上手玩），但汇报与记录没有分轴——体验问题和正确性 bug 混在一个清单里，修复优先级无从区分。
- 建议：`records/playtest.md` 按双轴分栏（体验：节奏/难度/困惑点 vs 缺陷：功能不符/崩溃/布局）；真机回传先分类再进修复队列。
- 落点：步骤6/7 文档 + playtest.md 记录模板。

### 3.3 GDD 不是 living document

- 行业：当代主流定义就是 living document（周度/日度修订、与可玩原型并行演进）[C7][C5]。
- 现状：步骤1 产出 GDD 后流程中无回写机制；但 HTML rework、平衡调整、真机发现都会漂移玩法语义——**跨会话恢复时读到的 GDD 可能已过时**（我们的恢复机制恰恰依赖文档准确）。
- 建议：凡用户裁决改变玩法语义（rework/平衡/砍范围），当轮回写 GDD 对应条目（增量即可，不必重写全文）。
- 落点：步骤3/5/7 文档各加一句回写义务；production-plan 记录 GDD 版本。

### 3.4 用例先于找-fun 的顺序代价（fork，二选一）

- 行业：先验证好玩、再投工程（含测试设计）——对未验证的玩法写规格被视为浪费 [B2][B6]。
- 现状：我们的顺序是 GDD→**TDD 用例**→HTML，即体验确认前先做了一笔工程投资；若 HTML 被 rework/kill，用例返工。
- 反方（保持现状的理由）：我们的用例很轻（规则→可观察结果追踪表），它把 GDD 锐化成可判定的胜负规则，反而提高 HTML demo 的质量；行业 test plan 也写在 alpha 前而非代码后 [C10]，我们只是更左。
- 建议 fork：A=保持现状（接受小返工风险，换规则锐化收益）；B=步骤2 降为「规则可观察化清单」，断言细节冻结推迟到 HTML 确认 go 之后。
- 落点：步骤2 文档；主表步骤 2/3 顺序约束的措辞。

### 3.5 修复循环计数 = 范围失控信号（crunch 信号的 LLM 翻译）

- 行业：Valve Handbook「长期加班=计划或沟通的根本失败」[B1]——压力信号触发的是**范围回顾**而不是更多加班。
- 现状：一个游戏在步骤5/6 反复 Red→修复循环时，我们没有触发器逼问「是不是 P0 范围本身就错了」。
- 建议：production-plan 加修复轮计数；同一缺陷域修复轮 >N（建议 3）时强制回步骤1 做 P0 范围回顾（砍范围/降深度），而不是继续加轮次。
- 落点：步骤5/6 文档 + production-plan 模板。

### 3.6 行为观察先于感受提问（Valve playtest 纪律移植）

- 行业：Valve playtest=固定时长+观察者禁言，先收行为再问感受 [B2]；投币机数据是遥测原点 [C9]——数据先于口述。
- 现状：模拟器本身可产生行为记录（play history/get），但我们问用户「好不好玩」之前不先看行为数据。
- 建议：步骤6 增加轻量行为观察项：试玩/回放里记录卡点（死点/反复失败/忽略的机制），作为步骤7 向用户提问的输入——「你在第 3 关停了很久」先于「你觉得难吗」。
- 落点：步骤6 文档 + playtest.md 模板。

## 4. 明确不适用（防过度移植）

- 主机认证 TRC/XR/lotcheck 全家桶：demo 无平台方；但步骤7 的索引校准/真机核验已是其 demo 级精神对应物，无需加步骤。
- 百人分工/外包/co-dev、Perforce+build farm：单人+LLM+单存档+git 已覆盖。
- soft launch/LTV/UA：demo 不运营；若未来做长线运营型千星游戏再回来查底稿（Wooga 六阶段模型在 [A12]）。
- crunch 治理本身：LLM 不加班——但其**信号价值**已翻译为 §3.5。
