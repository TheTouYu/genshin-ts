## P2 · 模型拼接 & 实体UI基础（道合三清）

主题：用**白盒物件**手工拼装复杂模型。核心是"几何体运用 + 叠色 + 比例"三件事。

### 2.1 几何体基础技巧

| 技巧 | 具体做法 | 备注 |
| --- | --- | --- |
| **旋转复制拼圆环** | 固定角度旋转 + `Alt+鼠标拖动` 复制；角度档位 **5/15/30/45/90 度**；拼圆**最佳是 15 度** | 拼前必须让模型**平放**（对齐到 90 或 180 度），带斜角转起来会歪 |
| **棱角处理** | 不留硬边，做贴合；用**多边形而非单调形状** | "效果看起来更好" |
| **球体陷阱** | 单用球体做模型容易"露馅"（坡度不相似）；**球 + 圆柱搭配**效果远好于单球 | 圆柱给"平面"，球给弧度 |
| **缩放微调** | 数值可调到 **0.95 / 0.001** 级别做合缝 | 圆柱与球包裹后用缩放找合缝 |
| **模型闪烁（Z-fighting）修复** | **上拉/下拉 0.01** 让面错开即可解决 | 0.015 引擎也能识别但不显示；闪烁是重叠导致的 bug 点，**正方形件多时更容易闪**，建议改用圆柱/三角形 |
| **坡度地形** | 坡度叠坡度做出地形，从上到下，可带小坑 | 不要平着放 |
| **曲面屏 / 弧度衔接** | 90 度管 + 中间弧度衔接；同一段弧度可再做一次 | 注意模型**厚度**，速度过快易穿帮；顶/底可补平面 |
| **手搓三角形** | 当所用白盒件只有矩形面（无三角面）时，手工拼出三角形；前端可做小再补齐、缩小到无缝 | 三角形可**旋转出圆锥** |
| **材质盲区提醒** | 建议不要用件背面（"背面比较容易看"）；线框长方体/线框圆柱无法更换材质 | 后者来自官方指南 |

### 2.2 叠色法 / 实体UI（本课最有方法论价值的技法）

- **原理**：**用大量单色白盒件一层套一层地叠**，模拟出 2D 立绘的观感——"高光/阴影/固有色/过渡色"都用实体件叠出来，做赛璐璐平涂效果。
- **成本量级**：讲师示范的侧背面用了 **近 1000 个件**（"阴影比较多不好叠"）。
- **偏移取色**：用坐标偏移（如 9.7.1 / 9.7.2 / 9.7.3）制造**不同颜色**的层——偏移本身就是取色手段。
- **阴影取色法**：阴影色 = 固有色在显示器里就近选取的相邻色，**距离不要太远**。
- **修边**：用长方形/三角形 + 其他颜色遮挡掉不想要的边。讲师直言"做模型的无一不是耐力大王"。
- **层次感**：在底色上继续叠弧形/小元素，再打高光；补一层过渡灰可显著提升立体感。
- **负载**：讲师称白盒件**负载很低**；但其第一张老图因模型复杂 + 金属多，"进图会卡爆"——**负载是真实约束**。

### 2.3 两种进阶造型法

1. **平面稿法（先平面后立体）**——适合"想做复杂东西但不会找角度"的人：
   - 先只拼**平面图**打底稿 → 复制多份 → 用**非整数偏移**（如 1/2/3/4/5）保持水平线对齐（用 10.01 会很难回归原位）→ 做角度 → **镜像**（现在有镜像了，可省掉对称那一半的手动做角度）→ 再动**第二个轴**让两面粘上 → 做衔接。
   - 需注意"不是只动一个轴就行"。
2. **两面包夹填充法**——**做 3D 模型的首选**：先做两片外壳，再填充中间。优于"从头修到脚"（比例难把控）。空心部位可以填实，加牙/加细节修饰。

### 2.4 比例与观感

- **比例参考物**：用**假人（人形模板）**做参考。讲师给的经验值：假人约 **1.5~1.7 米**；房子比人高一点点即可。官方网格线 = **标准 1 米**（`official-guide-concepts.md:1231`）。
- **拐角**：对齐、不要留缝（"特别容易漏线"），露一点点无妨；有弧度的方形拐角要专门练。
- **宽面不宜过宽**：旋转 + 突出角会导致"出戏"；宏大场景可放宽。
- **色彩题材学**：
  - 金属 / 科幻 → 偏**金属质感、灰白黑、浅灰蓝**
  - 野外 / 沙漠 → **暖色**为主
  - 太空 / 恐怖 → **青、绿、蓝**
- **中式/日式屋顶**：正方形 + 三角形；**三角形专做四角斜角**（歇山/日式建筑的四个角）。
- **水**：水可改色，用深水色 + 浅水色做**透视关系**（"舱体是用水做的，看起来有透视"）。

**我方对照**：我方强项领域（`static-gil-model-builder` + `assets:static-assemblies`/`entities`/`aux`）。差异点见 `能力缺口.md` GAP-07。

## P3 · 列表、字典、结构体入门（小猪之最）

主题：三种**容器数据类型**。结构清晰、节点覆盖全，是本课最"可当手册"的一节。

### 3.1 为什么需要容器

反例：存斐波那契前 8 项，用 8 个自定义变量 → 命名爆炸、取第 N 项要写名字、**复合节点里传递极不方便**。
正解：一个容器变量搞定。

### 3.2 列表（List）

**创建与基础**
- 类型**与基本类型一一对应**（字符串列表/整数列表/浮点数列表…），**同质**：一个列表不能混存两种类型。
- 定义变量组件里创建；右侧「**多少个**」= 一次性批量加 N 个元素（讲师坦言一开始不知道，一直一个个点）。
- **序号从 0 开始**（= 其他语言的索引 index）；长度 = 元素数。
- 内置节点大量用到列表，例：`获取指定玩家所有角色实体` 输出就是**实体列表**（超限/经典模式通用）；`获取指定类型的实体列表` = 筛选功能。

**节点清单**

| 类别 | 节点 | 语义要点 |
| --- | --- | --- |
| 读 | 获取列表对应值 | 按序号取值 |
| 读 | 列表的长度 | |
| 读 | 列表是否包含某值 | 输出布尔 |
| 建 | **拼装列表** | 节点图内创建列表；**泛型引脚可选**；元素可填常量也可连引脚进来 |
| 改 | 对列表设置值 | 覆盖指定序号 |
| 改 | 对列表插入值 | 在指定位置插入；**序号可取 0~N（N=长度）**，取 N 即在末尾新增 |
| 改 | 移除值 | 按位置移除，长度减一 |
| 改 | **拼接列表** | 把第二个列表接在第一个后面；**只改第一个，不改第二个**；末尾新增可用它替代"插入值"（不用算序号） |
| 改 | 排序 | 顺序 = 小到大；逆序 = 大到小。**千星里其实不太常用** |
| 改 | 清除列表 | 清空，类型不变 |
| 循环 | **列表迭代循环** | 与有限循环差不多，但写起来更简单 |

**列表迭代循环三个要点**
1. 迭代前**必须先把列表存进变量**（自定义变量 / 节点图变量 / 局部变量）——因为每次迭代都会重新取一次列表值，不存会不一致。
2. 典型场景：多人游戏里对"在场玩家实体列表"逐个设分数为 0。
3. 累加类（如列表求和）也走它。

**局部变量**
- `获取局部变量` 节点**既是创建也是获取**；可定义初始值，**类型必须匹配**。
- 有它 → 每次拿到的是设定值；没有 → 一直是初始值。

### 3.3 字典（Dict）

**键值模型**
- 概念对标英文词典：按键查到值（键 = 单词，值 = 释义）。
- 其他语言里叫 map 映射。

**键类型的硬约束（重要）**
- 键**只能**是：**字符串 / 整数 / GUID(配置ID) / 元件ID / 阵营 / 实体**。
- **为什么不能是浮点数**：小数在计算机里有误差（如 2.9979），**不稳定**。
- **为什么不能是列表**：列表是容器，也不稳定。
- 这是**千星特有**的严格规定（Java 等语言 map 可自由指定键值类型）。
- **键不能重复**（重复会提示并改回原值）；**值可以重复**。

**无序性**
- 字典是**无序**的：**不能按序号取键或值**，只能按键取值。
- 但**转成列表就有序了**（`获取键列表` / `获取值列表`）。

**节点清单**

| 类别 | 节点 | 语义要点 |
| --- | --- | --- |
| 查 | 一键查询字典值 | 最常用；键不存在返回该类型默认值 |
| 查 | 是否包含特定键 / 特定值 | 输出布尔；可当作"两个列表里有没有"来理解 |
| 查 | 获取键列表 / 获取值列表 | 转有序列表 |
| 建 | **建立字典** | 传两个列表 → 字典；**长度不同时取短的**（长的尾部被截掉） |
| 建 | **拼装字典** | 逐个填键值对；不会溢出，因为要求长度一致 |
| 改 | 新增 / 移除 / 清空 | 移除只需给键，不用管值——**字典所有操作都围绕"键"** |
| 改 | 排序 | 分**按键排序**/按值排序；按键排序要求**键是整数**，按值排序要求**值是整数或浮点数**；**输出的是键列表 + 值列表**，需要自己还原对应关系 |
| 循环 | ❌ 无字典迭代循环 | 只能 `获取键列表` + 列表迭代 + `一键查询字典值` 手动实现 |

**泛型引脚纪律**
- 字典引脚**很容易断**。创建字典类型变量时，**必须先选中字典再把键/值类型都填上**，不能留泛型（会报错）。
- 建好后**建议把泛型引脚全部先定义好**。

**两个现实用例**
1. **多人计分**：实体（玩家）→ 整数（分数）。注意**实体不能有初始值**（只能在节点图里动态改），GUID 可以。
2. **道具名字**（更现实）：**道具名字无法用节点图直接获取** → 预先用字典把「配置ID → 名字」全部填好，运行时查。前提是**所有道具都要挂上该节点图**。

### 3.4 结构体（Struct）

**为什么需要**
- 存关卡数据：一个关卡 = 名称/食材列表/起点终点/各种参数 → 装进一个结构体。
- 存装备数据：元素地牢 **49~50 把弓**，每把有名称/颜色/伤害/攻速/装填参数 → 结构体一次取全。

**定义（编辑器入口）**
- 左上角菜单 → **高级数据管理** → **创建结构体**。
- **参数上限 50 个**。
- **不能无限递归（套娃）**：结构体里再放自己 → "非法结构，不能保存"。
- 有**默认值**：自定义变量里创建结构体时默认套用定义时的默认值；什么都不连 = 用默认值。
- **拼装结构体**节点**每次调用都会创建一个新的结构体对象**。

**读写节点**
- **拆分结构体**：把所有成员一次性全拆出来。
- **修改结构体**：只改你指定的成员（可改一个，也可同时改多个）。

**导入导出（很实用）**
- 结构体**和字典都支持导出为 JSON 文件**，可在 VS Code 里编辑，**适合用 AI 批量填数值**（实例：50 把弓的数据导出 228K）。
- 讲师明确用它配合"代理/脚本"改数据。

**UI 绑定**
- **UI 现在可以直接绑定结构体里的参数值**（**以前不行**，以前只有文本框可以）；进度条的进度值等现在也能从结构体取。

**两个"必须用结构体"的场景**
1. **局内存档**（官方名，字幕误作"绝对存档"）——**必须用结构体列表**，"只存一个整数你也要用结构体"。
2. **消息队列**——近几个版本新增功能。**无等级限制**；局内存档有等级限制。

**局内存档实操（本课的干货）**
- 有**数据量限制**："加一个字符串数据量就直接变 1000 多"，量炸了运行不了；**浮点数比整数占用略小**（讲师实测）。
- **默认值不能直接改** → 必须**在初始化时拼装**。
- 玩家实体上要做**存档初始化**（如"玩家实体存档初始化"）：
  - **坑**：玩家第一次进游戏时，存档变量（**结构体列表**）**长度为 0，里面什么都没有**。
  - 做法：`实体创建时` → 判断结构体列表**长度是否为 0** → 是则用**拼接列表 + 拼装结构体**塞入开局存档（如第一关）。
  - 之后就能正常读取：`获取第 0 个` → `拆分结构体` → 把"当前关卡数"复制到玩家身上的常规变量。
- 官方补充上限（`official-guide-auxiliary-appendix.md:2145-2149`）：局内存档模板 **10**、单个模板结构体数 **100**、数据内结构体长度 **200**、单关卡局内存档大小 **10000**、试玩数据 **50**；**局内存档结构体不支持实体、实体列表、所有类型字典以及结构体**（`official-guide-concepts.md:10566`）。

### 3.5 注意事项（P3 收尾总结）

1. **迭代前必须存变量**（列表/结构体同理）。
2. **结构体嵌套多 → 获取负载高**：先把拆出来的值存到**节点图变量**做缓存，后续多次使用直接读缓存。
   - ⚠️ **局部变量不支持结构体和字典**，只能存节点图变量。
   - 反例：5 段伤害每段都从结构体现拆 → 拆 5 次；先拆一次存节点图变量再循环读 → 稳定可控。
3. **负载量级证据**：讲师优化过的对话模板，结构体拆多次**合计只有 80**；不优化的版本负载高很多；"结构体成员越多负载越高"。
4. **销毁类迭代的经典陷阱**：直接对"查询得到的实体列表"做迭代销毁 → 列表在循环中被改变，会漏删/错删（1→3→5，2 和 4 没销毁）。
   - **正解**：先存局部变量，再迭代销毁。
5. **变量变化时事件（容器类型）**：
   - 官方口径：**只有对容器类型变量的操作才触发**，非容器类型不触发。
   - **通过列表操作节点（插入/设置）改列表内部值 → 不会触发**；**只有通过「设置自定义变量」才会触发**。
   - 官方说"变化前值/变化后值没有值"——讲师实测**是有值的**，只是它是**局部变量**（不跟自定义变量绑定），仍可查询。但**按官方写法做最保险**。

**我方对照**：列表/字典节点与运行时 API 我方覆盖良好，**结构体是主要缺口**（GAP-01/02）。

## P4 · 程序架构与拆解（戀祈 / 沫沫）

主题：**如何把一个功能拆成模块**。这一节是"软件工程思维"而非引擎知识，价值最高、也最通用。

### 4.1 反面教材：逻辑与数据耦合

**案例：对话系统（按按钮切对话）**
- 初级写法 A：按钮 → 设置自定义变量（对话内容）；多段对话 → 加序号自增 + 多分支判断序号。
- 初级写法 B（从别人作品截的）：启动一个**特别长的定时器**，用**定时器的序号**去设置对话变量。
- 两者都能"跑出效果"，但问题一致：
  1. **大量重复的设置自定义变量**——明显可提炼成公共方法。
  2. **文本全部写在节点图里** = 经典的**逻辑与数据耦合**。
  3. 触发方式一改（按钮 → 踩机关 → 定时器自动推进）就要大改。
  4. **调试困难**：地图一大，渲染出问题却把其他执行部分一起弹出来。

**目标**：只要一套逻辑，未来**只加数据不改节点图**。

### 4.2 五问拆解法

一句话总结：**谁触发 / 谁处理逻辑 / 谁保存数据 / 谁来执行 / 谁需要知道**。

| 问 | 对话系统的答案 |
| --- | --- |
| **谁触发** | 玩家（按钮/碰撞箱）**或**定时器——不同触发源只是"请求推进对话" |
| **谁处理逻辑** | 单独创建一个**实体 + 其上的节点图**（对话管理器）；负责接收信号、序号自增、溢出反馈、强制关闭 |
| **谁保存数据** | 交给**触发对话的实体**（如树桩/NPC 实体）保存对话数据 |
| **谁来执行** | **对话渲染器**：拿到处理好的数据后显示文本；按样式/文本内容显示不同形态（站桩对话等） |
| **谁需要知道** | 对话结束时**触发回调**，通知持有对话的实体播放事件 |

**拆出的三段结构**：**输入 → 控制 → 输出**。

**收益**
1. 加一种触发方式（按钮/碰撞箱/选项卡）**只需加一个入口**，不碰后续逻辑。
2. 管理器只管自己，渲染器只管自己，**互不关心**。
3. **调试可快速定位**：切黑幕出问题 → 直接锁定渲染段，不用翻前后。
4. 变量改名不再引发所有文本设置出错；**低耦合**。

**类比**：这套拆法与**冯·诺依曼架构**高度相似——输入设备 ≈ 谁触发，中央控制器 ≈ 谁处理逻辑，存储器 ≈ 谁保存数据，输出设备 ≈ 谁执行。

### 4.3 通信机制：信号 vs 自定义变量事件

| | 信号 | 自定义变量（当信号用） |
| --- | --- | --- |
| 机制 | 全局广播（**一对多**） | **一对一** |
| 用法 | 发送信号 → 所有监听实体都收到并执行 | 对**指定实体**设置自定义变量 → 该实体收到"变量变化"事件 |
| 优势 | 广播天然解耦；官方范例：`触发机关` 信号 → 所有接收实体各自开门/播特效 | 可**指定接收方**；接多分支对变量名做分支，等于"用变量名当信号名" |
| 限制 | **数量有上限（讲师口径 99 个）** ⚠️ 官方文本未载此数字，待验证 | 需要在目标实体上有对应变量 |

**判据**：需要广播 → 信号；需要精准点名（"触发顾客的上菜事件"）→ 自定义变量事件。

**架构例**
- 房间机关：捡金币 → 发信号给管理房间的实体 → 该实体判断金币数量 → 再由房间实体通知门/火炬各自执行**自己身上的行为**。
- 推箱子：按按钮 → 发"游戏开始"事件 → 另一实体收到后做**深层逻辑**：**先预处理数据并保存**（网格方式存），**再由另一个专门实体/节点图生成模型**——数据与生成职责分离。

### 4.4 第二种拆法：组合式行为（怪物 / 顾客案例）

**反面**：在怪物实体上写一堆 `if/else` 判断"有没有某状态"，图又会变回大杂烩。

**正解：单位状态节点图**
- 怪物实体只保留**简单职责**：生成模型 + 处理死亡。
- 所有能力（看见玩家 / 闻到玩家 / 移动 / 伸手…）**全部写进"单位状态"里**，每个状态**绑定自己的状态节点图**。
- **单位状态变更时**可以为自己添加事件；**状态节点图能接收"单位状态结束"事件**，天然处理"获得状态/移除状态"的成对逻辑。
- 参数放怪物的**自定义变量**里；状态节点图在获得状态时修改自身参数来达成效果。
- 收益：加一个新能力 = **加一个状态**，不动主图。

**顾客案例（抽象通用行为）**
- 所有客人共享同一套行为事件：出现 → 可对话 → 上菜 → 结束离开 → 引用完离开。
- 差异化做法：**提炼公共事件**，新建顾客时**新建节点图并配置行为**，挂在顾客身上；触发时按该顾客身上的节点图执行对应逻辑。
- 触发方式仍是"设置自定义变量"（**点对点**）。

**我方对照**：架构方法论属通用工程知识（可迁移，见下）；**单位状态节点图**是缺口（GAP-03）。

## P5 · 从零开始搭建简易玩法节点图（kitakita）

主题：多人答题玩法的"准备就绪 → 游戏启动"模块化流程。**这一节把 P4 的架构思想落成具体节点**。

### 5.1 节点图的第一性原理

- 节点图**一定有分类**，但**所有节点图都从一个事件节点开始**。
- **开门例子**：玩家点界面控件/选项卡 → 节点图捕获 → 用运动器把门打开 = **完整的事件驱动逻辑**。
- **最难的其实不是逻辑，而是考虑是否完善**：
  - 门没完全打开时玩家**又点**选项卡怎么办？
  - 关门时玩家**不停点**选项卡怎么办？
  - → **必须预设玩家的各种非常规操作**。

### 5.2 模块化设计：把"游戏启动"做成信号

流程：**所有玩家就绪 → 整个游戏启动**，把"游戏启动"做成**单独信号**；先准备"启动前"的图，再调信号，再捕获信号做"启动后"的操作。

**就绪判定实现**
1. 所有界面控制**集中放在一个节点图**里（便于修改时快速定位）；**加注释**防止认不出索引。
   - 小细节：**没有页面空间组组合**时，**页面组组合索引与空间组索引相同**。
2. 玩家点"准备" → 发信号 → 收到"玩家准备"信号后把该玩家**加入"已准备玩家"实体列表**。
3. 对比 `已准备玩家列表长度` 与 **游玩人数/在场人数** → 相等即全员就绪。
   - 反复开局场景要用**在场玩家实体列表**（因为玩家可能中途退出，`对局游玩人数` 会对不上）。
4. ⚠️ **列表不能直接用相等去比较**，要取长度比。
5. **多轮复用的纪律**：准备就绪后**必须把"已准备玩家"清零**（清空列表），否则上一轮残留会污染下一轮。同理，所有可复用的图在轮次结束都要清空遗留信息。
6. 发"准备就绪"信号。

**超时兜底（必做）**
- 玩家迟迟不准备 → 用**定时器/全局计时器**超时后**强制进入后续流程**。
- 实现：全局计时器触发时 → 判断计时器名称是否是自己要的那个（**同一实体上可能有多个计时器，每个含"计时器触发时"的图都会捕获该事件**）→ 执行强制开始。

**玩家中途退出检测**
- **只有关卡实体能捕获**"实体移除/销毁"事件 → 玩家退出检测图**挂在关卡实体上**。
- 但该事件**看不出是哪个玩家退出** → 只能在别的实体上用自定义变量**先存好当前在场玩家**，再比对找出消失的那个（"好像只有这个笨办法"）。

### 5.3 定时器 vs 全局计时器（关键区分）

| | 定时器 | 全局计时器 |
| --- | --- | --- |
| 归属 | 必须指定**目标实体**；"定时器触发时"必须挂在该实体上 | 有**全局计时器管理工具**，需先**注册**才能用 |
| 循环 | ✅ **可以循环触发**（如每 2 秒一次） | |
| 删除 | 可直接删 | |
| 改时长 | ❌ 不能随意延长几秒 | ✅ **可以修改时长** |
| **UI 显示** | ❌ | ✅ **只有全局计时器能在玩家 UI 上显示倒计时** |

**判据**：需要**给玩家看**的时间量（准备倒计时）→ 必须用全局计时器；只是内部方便 → 定时器。
**命名纪律**：定时器/全局计时器**必须命名清楚**，且"触发时"**必须加分支判断名称**。

### 5.4 实体与组件规则

- **通用组件**：任何要在实体上用的东西（**运动器 / 物件镜头 / 自定义变量 / 单位状态**…）都要**添加通用组件**，**不添加会在日志里报错**。
  - 组件面板里勾选"关卡实体刚创建就启动计时器"这类选项 = 相当于自动生成启动节点。
- **节点图变量不跨实例**：同一个实体模板上挂一张图，在关卡里摆两个该实体，**两者的节点图变量不互通**（有人犯过这个错）。

### 5.5 初始化时机

- **关卡初始化** / **实体创建时**能做很多初始化：如 9×9 数独 → 需要长度 **81** 的列表存方格，就在实体创建时用**拼接**拼出一个长度 81、全 0 的列表。

### 5.6 答题玩法后半段

- 监听"玩家答题"信号做处理——**逻辑与准备就绪高度共通**：要么全员已准备/全员已答完，要么超时强制推进。
- **结果分组**：用实体列表记「答对玩家」「答错玩家」；**超时玩家不用单独放**，因为超时是全局触发的，后续**用「列表是否包含该值」**逐玩家判断归类即可。
- 判定"全员答完"：答对人数 + 答错人数 = 在场玩家数。
- **用逻辑运算替代双分支**（讲师强烈推荐）：如"既不在答对列表、也不在答错列表"用逻辑与/或组合一次算完；且**逻辑运算比加减乘快、负载更小**。

### 5.7 负载优化（本课最实用的一段）

**负载三大来源与对策**

| 来源 | 对策 |
| --- | --- |
| **有限循环次数太多** | 只能从**算法**上减少循环次数（"很困难"） |
| **设置自定义变量次数过多** | ① 开一个定时器把写入**拆到不同定时器/不同 tick** 处理；② 减少对实体自定义变量的操作 |
| 列表迭代取动态列表 | 先存变量再迭代 |

**负载排序（写入成本）**
```
设置局部变量（最小） < 设置节点图变量（中） < 设置自定义变量（最大，必须写入实体）
```
讲师补充：节点图变量与局部变量差距**没那么大**；但**写实体自定义变量**成本明显更大，频繁写会超载。

**实测数据**：讲师优化过的对话模板优化版负载只有 **500 多**；其中拆结构体几次合计 **80**。

### 5.8 节点图类型全景与选用（本节含官方权威口径）

**官方分类**（`docs/ui-tutorial/official-guide-concepts.md:6382-6429`）

| 运行端 | 节点图类型 | 挂载对象 / 生命周期 |
| --- | --- | --- |
| **服务端** | 实体节点图 | 挂实体；实体销毁则图失效 |
| **服务端** | 单位状态节点图 | 挂**单位状态**；状态移除则图失效。例：火环持续攻击附近敌人 |
| **服务端** | 职业节点图 | 挂**职业配置**；可挂玩家或角色实体；职业切换即失效/生效 |
| **服务端** | 道具节点图 | 挂**道具配置**；实现道具自身逻辑 |
| **客户端** | 技能节点图 | 自定义技能运行到挂载时点开始运行 |
| **客户端** | 造物状态节点图 | 复杂造物的行为模式 |
| **客户端** | 本地过滤器节点图 | 组件内使用；**布尔型**固定返回 是/否，**整数型**返回整数 |

**讲师选用建议**
- **推荐多用「角色技能节点图」（客户端）**：**运行速度很快，基本不会超载**（"目前只见过一次客户端超载"）。
- 服务端也能通过节点**释放技能实例/指定技能**，从而间接触发客户端图。
- 客户端图的用武之地不止 RPG 技能：**五子棋落子后横/竖/斜判五连**是一段循环次数极多的过程，适合放在**角色技能节点图**里判定胜负。
- **状态节点图**的价值：**可动态附着**——"捡到所有钥匙后才让门有开门逻辑"，用施加/移除状态来**动态增删一个节点图**。
- **道具节点图**：消耗品（RPG 血瓶/治疗苹果）只能挂在道具上，**不能从实体节点图挂上去**。
- **调试限制（重要）**：**客户端图的日志只在你自己的客户端**，看不到其他玩家的客户端图输出（隐私保护）。所以调试客户端图**只能用你自己的角色去释放技能**。

### 5.9 布尔过滤器 + 选项卡（本课收官实例）

- 需求：门**捡到钥匙之前不能开门**。
- 做法（优于用 P4 的 if 判断）：
  1. 门实体上加**布尔类型自定义变量**「允许开门」，初始为"否"。
  2. 选项卡组件配置**本地过滤器节点图（布尔型）**：`查询自身实体` → `获取自身实体自定义变量[允许开门]` → 作为输出。
  3. 捡到钥匙后把该变量改为"是" → **选项卡自动浮现**。
- 官方印证（`official-guide-concepts.md:3063`）：**"每个选项卡支持通过本地过滤器判定对每个玩家是否显示"**——与讲师用法完全一致。

### 5.10 工程卫生（讲师反复强调）

- 所有界面控件**集中一张图**；节点图**都要命名**（简洁通俗易懂）。
- **建文件夹按功能分图**（如"游戏逻辑"文件夹）。
- **记得把线理清楚**，"不然到时候太乱了你自己看起来也麻烦"。
- 循环完成后**清空列表/节点图变量**，为下一轮复用做准备。

## 可迁移清单（该领域做法 → 通用工程原则）

| 视频里的做法 | 通用原则 |
| --- | --- |
| 对话系统拆成 输入/控制/输出 三段，文本移出节点图 | **逻辑与数据分离**；一份逻辑 + 增量数据 |
| 五问法（谁触发/谁处理/谁保存/谁执行/谁需要知道） | 模块化拆解可直接复用的五问清单；与冯·诺依曼架构同构 |
| 信号（广播）vs 自定义变量事件（点对点） | **按通信拓扑选机制**，不是按习惯选 |
| 单位状态节点图挂能力，主图只留生成+死亡 | **状态/能力用组合而非 if-else 堆叠**（组合优于继承/分支） |
| 顾客/怪物共享公共事件 + 各自节点图 | **模板方法**：公共骨架 + 差异化实现 |
| 迭代前先存变量；销毁先快照 | **迭代中不要改被迭代的集合**（ConcurrentModification 同族坑） |
| 容器变化事件只认"设置自定义变量"节点 | **副作用的触发面看实现入口，不看直觉** |
| 准备就绪后清零、轮次结束清空 | **可复用模块必须显式复位**（否则上一轮状态泄漏） |
| 超时兜底、门重复点击、玩家中途退出 | **穷举异常路径**；正常路径只是冰山一角 |
| 负载排序（局部 < 节点图 < 自定义变量） | **按成本给写入路径排序**，热点路径选最便宜的载体 |
