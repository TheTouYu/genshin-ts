### 驱动方式（负载铁律违例点）

我们：**7 张图全部 When Timer 驱动**；错峰定时器 0.01~0.09s（faceTurnTimes 九槽）+ orbit2 0.16~0.24s

## 二、官方范例拆解（1073741913，读图证据）

### 客户端图 1082130436「指令->旋转魔方块实体+旋转信息_运动魔方块附加单位状态」（191 节点，type=20010）

on('start') 单入口执行全部：
1. **指令读取+解析**：读玩家自定义变量"指令"（手段 3 变量共享）→ 多分支链解析
   F/B/R/L/U/D/E/M/S + '/2 变体 + f/b/r 双层 + x/y/z 整体（9+9+9+6+6+6+6 组合）→
   确定旋转角度(90/-90/180)/旋转轴向(x,y,z)/旋转层数(1/2/3)/范围中心相对位置（字面量表）
2. **还原检测**：相等数值个数==3 → 是否还原（结算判定也在客户端）
3. **层归属判断**：遍历实体列表（单位标签 1073741825）→ 读每块"位置"变量 → 拆分三维向量 →
   6 个比较+逻辑与（x/y/z 三轴各 小于中心+半层 且 大于中心-半层）
4. **旋转计算**：三维向量旋转 ×2（向前/向上向量）+ 拆分/乘法/创建向量（位置旋转）+
   数据类型转换 807/801（四舍五入取整）
5. **busy 锁**：添加单位状态 1077936131（只加旋转层内的块——客户端本地，零服务器负载）
6. **信号回传**（手段 4）：正常 n=115（6 参数：旋转时长/旋转角度/是否还原/魔方整体向前向量/
   魔方整体向上向量/指令异常=0）；异常 n=116（指令不在表内时，指令异常=1）

### 服务端「魔方块-旋转」图（1073741835，30 节点，挂每块实体，f8=5..30）

监听"旋转信号" → Query Unit Status(busy) → List Iteration Loop 遍历变量名表
["位置","向前向量","向上向量"]：Get Custom Variable → 3D Vector Rotation（信号参数轴/角度）→
复合:三维向量取整 → Set Custom Variable 写回 → 检查"魔方动画"开关 →
**Add Basic Target-Oriented Rotation-Based Motion Device（每块仅 1 个设备，时长=信号 Float）**；
When Basic Motion Device Stops → Remove Unit Status（解锁）。

另 2 张监听图：玩家-界面（UI 响应）、角色-魔方块创建（镜头/悬浮页）。

## 三、候选迁移清单（按预期收益排序）

### A. 旋转数学计算迁移客户端（指令解析+层判断+向量旋转+取整）【主线】
- 迁移内容：turn 图 logic_apply_face 嵌套循环（051b 系链，单次面转 ~2000-3000 负载）→
  客户端图照官方 191 节点模式实现
- 服务端保留：监听信号 → 写回 3 变量/块（权威状态）→ 动画设备
- 预期收益：turn 图数学负载 →0；单次面转 5450 → ~2500（-54%）
- 前置工程：客户端图读每块"位置"变量（手段 3 已闭）+ 信号参数扩展（float/vec3 或 int 编码）+
  技能装配链（20002 手段 1 可用；20010 手段 2 需操控状态未闭环——**建议走 20002**）
- 风险：客户端图无定时器，一次 start 全算完（官方 1438 帧/次，客户端无 f6=不计负载，可行）；
  客户端执行时序未闭合（施放 tick 双执行）需在协议上防重（busy 锁/序号）

### B. 动画调度事件驱动化 + 单设备化【纯服务端，不依赖客户端图】
- 迁移内容：砍 0.01~0.09s 错峰定时器九槽 + orbit2 槽 → 信号/事件直达 Add 设备；
  motion_spin_block+motion_orbit_segment 两设备/块 → 学官方 Target-Oriented 单设备/块
  （官方用"取整后向量+时长"一个设备完成自转+公转）
- 预期收益：1e03 系两链（765 次×~26 载=38820 总载）至少减半；visual 图大部分 tick 消失
- 风险：Target-Oriented 设备语义是否覆盖"绕魔方中心公转 90°"（官方日志证明可，需我们图上复刻验证）；
  动画视觉不回归（块间错峰是我们为体感做的，官方无错峰也正常）
- **独立性：可先行单独一轮闭环，为 A 铺路**

### C. view_prepare_visual_order 重排下线/迁移
- 现状：每次转动后 54 帧数据链+Finite Loop 7 重排（1e08 系 5355 次 8407 载）
- 官方无此环节。需先弄清我们为什么需要（贴纸朝向/渲染顺序？）再决定砍或迁

### D. solver 求解器——不迁移（结论）
- 求解结果必须服务端权威；负载占比 <2%。A/B 落地后整转间隔 7-10s 可收紧（体验收益）

### E. busy 锁客户端化（addUnitStatus）
- 跟随 A 一起做（官方模式），单独做收益小

## 四、第 1 轮提案（交用户确认）

**推荐：B 先行（动画调度事件驱动化，最小切片=单次面转的动画链）**

理由：
1. 纯服务端改动，现有编译/注入/回读链路全复用，一轮可完整闭环（改动→核验→实测→perf 对比）
2. 直接消除负载铁律违例（0.0x s 错峰定时器群）
3. 为 A 铺路：A 迁移后服务端动画链就是 B 的产物，避免 A 做完又重构动画
4. 可归因性强：只动动画调度，数学/求解不动，perf 差异直接归因

若用户倾向先探索 A（客户端计算主线），最小切片 = 客户端图算"单块位置旋转"（硬编码 1 块，
验证 指令下发→客户端数学→信号回传→服务端写回 全链），再扩 26 块。
