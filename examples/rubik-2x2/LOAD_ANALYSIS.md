## 3. 根因分类

### 3.1 写法问题（→ 纳入质量规范）

- **F1 循环 off-by-one**：`f.finiteLoop(0, N)` **终点包含 N**（迭代 0..N）。
  宿主 `for (i=0; i<N; i++)` 由编译器转成 `finiteLoop(0, N-1)`。我在 do_move 里写了 `f.finiteLoop(0n, CORNER_COUNT=8n)` →
  迭代 0..8 共 **9 次**（第 9 次访问越界 blocks[8] 空实体）。已核实 GIA wire：finite_loop end=8、比较 `<= 8`。
  **规范**：复合内 manual `f.finiteLoop(0, N)` 终点必须写 N-1（与编译器宿主 for 语义一致）。

- **F3 逻辑层多消费者重求值**：read_slot 输出的 piece/twist 被 **2 个** set_or_add（tempP/tempT）消费 →
  整条 read 链（tblFrom 查询 + read_corner 的 cornerPos/cornerOrient 查询）**每个消费点重新求值**，
  tblFrom 实际读取 8 次/turn（应为 4）。这是已闭合的"引擎惰性求值"pitfall，我的复合违反了
  **数据引脚单消费者**原则。
  **规范**：数据引脚若被 ≥2 处消费，先 `set_or_add` 物化到临时变量/字典再复用，禁止直连多消费。

- **F4 逻辑层设计成本**：dict 图变量读取成本高（GetNodeGraphVariable 整字典载荷，~20 负载/次）。
  apply_move ~30 次 dict 读/turn → ~3000+ 负载（占新增 3852 的绝大部分）。
  **规范**：受限环境里 dict 读取很贵——状态更新每 turn 每字典**只读一次并物化**，避免重复拉整字典；
  后续可用 packed int / 更紧凑状态表示。

### 3.2 疑似引擎/编译器问题（登记待受控实验确认）

- **F2 复合内 finiteLoop 循环值多消费 → 循环控制错乱/重启**：
  现象：do_move 的有限循环执行 9 次后**计数器重置重跑**（循环值序列 `[1..9, 1..7]`，rec1/rec41 均如此=系统性），
  导致视觉部分 2×。循环控制帧显示退出检查读到**过期值**（`<=8` 比较在 i=9 时仍判真）。
  差异对照：
  - 已验证复合循环 `verify/composite-family/finite-loop.ts`：循环值 `i` **只用 1 次** → 正常（8 次打印）。
  - 旧版**宿主**循环（编译器生成）：循环值 `i` 被 turn_block 和 orbit_scheduler **2 次消费** → 正常（4 spin）。
  - 我的**复合**循环：循环值 `i` 被 2 次消费 → **重启**。
  强指向：**复合内 manual finiteLoop 的循环值引脚被多消费时，惰性求值污染循环控制**（编译器宿主
  循环可能把循环值物化，manual 复合没有）。需最小受控实验确认（复合 + 循环 + 循环值双消费）。
  处置：登记待确认；无论是否编译器 bug，写法上应避免循环值多消费（物化 i 到临时变量）。

## 4. 优化方向（待用户拍板后实施）

1. **修 F1+F2（循环）**：end=N-1 + 循环值物化单消费 → 视觉 6007→~3000、控制 736→~370，省 ~3300。
2. **修 F3（重求值）**：read/write_slot 数据引脚物化单消费 → 逻辑层 3852→~1500-2000。
3. **修 F4（dict 成本）**：apply_move 每字典只读一次；或改为"需要时才同步逻辑状态"（如仅在胜利判定/
   求解器请求时），把 ~3000 从每次转动移除。
4. **基线问题**：即便修完，单次转动仍在 ~5000-6000（视觉 ~3000 + 逻辑 ~1500-2000 + 结算 ~400），
   点击瞬间突发仍超 2000/s 预算。需评估：①把逻辑更新/结算移出点击事件（分散/延迟）②是否分图
   （信号跨图，可能分摊预算）③视觉 turn_check 的 dict 读（axes/blocks）是否可减。
5. **实测节奏**：每修一项 → 编译 → 注入 → 用户游戏实测负载值 → 确认降幅后再动下一项。
