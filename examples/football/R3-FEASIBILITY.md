# R3 可行性调研：真实足球全套玩法能否落在「客户端计算链路」上

> doc-type: R · status: draft · updated: 2026-10-24
> 状态：**调研（未开工）** · 2026-10-24 · 依据：v3 客户端链路已实测跑通（15Hz、987 拍/68s、dup=0）
> 读者：决定「接不接物理内核」的人
> 结论先行：**能承担，但有 4 条硬约束 + 3 个必须先验的探针**；先做探针再写物理，能省掉一轮返工。

## 〇、先说约束（已核实，不是猜测）

| 约束 | 事实 | 影响 |
|---|---|---|
| 拍频 15Hz（dt=66.7ms） | 实测 987 拍 / 68s，CD 0.03 下仍 15/s ⇒ **上限是 AI 客户端拍** | 25m/s 的球每拍走 **1.67m** ⇒ 判定半径 0.5m 的区必漏（隧穿） |
| 执行权威 = **单客户端** | 双人实测：`kit-dup`=0，跑在哪个客户端**不可控**（有一轮跑在客机） | 权威客户端卡顿/掉线 = 全队球卡住；无身份机制可接管 |
| `creation_skill` 无输入原语 | `getPlayerMovementInput` / `getPlayerClientInputDeviceType` 均 **不可用**（mode 表白名单实测） | 玩家意图只能用**位置差分**估计（15Hz），或另开 20002 角色图读输入 |
| 无 `squareRootFunction` | 但 `_3dVectorModuloOperation` = 向量长度（内部含 sqrt） | 距离/速度可用；纯标量 sqrt 要绕成向量长度 |

可用原语（`creation_skill` 白名单实测 ✓）：`_3dVector{Subtraction,Addition,DotProduct,CrossProduct,Normalization,ModuloOperation}`、
`absoluteValueOperation`、`arctangentFunction`、`getEntityLocation`、`getEntityRotation`、
`filterEntityListWithinSphericalRange`、`getEntityListByUnitTag`、`triggerSphericalHitboxAtSpecificLocation`、
`getAllEntitiesWithinTheCollisionTrigger`、`complexCreationTeleport`、`complexCreationDirectedMovement`、
`creationTurnsToFaceSetDirection`、`enumerationMatch`。
服务端权威侧：`whenOnHitDetectionIsTriggered`（组件 type12，低频权威兜底）、`distanceBetweenTwoCoordinatePoints`、运动器。

## 一、架构分层（谁算什么）

```
客户端（每拍 15Hz，权威客户端一人）
  ① 采样：玩家位置/朝向（位置差分得速度）
  ② 球物理：位置/速度/自旋积分 + 碰撞（地面/边界/人）
  ③ 判定：带球/踢/接/拦截/门将（纯几何，见 §二）
  ④ 写：自持寄存器（技能变量）+ teleport 球位置 + 回传 kit_state
服务端（低频、权威、记账）
  ⑤ 收票：tick 单调去重 → 写镜像（球位置/速度/状态）
  ⑥ 运动器插值：把 15Hz 的跳变渲染成连续运动（v5 的 fb_pred 同款）
  ⑦ 权威兜底：球门命中区（type12 事件）判进球/出界；比分/球权记账
```

**为什么球用 teleport 而不是"施力"**：客户端没有"给实体加力"的节点（运动器只有服务端有）。
球的位置只能客户端每拍 `complexCreationTeleport`，服务端再用运动器做视觉平滑
（"客户端算、服务端演"——和 v5 的预测插值同一套）。

## 二、七个玩法的算法（都用可用原语，逐条给判据）

### 1. 带球（玩家贴近 → 给球一个受控向量）

- **玩家速度估计**：`v = (p_t − p_{t−1}) / dt`，`dt = Δtick / 15`；EMA 平滑 `v' = 0.7v' + 0.3v`（存自持槽）。
- **持球维持**：球在玩家 `1.6m` 内即"控球"；目标点 = `p_player + facing·0.9m + v·0.15`（提前量）。
- **追随力（临界阻尼弹簧）**：`a = k(target − p_ball) − c·v_ball`，取 `k=180, c=2√k≈26.8`（不振荡）。
  单拍位移上限 `|a|·dt²` 钳制 → 球速不会超过 `~9m/s`（"精准控制"= 有限加速度，不是瞬移）。
- **判据**：玩家静止时球停在脚前 ±0.25m；玩家 5.5m/s 冲刺时球贴脚不掉（偏差 <0.6m）。

### 2. 踢球 / 定点射门（给向量 + 力 + 旋转）

- 触发：球在玩家前方 `1.2m`、夹角 <60°、按键（或条件）——**服务端按键不可读** ⇒ 用"玩家速度 >3m/s 且朝球"或由 20002 图读输入再投递（后置项）。
- 出球：`v_ball = dir·speed + v_player·0.6`（`speed` 3~28 视力度）、`spin = cross(dir, up)·spinRate`。
- **弧线（马格努斯）**：每拍 `a_magnus = C·cross(spin, v_ball)`，`C≈0.004`（按 15Hz 标定）。
- 射门：`dir` 指向门框内目标点 + 小幅随机（扑救不可完全预判）；落点用**闭式抛物线**给到门线时间。
- 判据：30m 射门飞行 ≤1.1s，落点偏差 ≤0.4m（无风）。

### 3. 精准传球（**核心算法**）

传球不是"朝队友踢"，而是"朝**队友将要在的位置**踢"：

```
t̂_flight = |p_teammate − p_ball| / speed          # 初估飞行时间
target    = p_teammate + v_teammate · t̂_flight     # 提前量（一步迭代即够，15Hz 下误差小）
t_flight  = |target − p_ball| / speed              # 复算
feasible  = |t_flight − t̂_arrive_teammate| ≤ 0.35s  ∧  |target − p_teammate| ≤ 2.0m
            ∧ ∀enemy: |enemy − segment(ball→target)| ≥ 1.5m
```
- `feasible=false` 时自动降级：改踢"安全点"（向边路/回传），或在 UI 上标记"风险传球"。
- 传球时把 `target / t_flight / 球速` 写进**任务抽屉**（服务端实体变量）⇒ 队友客户端可预读并提前启动。

### 4. 接球（能接 / 漏）

每拍判：`d = |p_ball − p_teammate|`、`v_ball`、相对速度 `v_rel = dot(v_ball, p_teammate−p_ball 归一化)`：
- `d < 1.2m ∧ |v_ball| < 14m/s` → **接住**（球速归零 + 控球权转移）
- `d < 1.2m ∧ |v_ball| ≥ 14m/s` → **卸球**（球速 ×0.35，方向偏转 ≤25°），成功率随球员属性（先固定 0.7）
- `d ≥ 1.2m` → 漏（继续飞行）
- **可接性预报**（在球飞行途中就能告诉 UI/队友）：用 §3 的 `t_flight` 与队友实际到点时间比较，差 >0.35s 就标"接不到"。

### 5. 拦截（敌方中途断球）

**线段-球体**判据（不是点判据，防隧穿）：

```
seg   = p_ball_prev → p_ball_now            # 本拍位移段
d     = |(enemy − p_ball_prev) × normalize(seg)|
t_hit = dot(enemy − p_ball_prev, normalize(seg)) / |seg|   # 0..1 在段内
intercept = d < 0.8m ∧ 0 ≤ t_hit ≤ 1 ∧ 反应窗(≥0.2s)可用
```
- 命中：球速 = 敌方朝向·4m/s（捅球）或沿法线反弹 ×0.5；球权转给该玩家，记 `state=LOOSE`。
- 反应窗：敌方"上一拍位置"到球段的距离，也要满足 → 防止"瞬移式拦截"。

### 6. 守门员（接住 / 击出 / 漏）

球过门线时刻 `t_goal = (x_goal − x_ball)/v_x`，预测落点 `p_pred = p_ball + v_ball·t_goal + ½g·t_goal²`：

| 条件 | 结果 |
|---|---|
| `|p_pred − p_keeper| ≤ 0.8m ∧ |v| < 15` | **接住**（球停在手上，球权给守门方） |
| `|p_pred − p_keeper| ≤ 2.5m ∧ |v| ≥ 15` | **击出**（反弹：`v' = −0.4v + 侧向 0.3·rand`，附 `state=SAVED`） |
| 其它 | **漏球**（继续飞，服务端命中区判进球） |
- 守门员"手"的覆盖半径 2.5m 是**可调参数**（AI 难度旋钮）；反应延迟用"连续 2 拍都满足才出手"模拟。

### 7. 状态机（互相可转化）

```
DRIBBLE ──踢──▶ FLIGHT(pass/shoot) ──到达队友──▶ DRIBBLE
   │                    │  ├─被拦截──▶ LOOSE ──最近者捡起──▶ DRIBBLE
   │                    │  ├─守门员接/击──▶ SAVED → 门球/角球
   │                    │  └─越界──▶ OUT → 掷界外/门球
   │被抢断──▶ LOOSE      └─进球门区──▶ GOAL（服务端权威事件）
   └─球滚出控球半径──▶ LOOSE
```
- 每态都有 `enter/exit` 与"看门狗"（某态停留超时强制回 LOOSE），防止单客户端掉线导致球卡死在 FLIGHT。

|---|---|---|---|---|

## 四、三个探针（各 20 分钟内可做，先做再写物理）

- **E1 隧穿探针**：球以 25m/s 直线飞过一个人形判定区（半径 0.5m / 0.8m 两档），比较"点判据 vs 线段判据"的命中率。
  判据：线段判据命中 ≥99%，点判据 <70%。
- **E2 插值探针**：客户端 15Hz teleport 一个球，服务端运动器插值渲染，用日志/录屏确认"看得见连续运动"且无过冲。
- **E3 地形探针**：客户端 teleport 球到若干已知高度，读回实际位置 → 确认球是否被地形抬升/卡住；决定是否需要地形高度查询。

## 五、分阶段路线（每阶段都能独立验收）

| 阶段 | 内容 | 验收（行为层） |
|---|---|---|
| **R3-a** | 球物理（重力/摩擦/反弹）+ 带球弹簧 + 踢球/射门 | 带球贴脚不掉、射门能进门、球落地反弹衰减合理 |
| **R3-b** | 传球（提前量算法）+ 接球（接/卸/漏） | 30 次传球成功率 ≥85%、"能接/漏"预报与结果一致 |
| **R3-c** | 拦截（线段判据）+ 守门员（接/击/漏） | 拦截成功率随难度可调；守门员三态各出现 ≥10 次且分类正确 |
| **R3-d** | 多人（球权、掉线看门狗、双人同图） | 双人 5 分钟无球卡死、无 dupe tick、球权切换正确 |

## 六、结论

- **能承担**：所有判定都是几何计算，客户端白名单里的向量/距离/线段能力足够；15Hz 拍频 + 自持寄存器 + 信号回传已实测跑通。
- **最大的两个未知**不在玩法算法，而在 **15Hz 隧穿（R1）** 与 **单客户端权威的健壮性（R2）**——所以先做 E1/E2/E3 探针，再写物理内核。
- 与"手感基线 = 地图足球_2"的关系：算法能保证**行为正确**（球不乱飞、传球有提前量、门将分三态），
  但**手感**要看 15Hz + 插值后的观感，这条只有真机能判。
