## 3. 阻碍清单（按浪费的时间排序，全部带证据）

1. **daemon 帧停滞（最大黑洞，~6 轮 × 3 分钟）**
   `ys-capture latest` 两次 grab 的 `src` 是同一个 `f-000178583.rgb`（seq 178583→178601 但 rgb 没换）。
   抓到旧帧 ⇒ OCR 行位置旧 ⇒ 点边界 ⇒ 正文不变 ⇒ 下一帧还是旧的。
   症状伪装成「渲染慢」，导致我连续 6 轮加长 sleep（v5→v16）全部无效。

2. **坐标系没先钉死（~3 轮）**
   一开始按逻辑坐标（1707×960）点击，首次点击把第 2 行点成第 1 行。
   真相：`ys-pointer-click` 用**帧坐标（2560×1440）**。一条 `xdotool getdisplaygeometry` 就能确认。

3. **回顶距离 10 倍低估（v1~v11 全部重跑）**
   按「几百格」估算，实际要 1300+ 格 ⇒ 前 6 版从错误起点开始，坐标全废。

4. **行位置判据用整块 md5 + 固定 sleep（~2 轮）**
   平滑滚动 + 帧停滞下「连续两帧 md5 相同」会误判稳定；改用「OCR 行位置双测 + 先变化后稳定」。

5. **ys-text 默认 row_merge 把 `W`/`S`/`新` 并进标题行（1 轮）**
   行中心偏移 → 点邻行。必须 `--no-row-merge`。

6. **点击成功率只有 25~50%，却最后才做单变量实验**
   probe3/probe5/probe6 都是第 8 轮之后才做的；如果一开始就做，能直接设计对。

7. **条目数低估（假设 ~30 条，实际 138 条）**
   每批时间按 30 条规划，导致频繁 BUDGET-EXIT、批次切分反复。

8. **`ys-pointer-click --text` 全等匹配在这类列表上不可用**
   列表 OCR 读 `关于风车·`、工具内部读 `关于风车…` ⇒ **rc=4 占 19/37（51%）**。

## 4. 下一步（建议按此顺序）

1. **先修抓帧通道**：给 `ys-capture latest` 加「seq + src 都不动 ⇒ 重抓/换 ys-observe」的判据；
   这是所有后续自动化的地基。
2. **每条点击前重建定位**（不要缓存坐标），点击后用正文标题断言，断言不过就换 y（±30 内）。
3. 若仍不稳，**给 ys-find 加模糊匹配**（去尾部省略号/标点后前缀匹配），改用 `--text` 点击。
4. 采集完成后用 `assemble03.py`（未写）按 `frames*/slide-*.png` + 正文 OCR 组装，
