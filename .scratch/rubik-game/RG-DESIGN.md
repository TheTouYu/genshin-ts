## 1. 玩法设计（残局闯关）

### 1.1 核心循环
进选关面板 → 选档位（3/5/8/12 步残局）→ 系统按档位打乱（记录随机 move 序列，par=打乱步数）→ 玩家转动复原 → 步数/par 实时反馈 → 复原判定 → 星级结算 → 解锁下一档/重开/回选关。

### 1.2 档位与星级
| 档位 | 打乱步数=par | 解锁条件 |
|---|---|---|
| 新手 | 3 | 默认开放 |
| 进阶 | 5 | 新手任意★通关 |
| 大师 | 8 | 进阶任意★通关 |
| 宗师 | 12 | 大师任意★通关 |

星级：**3★ ≤par 步；2★ ≤par+3 步；1★ 完成复原**。星级与最佳步数持久化（地图变量）。

### 1.3 提示按钮
solver 改造为**单步提示**：点击 → 若当前局面已在 solver 可解路径上，给出并执行下一步正确转动（金色按钮，计 hint_used，不影响步数判定但结算显示"用了提示"）。

### 1.4 自由模式
无 par 压力：自由打乱（随机 N 步）/手动重置/自动还原演示（1899 原 solver 全程能力保留入口）。

### 1.5 状态机与数据流
```
UI 事件（玩家节点图）──信号──▶ 对局状态机图（挂关卡实体/控制器）
                                │ 打乱/计步/判定/结算/解锁
                                ▼
                          转动执行图（1899 turn 图迁移，零改动原则）
                                ▲
solver 图（迁移+提示改造）──信号──┘
```
- 状态：IDLE → SELECTING(选关面板) → SCRAMBLING(打乱动画) → PLAYING → SETTLED(结算面板)。
- 打乱序列生成：对局图内随机选 move（避免连续同面互逆），逐步经转动通道执行并记录 → par 已知。
- 胜利判定：复用 1899 solver 状态判定（op7 最终完成语义核验后复用或同构重写，挂对局图）。
- **零轮询**：所有转移事件驱动（UI 事件/转动完成回调/判定完成）。

## 2. UI 设计 v3（悬浮交互页体系）

### 2.1 界面清单
| 界面 | 形态 | 内容 |
|---|---|---|
| ① 选关主菜单 | 悬浮交互页「残局挑战」 | 页签×3（闯关/自由模式/玩法说明）；闯关页=单选项视窗（档位列表，唤起时按解锁状态初始化）+「开始挑战」自定义按钮（**关联监听单选项**——点击时列表选中项回传=所选档）；说明页=文本视窗；单人暂停✓ |
| ② 对局 HUD | 界面布局**常驻层** | 顶部：关卡名文本框（插值）+步数文本框（插值，超 par `<color=red>`）+官方进度条（moves/par）+官方计时器控件（正计时）；底部：18 转动按钮（自定义按钮+素材库皮肤，六面色系）+金色提示+重开+菜单（呼出①） |
| ③ 结算 | 悬浮交互页「结算」 | 文本视窗：星级染色文本+用步/par+用时+是否用提示；按钮组：再来一局/下一关/返回选关（关闭③唤起①）；单人暂停✓ |

**设计决策（对局按钮放常驻层，非悬浮交互页内）**：官方明示悬浮交互页"断线重连等异常行为不恢复"+模态语义；高频转动操作需要常驻不可断层。此拆分待用户认可后固化。

### 2.2 服务端节点（官方已实证，docs/ui-tutorial/）
- 执行：`切换当前界面布局`/`激活控件组库内界面控件组`/`移除控件组库内界面控件组`/`设置界面控件(组)状态`（开启=可见+逻辑运行；关闭=不可见+逻辑不运行+重置；隐藏=不可见+逻辑运行）
- **悬浮交互页族**：`唤起悬浮交互页`（玩家实体+页索引+初始化列表数据字典）/`关闭悬浮交互页`/`更新悬浮交互页列表数据`（列表索引+整数列表+默认选中首项）
- 事件：`界面控件组触发时`（常驻层交互按钮族；玩家节点图专属）；`悬浮交互页操作触发时`（页签选中/按钮确认/关闭按钮；出参：页索引+交互项索引+列表索引⇄列表选中项一一对应）
- FAQ 红线：UI 事件**只有玩家节点图能收**，图需挂玩家身上；文本框支持 `\n` 与 `<color=xx>文本</color>`；文本插值=自定义变量/形式变量，变量变化实时刷新

### 2.3 素材体系（UI 美术）
- 素材库皮肤：自定义按钮/开关/悬浮交互页/页签/图片控件可引用；素材组支持遮罩
- 转动按钮六面色系素材（U白/D黄/F绿/B蓝/L橙/R红——与魔方面色对应）
- 提示按钮金色系；中性灰系（重开/菜单）
- 初版允许 from-official 克隆官方皮肤再调色（ui 模块 L2 通道）

### 2.4 变量
玩家变量：`moves` `par` `level` `stars` `hint_used`（HUD 插值+进度条绑定）。地图变量：各档最佳步数/解锁状态/累计星数。形式变量=二阶优化（同模板多处引用不同绑定时才需要，初版不用）。

## 4. 性能预算与图规划

**红线**（PROGRESS 实证）：单图 gameNodeCount ≤2000；单记录 <3000 帧；零高频轮询/常驻定时器（事件驱动）；Multiple Branches ≤10 case+default；solveBuf ≤100；全 0 int_list 需哨兵非零位；finiteLoop 闭区间用 N-1；分支内先写回再读回；定时器延时两位小数且唯一。

**新图清单**（每图独立算两笔账：节点+帧）：
| 图 | 挂载 | 职责 | 预算 |
|---|---|---|---|
| 玩家输入图 | 玩家 | UI 事件接收→信号转发 | ≤500 |
| 对局状态机图 | 关卡实体/控制器 | 选档/打乱/计步/判定/结算/解锁 | ≤1500 |
| 胜利动画图 | 控制器 | 结算触发的一次性动画 | ≤800 |

**turn 图零改动原则**：1899 turn 图预算近满（~1988/2000），不内部加节点。输入通道两方案（实现期读图核验后定）：
- 方案 A（首选）：玩家输入图复用 **solver 驱动转动的同一信号通道**（solver 能命令转动→该通道即程序化转动入口）→ turn 图零改动
- 方案 B（兜底）：turn 图入口手术——tabBar 事件节点替换为信号事件节点（同数替换不加量，预算风险小但需改满图）
