# 17 — 结构体资产 CLI：创建 / 查询 / 修改 + 变量类型落地

**What to build:** `gsts assets:structs` 命令族 —— 让创作者能用命令行**建、列、查、改**结构体
（含局内存档结构体），并把 **struct / struct_list** 接进变量系统，使变量 CLI 能读写结构体类型的变量。

**Blocked by:** ~~16（wire 结论）~~ ✅ **已解除** —— 16 的取证已闭合
（`docs/game-engine-knowledge/struct-assets.md` 第一～十三节，八轮相邻快照差分）。

**Status:** ⬜ 待开工
**Triage:** `ready-for-agent`

## Problem Statement

**创作者视角**：我在编辑器里能定义结构体（把「名字/攻击力/是否已强化」打包成一个数据类型），
然后把它当常规数据类型用——放进自定义变量、放进节点图、发信号。

但在 `gsts` 里我**做不到**：

- 没有命令能建结构体。我只能开编辑器手点，**无法脚本化、无法复现、无法随别的资产一起交付**。
- 变量系统**不认识 struct 类型**。我想建一个「武器数据」类型的变量，CLI 侧根本没有这条路
  （类型表里有 dict，唯独没有 struct / struct_list）。
- 改结构体更麻烦：加一个成员要重开编辑器，而且改完**节点图里已经实例化的拼装/拆分节点会怎样**没人知道。

结果就是：**结构体成了「只能在编辑器里做的资产」**，而项目其他一切（元件/实体/变量/UI/信号/
节点图/计时器/单位状态）都能用 CLI 做。这是当前资产命令面唯一的一块人为缺口。

**为什么现在能做**：16 已经用相邻快照把结构体的 wire 完全闭合了——注册位置、id 段、定义记录形态、
成员编码（含 12 种类型的默认值字段规律）、引用形态、物化节点族、整表改写规律。
**剩下的只是实现，不是未知。**

---

## Solution

新增 `gsts assets:structs` 命令族，提供四个动作：

```text
list    列出地图里所有结构体：名字、成员、类型、默认值、id、是否存档结构体、被哪些变量引用
inspect 单个结构体详解：成员表 + 物化的节点族 + 引用它的变量/模板
create  建结构体（--archived 建局内存档结构体）
update  改结构体：加成员 / 删成员 / 改名 / 改类型 / 改默认值
```

同时把 **struct / struct_list** 接进变量类型表，使 `assets:level-variables` /
`assets:custom-variables` 能创建、列出、更新结构体类型的变量。

写回沿用既有惯例：**默认只出候选**（`--output`），回读确认后才 `--write`（自动备份 + Temp 同步）。

## User Stories

### A. 建结构体

1. 作为创作者，我想用一条命令定义一个结构体并指定成员名与类型，这样我不用开编辑器手点。
2. 作为创作者，我想在定义成员时直接给默认值，这样新建的变量实例就有合理初值。
3. 作为创作者，我想省略默认值时得到编辑器一致的默认（而不是空值或报错），这样行为可预期。
4. 作为创作者，我想在一条命令里定义多个成员（含各列表类型与字典类型），这样复杂结构体能一次建好。
5. 作为创作者，我想让成员类型支持**嵌套结构体**（引用已定义的结构体），因为官方明确结构体支持嵌套。
6. 作为创作者，我想在建结构体时就被挡住非法成员类型，这样不用等到游戏里才发现选不了。
7. 作为创作者，我想让 CLI 建的结构体与编辑器建的**逐字节同构**，这样两者可以混用、互相编辑。
8. 作为创作者，我想在建结构体时自动得到一个不冲突的 id，这样不用关心 id 段分配。

### B. 建局内存档结构体

9. 作为创作者，我想在建结构体时用 `--archived` 标记它是局内存档结构体，因为存档结构体是**独立资产类型**而非基础结构体的变体。
10. 作为创作者，我想在使用 `--archived` 且成员含实体/实体列表/字典时被明确拒绝，因为官方规定局内存档结构体**不支持**这些类型。
11. 作为创作者，我想在存档结构体里引用另一个存档结构体时被明确拒绝或被提示，因为官方禁止存档结构体嵌套。

### C. 查询

12. 作为创作者，我想一条命令列出地图里全部结构体，这样我能快速盘点已有资产。
13. 作为创作者，我想在列表里看到每个结构体的 id、名字、成员数、成员名与类型，这样我不用逐个打开。
14. 作为创作者，我想一眼分辨哪个是基础结构体、哪个是局内存档结构体，因为它们注册在不同的 folder。
15. 作为创作者，我想查某个结构体被哪些变量/模板引用，这样改它之前我能知道影响面。
16. 作为创作者，我想查某个结构体物化了哪些节点族记录，这样「图里选不选得到它」有据可查。
17. 作为创作者，我想让 list/inspect 支持 `--format json`，这样我能脚本化消费结果。
18. 作为创作者，我想在读到一个未闭合形态（如非空列表默认值）时得到明确标注而不是静默跳过。

### D. 修改结构体（本票最初遗漏的动作）

19. 作为创作者，我想给已有结构体**加一个成员**，这样我不用删了重建（重建会换 id、断掉所有引用）。
20. 作为创作者，我想**删掉一个成员**，这样废弃字段能清理掉。
21. 作为创作者，我想**改成员名**，这样拼错的字段名能修。
22. 作为创作者，我想**改成员类型**，这样设计变更不用重建结构体。
23. 作为创作者，我想**改成员默认值**，这样新实例的初值可以调整。
24. 作为创作者，我想在加/删成员后**物化的节点族被同步重写**，因为拼装/拆分/修改节点的引脚是按成员展开的——**不同步的话节点图会带着旧引脚失配**。
25. 作为创作者，我想在改结构体后被告知「哪些既有节点图实例可能受影响」，因为引用传递意味着影响面在图上。
26. 作为创作者，我想让「改结构体」在无法安全完成时**明确失败**而不是写出一半，因为半成品结构体会让整张地图选不到该类型。
27. 作为创作者，我想让「改结构体」与「建结构体」共用同一套成员编码路径，这样两种操作的产物形态不会漂移。

### E. 变量类型落地

28. 作为创作者，我想创建 struct 类型的变量并指定它引用哪个结构体定义，这样我能在图里存一个结构体。
29. 作为创作者，我想创建 struct_list 类型的变量，这样我能存一组结构体（局内存档的必要条件）。
30. 作为创作者，我想在读变量时看到 struct 类型被正确识别而不是「未知类型」。
31. 作为创作者，我想让 dict 的**值类型/键类型**也能是 struct，因为官方允许所有类型的字典。
32. 作为创作者，我想让变量的 wire 核验（`variables:verify`）覆盖新增的 struct 类型，这样新增编码也进照规律表的核验范围。
33. 作为创作者，我想在创建 struct 变量时若不指定结构体引用就**明确报错**，因为结构体类型由名字/id 唯一确定，不指定就是歧义。
34. 作为创作者，我想让「同名不同结构体」被拒绝，因为官方明确结构体类型由名字完全确定、且不允许同名。

### F. 安全与可复现

35. 作为创作者，我想让所有写操作默认为「只出候选」，这样我能先回读确认再落盘。
36. 作为创作者，我想在 `--write` 时自动获得备份，这样出错能回滚。
37. 作为创作者，我想让回读核验**核对到具体字段**（folderId / typeValue / 成员数 / 成员类型码），而不是「产物存在就算通过」。
38. 作为创作者，我想让命令在夹具副本上就能端到端验证，这样核验不需要碰我的真实地图。
39. 作为创作者，我想在超出官方上限时被提前拦住，而不是建出一个编辑器打不开的地图。

## Implementation Decisions

### D1. 命令族划分

一个族 `assets:structs` 覆盖**基础结构体**（folderId 29 / typeValue 4100）与
**局内存档结构体**（folderId 33 / typeValue 4600），用 `--archived` 区分。

局内存档**模板**（folderId 31 / typeValue 4400，定义根在 `root31`）**不做**，归票 20 ——
模板是另一条资产线（自己的语义根、自己的 id 段），塞进同一族会让命令语义混乱。

### D2. 结构体是「地图级资产」，不是元件也不是变量

结构体注册在地图级的 folder 记录里，定义在 `root10` 的 `f6`。**它与自定义元件共用 id 空间**
（≥1077936129，逐个 +1），**不与节点图/模板共用**（后者走 1073741824+ 段）。

→ 命令必须把「地图级」这件事说清楚：作用于地图，而不是作用于某个实体。

### D3. 建结构体不能只追加——必须同步改写既有记录

差分实证：编辑器每新增一个结构体，会把地图里**所有既有结构体记录一并改写**
（成员的序号字段 = `2 + 该结构体之后创建的结构体数`）。

→ `create` 是**整表改写**操作，不是 append。若只 append，产物与编辑器形态不一致。
→ 这是本票最容易写错的一点，必须有专门的断言。

### D4. 成员编码复用既有规律

成员是「名字 + 类型 + 默认值」三元组，其中默认值字段号 = **类型码 + 10**
（该规律已在标量、普通列表、struct、struct_list 四种形态上重复验证）。
列表与字典类型码沿用既有变量系统的类型码空间（1..27）。

→ 成员编码器应与变量默认值编码器**共用同一套类型映射**，避免两处各写一份而漂移。

### D5. 物化节点族是本票的必要组成部分

编辑器建结构体时会物化 **9 条节点族记录**（拼装结构体 / 拆分结构体 / 修改结构体，
按该地图支持的图类型各一份；执行类的「修改结构体」只属于服务端图）。

这些复合定义就是节点图里「拼装结构体」「拆分结构体」「修改结构体」三个节点的**实际载体**，
引脚按该结构体的成员展开。

→ **不做这一步，结构体在节点图里就选不到、用不了。** 所以本票必须做，不能推迟。
→ 它们是**公式化**的：一个结构体一条模板，按成员列表展开引脚；引用字段带结构体 id。

### D6. 修改结构体 = 定义改写 + 节点族重写 + 引用一致性

`update` 的原子性要求比 `create` 高：

1. 改写 `root10` 的定义记录（成员列表 / 成员数 / 名字）；
2. **按新成员列表重写全部物化节点族**（引脚增减会改变记录长度）；
3. 维护既有记录的序号字段（只有新增结构体时才变，改名/改成员不变）；
4. 任一步无法安全完成 → **整体失败，不落盘**。

→ 官方明确「结构体在节点图中以引用方式传递」，成员变更会让**既有图上的引脚失配**；
→ 命令成功时必须输出「受影响的节点族记录」清单，让人知道要不要回编辑器检查。

### D7. 变量类型表补 struct / struct_list

类型码空间是 1..27，其中 25 = Struct、26 = StructList —— **缺口在类型映射面，不在 wire 空间**。

→ 变量 CLI 的类型枚举补 `struct` / `struct_list`；
→ 解析侧（读变量）必须识别这两类，不报未知类型；
→ 字典的值类型枚举同步补 struct；
→ 创建 struct 类型变量时**必须指定结构体引用**（名字或 id），否则是歧义类型，直接报错。

### D8. 结构体类型身份 = 名字 + id，且不允许同名

官方明确：结构体类型由名字完全确定，**不同名的结构体即使内部结构相同也是不同类型，在节点图中不能相连**，
且不允许同名。

→ 命令以**名字**为主索引（人可读），内部以 id 定位；
→ 重名必须拒绝，并给出冲突的两个 id。

### D9. 官方限制前置校验

- 全局结构体数量上限、单个结构体成员上限（官方上限表已登记）；
- 局内存档：模板数上限、单个存档结构体上限、嵌套禁令（不支持实体 / 实体列表 / 所有类型字典 / 结构体）；
- 基础结构体**允许**嵌套结构体与字典。

→ 超限在建之前就拒绝，不产出一个编辑器打不开的中间态。

### D10. 写回安全门沿用既有惯例

默认 `--output` 出候选 → 独立回读 → 用户确认 → `--write`（自动备份 + Temp 同步）。
回读必须核对到具体字段，**不是「产物存在即通过」**——本会话已有两次教训
（回读读了输出却没核到关键字段：`kind` 得 `SysCall`、6.7KB 残缺文件当成功）。

## Testing Decisions

**测试缝（只有一个新缝）**：`gsts assets:structs` 命令面本身，端到端跑在**夹具副本**上。

- 用仓库既有夹具（真 `.gil`）复制到临时目录，全程 `--output` 非破坏输出，**输入夹具的 sha256 必须不变**；
- 这是项目既成的验证入口（技能明文要求「验证走真实命令入口（CLI 端到端）」），
  不需要新建测试基础设施；20003/20004 那次就是这么验的。

**好测试的标准**：只断言**外部可观察行为**——命令跑完后，**从产物文件读回的字段**是否与输入一致。
不断言内部函数、不断言中间结构、不依赖实现细节。

**必须覆盖的断言**：

| 断言 | 为什么 |
|---|---|
| 回读成员名/类型/默认值逐字段等于输入 | 基本正确性 |
| 回读 folderId / typeValue 等于该资产类型的值 | 两者写错会静默落错目录 |
| **整表改写**：新建后既有记录的序号字段被同步改写 | 这是 CLI 与编辑器形态一致的关键（D3） |
| **节点族**：成员数 N → 物化记录的引脚展开正确 | 不做就「图里选不到」（D5） |
| **修改后节点族同步重写** | 不对称会留下失配引脚（D6） |
| 变量：struct / struct_list 创建 → 回读类型码正确 | D7 |
| `variables:verify` 覆盖新增类型 | 让新编码进照规律表的核验范围 |
| 非破坏：输入夹具 sha256 全程不变 | 安全底线 |

**最强的对照（不是新缝，是验证方法）**：拿**编辑器刚产出的快照当基准**，
让 CLI 在副本上做同样的事，然后**逐结构对照**两侧产物。
比「只看 CLI 自报」强一个量级——本会话两个检测器缺口（CLI 报 `type=20003` 而产物是 20000、
folder `typeValue` 未核对）**正是 CLI 自报漏掉的**。

**先例（prior art）**：
- `assets:node-graphs create` 的 `verifyNodeGraphReadBack` 回读模式（本会话刚补强了类型号与 typeValue 核对）；
- `assets:global-timers` / `assets:unit-status` 的 `list → create → 回读` 命令测试形态；
- 20003/20004/20005 的夹具副本 + 逐类型回读核验流程。

**验证成本分级**：本票改生产 TypeScript（公共 CLI seam）→ 需要 focused regression + `npm run build` + `git diff --check`。

## Out of Scope

**1. 节点图 DSL 侧的结构体支持（票 18）—— 明确需要更多差分才敢设计。**

当前状态：`struct` 运行时类是空占位，三个节点 API 都是 `args: []` 的空壳。
**为什么不能现在设计**：这三件套是**泛型节点**——必须先选定结构体类型，节点才展开出成员引脚。
要设计 DSL 表示，至少还需要 Further Notes 里列的那批差分。

**2. 局内存档模板与运行期行为（票 20）。** 模板资产的 CLI、`启用` 写法、
以及「存档变量何时落到玩家实体」的负结果，都归票 20。

**3. 游戏内验证。** 结构体在游戏里的读写行为、存档能否真的存下来，只能由用户在游戏内确认。
差分只覆盖编码结构。

**4. 编辑器侧的行为差异。** 例如「CLI 建的结构体在编辑器打开后是否被首存规范化」——
本轮不追，若发现再登记。

### 计数器规律（本轮从 v3→v4 差分闭合）

**每次写入 → 所有结构体 +1；被写入的那个再 +1。**

| 结构体 | v3 | v4 |
|---|---|---|
| 测试结构体名称（没被动） | 4 | 5 |
| 结构体测试test2（没被动） | 3 | 4 |
| 结构体（被改的） | 2 | **4** |

与 create 时新结构体 `f503=2`（=0+1+1）自洽 → create/update 同一条规则。
**DefBlock 内的 `f503` 与 content 层的 `f3` 是同一个计数**，必须同步。

### 验证：拿差分样本执行同一操作

输入 `raw/struct-def-v3.gil`，执行编辑器当时的操作（1077936131：0 → 4 个列表成员），

整文件差 2025B = 物化记录（已知节点图侧差距）。create 路径同步回归仍逐字节一致。
