# GUI 界面语料库（用户反馈轮，2026-10-18 起）

用途：用户主动展示真实界面，我逐帧记录**我看到的**与**我的工具输出的**，用差异来定位设计问题。
用户原话：「我是想多给你看一些经典图片，记录，最后来给出设计的」。

### 本帧结论
1. **纯图形元素（头像行、W/S、裁切图标）在文本驱动的结构里全部不可见** —— 这是"先文字后图形"顺序的直接代价。
2. 左列表行距 403/523/646/766/889 → 间距 120/123/120/123 **极均匀** ⇒ 列表容器签名可靠。
3. 同一个 App，不同活动类型 ⇒ **右侧布局完全不同**（上一帧是奖励图标行，本帧是角色头像行 + 大立绘）。
   任何"按固定模板解析"的方案都会碎。

## 关键实验：图形块定位能救回文本结构丢失的元素（f00）

用户点破：「这一帧已经暴露了，我们在图形块定位和理解能力的缺失了，它这里几个核心的可交互区域
就是角色本身的头像，没有文字。」

### 只用像素的图块检测（不看任何文字）

方法：8×8 块内色彩方差 > 22 ⇒ 有纹理（纯色面板/背景不算）⇒ 8-连通域 ⇒ 按行归组。
成本：右详情区 ROI **140ms**（grid 135 + 连通域 4）。

检出（全部是文本结构里**没有**的元素）：

```
[1724,406,1820,510]   96x104   角色头像
[1868,398,1948,510]   80x112   角色头像
[1996,398,2084,510]   88x112   角色头像
[1692,870,1812,990]  120x120   奖励图标(20)
[1828,870,1948,990]  120x120   奖励图标(3)
[1916,1030,2276,1126] 360x96   开始试用按钮
```

按行归组后自动还原出"行"：
```
y= 868 高=128 个数=4 跨度=720 间隙=[16,16,80]   ← 3 奖励图标(间距16px) + 打勾
y=1042 高= 76 个数=2 ...                        ← 角色预览 + 开始试用
```

### 结论（这是本语料库目前最重要的一条）

**正确的处理顺序应该是：**
1. **图形块**（像素方差 → 连通域 → 坐标）—— 纯几何，不依赖任何文字
2. **行/列归组**（y 对齐 + 高度相近 + 间隙小）—— 纯几何
3. **文字绑定**（把 OCR 框归属到图块/行）
4. **经验解释**（行距均匀的竖列=列表；同尺寸等距横排=图标行；宽扁+内含文字=按钮）

我原来的实现是 **3→1**（先用文字猜结构），所以：
- 纯图形元素（头像/图标/打勾）**系统性丢失**
- 角色名被"文本质心间隙"切成假面板
- W/S、被裁切的图标这类图形证据抓不到

**代价对比**：图形块检测 140ms（ROI），比 OCR（~600ms）便宜 4 倍，且完全确定性。
⇒ 应该让**图形先行**，OCR 只做"给图块贴标签"，而不是反过来。

## f01 — 活动一览 · 风仙亦是仙（切回）

同样结构（左列表 6 项 + 右详情），但**奖励行多出被裁切的第 6 个图标**。

### 图形块检测（47ms，比之前更快：8×8 块 + 方差阈值）

奖励行检出的 8 个图块（y≈886–1006）：

| bbox | 宽×高 |
|---|---|
| [1556,886,1644,982] | 88×96 |
| [1836,886,1924,950] | 88×64 |
| [1956,878,2068,1006] | 112×128 |
| [2108,886,2220,990] | 112×104 |
| **[2260,894,2292,974]** | **32×80** ← 同行最窄 |

### 关键发现：**"同行尺寸离群" = 被裁切的硬证据**

奖励行其它图标宽 88~112px，**最右那个只有 32px** —— 它被面板右沿切掉了大半。
这不是靠"贴屏幕边"判的（那块距屏右侧还有 268px，**贴的是面板边不是屏幕边**），
而是靠**同一行内同类元素的尺寸离群**判出来的。

⇒ 这给出一个纯几何、可计算的"还有更多"判据：

> 同一行/列内，若某元素的尺寸显著小于同行中位数（如 < 中位数×0.6），
> 且它位于该行的**首端或末端** ⇒ 该容器内容被裁切 ⇒ **可滚/可翻页**。

### 反面证据：边缘纹理判据不可靠

左列表顶部条带（y 181–240）纹理块占比仅 **15.5%**，按我原先设的 25% 阈值判"没裁切"，
但**肉眼看得到**那里有一个被切掉一半的图标。

⇒ "容器边缘像素有没有纹理"这个判据**太钝**；**同行尺寸离群**才是可靠的。

### 累计设计要点（f00 + f01）
1. 图形块先行（47~140ms，纯几何，确定性），OCR 只负责贴标签
2. 行/列归组 = y 对齐 + 高度相近 + 间隙小
3. **裁切/可滚判据 = 同行尺寸离群 + 位于行列端部**（不是"贴屏幕边"，也不是"边缘纹理"）
4. 同一 App 不同活动类型，右侧布局不同 ⇒ 不能靠模板，必须靠通用几何

## f02 / f03 — 跨帧对比给出**最硬的滚动判据**（本轮核心结论）

### 实测：左列表滚动一屏

```
f02: 砺行修远 | 虹旅藏金 | 无神怜爱的冻土 | 且试身手 | 风仙亦是仙 | 溯流的变奏曲
f03:          | 虹旅藏金 | 无神怜爱的冻土 | 且试身手 | 风仙亦是仙 | 溯流的变奏曲 | 绮星盛会
```

- `砺行修远` **移出**（顶部）
- `绮星盛会` **进入**（底部）
- 其余整体**上移恰好一行**（约 121px）

### 这比前面试过的所有单帧判据都硬

| 判据 | 结果 |
|---|---|
| OCR 抓 W/S 小图标 | ❌ 同一界面两帧一正一反，不可靠 |
| 末行距容器下沿 | ❌ 世界页队伍栏（真不可滚）也满足 |
| 容器边缘纹理占比 | ❌ 左列表顶部真实被裁切时只有 15.5%（阈值 25% 判"没裁切"） |
| 同行尺寸离群 | ⚠️ 规则对（f01 右端 32px 残块），但**元素分割不稳**（相邻 16px 间距会连通合并） |
| **跨帧条目进出 + 整体平移** | ✅ **直接、无阈值、可解释** |

### 由此得出的设计结论

**"可滚"不该由单帧推断，而应由"动作+对比"确证。**
这正是 AGI 视角下该有的形态：不理解就先试一下，用**结果差异**来定义性质，
而不是靠视觉特征猜（视觉特征在这个 UI 上已被证明全部不可靠）。

具体判据（可机检）：
1. 记录容器内条目集合 A + 各项 y
2. 对该容器发一次滚动
3. 记录集合 B + 各项 y
4. **有移出 + 有进入** ⇒ 该方向可滚；**整体平移量** ⇒ 步长；**只有移出无进入** ⇒ 到底
5. 连续两次无变化 ⇒ 到边界

### 同一批帧还确认的结构事实
- 奖励行可**横向**滚动（f01 右端被切 32px 残块 / f02 左端被切）⇒ 横向容器存在，不能只考虑纵向
- 同一 App 内不同活动：右侧布局三种（角色头像行 / 奖励图标行 / 大立绘+说明）⇒ 无固定模板
- 左列表项高度一致（≈121px 步长）⇒ 纵向列表容器可靠

## 七帧语料收束

**界面形态**（4 类）：左列表+右详情（4 变体）/ 左列表+卡片群 / 混合卡片+按钮 / 角色信息+网格+分区
**反复出现的核心缺口**（跨所有形态）：
1. 图形元素不可见（头像/图标/徽标/红点/立绘/左侧图标列）
2. 容器本体不可见（卡片/格子/面板边界）
3. 层级不足：面板→行，缺 **分区 → 卡片 → 行** 三层的中间两层
4. 可点性不可判（按钮与正文同为 `content`）
5. 可滚只能靠跨帧行为判，单帧特征全被证伪
6. **不滚动 ⇒ 结论错误**（本条已有实证事故：千星奇域入口）
