# Spec：渲染负载分载——服务端只保留「添加运动器」，复制渲染搬到客户端

> 状态：待用户确认 seam 后落票（ready-for-agent）
> 来源：用户 2026-09-04 定调（原话：「服务端理论上只需要保留添加运动器，其他的都可以在客户端计算完成」）+ 本会话负载分载 Round 0-4 通道资产（票 03/04 已闭环）
> 领域术语：见 examples/rubik-3x3-client/AGENTS.md 与 docs/game-engine-knowledge/rubik-autosolve-playbook.md

## Problem Statement

自动还原/手动转动时，服务端承担了「复制渲染」的全套工作：每次面转后，服务端在 turn 图与 visual 图里计算 9 个块的槽位查表、轨道速度、局部轴、旋转参数，再调度两段运动器动画（turnblock/orbit2 定时器链）。3099 负载画像显示 visual 图 19.6MB/1470 条记录 + turn 图 14.6MB/488 条，是服务端负载大头——开日志全程自动还原因此被负载踢出（715s 实证）。这些计算全部是纯数学（表查询+向量运算），不需要服务端权威性，只有「添加运动器」这一动作本身必须在服务端执行。

## Solution

复用已实证的客户端算力通道（20008 造物单元 + 寄存器/信号回传 + first-wins 门，票 03/04），新增「渲染参数单元」：每次面转前服务端只发一个任务（moveId+当前帧状态），客户端算好整步执行包（9 槽各自的自旋轴/角速度/时长、两段轨道速度与延时），信号回传；服务端收到包后**只做动作**：按槽添加运动器设备 + 按包内时序启动既有定时器。服务端 flowDoMove/visual 中的全部参数数学删除；逻辑状态权威（logic_apply_face 与发布）与输入事件处理保留服务端。

## User Stories

1. 作为玩家，我点击面转/自动还原时，魔方动画应与现在完全一致（9 块两段折线轨道+自旋，节奏不变），因为视觉参数只是换了计算地点。
2. 作为玩家，我开详情日志跑自动还原时不再被负载踢出，因为服务端每帧执行量大幅下降。
3. 作为维护者，我打开服务端 turn/visual 图时只看到设备调用与事件流，不再看到表查询/向量数学（那些在客户端图里）。
4. 作为维护者，我新增一种旋转类型时只需改客户端渲染单元的数学，服务端零改动。
5. 作为维护者，我排查渲染问题时从客户端记录读数学、从服务端记录读动作，职责单一。
6. 作为玩家，手动转动与自动还原共用同一渲染路径，手动 0.3s 手感节奏不回退。
7. 作为求解链，自动还原每步之间的状态发布时序不变（logic_apply_face 仍在 turn 内、紧随动作之后），保证求解器读到的状态不错位。
8. 作为维护者，执行包协议有明确的回传契约（槽位→参数），可用日志帧级验证。
9. 作为维护者，多造物实例重复计算同一执行包被 first-wins 吸收，不产生重复设备。
10. 作为维护者，视觉参数表（localAxis/槽位表/常量）随客户端单元资产化，服务端表变量删除后预算显著下降。

## Implementation Decisions

- **复用通道不变**：延续 rbx_ 链模式新增 rbv_ 渲染单元链（20008 图 + 20009/20007 + 28 瞬发配置 + 独立信号组）；服务端 dispatcher 在 flowDoMove 视觉分支发任务（求解器仍经 solverPlan——不动）。
- **服务端最小保留清单（用户裁定的边界）**：
  - 保留：`add_uniform_basic_rotation_based_motion_device` / `add_uniform_basic_linear_motion_device` 调用、`start_timer`（按包内延时执行 orbit2 段）、logic_apply_face 与状态发布（权威性，见 Further Notes）、unlock/lock 输入保护、事件分派。
  - 删除（搬客户端）：槽位查表（view_turn_lookup 表数据）、轨道速度分解（motion_orbit_prep/step 数学与 C1/S1 常量）、局部轴长表查询与符号、自旋参数换算、orbit2 延时编排数据、turnblock/orbit2 定时器列表构造。
- **执行包协议（单步，客户端→服务端）**：9 槽 × {piece 序号, spin: axis(vec3)+angVel+duration, orbit1: vel(vec3)+duration, orbit2: vel(vec3)+delay}；单条信号参数量 ≤10（vec3 计 1 参），超限形态沿 fb_ball_state 先例做 vec3 化；槽间多信号流（tag=槽位/段标识），服务端收齐包后落图变量缓冲再机械执行。1914 无 vec3 信号 donor——前置注册任务（沿 football_push 先例）。
- **执行时序**：spin+orbit1 同回调添加；orbit2 由服务端按包内 delay 启动既有单槽延时定时器——两段折线动画的段间停顿由客户端算入 delay（原机制语义等价）。
- **客户端单元计算输入**：moveId + 中心/朝向状态（实例级变量已实证可读）；输出仅执行包——不含任何实体寻址（块实体寻址仍服务端 get blocks[slot]）。
- **阶段拆分（降风险）**：先搬 visual 图的 turnblock 数学（自旋+orbit1），动画对拍通过后再搬 orbit2 段；手动 0.3s 路径与自动还原共用同一渲染单元。
- **预算**：服务端 turn/visual 删表删数学后 engineExpanded 显著下降（目标 ≤1300/图）；客户端渲染单元 ≤2000（预算实测按沙箱注入+assets:node-graphs nodes）。

## Testing Decisions

- **行为对拍 seam（最高 seam，现有）**：用户游戏复测协议——面转/自动还原动画逐帧一致（9 块两段轨道+自旋+节奏不变）；失败判据：视觉坍缩/少块/节奏错乱（3071 教训）。
- **负载验收 seam（现有工具）**：开详情日志跑 N 次面转 + 一段自动还原，`gia_log.py perf` 服务端秒负载与 3099/3143 基线对比（目标：turn+visual 记录字节数下降 ≥60%，全程不被踢）。
- **帧级协议 seam（现有工具）**：客户端单元记录（f8=4194309 任务拍帧数与回传信号逐槽核对）vs 服务端设备帧（每槽 add 设备参数与执行包一致）。
- **数学对拍 seam（新建最小工具）**：执行包生成逻辑的 JS 离线模拟，对拍服务端现行复合在相同输入下的输出（复用 3093/3099 的离线验证方法论）；不引入新测试框架。
- 不做：headless 自动回归不覆盖跨图时序/设备语义（沿用 rubik 惯例，sim PASS ≠ 游戏可用）。

## Out of Scope

- 求解规划/E/L 层单元的后续搬迁（票 05/07 范围，独立推进）。
- logic_apply_face 状态维护的搬迁（状态权威留服务端——客户端算状态需双端一致协议，本票不做）。
- unlock/lock 输入保护逻辑、事件分派、胜负结算的搬迁。
- 手动 0.3s 手感数值调整（节拍数值不动，只搬计算位置）。
- visual 图整体删除——本票后 visual 图仅剩设备动作壳（若空壳可并入 turn 图属后续清理票）。

## Further Notes

- 用户边界原文：「服务端负责实体的旋转和位置变更，这一块只有服务端能做」「服务端理论上只需要保留添加运动器」——「旋转和位置变更」= 引擎对实体做位移/转动的动作本身（add device）；本 spec 的删除面=一切「决定动作参数」的计算。
- 状态权威边界：logic_apply_face 是「转动在逻辑层的后果」，不是渲染——求解器与胜负依赖它，且手动/自动同源；搬客户端需要客户端回写状态（写通道 9 节点中无通用自定义变量写）——不可行，故留服务端（与用户「事件/反选/渲染运行」服务端口径一致）。
- 依赖既有闭环资产：票 03/04 的实例级变量注册（CLI 84819bb）、first-wins 门、客户端 DSL 约束 6 条（无 variables/无 modulo/无 multipleBranches/循环变量运行时值等）——渲染单元照抄 rbCrossSkill 形态。
- 背景：仓库多人并行（football/ui 会话穿插提交）；npm run build 暂被 football WIP 语法错误阻塞（O-2026-09-04-02），本票构建沿用 dist.tmp 手动 promote 临时通道或等待修复。
