### C8 结构体 id 空间与「序号」在第二样本上的表现

### ❓ 未闭合（本轮唯一未解释项，不猜）

`f503`（及等值的外层 `f3`）的语义**不确定**。已排除的假设：

**待验假设**：该值可能是「**创建该记录时的全局计数**」——A 在 v1 时写 2，v2 被改写为 3；
B 创建时写 2 但**尚未被改写**。若如此，再保存一次（不做任何修改）应使 A、B 两值趋同。
→ 需**第三个样本**（再建一个结构体，或原样再保存一次）才能判定。

### C9 第二样本的**独立确认**（重复出现 == 规律稳定，这是本轮主要目的）

### C10 方法论：**差分配对假象**（本轮实测踩到）

`gil-quick-diff.py` 的紧凑文本输出把 `f6` 记录渲染成
`- 314B …结构体A… / + 312B …结构体B…`，**看起来像「A 被替换成 B」**。
实际用 `compare-level10-containers.ts` + `gil_wire_lib` 定点复核后：
**A 的记录仍在（314B），B 是新增的（312B）**——那是**按 index 配对重复 occurrence** 造成的显示假象。

→ **纪律强化**：紧凑差分文本**只能用来发现「哪里变了」，不能用来断定「什么被替换了」**；
凡出现 `-X / +Y` 长度相近的配对，必须用定点工具按 occurrence 复核一次再下结论。
（技能已有「重复字段必须按 occurrence 比较，不能按字段号去重」——本条是它在**展示层**的同类陷阱。）

## 第三轮差分：f503 闭合（2026-09-16，用户再建一个结构体「结构体」，**0 成员**）

### C11 ✅ `f503` 语义闭合：**`f503 = 2 + （该结构体之后创建的结构体数量）`**

把三张快照的九个观测点排开（N = 当时的结构体总数，i = 创建序，1-based）：

| 结构体 | 创建序 i | v1 (N=1) | v2 (N=2) | v3 (N=3) | 公式 `2+(N−i)` |
|---|---|---|---|---|---|
| A `测试结构体名称` (1077936129) | 1 | **2** | **3** | **4** | 2 / 3 / 4 ✓ |
| B `结构体测试test2` (1077936130) | 2 | — | **2** | **3** | 2 / 3 ✓ |
| C `结构体` (1077936131) | 3 | — | — | **2** | 2 ✓ |

**6/6 观测点完美拟合。** 等价表述：**列表按「最新在前」排序时的 0-based 下标 + 2**。

**机制（这是本轮最重要的操作性结论）**：
**编辑器每新增一个结构体，会把该地图里所有既有结构体记录一并改写**——
既有的 `f503` +1，新建的写 2。前两轮观察到的「A 的 314B 记录只变一个字节」正是这个改写。

→ **票 17 实现含义**：CLI 创建结构体时**不能只追加一条记录**，必须
**把既有结构体的 `f503`（外层 `f3` 同值）全部 +1**，否则与编辑器行为不一致。
（是否影响游戏/编辑器读取，尚未验证。）

### C12 ✅ `f4` = **成员数量**（0 成员时省略）

第三个结构体 C **0 成员**，其 `f6` 记录只有 **56B**：

```

              f2{ …镜像… } f3=2 f5=1 }
```

而 A / B（各 2 成员）的记录均为 `f3=<f503> f4=2 f5=1`。
→ **`f4` = 成员数**（proto3 默认值 0 被省略，故 0 成员时不出现）。

第三个结构体同样物化 **9 条 CompositeDef**（拼装/拆分 × 20000/20001/20002/20007 四类图 + 修改结构体），

### C20 ✅ 成员引用结构体的编码：`f2{ f1: 1  f2: <structId> }`

**引用出现在成员条目的 `f1`（类型包裹）内**，与标量/普通列表形成清晰对比：

| 成员类型 | `f1` 内层 |
|---|---|
| 标量 / 普通列表（如 int） | `f1{ f1:3  f2:{} }` ← **f2 为空** |
| **struct (25)** | `f1{ f1:25  f2:{ f1:1  f2:1077936130 } }` |
| **struct_list (26)** | `f1{ f1:26  f2:{ f1:1  f2:1077936130 } }` |

→ **`f2{f1:1, f2:structId}` = 「引用某个结构体定义」**（`f1:1` 疑为引用种类标记）。
**struct 与 struct_list 的内嵌引用形态完全相同**（差别只在外层类型码 25 / 26）。

## C38 拼装结构体（2 成员）的完整 wire

```
4:{ 1:{ 1:10001 2:20000 3:22001 5:1610612737 }      ← genericId
    2:{ 同 1 }                                       ← concreteId
    4:hex(0)= }                                      ← 空
102:{ 1:"新增变量1" 2:1 3:{1:3}      4:{1:5  3:6  4:6}  8:1 }   ← 输入引脚 1（str）
102:{ 1:"新增变量2" 2:1 3:{1:3 2:1}  4:{1:2  3:3  4:3}  8:2 }   ← 输入引脚 2（int）
103:{ 1:"测试结构体名称" 2:1 3:{1:4} 4:{1:10001 3:25 4:25 104:{2:1077936129}} 5:{1:13} 8:3 }  ← 输出（struct）
107:{ 1:1003 104:{1:1077936129} }                     ← 类型绑定：1003=拼装，指向结构体 id
```

**规律（2 个样本）**：
- 引脚字段 `102`=输入 / `103`=输出（输出多一个 `5`）
- `f1`=引脚名（成员名；输出侧=结构体名）
- `f3`=index `{1:kind, 2:idx?}` —— **kind 3=输入 / 4=输出；第一个省略 idx，之后递增**（与「默认 index 省略」同族）
- `f4`=类型 `{1:<?>, 3:<VarType>, 4:<VarType>, 104?:{2:<structId>}}` —— **f3=f4=VarType 码**；
  struct(25)/struct_list(26) 额外带 `104:{2:<structId>}`；**`f1` 的含义未闭合**（str→5 / int→2 / struct→10001）
- `f8`=pinIndex（**跨三个复合连续**：拼装 1-3 → 拆分 4-6 → 修改 7-14，见已录条目）
- `107`=该复合绑定到哪个结构体操作：`1003`=拼装（拆分/修改的码待补）

否则建出来的结构体是「半成品」——能在资产列表看到，但**节点图里用不了**。

生成所需材料现已齐备：
- **C37–C40**：复合记录的完整 wire 结构（容器布局、引脚字段、`107` 绑定）
- **C55–C58**：节点实例形态 + `107.f1` 操作码表（1003/1004/1005）+ 每结构体 9 条的分组
- **C60–C61**：`f4.f1` 引脚类型表（全类型）+ 码空间随图类型变化
- **C62**：成员默认值的零值实例化规则

**仍未闭合**：def id 的分配（看起来是全局 max+1，未验证）；「4 个图类型」的确定顺序（20000/20001/20002/20007？）。
