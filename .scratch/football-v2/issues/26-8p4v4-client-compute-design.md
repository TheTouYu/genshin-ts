## 0. 引擎事实（本轮核查，设计地基）

| 事实 | 出处 | 对我们的意义 |
|---|---|---|
| **客户端射线检测节点存在**：`getRayDetectionResult(detectionInitiatorEntity, launchLocation, launchDirection, maxRayLength, factionFilter, entityTypeFilter[], hitLayerFilter[])` → `{onHitLocation: vec3, onHitEntity: clientEntity}` | `src/definitions/client_nodes.ts`（在 `client_method_modes.ts` 白名单内=客户端可用） | 10Hz+ 的几何查询可以全在客户端做，零网络成本 |
| 筛选维度：**阵营** / **实体类型**（关卡·物件·玩家·角色·造物）/ **命中层**（受击盒·场景·物件自身碰撞） | 同上 | 球→人、球→门、球→场景 都能一次查询解决 |
| 客户端还有：`getPreAimingRayHitInfo`、`getCursorHitResult`、`getListOfPlayerEntitiesOnTheField`、`getPlayerMovementInput`、`getEntityLocation/Rotation`、`getCurrentClientTime(HighPrecision)` | `client_method_modes.ts` | 8 人位置/朝向/输入都能客户端直读；**客户端有时钟** |
| **服务端命中检测事件**：`whenOnHitDetectionIsTriggered` → `{eventSourceEntity, eventSourceGuid, onHitHurtbox: bool, onHitEntity, onHitLocation: vec3}` | `events-payload.ts`；组件 type12 | 低频权威兜底通道；区半径=**局部单位 × 实体 scale**（已实证） |
| 自定义变量客户端**只读不写**；技能变量**按施放实例隔离**；图内局部变量**不跨施放保存**；信号参数上限 **10** | 票 19/20 实证 + 技能 | 决定协议必须"服务端写、客户端读 + 自持存" |

## 1. 架构决策（4v4）

- **D1 一个球 = 一个客户端工人（单实例）**：球状态（自持 11 分量）= 客户端算；服务端只镜像（球实体变量）供其他图/UI 读。4v4 只有一个球 → 仍然一个工人。
- **D2 输入面 = 每人一个抽屉 + 一个全局"举手牌"**（本票核心，§2）。**客户端不扫 8 个抽屉**（节点数会随人数线性膨胀）。
- **D3 意图走抽屉、连续物理客户端自算**：离散意图（踢/传/射/铲/扑/复位）走抽屉；连续行为（贴脚带球、接球缓冲、抢断判定、出界/进球、六态积分）客户端算。
- **D4 球员态读取走"客户端直读引擎状态"**（`getEntityLocation/Rotation`、`getPlayerMovementInput`），不走服务端写表——待验证 §5-V2。
- **D5 计算权威 = 最高风险未知项**（§5-V1）。若"每个客户端各跑一份球"，则需选举/仲裁；若"单客户端权威"，则本设计直接成立。
- **D6 服务端职责收窄**：记账（比分/球权/犯规）+ 广播（进球/出界事件）+ 权威兜底（命中检测区）+ 表现（运动器驱动球与球员反馈）。

## 2. 任务抽屉协议（8 人版）

### 2.1 单人版（票 25-C，已对齐）
抽屉挂玩家实体 `fb_t1..t8` + `fb_sum` + `fb_epoch`/`fb_ack`；服务端写、客户端读；客户端回 `fb_echo` 由服务端推进 ack。**一次一往返 ~5 任务/s。**

### 2.2 8 人版：抽屉 + 举手牌

```
玩家 P 按键/点选项
  └ 服务端（挂玩家实体的图，天然 per-player 执行）
       ①写 P 自己的抽屉：t1=动作码, t2..t7=参数, t8=自校验和
       ②写全局牌（挂球实体，全场唯一）：who=P, seq=seq+1      ← 只有一个写点竞争
  └ 客户端工人（每拍，成本与人数无关）
       ③读牌 who/seq  →  seq == 自己存的 lastSeq ? 跳过 : 继续
       ④按 who 读那一个人的抽屉（8 格）→ 校验 → 应用意图
       ⑤lastSeq = seq（存**技能变量自持槽**：图内局部变量不跨施放保存）
```

要点：
1. **牌是唯一竞争点**：写者多（8 人）但写点少（3 个 int），服务端写、客户端只读 → 无锁竞争。
2. **不需要 ack 往返**：客户端用自持 `lastSeq` 防重放（旧 E1 的 ack 是"服务端确认送达"，对玩法意图属多余；保留 ack 只用于必须确认送达的任务）。
3. **同拍多人提交**：牌只存最后一个 → 前一个丢。取舍：人手操作 1~2 次/s，8 人同拍冲突概率极低，且"最后动作者优先"符合体育直觉。若需严格排队 → 牌扩成 4 槽环形队列（who[4]+seq[4]+码[4]，成本 +12 读）。
4. **参数编码**：方向/力度沿用 ×1000 定点 int（协议不变）；队友目标编号 0=自动、1..8=指定。
5. **蓄力类动作（射门）** 需要两段事件：`PRESS`(蓄力值 0) / `RELEASE`(力度值) → 动作码分两个（SHOOT_DOWN / SHOOT_UP），客户端收到 DOWN 开始蓄力（自己计时），UP 时发射。

## 3. 五个机制的设计

### 3.1 带球（dribble）
- **客户端每拍**：对 8 个球员算 `dist(球, 球员)`（用 `getEntityLocation`）→ 最近者且 `< r_dribble` 且球速 `< v_capture` → 进入**贴脚模式**。
- 贴脚目标点 = 球员脚前 `0.4~0.6m`，方向取 `getPlayerMovementInput`（客户端直读输入，比等位置更新更跟手）；球速 = 玩家速度 × **1.2**（R2 手感基线）。
- 持久状态新增自持槽：**holder（0=无人，1..8=持球人）** 与 lastTouch。
- 8 人差异：每拍 8 次距离判定 ≈ 40 节点；只对"最近者"做后续逻辑（不展开 8 份）。

### 3.2 传球（pass）
- 意图：传球键 + 方向（或"自动索敌"由客户端算：按方向在 ±35° 内选最近队友——它知道 8 人位置）。
- 抽屉：`PASS`, t2..t4=方向(×1000), t5=力度档, t6=目标队友编号(0=自动)。
- 客户端：给球初速度（方向 × 力度 + 小幅抬升）；接球成功与否**不靠判定靠物理**——接球方进入 `r_dribble` 后触发"接球缓冲"（球速按系数衰减、方向对齐球员），于是"传大了/传偏了"自然表现为接不到。
- 手感参数：滚动摩擦、接球缓冲半径、缓冲衰减——**全部参数化**（与 fb_p_* 同风格）。

### 3.3 射门（shoot）
- 意图：`SHOOT_DOWN`（开始蓄力）/ `SHOOT_UP`（力度）；客户端自己计时蓄力（不依赖服务端节拍）。
- 客户端：初速度 = 方向 × 力度 + 抬升角；`spin` 参数产生弧线（六态物理里已有 Magnus 项）。
- **进球判定**：客户端纯数学（x 跨门线 52.5 + z 在 ±3.66 + y < 2.5 + 球整体过线）→ 立即出表现（网抖/音效/UI），同时发 `GOAL` 信号给服务端**记账并广播**（比分）。
- **双轨一致性**：客户端判定为"快"，服务端记录为"权威"；冲突时以服务端收到的第一条为准。

### 3.4 命中检测（三条路线分工，本票关键结论）

| 需求 | 实现路线 | 理由 |
|---|---|---|
| 球↔球员接触（接球/贴身/抢断） | **客户端自算**（距离+速度+朝向） | 15Hz、与物理同拍、零网络延迟、参数在代码里 |
| 球进门 / 出界 | **客户端数学** + 服务端记账广播 | 静态几何、判定廉价；账目归服务端 |
| 球↔门柱/场景碰撞 | **客户端物理**（phys2 已有） | 同上 |
| 射门路径遮挡 / 打人 / 拦截点 | **客户端射线检测** `getRayDetectionResult` | 节点现成，一次调用解决；避免服务端事件洪泛 |
| 服务端必须知道的"粗判定"（进球区、越位区、出界区） | **服务端事件** `whenOnHitDetectionIsTriggered`（组件 type12） | 低频、权威、防作弊；注意区半径=局部单位×scale |

**原则**：**算球的人在客户端 → 一切与球相关的检测都在客户端；服务端只用"事件/区"做低频权威兜底 + 记账。**
（补充：客户端射线还能做"传球目标高亮""射门角度提示"等 UI 辅助，零服务端成本。）

### 3.5 断球（tackle）
- 意图：`TACKLE`（PRESS）→ 抽屉。
- 客户端判定四要素：①距离 `< r_tackle`(1.0~1.5m) ②球在对方脚下（holder=对手）③朝向对齐（断球者朝球方向 `dot > 0.3`）④**同队不触发**（队友间只做"让球"）。
- 结果：holder 转移 + 球获得短促弹开速度（断球者朝向 ± 小随机）+ **保护期 0.3~0.5s** 防反抢抖动。
- 可选规则：背后断球 = 犯规 → 客户端发 `FOUL` 信号，服务端记账（不参与判定）。

## 4. 判定归属分工表（一句话版）

| 层 | 负责什么 |
|---|---|
| **客户端工人（15Hz）** | 球的六态物理、带球贴脚、接球缓冲、抢断判定、进球/出界判定、射线类几何查询、球员态读取 |
| **服务端（事件/低频）** | 输入汇聚（写抽屉+牌）、账目（比分/球权/犯规）、广播（GOAL/OUT/FOUL）、权威兜底（命中检测区）、表现驱动（运动器/音效/UI） |
| **客户端表现层** | 收到服务端广播 → 各自播放画面反馈（球由工人复位） |

## 6. 负载与节点预算账（8 人）

- **客户端图增量**：8 人位置/朝向读 ≈ 24~32n；距离与最近者选择 ≈ 40n；带球/接球/断球状态机 ≈ 60n；意图应用 ≈ 30n → **新增 ≈ 150~170n**；加 phys2 705n ≈ **~880n**（< 2000 ✅）。
- **每拍读取量**：球自持 11 + 牌 3 + 8 人位置/朝向 ≈ 24 + 抽屉（按需 8）≈ **~46 次/拍** → 15Hz ≈ 700 次/s。
- **信号**：每拍 1~2 条（球状态 + 驱动）；事件（GOAL/OUT/FOUL/TACKLE）低频。观测类信号一律事件门控（既有纪律）。
- **服务端**：每拍收 1~2 条 → 写镜像 11 + 驱动一组运动器；8 人输入事件极少。

## 7. 方法论提炼（用户教学 → 可复用知识，C 批收口后并入技能/PKC）

1. **判定归属法则**：算球的人在客户端 → 与球相关的一切判定都在客户端；服务端只做低频权威兜底 + 记账 + 广播。
2. **三通道模式**：任务（S→C 意图，低频）/ 自持（客户端状态，破 ~10/s 读上限）/ 广播（C→S 结果，每拍）。
3. **多写者协议**：N 个玩家 = N 个抽屉 + **1 个全局举手牌**（who+seq）→ 客户端按牌取货 → **节点成本与人数无关**。
4. **防重放靠自持**：图内局部变量不跨施放保存 → lastSeq 存技能变量槽，不需要 ack 往返。
5. **选型表**：高频+手感+纯数学 → 客户端；低频+权威+记账 → 服务端；粗判定+需权威 → 服务端事件（命中检测组件）；高频几何查询 → 客户端射线检测。
6. **载体与保频**：造物（常驻高频）藏地下 + 定时瞬移贴玩家；角色技能（按需单次）用于低频。
