# 操作面清单 · B 通道（界面帧枚举）

> **状态**：2026-10-19 19:1x 首版，实测 4 帧（t16/t17/t18 + 一张抓于 19:10 的实况帧，2560×1440）。
> **口径**：只做**离线帧分析**——不点、不注入键鼠、不抢焦点（同一块屏上有另一个代理在做实测）。
> **产物**：本文件 + `.scratch/gui-stack/ops-inventory-crawl.tsv`（151 行，`source=enum-B`）
> + 原始 JSON/overlay 在 `.scratch/gui-enum/out/`、`.scratch/gui-enum/preview/`。

## 0. 一行用法

```bash
tools/ys-editor/ys-enum 帧.png [帧2.png …] --path "界面路径" \
    --json out.json --tsv out.tsv --overlay-dir preview/ [--debug] [--no-ocr]
```

只读文件，不碰屏幕。多帧一次跑可以摊掉 OCR 模型加载（~0.7s）与首块预热（~1.6s）。

## 1. 读数（实测，非估算）

| 帧 | 界面 | 候选 | 按 kind | 文字保留/丢弃 | 耗时（冷/热） |
|---|---|---|---|---|---|
| t16 | 实体布设页（左面板+顶栏+画布） | **41** | icon_button 20 / tile 8 / menu_item 13 | 21 / 13 | 4.6s |
| t17 | 界面控件组管理 | **31** | icon_button 17 / button 6 / tab 3 / menu_item 2 / tile 2 / input 1 | 15 / 44 | 2.9s |
| t18 | 同上 + 左下「添加界面控件」 | **32** | icon_button 18 / button 6 / tab 3 / menu_item 2 / tile 2 / input 1 | 15 / 43 | 3.1s |
| live-1910 | 实体布设页，**多开了 3 个文档页签** | **47** | tab 3 / icon_button 22 / menu_item 13 / tile 7 / button 2 | 25 / 11 | 2.4s |

### 同屏不同状态：t16（41）vs live-1910（47）

同一块界面，只因**多开了 3 个文档页签**（`界面控件组管理 ×` / `关卡设置 ×` / `资产导入导出管理 ×`），
候选从 41 变成 47：多出来的是 **3 个页签 + 3 个关闭 ×**（工具全部检出，`kind=tab`），
`主镜头管理` 从「格子」退化成了「button」（因为图标被页签行遮挡，`_above` 判据不成立）。

这条实测直接证明了第 5 节的结论：**单帧枚举的是"一个状态"，不是"一个界面"**。
同一天里这块屏至少有 2 个状态（无页签 / 有页签），差 6 个操作点 = 14%。

**平均 3.2s/帧**（四帧连跑 14.2s；单帧冷启 4.6~5.8s，热跑 2.4~3.1s）。三通道原始产出：text 15~25 / fill 15~21 / glyph 56~96。

**通道路径**：①切块 OCR（800×600 块、40px 重叠、1x；整帧 OCR 在同一帧上只出 54 行且左栏 3 行漏 2 行，切块后 61 行全中）
②量化色填充连通域（找"外皮"）③局部背景减除找图标团块（`uniform_filter` 背景；`median_filter` 31px 全帧实测 29.5s，不能用）。

## 2. 判据（把"可交互"和"装饰"分开）

一条候选必须至少满足一条，并带证据串（写进 TSV `evidence` 列）：

- **A 归属**：文字被"控制器形状的外皮"包住（同一填充框内、且框大小 ≤ 文字 3.5×），或同一行/同一格里有图标。
  图标+文字=一个控件；只有文字没有外皮也没有图标的，当标签。
- **B 结构**：与其它项构成等距列表 / 页签条 / 工具条。t16 的 13 行管理项 pitch=59px σ=0.7px，一次成型；
  t17 的 `界面布局/界面控件组库/素材库` 三个页签同 y ±1px 成条。等距=集体性证据，单看一个像装饰，连着看就是控件。
- **C 语料**：文字命中控件动词/名词表（设置/管理/导入/试玩/布局…）或符号（+ × ▸ ⌕）。**最弱证据**，只给 0.45 置信度。

置信度 = 通道数加权：text+fill+glyph 三通道齐 0.86~0.97；text+结构 0.7~0.86；纯形状（只有图标/只有外皮）0.4~0.68。

**反过来判"不是控件"的两条硬规则**（本仓踩过的坑）：

- **游戏画面内文字**：用「文字环内高彩度像素占比」`photo_frac` 判，>0.55 判为游戏画面内容
  （实测：游戏内 造物名称/玩家1..8/Enter 0.60~0.88，编辑器面板文字 0.00~0.37）。
  这条比"局部标准差"干净——标准差在 t17 的平坦沙滩/天空上会被打散，在 t16 的文字区又会被文字本身拉高。
  t17 靠它清掉 44 条预览内文字 + 随后用这些文字的自校准包围盒清掉预览内图标。
- **宿主 HUD**：DXVK/FPS/GPU/min/max/UID/`N ms` 用文字正则；**不要用几何框**——
  左上角 DXVK 覆盖层与编辑器自己的页签/工具栏重叠，一个 340×120 的框会把「界面布局/界面控件组库/未分类页签」一起吃
  （实测踩过：t17 三个页签全被判成 host_overlay 丢掉）。

## 4. 误报 / 漏报清单（各三个，带 bbox）

### 误报（工具报了，人眼说不是可交互）

1. **`[2226,10,96,34]` t16 右上「35 ms」信号条** —— 它是**状态读数**不是按钮；被图标通道当成 84×22 的大图标。
   （同理 t17 `[1390,54,62,54]` 其实是 50% 下拉的底框，但箭头另出了一条 `[1486,66,32,28]`，一条控件两条候选。）
2. **`[2120,106,134,90]` t17 右栏「默认布局」标题** —— 分区标题，被判成 menu_item。
   机制：它和下面的「索引 1073741825」同左沿、纵向相邻，正好满足竖列结构判据 B —— **结构判据在"标题+内容"布局上会误判**。
3. **`[2430,4,48,46]` 这类是正确的**；反例是 **`[0,1348,74,62]` / `[270,1346,64,50]` t16 左下 DXVK 图表**（t17 对应 `[2,1294,54,30]` 等 5 条）—— 图表亮块被当图标。
   HUD 几何框只框得住最底 60px，图表区（h≈140px）露在框外。

### 漏报（人眼说可交互，工具没出候选）

1. **`[325,55,36,30]` t16 页签右侧的铅笔编辑图标** —— 图标与页签文字粘连，被文字过滤（`overlap_frac>0.35` 判为文字内部）后丢掉。
2. **`[1099,68]` t16 顶部模式条里的蓝色选中项** —— 4 个模式图标只出 3 个；选中态是浅色图标压在高亮蓝色药丸上，
   团块被药丸背景"吃掉"（`uniform_filter` 背景≈药丸色，图标对比度掉到阈值下）。
3. **`[8,770,238,34]` t17 左栏搜索框本体** —— 框内只有放大镜图标、没有文字；外皮（填充框）本身没有"控制器形状"证据，
   纯图标通道只给了放大镜，框整体漏掉。**"无文字+无图标+只有一块框"的输入框是系统性盲区**。

（其余漏报：t16 `[99,70,327,30]` 未分类页签、`[545,120,14,24]` 面板折叠柄、t17 `[2160,300,20,20]` 漏斗图标、`[150,175,200,30]` 左栏默认布局选中行
——选中行是被 `photo_frac` 误杀的：蓝色选中条彩度高，0.74 > 0.55。这条已登记为已知缺陷。）

## 5. 纯视觉枚举的天花板（这条决定 99.5% 能不能到）

**能枚举的**：看得见、离散、有文字或有边框/图标的那一层。实测召回 **83~86%**。

**枚举不出来的，按"为什么"分七类**（每一类都直接削减可达覆盖率）：

1. **无视觉差别的图标（同形不同义）**：顶栏 4 个圆形图标、左栏 5 个方块图标，形状相似且**没有文字**。
   帧上只能给"这里有个图标"，给不了名字 ⇒ 分母要的 `(路径, 控件, 动作)` 三元组里**控件名这一格填不出来**。
   补法只能是：点开看效果 / hover 看 tooltip / 查 A 通道文档 —— **全是帧外信息**。
2. **条件出现的控件**：选中实体后才出现的属性面板、hover 才浮出的按钮、滚轮后才可见的列表项、右键上下文菜单、
   二级/三级弹窗。单帧只拍到一个状态，**状态空间不遍历就永远缺**。
3. **连续量控件**：滑块（吸附强度/笔刷半径）、拖拽、滚轮数值、颜色选择器。它们不是"一个操作点"，是**一个参数域**；
   帧上最多说"存在一个滑块"，说不了两端之间的动作实例。
4. **场景/世界坐标操作**：拖实体、拉 gizmo 轴、地形笔刷、框选、移动镜头。屏幕上没有"元素"，
   可交互区域是**整个画布**（1920×1080 的每一像素 + 修饰键组合），无法用 bbox 穷举。
5. **键盘/快捷键入口**：Alt+N、Enter、数字键这些在游戏内 HUD 上，不在编辑器帧上。
6. **同形多实例**：t17 预览里 8 个"玩家名称"、t16 的 13 行管理项 —— 帧上完全同构，**路径里的索引不可见**。
   （这也是为什么 B 通道产物必须带 `path` 而不是只有 bbox。）
7. **语义/后果层**：就算框对了，也**分不清 dropdown / toggle / 一次性按钮**（形状相同、都没文字），
   更给不出"点下去会发生什么"——而 99.5% 覆盖率的判据要求"观测差异 + 判据值"，那是行为读数，帧里没有。

**结论（给覆盖率目标的直接含义）**：纯视觉枚举**做不到 99.5%**，它的天花板大致是
「可见离散控件 × 名字可读率」≈ 一屏 80~85% 的**候选召回**、其中**有文字的那部分才可能命名**。
剩下 15~20% 与上面 7 类必须靠：**状态遍历（爬取器逐个进入/展开/滚动）+ 点击探测（点一次看差异）+ A 通道文档（给名字）**。

所以 B 通道的正确用法不是"当分母"，而是**当爬取器的雷达**：
它给的是「这一屏有哪些地方值得去点、哪些地方有名字」，以及**界面拓扑的变化信号**（新面板/新页签出现 = 新状态）。
把"帧枚举"升级成"状态枚举"（同一界面在 N 个状态下各枚举一次），才是把这条通道推到可用的唯一路径。

## 6. 与爬取器的分工（避免互相踩）

| 谁 | 做什么 | 落到哪 |
|---|---|---|
| **本通道（enum-B）** | 离线帧枚举：候选 + 证据 + 置信度；**不点** | `ops-inventory-crawl.tsv` 里 `source=enum-B` 的行 |
| **爬取器（ys-crawl）** | 在线枚举 + 真点 + 记账（覆盖判据 ①②③） | 同表 `source=crawl` 行；`ops-ledger.tsv` |

`ops-inventory-crawl.tsv` 的列：`id / source / frame / screen / region / path / control_text / bbox_xywh / bbox_kind / kind / confidence / channels / evidence`。
**合并规则**：先按 `(screen, path, control_text)` 去重；`control_text` 为空的（纯图标）按 `(screen, bbox 中心 ±40px)` 归并成一条，
命名等点击/tooltip 补齐后再回填。
