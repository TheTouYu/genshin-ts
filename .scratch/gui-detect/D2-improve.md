同一套留族验证 7 帧 / 519 GT，同一台机器，热态 p50）：

| | micro | row | panel | button | tile | chip | icon | p50 | p90 |
|---|---|---|---|---|---|---|---|---|---|

（avatar 只有 1 个 GT 实例：v1 命中 1、v2 命中 0 —— 单例，不做结论。）

四个改进方向各自的裁决：

| # | 方向 | 裁决 | 关键读数 |
|---|---|---|---|
| ① | **行 → 1D 条带** | ✅ **有效（有天花板）** | row 0.133→0.192（+44%）；叠加「行距当行高」后 → **0.266**；成本 ≈ 0 |
| ② | 粗类 + D3 细化 | ❌ **无效** | 专门训 2 类 0.310 vs 8 类事后按粗类评 0.316；错类只值 +4.4pp；GT **无 text 类** |

| ④ | 损失层（logw / 宽框加权） | ❌ **不推荐 logw**；宽框加权未跑完 | 80 轮 A/B：micro 0.170→0.106、row 0.232→0.123（初始化未控，判"不推荐"） |

**一句话**：有效的是**表示（1D 条带）**与**几何先验（行距=行高）**，不是类别合并或损失改写；
row 从 0.079 提到 **0.276**，但**没到父会话要的 0.4**——差的部分被"46px 的行在 640 输入下只有 2.9 格"这条硬约束卡住，
唯一有实测支持的通路是**提高有效分辨率**（③证明了它：0.305），代价是 1.85× 延迟与本机吃不下的训练内存。

**它稳不稳？** 把 7 帧拆成「调参 4 帧 / 留出 3 帧」复核（§3.4）：留出帧上 **pitch 0.372 vs logh 0.233**（+60%），
pc 在 0.0–0.3 平坦；同时暴露**按族异质性**——行密集族 0.372、行稀疏的编辑器族只有 0.05–0.12（单一数字掩盖了它）。

**⚠ 线上生效状态**：`gui_det.DEFAULT_MODEL` 已指向 v2（v1 原文件未动，一行可回退），
但**常驻服务 `ys_lookd` 没重启**，它内存里还是旧模块 —— 要吃到 v2 得重启服务（未授权，本轮没做）。

## 1. 口径（所有读数用同一套）

- **数据**：`.scratch/gui-detect/dataset/annotations.json`，50 图 / 1956 实例，图统一 **2560×1440**。
- **切分**：`.scratch/gui-detect/train.py:Data` 的**按界面族留出**（seed=0、val_frac=0.25）→ **43 训 / 7 验**，
  验证族 = ①标签栏编辑器 / ①顶栏+左树（音乐窗口）/ ①顶栏+左竖栏（模型库）/ ①顶栏+左资源栏 / ①顶栏+时间轴 / 左上玩家信息卡 / 教程页顶栏。
  新脚本 `d2.py:Data` 原样照抄这段（读数可比的前提）。
- **指标**：per-kind **recall@IoU 0.5**（与 `train.py:evaluate` 逐字一致：某个同类检测与之 IoU≥0.5 即算命中，不做一对一匹配），
  micro = 总命中 / 总 GT（验证集 519 个实例）。
- **评测器一致性校验**：用新评测器复评 `train-v5/model.pt` → **micro 0.272**（与 v5 `metrics.json` 报送值一致）。
  per-kind 略有差异（panel 0.405 vs 报送 0.50、row 0.069 vs 0.084）——原因是 `metrics.json` 评的是 **ep400 内存模型**，
  而 `model.pt` 是**历史 best 快照**（两者 micro 撞在同一值上）。本文件所有对比都用同一份快照口径。
- **两条评测通道，别混用**：
  ①**训练口径** `d2.py:evaluate`（不做 NMS、thr=0.35）——所有 A/B 对比都用它（噪声最小、可比）；
  ②**线上口径** `d2_prod_eval.py` → `gui_det.Detector.detect`（真链路：缩放→前向→decode→NMS0.5）。
  两个口径绝对值不同：**v1 权重** 训练口径 0.272 / 线上口径 **0.254**（NMS0.5 + postprocess 的最小边长闸门会吃掉部分重叠窄框）；
  **v2 权重** 恰好两个口径都是 **0.326**。
  **本文件的 A/B 一律训练口径，交付前/后一律线上口径**。
- **耗时**：端到端单帧（PIL 缩放 → 前向 → 解码 → postprocess），热态 p50，输入取验证集第 0 帧（2560×1440）。
  训练口径的 `bench` 只测 net+decode（不含 postprocess）：v2 = 35.6ms；**线上口径（含 postprocess）v1 36.4ms / v2 41.3ms**。
  外部参照：生产服务当时实测 27.6ms（不同时刻、机器负载不同，绝对值只与同批对比）。
  ⚠ 计时必须在**没有其它训练任务**时做：本轮有一次在训练并行时测到 94.6ms，是负载污染，已作废。

## 3. ①行 → 1D 条带：**部分有效**（row 0.133 → 0.192，+44% 相对；但天花板被行高回归卡住）

### 3.1 改法（`d2.py:Net(row_strip=True)` + `decode_rows`）

热斑分类不再有 `row` 类（7 类），另加一条 **1D 条带分支**（与 head 同网格 160×90，3 通道）：

| 通道 | 语义 | 目标 |
|---|---|---|
| `ctr` | 这一「带」是行 | 行中心线：x 方向平铺、y 方向窄高斯（σ=0.7 格），逐 y 取 max 得到 1D 剖面 |
| `mask` | 行的像素支撑面 | 行的外接矩形格 |
| `logh` | 行高 | 该带内 `median(log(h_cells))` |

解码（`decode_rows`）= **逐 y 峰值**（±1 邻域最大 + 过阈）→ 行高 `exp(median(logh))` → **x 跨度从 mask 列支撑面读**（连续段 + `gap≤4` 格合并，把行内图标打断的空洞接上）。
回归 y、分类型 x：这是 §2 oracle 的直接结论（全宽只剩 16.6%，按支撑面读能到 89.5%）。

### 3.2 读数（同口径，400 轮，同一留族验证 7 帧 / 519 GT）

| 指标 | 基线 8 类（行在热斑里） | ①条带模型 | Δ |
|---|---|---|---|
| **row recall** | **0.133** | **0.192** | **+0.059（1.44×）** |
| micro（八类） | 0.306 | 0.297 | −0.009 |
| panel | 0.381 | 0.405 | +0.024 |
| chip | 0.446 | 0.289 | −0.157 |
| button | 0.289 | 0.254 | −0.035 |
| tile | 0.711 | 0.711 | 0 |
| icon | 0.419 | 0.387 | −0.032 |
| avatar | 1.0 | 1.0 | 0 |
| element 粗类 | 0.442 | 0.380 | −0.062 |
| **p50 / p90 耗时** | 32.5 / 38.8 ms | **32.5 / 38.4 ms** | **0（条带分支免费）** |
| 输出框数 | 809 | 1002 | — |
| **①+pitch 解码（交付配置）** | — | **micro 0.326 / row 0.266** | row 再 +0.074 |

**早期收敛速度差 3 倍，最终只差 1.4 倍**：ep100 时 条带 row 0.232 vs 基线 0.074（3.1×），
到 ep400 收敛为 0.197 vs 0.158。即：条带让 row **学得快**，但**上限**被别的因素卡住（见 3.3）。

### 3.3 为什么会卡在 0.19（诊断，不猜）

1. **解码参数不是瓶颈**：`d2_sweep.py` 扫 `thr_ctr∈{0.15..0.40} × thr_mask∈{0.2,0.3,0.4} × gap∈{2,4,8}`（54 组），
   row recall 只在 **0.182–0.197** 之间动，最优 `(0.15, 0.40, 8)` 也只有 0.197。⇒ 阈值调不出召回。
2. **误差预算在「行高」上**：`d2_diag.py` 在 3 帧 71 个 row 上逐框拆误差（绝对均值，原图 px，2560 空间）：
   **dy 16.3 / dh 18.7 / dx 62.4 / dw 122.6**（有符号版：dy +7.1、dh −10.7 → 预测框整体偏上、偏矮）。
   数据集 row 的**中位高只有 46px**，也就是 **dh 相当于 40% 的框高** —— IoU≥0.5 在这个误差下大面积不过。
3. **根因是分辨率**：640×360 输入下 1 格 = 原图 16px，46px 的行只有 **2.9 格**；
   行高回归要在 3 格量级上分辨 1.5 格 vs 3 格，量化误差本身就 33%。这是 ③ 的直接动机。
4. 覆盖图（`/tmp/rowdiag/val4.png`，53 行帧）可见形态：条带能找到「这里有行」（右侧音乐列表一排红框），
   但**行高普遍偏大/偏小**，且 x 跨度有时吃掉整列 —— 与 dh/dw 的数字一致。

**结论**：①的表示选型是对的（1D 条带 + 像素支撑面读 x，成本 0ms，学得快），
**但在 640 宽输入下被行高回归的分辨率上限封在 ~0.2**；要兑现它必须叠加 ③（提高输入分辨率）。


### 3.4 防「调参调在验证集上」：4 帧调 / 3 帧验

`pitch_gap`、`thr_ctr` 这些解码参数是我在**同一套 7 帧验证集**上选的，先把这件事验一下：
把 7 帧拆成 **调参 4 帧（idx 0–3，74 个 row）** 与 **留出 3 帧（idx 4–6，129 个 row）**：

| 解码 | 调参 4 帧 | **留出 3 帧** |
|---|---|---|
| logh 回归（旧） | 9/74 = 0.122 | **30/129 = 0.233** |
| pitch（pc=0.0） | 4/74 | **48/129 = 0.372** |
| pitch（pc=0.2） | 5/74 | 48/129 = 0.372 |
| pitch（pc=0.3，交付值） | 6/74 | **48/129 = 0.372** |
| pitch（pc=0.6） | 9/74 | 39/129 = 0.302 |

- **pitch 的收益在留出帧上成立**：0.233 → **0.372（+60% 相对）**，而且 pc 在 0.0–0.3 之间平台平坦 → 不是"挑出来的一个幸运值"。
- 同时暴露一个**按族异质性**（比单一数字更有用的结论）：
  - **行密集的族**（idx 4–6：时间轴/特效面板/播放面板，129 个 row）→ **row 0.372**；
  - **行稀疏的族**（idx 0–3：编辑器窗口族，74 个 row，多数帧只有个位数行）→ **row 0.05–0.12**，几乎全灭。
  ⇒ 单一 micro/row 数字掩盖了"密集列表能读、零散单行读不出"这件事；D3 接的时候要按族看能力。
- 另注：稀疏族里 pitch 拿不到（只有一个峰）时回退 logh，所以那部分没有改善 —— 这也是 ④"用几何先验替代回归"的**边界**：先验需要**至少两个峰**。

## 4. ②粗类 + D3 细化：**无效**（专门训粗类模型 = 没有提升；错类不是主要损失）

### 4.1 三个可比读数（同一验证集 519 GT，其中 container 245 / element 274）

| 方案 | container | element | coarse micro | 说明 |
|---|---|---|---|---|
| 8 类细分类模型（基线，**按粗类评**） | 0.176 | **0.442** | **0.316** | 事后把细类并成粗类算命中 |
| ①条带模型（7 类，按粗类评） | **0.229** | 0.380 | 0.308 | 条带模型顺带把 container 抬高了 |
| **专门训的 2 类粗类模型**（400 轮） | 0.204 | 0.405 | **0.310** | 只学 container/element |
| 差别（2 类模型 − 8 类模型事后评） | +0.028 | −0.037 | **−0.006** | 净收益 ≈ 0（噪声内） |

### 4.2 结论

- **把类别合并成 container/element 再训练，不会提高"大类正确率"**：0.310 vs 0.316（−0.6pp，噪声量级）。
- 原因是**错类不是 D2 的主要损失**：把「错类」也算命中（coarse 口径）只让非行实例的召回从 **0.376 → 0.442（+4.4pp）**；
  真正丢的是**整条实例没被检出**（漏检），不是"检出来了但叫错名字"。
  题面给的「icon/tile/chip 同构 → 49% 错类」是**在已匹配的检测里**的错类率，不能直接当成召回损失。
- **`text` 粗类不存在**：`annotations.json` 的 categories 只有 8 类，GT 里**零个 text 标注**，所以三类（container/element/text）
  里的 text **无从训练**——要它得先回到标注环节补 text 类（`gui-annotation`），不是模型层能补的。
- **给 D3 的建议**：粗类化在 D2 侧无收益，别为它重训；D3 直接拿 8 类模型的输出做「同构类（icon/tile/chip/button）归并 + 容器归属」即可，
  归并处用几何先验（尺寸/长宽比/是否在容器内），比让 D2 学一个更粗的分类头更省。
- 顺带读数：2 类模型的 **ndet 只有 399**（8 类 809、条带 1002）——粗类模型输出更"干净"，precision 更高（element 0.44 / container 0.34），
  若下游更怕误检（D3 结构推理），粗类模型可作**低噪通道**使用（代价是召回 0.31 vs 0.316，几乎相同但框更少）。

## 5. ③分辨率 1024×576：**方向成立（row 最高），但这台机器撑不住**

### 5.1 做法

从 ①的 640 模型**热启动**（权重与输入尺寸无关，`missing=[] unexpected=[]` 已核对），
在 1024×576 上微调：`--epochs 150 --lr 1.5e-4 --batch 2`。
**实际只跑到 ep80**：进程被父会话按「内存/swap 压力」杀掉（VmSwap 1.46GB，整机 swap 12GB 已在换页），
所以下面 1024 的读数是 **80 轮**、640 的读数是 **400 轮**——1024 还没收敛，**结论偏保守**。

### 5.2 读数（同一验证集 519 GT，同一 pitch 解码口径）

| 输入 | micro | row | panel | chip | button | tile | icon | p50 | p90 | 框数 |
|---|---|---|---|---|---|---|---|---|---|---|
| 640×360（①，400 轮） | **0.326** | 0.266 | 0.405 | 0.289 | 0.254 | 0.711 | 0.387 | **35.6ms** | 39.6ms | 1002 |
| 1024×576（①+③，80 轮） | 0.316 | **0.305** | 0.286 | 0.301 | 0.193 | 0.733 | 0.323 | 65.8ms | 72.6ms | 1554 |

- **行的收益最集中在 row 上**：0.266 → **0.305**（+14.7% 相对），与 §3.3 的诊断吻合
  （46px 的行在 640 下只有 2.9 格、在 1024 下有 4.6 格 → 行高/中心的可分辨度直接上去）。
- **代价**：p50 35.6 → **65.8ms（1.85×）**，框数 1002 → 1554（precision 全线下降），且训练显存/内存 **3–4 倍**。
- **micro 反而 −1.0pp**：其他类（panel/button/icon）在 80 轮里没跟上，且 1024 的 stride-4 网格更细 → 峰值更碎。

### 5.3 反证：「不重训、直接把图切块喂进去」不行（实测）

为了绕开 1024 的训练成本，试过**分块推理**：把 2560×1440 切成 2×2 块（每块 1280×720 带 160px 重叠），
每块 0.5× 后仍以 640×360 送进**同一个 640 模型**（行在模型眼里变成 5.8 格高），块内行框平移回原图 + NMS：

| 推理方式 | row recall | 每帧行框数 | p50 |
|---|---|---|---|
| 整图（640 输入） | **0.271** | 23–67 | 29ms |
| 2×2 分块（同权重） | **0.084** | 95–149 | 95ms |

⇒ **直接切块复用整图权重是灾难**（掉到 0.084，框数爆炸）：行在被裁掉上下文的块里是**分布外**目标。
想要分块收益必须**按块尺度重训**，不是推理技巧能捡的。这条记下来，省下后来者一次试错。

**裁决**：③ 只在"离线精修/换大机器"时值得；在 6GB 显存的 3060 laptop + 15GB 内存的这台机器上，
1024 训练会把整机拖进换页风暴（已实测发生），**不进生产线**。

## 6. ④损失层小改：**logw 不推荐启用；「宽框更差」的前提成立，但真正的杠杆不在损失函数**

### 6.1 做了什么

1. **`--loss logw`**：把 `wh` 头的回归目标换成 **log 空间 L1**（`log(wh+1)`，解码 `exp(clamp)−1`），
   即题面说的「h 回归换 log 空间」。
2. **`--aspect-w`**：热斑 BCE 的**逐格权重**——长宽比 >6 的正样本按 `min(1+ar/6, 6)` 加权（宽框正样本加权，IoU 感知的检测侧版本）。已实现并单测通过，**未跑完**（见 6.4）。
3. **`--wide-w`**：`wh` 头的宽框权重。同样未做完整 A/B。

### 6.2 等轮次 A/B（80 轮，640×360，条带架构，同一留族验证）

| 变体 | micro | row | tile | box p50 |
|---|---|---|---|---|
| 基线（base） | **0.170** | **0.232** | 0.644 | 37.6ms |
| logw | 0.106 | 0.123 | 0.400 | 40.9ms |

要硬结论需 3 个种子 × 400 轮，本机时间/内存不允许。

### 6.3 为什么 log 空间不是关键（真正的发现）

题面的推断是「h 在像素空间回归，对宽框/小框不公平」。
本轮实测把这条链拆开了：

- 行高在 ①的条带分支里**本来就是 log 空间回归**（`logh` 通道 + L1）。
- 而**问题不在 log 不 log，在于"回归"这件事本身**：`d2_hvar.py` 把行高换成「相邻峰间距 − 0.3 格」后，
  row **0.192 → 0.266（+39%）**，precision 0.128 → 0.177，**零训练成本**。
- 也就是说：列表/树的**行距本身就是行高**（等距平铺），比让网络回归行高稳得多。
  log 空间回归的绝对误差仍然被 2.9 格的量化吃掉（§3.3）。

⇒ ④ 的**可迁移结论**：与其在损失函数上给宽框加权，不如**用几何先验替代回归**（行距、容器高度、等距假设）。
这也解释了为什么 ②（粗类）和 ④（损失）都没什么收益——**信息量不在类别/损失上，在几何与分辨率上**。

## 7. 有效 / 无效清单（一句话版）

### ✅ 有效
1. **①行 → 1D 条带**：row **0.133 → 0.192**（+44% 相对，同 400 轮同口径）；**推理成本 ≈ 0**（p50 32.5→35.6ms）。
2. **行高用「相邻峰间距 − 0.3 格」代替 logh 回归**（纯解码层改动，零训练）：
   row **0.192 → 0.266**、precision 0.128 → 0.177。**本轮性价比最高的一条**，`decode_rows(pitch_gap=0.3)`。
3. 合起来：**row 0.084（v5 报送）→ 0.266 = 3.2×**；八类 **micro 0.272 → 0.326**。
4. 换解码器复评**老权重也有效**（不重训）——`--eval-only` 即可。

### ❌ 无效 / 不成立
1. **②粗类模型**：专门训 container/element 只有 **0.310**，比 8 类模型事后按粗类评（0.316）还低。
   错类只值 **+4.4pp**（非行实例 0.376→0.442），主要损失是**漏检**不是错类；且 GT 里**没有 text 类**，三类粗分无从训练。
2. **把 mask 的垂直支撑当行高**：row **0.010**（`cap` 变体 0.089）——mask 在 y 方向是糊的，别用。
3. **③1024 分辨率进生产线**：row 确实最高（0.305），但 p50 **65.8ms（1.85×）**、训练内存 3–4×、实测把整机拖进换页风暴。只适合离线精修。
4. **调解码阈值**：`thr_ctr` 0.15–0.40 × `thr_mask` 0.2–0.4 × `gap` 2/4/8 共 54 组合，row 只在 0.182–0.197 之间动 —— 阈值不是瓶颈。
5. **亚格 y 质心（cent）**：与峰值完全同分（0.192）；**把相邻峰中点当行中心**：0.202（更差）。
6. **分块推理（2×2，复用整图权重）**：row **0.084**（整图 0.271），p50 95ms —— 分布外，必须重训。
