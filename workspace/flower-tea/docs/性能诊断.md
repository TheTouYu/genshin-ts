# 模拟器「60 帧但很卡」诊断

> 2026-10-28，用户反馈：模拟器里 1s 渲染 60+ 帧，但实际卡；补充“卡是只有几帧”。  
> **更正后的结论**：这不是 30Hz 的观感问题。同一渲染路径下做 A/B，**6 个控件的场景 59.7 fps，276 个控件 0.72 fps，421 个控件 1.32 fps**，而三者逻辑帧都约 30。  
> ⇒ **这是模拟器渲染层在约 200+ 控件时的真实性能瓶颈/ bug 级表现**，不是三消 Lua 算不动，也不是“60 显示帧 vs 30 逻辑帧”的误读。


## 0. 关键 A/B（同一台机、同一页面、同一画布、自调度 rAF）

| 存档 | 可见图元 | 逻辑帧 | 自调度 rAF | rAF p50 |
|---|---:|---:|---:|---:|
| `counter-demo` | 6 | 30.36/s | **59.65/s** | 16.7ms |
| `tetris` | 276 | 30.00/s | **0.72/s** | 1150ms |
| `花间茶会` | 421 | 30.24/s | **1.32/s** | 500ms |

- 三个场景的 **Lua 逻辑帧都约 30/s**，但 **rAF 只有 6 控件场景是 60**；一上 276/421 控件就掉到个位数。
- 同一轮的 **longtask = 0 条**（不是单次 >50ms 的大卡死，而是大量细碎渲染把浏览器帧产出生吞掉）。
- GL 调用时间很低（约 22–33ms/s），说明不是“GPU 画不动”，更像 **Pixi 场景应用/渲染循环 + 浏览器合成**在 200+ 控件时的瓶颈。
- ⚠️ 这台测试用的是 headless Chromium + SwiftShader，**绝对 FPS 不能代表你的硬件**；但 counter 60 vs tetris 0.72 是**同一路径对照**，说明“场景规模”是主导变量。你机器上也出现几帧，方向一致。

## 1. 源码事实（不是猜）

- `studio/host/worker.js`：Web/DSH 使用 **33 ms 时钟 / `FIXED_DT = 1/30`**，最多追 5 步。  
  ⇒ 游戏逻辑、Lua `OnUpdate`、画面内容的更新是 **30 次/秒**。
- `web/public/play-renderer.js`：页面每 **33 ms** 拉一次快照（`PLAY_POLL_INTERVAL_MS`）；指针移动节流 **60 ms**（`PLAY_MOVE_THROTTLE_MS`）。  
  ⇒ 点击视觉反馈最多等 1~2 个轮询（约 33~66 ms），拖拽移动最多 60 ms 才发一次。
- 页面底栏的 **`Frame N`** 才是模拟器的逻辑帧；浏览器 FPS 浮层/合成器显示的 60 是**显示帧**。两者不是同一个数。

## 2. 本机实测读数

### 2.1 无头浏览器（同一份 `花间茶会.save.json`，本机 Chromium）

在临时 web server + 同一个存档上启动试玩，读取页面 `#frame`：

| 指标 | 读数 |
|---|---|
| 逻辑帧 | 4.36 s 内 131 帧 → **30.03 帧/s** |
| 页面 `#time` | 同步前进 4.36 s |
| 启动后 longtask | **0 条**（4.36 s 观察窗） |
| 启动瞬间 buffered longtask | 942 / 414 / 343 / 116 ms（首次建场景） |
| 无头 `requestAnimationFrame` | 被节流到 0.46 帧/s（**无头限制，不能代表你的机器**） |

> 无头 Chromium 的 `requestAnimationFrame` 会被节流，所以不要拿它的 rAF 数值判“卡不卡”；逻辑帧 30.03 是可靠的。

### 2.2 游戏本身每帧成本（Node headless，不含浏览器绘制）

| 项 | 读数 |
|---|---|
| 标题 `playStep(1/30)` | avg **2.17 ms** / p95 4.01 ms |
| 对局 `playStep(1/30)` | avg **0.53 ms** / p95 0.71 ms |
| 全量场景快照 | 224–280 KB / **3.7–4.5 ms** |
| 增量快照 | 2–4.5 KB / **0.03–0.05 ms** |
| 点击（服务端） | **< 3 ms** |

⇒ **Lua 逻辑和 JSON 序列化不是瓶颈**；瓶颈在「30 Hz 设计 + 浏览器侧绘制/输入节流」。

## 3. 怎么在你机器上测（按顺序）

### Step 1：先看 `Frame` 1 秒涨多少

在模拟器页面底部读 **`Frame N`**，隔 1 秒再读：

- **约 30** → 逻辑帧 30，符合设计；60 是显示帧。
- **约 60** → 逻辑时钟异常（或你开的是另一个版本的播放器）；记录页面 URL、模拟器版本、`Frame` 前后值，报给模拟器上游。

控制台脚本（独立 play 页面；若是嵌入 editor，加 `.qxsim-play-overlay iframe`）：

```js
const d = document.querySelector('.qxsim-play-overlay iframe')?.contentDocument || document
const el = d.querySelector('#frame')
const t0 = performance.now(), f0 = parseInt(el.textContent.match(/\d+/)[0], 10)
setTimeout(() => {
  const f1 = parseInt(el.textContent.match(/\d+/)[0], 10)
  console.log('logic FPS =', (f1 - f0) / ((performance.now() - t0) / 1000))
}, 2000)
```

### Step 2：看显示帧 vs 逻辑帧

在真实浏览器（不是无头）控制台跑 2 s `requestAnimationFrame`，同时读 `Frame`：

```js
let n = 0, t0 = performance.now(), last = t0, gaps = []
function f(t) { n++; gaps.push(t - last); last = t; if (t - t0 < 2000) requestAnimationFrame(f); else {
  gaps.sort((a,b)=>a-b)
  console.log('display FPS', n / 2, 'p95 frame ms', gaps[Math.floor(gaps.length*.95)])
}}
requestAnimationFrame(f)
```

- 显示 60 + 逻辑 30 = **不是游戏 bug**，是 30 Hz 设计。
- 显示 30 + 逻辑 30 = 浏览器也只画 30（可能软件渲染/掉帧）。
- 显示 60 + 逻辑 30，但输入延迟 >200 ms = 继续看 Step 3。

### Step 3：长任务 / 主线程阻塞

Performance 面板录 5 s，或控制台：

```js
new PerformanceObserver(l => console.log('longtask', l.getEntries().map(e => Math.round(e.duration)))).observe({ type: 'longtask', buffered: false })
```

连续出现 **>50 ms** 的长任务，说明主线程被绘制/场景应用阻塞；把 Performance 截图发我。偶发 1 次 900 ms 多半是**开局建 425~546 个控件**的首次场景应用。

### Step 4：A/B 对照

在同一个模拟器、同一画布下切换：

- `花间茶会.save.json`（本工程，开局约 425 控件 / 对局约 546）
- `tetris.save.json`（约 200 棋盘格）
- `counter-demo.save.json`（极小场景）

若三者逻辑帧都约 30 → 是模拟器设计；若只有花间茶会明显更卡 → 场景复杂度/绘制优化问题，我可以减控件或降动效。

### Step 5：画布和 GPU

- 切 `mobile-16-9`（1280×720）对比 `pc-16-9`（1600×900）；分辨率降低明显变好 = 绘制/GPU 瓶颈。
- Firefox `about:support` / Chrome `chrome://gpu` 看 WebGL renderer 是否为 `llvmpipe` / `SwiftShader`（软件渲染）。软件渲染下 500+ 控件会明显卡。

## 4. 判据表

| 读数组合 | 判断 | 处置 |
|---|---|---|
| Frame ≈30/s；rAF ≈60；长任务少 | 30 Hz 设计上限，**不是游戏 bug** | 要 60 需改模拟器时钟（`33ms/1/30` → `16.7ms/1/60`）或换桌面/原生试玩 |
| Frame ≈60/s | 逻辑时钟异常/版本差异 | 记录 URL+版本+前后值，报上游 |
| Frame ≈30；rAF ≈30；长任务多 | 浏览器绘制/主线程瓶颈 | Performance trace；减控件/动效，或检查软件渲染 |
| 点击后 >200ms 才有变化 | 输入/轮询/绘制链路延迟 | 查 `PLAY_POLL_INTERVAL_MS=33`、`PLAY_MOVE_THROTTLE_MS=60`、长任务 |

## 5. 结论（更正版）

- **已复现：场景 200+ 控件时浏览器 rAF 掉到个位数**，而逻辑帧仍是 30；`tetris`（276 控件）同样中招，所以**不是花间茶会独有的 Lua 逻辑问题**，是模拟器渲染层/场景规模的瓶颈。
- **不是“60 显示 vs 30 逻辑”的观感问题**：`counter-demo` 6 控件能跑 59.7 rAF；一上控件就崩，说明你看到的“几帧”是真实的渲染掉帧。
- **可修方向**（按优先级）：
  1. **节点瘦身**：把标题 421 → 约 150、对局 546 → 约 250，再复测；这是游戏侧最可控的。
  2. **模拟器渲染层优化**：`applyScene`/Pixi 批处理、静态节点缓存、跳过无变化重绘；这是上游/本地 fork 的修法。
  3. **降画布/降 DPR**：1600×900 → 1280×720，先确认是否填充率主导。
- **测试方法**：同一页面同一画布，在控制台自调度 `requestAnimationFrame` 2.5s，同时读底栏 `Frame`；再切 counter/tetris/花间茶会三份存档做 A/B。只看底栏 `Frame` 不够（它只证明逻辑帧 30，不证明浏览器画得出来）。
