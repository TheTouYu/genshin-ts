## 摘要（三十秒版）

现工程是「无尽 + 3 个对战/演出模式」，**没有任何关卡层**（`关卡/闯关/章节/campaign` 在 `lua/` 与 `docs/` 全文 0 命中）。本企划补的是这一层：

- **一句话玩法**：把现在的无尽俄罗斯方块切成一串**有终点的关卡**，每关给你一个**行数配额**，消满就通关，堆到顶就失败。
- **核心目标**：让玩家为了「**再多消 3 行就过关**」而在高速档继续冒风险，而不是在第 8 级时因为"反正也打不完"就放手。
- **难度不靠速度，靠 ρ**。这是本工程已验证的结论：目标 L 行的硬门槛是 `ρ ≥ 4L/(170+10L)`，速度为 0 也改变不了它。速度只是把门槛"催"出来。
- **7 关阶梯**（12→60 行）已算实，每关都有可机检的 ρ 门槛与预计时长。
- **一个必须先决的前提**：`OBSTACLE`（开局障碍行）在现网是**死分支**，一行都不会生成。要不要真开，是产品决策，本文给了两个方案。

## 一、玩法类型与概述

### 1.1 玩法类型

**标签：`俄罗斯方块 · 闯关（关卡制）`**

官方说得很清楚：类型不是限制创意的答案，作用是**给自己一个方向，防止制作中偏离目标**。所以这个标签要回答的只有一件事——玩家主要玩什么？

**玩家主要玩的还是俄罗斯方块本身**：旋转、横移、消行。闯关层不新增操作，不新增按键，不改任何一条现有玩法规则。它改的是**结束条件**：从"堆到顶为止，看你撑多久"改成"消满这一关的配额就通关"。

> ⚠️ 这是本企划最重要的一条边界。理由【实测】：现工程 `lua/main.lua` **5784 行** + `lua/tetris/` **39 模块 16843 行**（`wc -l` 实测），UI/技能/文案/双人/AI 全部已接线，并有 **80 个模拟器用例**（`tests/*.json`，`qxqy/runner.mjs` 全量跑）守着。**任何新增机制都会碰这套回归**。关卡层只要能做到"零新机制、只改结束条件"，就能落到现成的 `core_state.gameOver` 与 `view_settle` 上，不改玩法核心。

**不是**这个类型的情况：如果你想要的是"每关解锁一个新机制"（比如第 3 关才出现垃圾行、第 5 关才出现限时），那就变成**机制递进型闯关**，成本会高一个量级——但见 §2.3，现工程其实**已经有两个现成的难度旋钮**，够用。

### 1.2 玩法概述

官方要求这一节只写三件事：**玩法方向、主要操作、通过条件**，不要长篇。

| 项 | 内容 |
|---|---|
| **玩法方向** | 关卡制俄罗斯方块。每关开局给一张「通关配额」卡（消 X 行 / 限时 Y），玩家在标准 10×20 棋盘上堆叠消行，消满配额即通关 |
| **主要操作** | **完全不变**：←/→ 横移、↑ 旋转、↓ 软降、空格硬降、G 暂存（`NUM.HOLD_KEY`）。键盘 + 手柄（`main.lua:5248` 24 条 Controller 事件）+ 手机触屏键全部沿用 `input_map.lua` 现有映射，零新增 |
| **通过条件** | `lines ≥ 本关配额` 且未顶死。顶死（`core_state` 的 `gameOver`）= 本关失败，可无限重试 |
| **玩家反复做的事** | 判断这一块落哪 → 旋转/横移 → 落地 → 看行数涨了没有 → 差几行时决定"稳一手还是冲一把" |

**一句话描述**：*"消满 30 行。你现在差 3 行，速度已经到 0.15 秒一格了——你要不要为了这 3 行再冒险一次？"*

## 二、核心目标与主流程

### 2.1 核心目标

官方定义：核心目标 = **最希望玩家在这一局里最终达成什么成果**，它决定后面该加什么、不该加什么。

**本作核心目标：把「你能撑多久」变成「你能不能过这一关」。**

这句话不是修辞，它有可验证的差别【实测】：

- **无尽模式现状**：玩家在第 8 级（0.20s/格）时，如果 ρ 只有 0.25，模型告诉他顶死前最多 28 行——他离 L12 的 110 行差得远。**理性的选择是放弃**。这就是无尽模式在高等级时"手感发空"的数学原因。
- **关卡制**：同样是 ρ=0.25 的玩家，在"消满 30 行"的关卡里门槛是 0.255——**差 0.005，几乎就是能过**。他会为了这 30 行继续投入，而且过关时的成就感是"我赢了"而不是"我死了"。

围绕这个目标，**该加的**是：配额卡与行数进度的可见性、过关/失败的结算差异、重试成本为零。
**该放一放的**是：新道具、新方块形状、技能扩展、剧情。它们服务的是"玩更久"，不服务"这一关到底过不过得去"。

### 2.2 主流程

官方给的「准备阶段—游戏阶段—结算阶段」是参考不是模板。本作直接采用，因为现工程三个阶段的载体全都已经存在：

#### 准备阶段（进入关卡 → 开始游戏前）

| 要做的事 | 现状落点【实测】 |
|---|---|
| 让玩家理解目标 | 现成：`view_note` / `botBanner` 常驻提示位；开局打一行 `stage quota = 30 lines` |
| 让玩家做初始选择 | 现成：标题页四模式卡（`view_title.lua:110` 的 `M.CARD.rows`，最多 4 张）→ 闯关占第 5 张，需扩到 5 卡或改成"模式 → 关卡列表"两级 |
| 熟悉操作 | 现成：`view_help`（476 行纯描述，`tests-lua/view_help_test.lua` **58 断言全绿**已验），无需新增 |
| 关卡列表 | **需新增**：一个 `view_stages` 纯描述屏（照 `view_title`/`view_settle` 的现成手法：`M.new{config,layers,kit}` → node 数组）。这是本企划唯一的新 UI 面 |

#### 游戏阶段（主要游玩）

这是需要说清楚"**难度如何变化**"的地方。现工程有三条轴，其中两条能立刻用：

| 轴 | 现值【实测】 | 在闯关层怎么用 |
|---|---|---|
| **① 重力速度** | `NUM.SPEED = {30,26,23,20,18,15,14,12,10,9,8,7}` 拍/格 ⇒ L1 0.500s → L12 0.117s（`config.lua:49`） | **直接用**。每关按配额决定起始等级，速度曲线原封不动 |
| **② 干燥垃圾** | `NUM.DRYNESS_N = {14,10,7}`（`config.lua:123`；连续 N 块不消行顶 1 行带洞垃圾，`core_state.lua:218-226`） | **直接用**，且这个机制天然与"差几行"配合：它惩罚拖延。可选是否在低关卡关闭 |
| **③ 开局障碍行** | `NUM.OBSTACLE = {0,1,2,3}` —— ⚠️ **死分支**：`core_state.lua:391` 注释写明这段跑在 `level=1` 之后 ⇒ `seg` 恒为 1 ⇒ `OBSTACLE[1]=0` ⇒ **一行都不生成** | **需决策**，见 §2.3 |

**资源与反馈**：现成的 `NUM.SCORE/B2B/COMBO` 计分、`fx.lua` 的特效与横幅、`audio.lua` 的音效，全部沿用。关卡层只需要在 `lines` 越过配额的瞬间抛一个 `kind='stageClear'` 事件。

#### 结算阶段（通关 / 失败 / 退出后）

现成 `view_settle.lua` 已经在显示：`本局 N 分 / 最高 N / 消行 X 行 落块 N 等级 Z`（`view_settle.lua:306-315`，`settleScore`/`settleBest`/`settleInfo` 三条）。关卡层只加**一行**：

```
本关 30/30 行 ✓ 通关          或          本关 22/30 行 ✗ 差 8 行
```

通关额外给一个「下一关」按钮，失败给「重试」——两个按钮现网已有同类实现（`SETTLE_ACT.restart`）。

### 2.3 关卡阶梯（已算实，可直接抄进 `NUM`）

**这是本企划的硬核部分。** 现工程已验证的存活模型【实测 `docs/数值策划.md` §4.1 容量模型 / §4.2 时长】：

```
可用容量 C = 170 − 10×R      （R = 开局障碍行数；170 = 20 行 × 10 列 − 出生占 3 行）
净增长 = 4 − 10ρ            （ρ = 消行/块，上限 0.4）
顶死块数 N = C / (4 − 10ρ)
消满 L 行所需 ρ 下限 = 4L / (C + 10L)
```

有了它，每一关的难度就**不是拍脑袋填数字**，而是"我要玩家至少做到多少消行效率"：

| 关 | 配额 L | 障碍 R | 容量 C | **ρ 门槛** | 打包效率 | 需块数 | @τ=1.0s | @τ=1.6s | @τ=2.4s |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| S1 | 12 | 0 | 170 | **0.166** | 41% | 72 | 72s | 116s | 174s |
| S2 | 20 | 0 | 170 | **0.216** | 54% | 92 | 92s | 148s | 222s |
| S3 | 30 | 1 | 160 | **0.261** | 65% | 115 | 115s | 184s | 276s |
| S4 | 20 | 2 | 150 | **0.229** | 57% | 88 | 88s | 140s | 210s |
| S5 | 40 | 2 | 150 | **0.291** | 73% | 138 | 138s | 220s | 330s |
| S6 | 50 | 3 | 140 | **0.313** | 78% | 160 | 160s | 256s | 384s |
| S7 | 60 | 4 | 130 | **0.329** | 82% | 182 | 182s | 292s | 438s |

**怎么读这张表**（三条读法决定了它是否可信）：

1. **配额涨得比门槛快**：S1→S7 配额 ×5（12→60），ρ 门槛只 ×2（0.166→0.329）。因为 ρ 的上限是 0.4，**门槛天然是收敛的**——这保证了关卡数可以加，不会出现"第 15 关需要的效率人类不存在"。
2. **S4 的配额比 S3 低是故意的**：S4 加了两行障碍（容量 −20 格），同样 30 行会突然要求 ρ=0.31。所以**回落到 20 行**，让难度是"棋盘变脏了"而不是"效率要求跳崖"。这是本阶梯唯一的非单调设计，也是最需要试玩确认的一处。
3. **时长列是同一张表 × τ**：本工程 AI 自演 300s 实测 **τ=2.58s/块、ρ=0.145**（`docs/数值策划.md:348` 基线读数）。人类新手要 2~4 分钟，反解出 **τ ∈ [2.26, 4.52] s/块**（`docs/数值策划.md:373`）。**S1 在 τ=2.4 时 174s ≈ 2.9 分钟**，正落在新手目标带内。

> **试玩唯一要测的数**：每关的 τ（秒/块）与 ρ（本关实际消行/块数）。这两个数一测出来，整张表就能回代校准，不用猜。

### 2.4 前提决策：`OBSTACLE` 死分支要不要真开

`NUM.OBSTACLE = {0,1,2,3}` 的注释写着「Lv1-4 无 / Lv5-7 一行 / Lv8-10 两行 / Lv11+ 三行」，但【实测】它现在一行都不生成，理由写在 `core_state.lua:391`：那段代码跑在 `s.level = 1` 赋值之后，`seg` 恒为 1，而 `OBSTACLE[1] = 0`。

这不是 bug，是**从 main.lua 搬运时原样保留的死分支**，注释原话：「要不要真开是产品决定」。

两个方案：

| 方案 | 做法 | 成本 | 适合 |
|---|---|---|---|
| **A. 保持死着**（推荐先这样） | 关卡难度只用「配额 + 起始等级」两个旋钮，障碍行恒 0 | **零改动**；上表 R 列全填 0，S1-S7 门槛改为 0.166/0.216/0.261/0.281/0.291/0.313/0.329 | 先验证「配额制」这一个假设是否成立 |
| **B. 真开** | 把生成逻辑挪到 `s.level` 赋值**之前**，并按关卡配 `OBSTACLE` | 一处移动 + 关卡参数；要重跑 80 个模拟器用例（`OBSTACLE` 影响开局棋盘 ⇒ 出块/顶死相关用例期望值可能变） | 配额制验证通过后，用来做"棋盘变脏"这一维度 |

**建议**：先 A 后 B。A 能证明"玩家会不会为了配额继续玩"这个**核心假设**；B 只是给已经成立的东西加一个难度维度。反过来做，等于在假设没验证前先付回归成本。

### 2.5 一个必须说清的限制：进度不跨会话

【实测】现工程 `bestScore` 是 `main.lua:302` 的**全局变量**，注释写明"全局共享"；`skills.lua` 的经验/等级在 `OnStart` 由 `skills.newState` 创建。全仓 `grep storage|SavedVar|savedata` **0 命中**——**没有任何玩家侧持久化通道**。

这和 `PLAN-v6.16-production.md` §3「最高分跨会话持久化 = 不做」的结论一致：官方客户端 API 无玩家侧存储接口，唯一持久化手段是"技能变量"（属点名的技能域）。

**所以关卡进度也是会话内的**：退出重进，从 S1 开始。这决定了关卡设计的一个隐含要求——**单次会话内要能玩完全部内容**。按上表 τ=1.6s 算，S1→S7 合计约 1356s ≈ **22.6 分钟**。这是一次坐得住的长度。

> 如果之后要真持久化，需要的是「局内存档」能力。【实测】仓库根 `docs/maintenance/m1-full-flow-inventory.md:74` 记录：局内存档 **结构体侧已支持**（`assets:structs create --archived`，folder 33/typeValue 4600），状态 🟡。不在本企划范围内，但它是这条线的下一步。

## 三、收尾

官方对企划书的定位是「**这段思考的起点**」：后续制作中遇到新想法或调整方向时，回过头看这些变化是否还与自己最初为关卡设定的玩法方向一致。

**所以，这份企划里最该被记住的不是那张阶梯表，而是这一句边界：**

> **闯关层只改结束条件，不改玩法规则。**

只要守住这条，关卡层就能落在现成的 `core_state.gameOver` + `view_settle` + `view_title` 上，80 个模拟器用例的行为契约不动。一旦开始往关卡里塞新机制，成本就从"加一屏"变成"重跑整套回归 + 重新设计难度模型"。

**三个待你裁决的点**（按影响面排序）：

1. **做不做闯关层？** —— 现工程已经生产可玩（`PLAN-v6.16` 6 步全 ✅）。闯关是「从能玩到有目标」的一层，不是修 bug。
2. **`OBSTACLE` 走 A 还是 B？** —— 建议 A（零改动先验证核心假设）。
3. **7 关够不够，还是要更多？** —— 阶梯公式可外推（`ρ = 4L/(170+10L)`），加关不用重新算模型，只需确认 τ 实测值。
