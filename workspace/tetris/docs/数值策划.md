## 0. 三分钟摘要（结论先行）

1. **计分表保留 `100/300/500/800`，但它不是 NES 表**，而是现代 **Tetris Guideline** 表。NES 的经典表是 `40/100/300/1200`。
   任务书里"现 100/300/500/800 = 经典 NES 表"这个前提**不成立**，依据见 §2.1。
2. **`pts × level` 保留**（level 从 1 起算），**不要改成 `(level+1)`** —— `level+1` 是 NES 口径（NES 的 level 从 0 起）。
3. 新增：软降 `+1/格`、硬降 `+2/格`（**平值，不乘等级**）、连击 `50×combo×level`、B2B `×1.5`。
4. **速度必须新加一张帧表**（对齐现有 `tickCount % GRAVITY_TICKS` 机制）：`30/26/23/20/18/15/14/12/10/9/8/7` tick/格，
   **等级上限 12**（110 行）。**不能直接用 Guideline 公式**：它 L10=0.064s/格、L15=0.007s/格，而本工程**没有锁定延迟**（落不下去立刻锁定），
   到那两档人类物理上打不了（§3.1）。
5. **两个"目标时长"不是调参数调出来的，是玩家效率（ρ = 消行/块）的函数**：
   - 新手 2~4 分钟 ⇔ ρ≈8% 时**每块 2.0~3.5s**（本项目 AI 自演实测 2.58s/块 正好落在带内 ⇒ 2.2 分钟 ✓）；
   - 强玩家 5~8 分钟到上限 ⇔ **ρ ≥ 0.346**（85% 打包效率）且每块 0.9~1.5s。**"消行率 >20%"的玩家到不了 5 分钟**（会 1.7 分钟死在第 2 级），
     20% 与 5~8 分钟这两个目标**互不相容**，必须挑一个当验收口径（§4.4 / §9③D1）。
6. **已存在的计分缺口（P0）**：`clearLines` 里 `score = score + pts[cleared] * level` **没有 `autoDriving` 守卫**，
   而入场 AI 自演期间会真的消行（日志 `demo clear n=`）⇒ **玩家接管时 HUD 可能不是 0 分**，`pieceCount`（落块数）也含 AI 的块，
   连带结算页的"消行率"被低估。这与任务书"自演期间不应计分"的意图冲突，见 §7 P0。

## 2. 计分

### 2.1 基础分：保留 `100 / 300 / 500 / 800`

| 表 | 1 行 | 2 行 | 3 行 | 4 行 | 倍率 | 依据 |
|---|---|---|---|---|---|---|
| **NES（1989 任天堂）** | 40 | 100 | 300 | 1200 | `×(level+1)`，level 从 0 起 | 【经典】 |
| **Tetris Guideline（现代）** | 100 | 300 | 500 | 800 | `×level`，level 从 1 起 | 【Guideline】 |
| **本工程现值** | 100 | 300 | 500 | 800 | `×level` | 【实测】L746 |

> 说明：本节的两张外部表是**通行文献口径**，本轮网络不可用（`web_search`/`web_fetch` 均 `fetch failed`），
> 未能拉取 `tetris.wiki` 原文复核；若要写进对外文档，建议补一次联网核对。

**选 Guideline 表、不选 NES 表的理由**（三条，按权重）：
1. **奖励结构更合理**：Guideline 四消/单消 = 8.0 倍；NES = 30 倍（level 越大差距越大）。NES 结构下"只做四消"是唯一理性打法，
   新手会被诱导去憋四消（这个 demo 的引导语恰好是「一次消 4 行 +800」，而 NES 表下那句文案就得改成 +1200）。
2. **`×level` 与现有 `level` 基址（从 1 起）自洽**，零改动；换 NES 表就得同时把倍率改成 `(level+1)`，两处联动。
3. **幅度与反馈匹配**：一局典型分数落在 10³~10⁴ 量级（§6 E4），HUD 单行放得下，不会出现 6 位数挤爆 20 号字（HUD 宽度已到极限，见 §8.1）。

### 2.2 掉落分：软降 `+1/格`、硬降 `+2/格`，**平值不乘等级**

| 参数 | 值 | 依据 |
|---|---|---|
| `SOFT_DROP_PER_CELL` | 1 | 【Guideline】现代标准 1 分/格 |
| `HARD_DROP_PER_CELL` | 2 | 【Guideline】现代标准 2 分/格 |
| 是否乘 level | **否** | 【推断】见下方权重表 |

**为什么平值（不乘等级）**：掉落分是"你没浪费时间"的微量奖励，它的量级应与"块"挂钩，而不是与"进程"挂钩。
若乘 level，L10 时一次 18 格硬降 = 360 分 ≈ 单消的 36%，会长期盖过"消行得分"这条主线。平值下权重随等级自然收敛：

| 等级 | 单消 | 一次 18 格硬降 | 单消 / 硬降 |
|---|---|---|---|
| 1 | 100 | 36 | 2.8× |
| 5 | 500 | 36 | 13.9× |
| 10 | 1000 | 36 | 27.8× |
| 12 | 1200 | 36 | 33.3× |

**已知代价（不打算修，写在这里备查）**：新手期（ρ=8%）分数会以硬降为主 —— 53 块 × 36 = 1912 分（硬降）vs 约 425 分（消行），
硬降占 82%。这是"标准表 + 新手低消行率"的固有结果，**不是 bug**：随等级上升比重自动反转，且新手若不满地乱按空格，实际落在 300~600 分的量级。
若要彻底消掉这种偏斜，唯一干净的办法是**只给软降加分、硬降 0 分**（TGM 风格），但这会让本 demo 的"空格 直落到底"教学失去正反馈。

### 2.3 连击（Combo）

```
本块有消行：
    combo = combo + 1                 -- combo = 连续消行的"块"计数（1,2,3...）
    bonus = 50 * (combo - 1) * level  -- 第一块不给，第二块起给
本块无消行：
    combo = 0
```
| 参数 | 值 | 依据 |
|---|---|---|
| `COMBO_RULE.base` | 50 | 【Guideline】`50 × combo × level` |
| combo 从 0 起算的含义 | 第二块连消 = `+50×1×level` | 【推断】与 Guideline 的"combo 计数从第二次起 = 1"对齐 |

### 2.4 Back-to-Back（连续两次四消）

```
hard = (cleared == 4)
if hard and b2b then bonusB2B = base // 2 end   -- base×1.5 = base + base/2
b2b = hard                                       -- 非四消（1/2/3 行）清掉 b2b；没消行不影响 b2b
```
| 参数 | 值 | 依据 |
|---|---|---|
| `B2B_MULT` | 1.5（只作用于**基础分行**，不加在连击/掉落分上） | 【Guideline】 |
| 取整 | `base // 2`（base 恒为偶数：100/300/500/800 × 整数 level ⇒ 无小数） | 【推断】避免 float 进 HUD |
| 断链条件 | 出现 1/2/3 行消除即断 | 【Guideline】T-spin 本项目没有，故只认四消 |

### 2.5 等级乘数：用 `level`，不要 `(level+1)`

`level = lines // 10 + 1` 意味着初始 level=1（不是 0）。Guideline 的 `×level` 就是乘 1 起步；
换成 `(level+1)` 会让 L1 的单消 = 200 分，等于把基址和倍率重复加了一次。

### 2.6 可选：清盘奖励（默认关）

`PERFECT_CLEAR_BONUS = 0`（关闭）；若开启：`+ 1000 × level`。**理由**：AI 自演 300s 里出现过 4 次清盘（README §10.9 实测），
说明这局棋盘形状下清盘并不罕见；但它会让分数方差变大，且要额外 4 处判定（棋盘全空）。建议留作 P2。

### 2.7 计分顺序（可直接抄的 Lua 片段，`clearLines` 内）

```lua
local SCORE_TABLE = { 100, 300, 500, 800 }
local COMBO_RULE  = { base = 50 }
local B2B_MULT    = 1.5
local PERFECT_CLEAR_BONUS = 0        -- 0 = 关闭

-- 有消行时（cleared >= 1）
local oldLevel = level
local base     = SCORE_TABLE[cleared] * level
local hard     = (cleared == 4)
local b2bBonus = (hard and b2b) and (base // 2) or 0
combo = combo + 1
local comboBonus = COMBO_RULE.base * (combo - 1) * level
b2b = hard
maxCombo = math.max(maxCombo, combo)   -- 结算页『最高连击』用
score = score + base + b2bBonus + comboBonus
lines = lines + cleared
level = math.min(LEVEL_CAP, lines // LEVEL_UP_LINES + 1)
-- 无消行时：combo = 0（b2b 保持不变）
```

## 3. 速度曲线

### 3.1 为什么不能直接用 Guideline 公式

`t(L) = (0.8 - (L-1)×0.007)^(L-1)` 秒/格，代入（本轮实算）：

| level | Guideline 间隔 | 折合 tick(60Hz) | 18 格落到底耗时 |
|---|---|---|---|
| 1 | 1.0000 s | 60.0 | 18.0 s |
| 5 | 0.3552 s | 21.3 | 6.4 s |
| 10 | **0.0642 s** | 3.8 | 1.15 s |
| 15 | **0.0071 s** | 0.4 | 0.13 s |

两个致命点：
1. **L10 起已不是人类档位**：0.064s/格 ⇒ 方块 1.15 秒从顶掉到底。Guideline 游戏能这么干是因为有**锁定延迟（lock delay ≈0.5s）+ DAS/ARR**
   兜底；**本工程没有**：`local function stepDown()` 一旦 `collides(...y+1)` 就立刻 `doLock()`，没有落地缓冲、没有左右长按连发（按键是离散事件）。
2. 公式在前 5 级又**太慢**：L1=1.0s/格 ⇒ 18 秒落一块，玩家会以为游戏卡住了（现在的 0.5s 已经是"开局就中速"的手感，不能让 L1 反而变慢）。

### 3.2 选帧表（与现有机制同构）

现有重力判定是 `tickCount % GRAVITY_TICKS == 0`（L1887），**最小改动就是把整数 30 换成一张按等级取的整数表**：

- 曲线形状：`t(L) = 0.5 × 0.876^(L-1)` 秒/格（每 5 级约折半：0.5 → 0.30 → 0.15 → 0.083）
- 实现形态：**帧表**（整数 tick/格），不是浮点秒 —— 与 `modulo` 判定天然兼容，且人眼可逐档核对
- 封顶：从 **L12** 起固定 7 tick（0.117s/格）
- 为什么是 0.117s 而不是更快：L12 时 18 格下落 = **2.1 秒**，这是"看一眼 → 决定 → 挪 3~4 格 → 硬降"的物理下限；再快就只能纯赌

### 3.3 完整速度表（L1~L15）

**本设计（选定公式）的四个锚点值**：`L1 = 0.500 s/格`、`L5 = 0.300 s/格`、`L10 = 0.150 s/格`、`L15 = 0.117 s/格`（已封顶）；
对照同一四档的 Guideline 公式值 = `1.000 / 0.355 / 0.064 / 0.007 s/格`（§3.1）。两条曲线的关系是"前段稍快、后段压平"：
L1~L6 本设计比 Guideline 略快（0.500 vs 1.000 → 0.250 vs 0.262，保持现有手感、不让开局变拖沓），
L7 起反转成远慢于 Guideline（L10 0.150 vs 0.064、L15 0.117 vs 0.007），**把那条指数曲线在后半段压平成可玩区间** ——
这正是"本工程没有锁定延迟"这一实现约束下的取舍。

### 3.4 每级行数与上限：为什么是 10 行/级 + 上限 12

三个候选（都用 §4 模型算过，"到上限的耗时"取 ρ=0.35 玩家）：

| 方案 | 每级行数 | 上限 | 到上限总行数 | 到上限块数 | 到上限耗时（τ=1.0 / 1.1 / 1.5 s） | 评价 |
|---|---|---|---|---|---|---|
| **A（推荐）** | 10 | 12 | 110 | 314 | **5.2 / 5.8 / 7.9 min** | 正落在 5~8 分钟带；且"能否活到上限"与"能否活下来"是同一条边界（§4.4） |
| B | 8 | 15 | 112 | 320 | 5.3 / 5.9 / 8.0 min | 总行数等价，但升级提示每 8 行一次（更频繁的反馈，也是一种"更热闹"的选择） |
| C | 10 | 10 | 90 | 257 | 4.3 / 4.7 / 6.4 min | 更早到顶，之后是"满速生存赛"（到顶后还能再活 2~3 分钟） |

**选 A 的两条理由**：
1. `level = lines // 10 + 1` 是现值，A 方案**只加 `math.min(LEVEL_CAP, ...)` 一个包裹**，不动除法常量 —— 在"另一代理正在改同一文件"的前提下，改动面越小越好。
2. A 的 110 行恰好等于"ρ≈0.3465 的玩家刚好在到达上限的那一刻顶死"（§4.4 的边界），语义干净：**上限 = 你活不到，除非你几乎不犯错**。

> 注意：A 和 B 的总行数几乎一样（110 vs 112），**真正改变体验的是上限数字大小**（HUD 上写 12 还是 15），不是难度。

## 4. 难度节奏

### 4.1 容量模型（先推公式，再代数字）

- 棋盘 10×20 = 200 格；出生方块占 3 行（3 宽方块在 y=1 时占第 1~3 行）⇒ **可用容量 C = 170 格（17 行）**
- 每块填 4 格；每清 1 行移走 10 格 ⇒ **净增长 = 4 − 10ρ 格/块**，其中 **ρ = 消行/块**（注意：ρ 的上限是 **0.4**，
  即每 10 块消 4 行 = 100% 打包效率；"消行率 20%" = 半个满效率，不是"及格线"）
- 存活块数 `N = 170 / (4 − 10ρ)`（ρ < 0.4；ρ ≥ 0.4 永不堆顶）
- 存活时长 `T = N × τ`，τ = 每块耗时（秒）

| ρ（消行/块） | 打包效率 ρ/0.4 | 净增长（格/块） | 顶死块数 N |
|---:|---:|---:|---:|
| 0.05 | 12.5% | 3.50 | 49 |
| **0.08（任务书新手假设）** | 20% | 3.20 | **53** |
| 0.10 | 25% | 3.00 | 57 |
| 0.145（本项目 AI 自演实测） | 36% | 2.55 | 67 |
| 0.20 | 50% | 2.00 | 85 |
| 0.25 | 62.5% | 1.50 | 113 |
| 0.30 | 75% | 1.00 | 170 |
| 0.32 | 80% | 0.80 | 213 |
| 0.3465 | 86.6% | 0.54 | 318 |
| 0.35 | 87.5% | 0.50 | 340 |
| 0.38 | 95% | 0.20 | 850 |

> ⚠️ **模型是乐观上界**：它假设玩家每一块都落在"平均净增长"上，不模拟局部失误（一次塞不进去就把棋盘挖出洞）。
> 真实玩家会在高速度档出错，提前顶死，实测到达的等级通常比模型低 **1~2 级**；所以本模型用来定"上限与门槛"，
> 不用来预测某个具体玩家的分数。校准方式是真机测出 τ 与 ρ 后回代（§4.6）。

### 4.2 新手能玩多久：**由 τ 决定，不由速度曲线决定**

| ρ | 顶死块数 | τ=1.2s | τ=1.5s | τ=2.0s | τ=2.5s | τ=3.0s |
|---:|---:|---:|---:|---:|---:|---:|
| 0.08 | 53 | **1.06 min** | 1.33 | 1.77 | **2.21 ✓** | 2.66 ✓ |
| 0.145 | 67 | 1.33 | 1.67 | 2.22 ✓ | 2.78 ✓ | 3.33 ✓ |
| 0.20 | 85 | 1.70 | 2.12 ✓ | 2.83 ✓ | 3.54 ✓ | 4.25 ✗(超 4) |
| 0.30 | 170 | 3.40 ✓ | 4.25 ✗ | 5.67 ✗ | 7.08 ✗ | 8.50 ✗ |

**关键结论**：
- 任务书给的"落块 1.2s/块、消行率 8%" ⇒ **53 块 × 1.2s = 64 秒（1.1 分钟）**，**达不到 2~4 分钟**。差 2~4 倍，且**调速度曲线救不了**
  （L1 的 9 秒下落预算对新手完全不是约束 —— 是玩家自己按得快）。
- 换成**本项目自己的实测锚点**（入场 AI 自演 300s 平均 2.58s/块，且是刻意"拟人节奏"）⇒ 53 × 2.58 = **137 秒 ≈ 2.3 分钟 ✓**
- 所以**"新手 2~4 分钟"这条目标成立与否，等价于"真实新手每块是不是愿意花 2~3.5 秒"**。这是纯手感问题，只能真机试玩测（§4.7），
  离线只能把边界算出来：**要 2~4 分钟，新手必须 τ ∈ [2.0, 4.5] s/块**。

### 4.3 强玩家到上限：需要 ρ ≥ 0.346（模型硬边界）

到等级 L 需 `(L−1)×10` 行；在顶死前能否到达的条件（解 `行数/ρ ≤ 170/(4−10ρ)`）：

```
ρ ≥ 4 × 行数 / (170 + 10 × 行数)
```

| 目标等级 | 需要行数 | 到达所需最小 ρ | 实际含义 |
|---:|---:|---:|---|
| 5 | 40 | 0.281 | 70% 打包效率 |
| 8 | 70 | 0.322 | 80% |
| 10 | 90 | 0.336 | 84% |
| **12（推荐上限）** | **110** | **0.346** | **86.6%** |
| 15 | 140 | 0.357 | 89% |

**到上限耗时**（块数 = 行数/ρ，乘 τ）：

| ρ | 到 L12（110 行）块数 | τ=1.0s | τ=1.1s | τ=1.5s |
|---:|---:|---:|---:|---:|
| 0.30 | 367 | — 顶死前到不了（上限 213 块） | — | — |
| 0.32 | 344 | — 顶死前到不了（213 块） | — | — |
| 0.3465 | 318 | 5.3 min ✓ | 5.8 min ✓ | 7.9 min ✓ |
| 0.35 | 314 | 5.2 min ✓ | 5.8 min ✓ | 7.9 min ✓ |
| 0.38 | 290 | 4.8 min | 5.3 min ✓ | 7.2 min ✓ |

**结论：5~8 分钟窗口对应的玩家画像是「ρ≈0.35（87% 打包）+ 每块 1.0~1.5 秒」，不是 20% 消行率。**
20% 消行率的玩家（ρ=0.20）在模型里 **85 块、1.4~2.8 分钟、死在第 2 级**（17 行）—— 两个目标不相容，见 §9③D1。

### 4.4 为什么上限定 12（而不是 15）

- L15 需要 ρ ≥ 0.357（**89% 打包效率**），且必须恰好活到那一刻；模型内几乎没有余量 ⇒ HUD 上写 13/14/15 是"写了也看不到"。
- L12 需要 ρ ≥ 0.346，与"5~8 分钟"带的下沿重合 ⇒ 上限与验收口径**用同一条判据**，省掉一层推断。
- 若改成"速度在 12 封顶、等级数字继续涨到 15"（解耦）：分数倍率还能涨 25%，但 HUD 会长期停在"等级 12 + 满速"，
  提示语（§5.3）也就不再有新内容 ⇒ 收益低。**解耦方案列为备选**（§9③D2）。

### 4.5 本项目的真正难度轴

```
难度 = 玩家消行效率 ρ 与棋盘容量 C 的赛跑（ρ < 0.346 时速度曲线基本无关紧要）
       速度曲线只对 ρ ≥ 0.30 的玩家起作用，因为低 ρ 玩家在 L1~L3 就顶死了
```
⇒ 想让"中等玩家也活 5 分钟"，唯一有效旋钮不是速度表，而是**提高 ρ 的容错**（例如加 0.5s 锁定延迟，让玩家落地后还能修正）。
这是玩法级改动，本轮只登记不实施（§9③D3）。

### 5.1 消行闪白：按行数分档（现值 0.12 恒定）

```lua
local FLASH_T = { 0.10, 0.13, 0.17, 0.22 }   -- 【推断】
```
- **硬约束**：`FLASH_T[n] < SHAKE_DUR[n]`（已满足：0.10<0.18 / 0.13<0.20 / 0.17<0.23 / 0.22<0.28）—— 让"闪白先收，抖屏后收"，两段反馈不打架。
